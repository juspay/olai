
Olai serves one directory. `.jsonl` files under it are outlines ([format.md](format.md)); `.md` files are documents, carried in the same snapshot with their text, because a document is content of the directory the way a note is. There are two entrypoints and they are the two write surfaces, not two products: `olai web <dir>` puts a browser in front of the ops layer, `olai mcp <dir>` puts an agent's pipes in front of the same one. There is no write CLI and there never will be — nothing on the command line adds a node, marks one or moves one, and both subcommands are transports rather than tools.

It reads that directory and keeps reading it: edit a file or `git pull`, and the open page follows without a reload. It also writes it, through one gate, from one layer: an agent asks for a node to be marked, or a person presses `Ctrl+Enter` on the row, and the tree in front of you follows — because both writes went to disk and came back through the same probe every other change does. Two writers, one ops layer, and neither of them can name a byte.

## Shape

```
files on disk ── load + validate ──▶ snapshot ── surface collection ──▶ browser (SolidJS)
      ▲                                                          │           │
      │                                                    chat panel     keyboard
   commit(baseRev)                                               │           │
      │                                       ACP session ◀──────┘           │
      │                                            │                         │
      │                                       MCP tools           edit procedures
      │                                            │                         │
      └── ops (create, add, mark, move, archive, unarchive, see) ◀───────────┘
                                                 ▲
                                                 └── stdio ── an agent in a terminal
```

- **Store** (`packages/store`, generic — caller-supplied codec, no olai types; extractable to its own repo later): files load into a validated snapshot, revision-tagged, with errors on a second independent channel so a broken set does not blank what is on screen. A published snapshot also names WHAT MOVED to make it — the paths re-decoded and the paths the listing lost — which is the probe's own stamp diff kept rather than thrown away, and what lets a consumer publish per file without re-deriving the diff by comparing two whole snapshots. It spans the gap between two published revisions, not one probe: a probe the codec refuses publishes nothing, so what it found is still owed to the next revision that validates. It stays current by PROBE — re-list the tree, re-stat everything, diff against a table of mtime+size stamps — with a file watcher that only *triggers* the probe and whose event payloads are dropped unread, plus a settle delay that turns a `git pull` into one probe and a slow backstop for the events a watcher loses. So a file arriving via `git pull` appears without a restart, and only the files whose stamps moved are re-parsed. The walk prunes dot-directories and `node_modules`: a served directory is somebody's working tree, and `.git` is both the largest thing under it and the one git writes to constantly — an unpruned probe would do its most expensive work exactly when git is busy. Design and the decisions behind it: [brainstorming/architecture.live-store.md](brainstorming/architecture.live-store.md).
- **The write gate is the same loop, run deliberately.** `commit({baseRev, changes, afterPublish?})` takes the probe's own permit, so a write and a `git pull` can never interleave over the stamp table they both read. Inside it: probe (so a change that arrived out of band is part of the revision this write is judged against), then the optimistic check — a `baseRev` the store has moved past is a typed `StaleWrite{currentRev}` — then validate the set the write WOULD produce, then stage every file beside its destination and rename them all, then re-probe and publish. Validation before any rename is what makes a refusal cost nothing on disk. The two outcomes travel on different channels because they mean different things: `StaleWrite` is a failure and the caller re-derives; a set the codec refuses is an *answer*, so the caller renders the errors rather than retrying. The changed files are re-read because the gate says so rather than because a stat noticed — stamps are deliberately coarse, and a write landing in the same second at the same length is exactly what they cannot see. The git commit rides `afterPublish`, an Effect the caller supplies, so the store never learns what git is.
- **Error scope is hybrid**, and the two halves answer different questions. A file that does not PARSE costs that one outline: the sidebar still lists it, opening it shows its own errors where its tree would have been, and every other outline stays live. A failure that no single file owns — a dangling cross-file reference, a duplicate id, a cycle — holds the whole last-good snapshot and raises a banner over it, because half a set is a set that was never on disk. The codec decides which of the two applies (`validate` is handed each file's `Result`, decode failures included) and the store only publishes the answer. A third failure is neither, and it travels the same channel for the same reason: the directory could not be READ — EACCES, a mount that vanished, no room to answer a stat. That one is the store's own rather than the codec's, so the codec is asked to translate it (`Codec.unreadable`) into the vocabulary its surfaces already draw, and it lands under the same banner over the same last-good tree. It used to be a log line and nothing else, which meant an outline that had stopped tracking the disk went on looking live — the exact failure a live store exists to prevent.
- **Git** (`packages/git`, a LEAF — `effect`, `node:child_process`, `node:fs`, and no workspace sibling at all): git as plumbing, and nothing that decides anything. One socket, `open(root)`, answering with a repository handle whose verbs are business questions rather than the commands behind them — what state the repository is in, what has moved in it, what HEAD had in a file, what was last recorded under a caller's own audit filter, commit exactly these paths, push the current branch — or with `NoRepo` for a directory that is not a work tree, or `Unusable` for a git that ran and could not answer, which are two different pieces of news and were one `null` until #108. It was `ops/src/git.ts` and moved out under `commit-whole-repo`, which is also the answer to "should olai take a git library": the handroll is a few hundred careful lines that work, and a package with one dependency is a smaller thing to own than an adapter over `simple-git`, a reimplementation of git (`isomorphic-git`) that can diverge from the one on your PATH, or a bundled binary (`dugite`). What it does NOT know is olai — who a writer is, what a commit message says, which dirty files matter — and both of the olai-isms it used to carry are handed in now: the audit convention (`olai:` and `X-Olai-Writer`) is an argument, and the trailer comes back verbatim for the ops layer to classify. Its `./state` subpath is the half with no subprocess in it — `RepoState` and `Reason` travel the wire, `@olai/format` re-exports them for its pending schema, and a browser bundle must never reach `node:child_process`. Two properties are its own rather than a caller's: a commit names only the paths it was given, and a commit that REFUSES puts the index back bit-identical — the `add` a commit needs writes the real index, and leaving it there meant a refused commit staged a selection nobody asked for.
- **Ops** (`packages/ops`): the only writer, and the only reader an agent gets. Between `format` and `store`, because it is where an EDIT lives — "mark this done", "put this under that", "start a new outline", "archive this", "point this at that" (`see`) — and neither of those two knows what one is. Every request names a NODE or a DOCUMENT (or, for the two creates, a relative path — `.jsonl` or `.md` — judged segment by segment the way `/media/*` is), never a free-form byte range, and three things follow from that: a retry against a newer snapshot lands cleanly, so no writer silently loses an update; a plan is whole RECORDS through the format's own writer, so a malformed file is unrepresentable through this path; and an answer carries structured detail rather than prose — a refusal brings the validator's own rows, each pinned to its `file:line`, and a write that LANDED can bring a `nudge` (what the rollup noticed: a branch ticked done over tasks still open, the last task under a parent finishing), which is advice on a success and never a reason nothing happened. `create` is the one op that mints a file the set does not yet hold — `add` refuses any path that is not already loaded — and it rides the same stage → validate → rename → commit gate, optionally seeding it with a capture. `add` takes a whole nested subtree in one request, and `create`'s seed is that same capture, which is the same property read from the other side: one plan over N records is one validation and one all-or-none rename, so an outline is captured in one gesture and cannot half-land — and a new outline arrives holding its contents or does not arrive, rather than being created empty and filled by a second call that might refuse. `split` and `merge` are that same argument for the two edits that change how many rows there are: a split is a retitle plus a create and a merge is a retitle, a note, N reparentings and an archive, so composed by a caller each would be several writes at several revisions, able to stop in the middle and leave an outline saying something nobody wrote. They are one request each instead, which is also what keeps the faces equal — the keyboard's `Enter` mid-line and `Backspace` at line start ARE these ops, rather than a sequence the web can perform and an agent has to spell out four times. It also owns the codec that joins `format` to `store` — the same joint the write gate validates through — and the closed TABLE of what an agent may do, each entry carrying its own schema and, for a read, its own reader. How that table reaches an agent is not this layer's: `server` projects it onto `@kolu/surface-mcp` bespoke tools, which is what keeps the MCP SDK out of the closure of a package that knows nothing about a listener or a socket. The KEYBOARD reaches the same procedures by another projection, and the layer is unchanged by it: the browser's edit procedures are resolved into these same requests by `server/src/edit.ts`, so an op still does not know it is being called over a wire, and there is one writer rather than two things that both write.
- **Documents ride the snapshot, and reach a reader one at a time — and they are WRITTEN through the same gate** (`md-editing`). A document write is an op like a node's: the whole new text, validated with the set, staged and renamed atomically, audit-trailed with the same trailer, landing on its own revision — so a save in one tab reaches the other tabs the way a `git pull` does, and an agent's `write_document` is the same call the browser's editor makes. The write may carry `was`, what the caller read, refused on every retry when the disk has moved since; that refusal is the whole conflict story for a file edited in vim under an open editor, and the browser draws it verbatim with the draft kept. Creation is its own op (`create_document`), refusing a path that exists as write refuses one that does not, so a typo can never quietly mint a file. A `.md` decodes to its text through the same codec, is cached against the same stamp, and travels in the same revision, so an edited document reaches an open page by the mechanism that was already there and there is exactly one answer on screen to "what does this directory say right now". What CROSSES the wire is a `documents` collection keyed by path, `keys` + `get` and deliberately no `deltas`: the sidebar draws paths, so the key set is the whole of what a first paint needs, and a body travels to the tab that opens one. That is `snapshot-scale`, and it is a wire change only — the server still reads and validates every document, because a `doc` reference has to be checkable. What it replaced was the documents (text and all) on the `manifest` cell, which put every served body in the FIRST frame of every subscription: ~124 KB of a ~212 KB snapshot for this repo's own `docs/`, and O(corpus) for the directories of thousands olai has to serve. What a second read path would have cost — the reason a body still rides the live store rather than an HTTP fetch — is a second thing to invalidate and a page whose outline and document could be two different reads of the disk; a per-key `get` is the same store, the same revision, and an entry stamped with the revision it was published at. The one thing that cannot ride it is a PICTURE — the browser fetches an `<img src>` itself — so there is one HTTP route besides the bundle, `/media/*`, restricted to picture extensions, and its URL is declared in `surface` so the renderer that writes it and the route that reads it are one bijection rather than two spellings kept in step by hand. A relative LINK between two `.md` files goes through the same seam and lands at `/doc/<path>`: `format` resolves it beside the file the link was written in (never beside the route the rendering is drawn under, which is what a browser would do and is wrong for a note on a day page), the client spells the address, and a click on one is answered in place by a single delegated listener on the main pane — rendered markdown arrives as HTML, so its anchors belong to no component and cannot be the app's own `<Link>`. Nothing else about a link is touched: a scheme goes where it says, a fragment stays the platform's, and a relative path to anything that is not a document is left as written.
- **Surface mapping** (kolu's surface framework, pinned via npins): the outlines are a `collection` keyed by root-relative file path, served with the batched `deltas` verb — one entry per file, so a probe tick that touched one outline sends that outline's slice and a `git pull` of forty is one coalesced `{upserts, removes}` frame, and the key is DECLARED in the protocol (`keySchema`) rather than inherited from a client library's default. The documents are a second collection on the same key, `keys` + `get` and no `deltas` — the batched verb opens with every entry, which for documents is every body, so its absence is what keeps the corpus off a first paint. The set-wide facts are a `manifest` cell: the revision the set has reached, and the `null` that says a directory has never loaded, which an empty collection cannot say. What the entries are, and what the store's per-publish change summary has to do with them, is [brainstorming/outlines-as-collection.md](brainstorming/outlines-as-collection.md). Error state is a `cell`; what git is doing for the directory is another (four states, moving at most twice in a serve — the probe, and a commit that refuses — which is why it is a cell and not a stream of anything); folding and the view toggles are on no member at all — they are client-local, and folding is this browser's own storage (`web/src/client/fold/`); chat is a `collection` with batched deltas for the transcript, a `cell` for where the conversation stands, and `procedures` for send/cancel/new/load/list — `send` carrying the nodes a message is ABOUT as bare IDS, because the set is the server's to read and a browser's account of it is a frame old — the two that answer a question the agent asked (a question's row key IS the id those verbs name, because it is the one entry a browser talks back about and two spellings would be a mapping to keep in step for nothing) — plus `attach`, the one member that carries BYTES, in bounded chunks: a pasted picture would otherwise be a frame that scales with the file, and an oversized frame is answered by closing the socket rather than by failing the call, taking every other subscription on that tab down with it. How big a chunk is, and why, is the framework's and not olai's — the arithmetic sits beside the frame cap it is derived from (`@kolu/surface/frame-chunking`, juspay/kolu#2158). Olai carried a copy of that derivation, taken from kolu's own padi where a 26 MB drop had proved it the hard way, and two copies of a margin is the shape of bug where a second `maxPayload` disagreed with the classifier above it and killed the frames in between. What olai keeps is the GATE, which no framework can decide: the two extension allowlists, the cap on a file, the tmp directory the bytes land in. A procedure rather than an upload route, because a procedure inherits the origin gate and the session the listener already enforces for the websocket; a sibling of `send` rather than a widening of it, because the two answer different questions and one picture is N calls to one send. EDITING is a `procedure` and deliberately nothing else — ONE of them, over a tagged union of what a keyboard may ask for (the shape the ops layer already uses for the same kind of thing, so the list of verbs is spelled once rather than five times), and the collections stay read-only on the wire, because an edit changes a FILE and a file reaches every open tab the way a `git pull` does. What they carry is the keyboard's own vocabulary rather than the ops requests re-spelled: `Tab` says "indent this", `Ctrl+Enter` says "toggle done", `Ctrl+Shift+Enter` says "walk this row's mark on" — and which answer that lands on is read off the snapshot as well, round a ring (bullet → `todo` → `doing` → bullet) that deliberately does not pass through `done`, since finishing something is a thing a person means rather than a thing to do on the way past, and a walk asked of finished work resolves to the request the ops layer refuses in its own words rather than to a rule the resolver would be inventing — and the placement each implies is read off the snapshot the write is judged against (`server/src/edit.ts`) rather than computed in a tab from a tree some frames old. What it answers with is the node the write was about, the ops layer's own `nudge` — advice on a success, which a person who pressed a key deserves as much as the agent that already gets it — and what would TAKE THAT WRITE BACK: the edits that reverse it, derived from the same reading the request was resolved against, because where a row sat and which mark it replaced stop being true the moment it lands, and a browser noting them down for itself would be the second reading of the set this whole seam exists to avoid. That is what ⌘Z spends (`web/src/client/edit/undo.ts`): an undo is the inverse REPLAYED through this same procedure, judged against the snapshot as it is now, never a restore of an older one — which is the difference between taking back your own edit and quietly taking back everything another writer has done since. The two verbs that only an undo sends (`place`, `remove`) are the only ones here that name an absolute placement or an id nothing on screen chose, and they are ids the SERVER derived; the `•••` menu speaks three more (`date`, `unmirror`, `archive`), the Trash view's `Put back` a fourth (`unarchive` — born in the ops layer and exposed on both faces together, since no face had it), the two EDGE fields two more (`see` and `after` — `set_see` and `set_after` in the ops layer's own shape, two optional lists rather than one target and a direction, because nothing is resolved behind them and a narrower spelling could not express its own inverse; the web had DRAWN both edges since edges-ui — the links under a node, the dim and the `blocked by` line of a blocked row — and could write neither, which is the same standing deviation the menu's verbs closed one field at a time, and what differs between the two is the planner's alone: an `after` add that would close a loop is refused NAMING the loop, in words both faces read verbatim), the OUTLINE one (`outlineNew` — `create_outline` from the sidebar, `docNew`'s twin, carrying no seed because a person's first row has a place to be typed and an agent's seed only saves it a second call), the DOCUMENTS three more again (`doc`, which commits a document's editor and is the only verb here whose subject is a file rather than a node; `docNew` and `docDay`, the two creation doors — and the second of those carries a DATE rather than a path, because where a vault keeps its daily notes is a fact about the set and so is read on the server like every other placement), plus `mark`, which is BOTH theirs — a menu entry meaning "this is doing now" and an undo meaning "it carried `todo` before I ticked it off" are one request, so they are one arm. Those are the closing of a DEVIATION rather than growth: an agent could clear a date, retire a placement and archive a subtree, and a person could do none of them, which HACKING.md's consistency rule forbids. Each resolves to the request the equivalent tool would have sent, so a fence a menu wants — the archive confirm, which names how many rows go — lives in the panel and never in the schema, where it would be a rule the agent's own op does not have; the two TEXT verbs need no undo twin, because the inverse of setting a title is setting the title it replaced — what an undo adds there is `was`, the text it expects to find, so putting back what this tab replaced can never overwrite what somebody else has typed since (the human found the hole this closes by driving it: a committed title used to answer "nothing to undo"). One of them is the UN-CREATE and not a delete: nothing but an inverse produces a `remove`, no key sends one, the only row it can take back is a row that was just made and has nothing under it, and it resolves to the ops layer's own `archive`. Whether this face gets a delete KEY is still the deferral #109 recorded. TWO of them are COMPOUND — `split` (`Enter` with text on both sides of the caret) and `merge` (`Backspace` at offset zero) — and they are the one place this list grew by growing the OPS layer rather than by re-spelling it. Each changes an outline in several ways at once (a retitle and a create; a retitle, a note, N reparentings and an archive), and each is ONE request at the write gate, because a sequence assembled in the resolver would be two things at once: the web doing in one keystroke what MCP needs four calls for, which is the deviation HACKING.md forbids, and a write that can stop in the middle, which for a merge means an outline saying something nobody wrote. So they were born in `@olai/ops` and reached both faces in the same change (`split_node`, `merge_node`), which is `parity-unarchive`'s shape. `split` is the only verb here carrying text it did not read off the set — the two halves are the DRAFT's, and they cross as two TITLES rather than a caret index, because no verb on either face names a range into a field — and `merge` carries nothing but an id, since which sibling is above is a fact about the snapshot. Both name the ROW's own record rather than the node the row shows, which is where they part from every plain text edit: each puts a row on the page a reader has open, or takes one off it, so each is a question about where rows SIT — and asked at a mirror both are refused in the ops layer's `notANode` words, because a split named through a placement would mint its tail beside the TARGET, in a file the reader is not looking at (a mirror draws its target's children and never its siblings), leaving the two halves of one sentence unrelated on screen and the caret following the tail off the page. What a merge does with the rest of the row is the semantics and every line of it is a decision: the titles run together, the notes join a blank line apart, the children are adopted in order by the row above, and the mark, date, attached document and edges go with the RECORD into the archive — recoverable by id, and never silent, because the reply's `nudge` says what went. The transcript is a collection rather than an event because an event replays nothing: the `deltas` verb IS snapshot-then-deltas, so one subscription carries both the history a reloaded tab needs and the frames a live one is watching, with no dedup rule in the browser. Every subscription sends a full snapshot first, then deltas; a reconnect is just a fresh snapshot — no resume protocol, no optimistic UI. No raw wire code — Effect RPC, sockets, HTTP routes — exists outside surface's API, with two deliberate exceptions, and neither carries surface data: everything an MCP CLIENT speaks (the internal route, and the stdin/stdout `olai mcp` answers on) — which is the same surface, re-projected by `@kolu/surface-mcp` rather than re-declared — whose consumer is an agent rather than an olai browser, and `/media/*`, which the browser fetches itself — the URL of that one is still declared in `surface`, so the renderer that writes it and the route that reads it are one bijection rather than two spellings kept in step by hand.
- **The connection is a thing the page reports on.** A page that is live and a page whose server died look identical unless something says otherwise, so a pill in the app header reports the wire in every shape of the app, green only while a server is answering. It reads `connectSurface`'s own `readout` — `connecting` / `live` / `degraded` / `reconnecting` / `retired` — and `retired` is the one that matters most: the server this page came from has been replaced, the link has stopped dialling for good, and the only recovery is a reload, which the page offers rather than pretending (and which it knows to offer because the readout carries `needsReload` rather than because a list of terminal states is kept here by hand). The handshake behind it is the framework's, not ours: the socket probes the reserved `system/identity` member on every open and echoes the server's process id back as `?pid` on the next dial, and `gateStaleSocket` on our side closes a tab presenting an id this process did not mint. Both halves used to be an app's to remember, and forgetting them is what shipped a tab that sat on a dead server looking healthy (juspay/kolu#2133 moved them into the seam and made the terminal state a required option). And green is a claim about what REACHES the page rather than about a socket, so it is the conjunction of the wire's status and the subscription-health fact, which knows what the transport cannot: a socket that is open and answering while a subscription over it is dead. That is a fifth state, `partly live`, and its detail NAMES the streams that stopped, because "something is not arriving" is the least useful true thing available. That conjunction was olai's own for one release — a `client.health()` walk in `status.ts` — and it is the framework's now (juspay/kolu#2160), for the reason the identity handshake became the framework's: it was a step every consumer had to remember, and the consumer that forgot it is exactly what left a dead `documents.keys` rendering as a directory with no documents in it under a green light. So the three rules travel with the readout rather than being restated here — `live` is the conjunction, `degraded` names what stopped and is non-empty by type, and a subscription still waiting for its first frame does NOT degrade, because that is what every page load looks like and a pill that is amber most of the time is a pill nobody reads. What did not graduate is the LOOK, and that is the whole of what `connection/status.ts` still holds: what this house CALLS `degraded`, and the sentence green makes about this directory. Folded into the pill rather than drawn beside it, for the same reason the git pill beside it is quiet when it is happy: one green claim per page.
- **So is git, and for the same reason — in ONE pill.** "Is this page still reading?" and "is what gets written to it being kept?" are the same shape of question about the same page, and both are facts a page can only get wrong SILENTLY — so the header carries an indicator for the second beside the connection pill answering the first. It is the **Commit pill**, and it is the only one: a separate `● git` readout sat beside it for a while, both answering "what is git doing here", which is what the human filed as `one-git-indicator`. They were already one derivation rather than two probes, so the fix was the face rather than the data — every state that readout drew is a face of the pill now, reading the `git` cell alongside the `pending` one. `commits off` under `--no-commit` and `no git here` are SETTINGS: dim, inert, no warning, because an owner's choice about a directory whose history is somebody else's job is not a fault. `git error` is the fault, and it carries git's own words on the tip AND on the `aria-label`, never hover-only. Healthy is quiet — `✓ committed · 3m ago`, with the tick deliberately not wearing the connection's green: one green claim per page, or neither is scanned. What the pill may NOT do is disappear when all is well: an indicator that is only there when something is wrong cannot be trusted when it is absent, because healthy and not-rendered look identical. It also carries what is recorded HERE AND NOWHERE ELSE (`· 3 unpushed`), which is a second fact about the same work rather than a second control — an audit trail on one machine is one disk failure from not existing, and the panel behind the pill is where the Push button lives.
- **Web**: a SolidJS client over WebSocket, using surface's solid hooks (subscriptions reconcile into Solid stores). The read side is two modules, one per collection — `web/src/client/outlines.ts` and `web/src/client/document/documents.tsx`, the second owning the documents member entirely because the rule about it (never a plain `.use()`, which would open a value stream per key) is enforceable only where the member is reached. Their two key sets become the sidebar's file tree (`fileTree.ts` — one walk mixing `.jsonl` and `.md` under the folders they live in; folders start collapsed, collapse is client-local and remembered by this browser like the outline tree's folds, and the open file's ancestors stay open so the selection is never hidden), `derive` over every entry's nodes is the one derivation the whole app reads, the entries carrying a `broken` are the files that would not parse, and the manifest is what decides between waiting, never-loaded and reading. **The client reads that store and never writes to it — including now that it can EDIT.** A keystroke is a procedure call, and what comes back is the file on the next frame: there is no local model of the outline to keep in step, no optimistic row, and the only client-side state an edit involves is the DRAFT (`web/src/client/edit/`), which is the text in an open editor rather than a claim about the set. That is the same rule the chat composer follows, and it is what lets the paragraph below stay true. Committing is on blur / `Enter` / idle; a commit that would change nothing writes nothing; a commit that is REFUSED keeps the draft and shows the validator's own reason under the row, because a keystroke a person typed may not vanish into a rejected write. A NEW row is a draft too — `Enter` opens an editor where the row will go and the `add` lands when it has a title — so a blank record is never written. What a structural key costs is the caret: the row is redrawn where the file now says it is, which in a browser takes focus off it, so the editor follows its NODE across the frame and asks for the caret back (`edit/editing.tsx`). Which id an edit names is a rule: what a node SAYS names the node a row shows (so typing in a mirror edits its target), and where a row SITS names the row's own record (so moving a mirror moves the placement). A row's `•••` menu writes as well (`web/src/client/menu/`), and there is no draft in it: one op per click — any of the three marks, clearing a date, naming what this node points at or waits on, retiring a placement, archiving a subtree behind a confirm that names how many rows go with it — plus a plain-text copy of the subtree, which writes nothing, and *Ask agent*, which writes nothing either: it arms the composer with this row's node and opens the panel, and what happens to the node afterwards is whatever is typed next, through the same tools and the same gate. It is the established door for a row verb and deliberately the only one — a control in the gutter would cost title width on a phone (`touch.ts`), and a chord would cost an entry in a registry whose value is that it is short and collision-free (`keys.ts`). THREE of them cannot be a click, and they are one shape rather than three exceptions: a date, a `see` target and an `after` target are each a value somebody has to CHOOSE, so each opens a panel in place under the row rather than writing on the spot — the date picker (`web/src/client/date/`), reached from the menu entry and from the row's own date pill, whose pick is the same `date` edit the menu's `Clear date` sends — a native `<input type="date">`, whose value is the ten characters the record will hold, because a date is TEXT and this codebase does not parse one anywhere; and the edge panel (`web/src/client/edges/`), one panel for both fields because the ops layer plans them with one function, holding what the node says NOW with an `×` on each and the SERVER's own node search for what to add, so what it finds and what an agent's `search_nodes` finds cannot drift. The client bundle is built by `Bun.build` via `@kolu/surface-app`'s helpers; the server is a Node `http` server with a `ws` upgrade. Started as `olai web <dir> [--port] [--host]` — a nix-built binary whose only job is serving; `just serve` and `nix run` wrap it — bound to loopback by default. The ordering graph both that and the acyclicity rule read is one graph in terms of NODES, mirrors resolved at both ends, so a deadlock closing through a placement is refused rather than drawn. There are seven routes, and the difference between them is what each is a property of: `/o/<file>` names a file, so it spells the path; `/doc/<file>` names a document, which is also a file and also spells its path — a second prefix rather than more work for the first, because an outline and a document are two different things a file can be, and the address says which before the set is in hand; `/n/<id>` names a node, and an id is all it may spell — ids are unique across the loaded set and survive renames and moves across files, so the permalink outlives every edit short of a delete, while a URL that also carried the outline could disagree with the file it named; `/d/<ISO-date>` names a day, which is not a thing on disk at all; `/today` names no day but the day it *is*, which is what an agent, a bookmark and a home screen can each keep; and `/agenda` names no day either and never will — it is those same dates read forward, so a horizon in the address would be a link that meant something else tomorrow; `/trash` spells nothing for the same reason — which archives exist is the set's answer, and an archive's own `/o/…` address opens the same view, because an archive is not a place you edit. A zoomed page is the node as heading, its note, its children as the same tree, above the *canonical* parent chain as breadcrumbs — derived, so the crumbs are the same however you arrived, and a mirror's id resolves through its chain to the one page its target has. What is folded, whether done nodes are drawn, and which month the calendar shows are client-local: they belong to a reading rather than to the file, nothing is written to the directory, and hiding what is done is a row not drawn. Folds are stored by NODE ID under the file the node is defined in (2026-08-13, human — a reader with a real corpus was re-collapsing the same trees on every visit), so a fold survives a reload, a move, and zooming in and back out, and every mirror of a node is folded wherever that node appears — one node, one fold state. Nothing about it is committed and nothing crosses the wire. Ids are dropped as the entry is rewritten, and GONE MEANS GONE FROM THE SET rather than from the file the fold was filed under: `archive` is a move that keeps the id, so a node that has left one file is looked for in the others and re-filed under where it landed, and only an id no served file declares is forgotten — while a file that is broken or unserved keeps its folds rather than losing them to an absence. A write starts from the stored entry unioned with what the tab holds, so two tabs folding different trees do not discard each other. **Where a preference of this browser's is SET is one place** (`web/src/client/settings/`): a trigger in the app header opens a panel of rows, each a label, a control, and a line under it read off the choice in force — kolu's settings shape, whose rows read and write wire singletons because its preferences are the server's, over olai's store, which is the paragraph below and no wire at all. "I do not want to look at finished work" is a claim about the READER, so it applies to every page and follows across tabs. Notes have one shape under a row — one dim plain-text line under the title, clamped with an ellipsis (Workflowy-style), and a click (or tap) expands it in place to the full note and see links; a click in the note you are then reading puts the CARET in it (2026-08-11, human — the clamp is olai's compression of a note Workflowy always shows in full, so the expanded note is what Workflowy's single click maps onto), and clicking away folds it back; the date badge stays on the title line; there is no density switch, no hover, and no per-place unfold cell. A zoomed page's own note is always full — it is the body of the page. Three decisions belong to the client rather than to the set and are named here because nothing else would name them: the shell is wrapped in kolu's `SurfaceFaultBoundary` (which catches, records to the console, and prints the thrown value; `errors/Fault.tsx` keeps only the LOOK), because the three error surfaces above are errors as DATA and none of them can catch a bug in this app's own render — a thrown render used to be a white tab with the truth in a console nobody opened; navigating decides where the PAGE is, since a route change redraws the main pane and moves nothing else, so a page you go to starts at the top and a page you go back to is where you left it (remembered per history entry, in the document's own memory, recorded as the reader scrolls because `popstate` fires after the position it was made from is gone); and a preference of this browser's belongs to the BROWSER rather than to the tab, so the `storage` event carries a pick into every other tab this app is open in — a circuit (read the entry into a signal, write a change back, follow the other tabs) wired once as `createPreference` (`web/src/client/preference.ts`), a codec per stored key; the theme alone stays on the primitives, its first read being the boot script's, and a claim test holds that line.

Below 48rem the directory sidebar stops being a column and goes behind a burger in the app header as a slide-over drawer with scrim; chat is a bottom sheet (half/full snap) collapsed to a thumb strip with the last agent message. - **The journal is a query.** There is no stored year→month hierarchy, no journal file and no filename anything is special about (format.md's [Days](format.md#days); rewrite decision 11): a month in the sidebar aggregates the *whole set's* dated nodes, and a day page is every node with a date on that day, in any outline, grouped by the file it lives in and shown with the same ancestry, tags, mark and note a zoomed page gives it. TWO fields put a node on a day — the `date` it is scheduled for and a dated `done`, since a `done` records the instant work was finished — so a node with both is on both days, once each, and each row says which of its dates put it there; a dated `doing` or `todo` is read by neither the calendar nor a day page (2026-08-11, human: the format allows the value, a journal is narrower than the format) (a word in front of its date badge; the checkbox has already said which kind of mark it is). All of it is derived at view time by `format`'s date derivations — the one place both surfaces read from, so a dot and the day it opens cannot disagree — and none of it writes about NODES: a day with something on it is a link with a dot, today wears a ring and the day being read is filled. A BARE day — no node, no note — is the one cell that presses into a write now (`md-editing`), and it is the write the roadmap ruled it would become once editing existed: minting that day's NOTE, at the path the vault's own convention names — the newest existing daily note's directory with its date segments re-spelled (`format`'s `dailyNotePathFor`), read on the SERVER against the same snapshot every placement is — landing in the new document's editor. A day page still writes nothing, and a day is still a QUERY; what changed is only that the month's one dead cell now starts the day's note. **The doctrine is knowingly amended in exactly one place, and only to ADD:** a document whose basename is exactly an ISO date (`2026-08-12.md`, wherever in the tree it sits — `2026-08-10-recap.md` deliberately not) is that day's NOTE, and it joins the query's answer rather than replacing it — drawn first on `/d/<date>` and `/today`, with the dated nodes below exactly as before, and marked in the month by a second and visibly different mark (a corner fold, against the node dot) so note-days and node-days are legible apart at a glance. Two documents claiming one date are both listed, in path order, because there is no conflict rule worth inventing over two files a person wrote. The derivation lives beside the other two in `format/src/dates.ts` for the reason they live beside each other: a calendar mark and the page it opens must not be two readings. Days remain queries, and a note is a document like any other now that documents are writable: its page edits (`md-editing`), and the bare-cell mint above is how one is born from the month.
- **The agenda is the same query, forward.** A day page answers *what is on*; the agenda answers *what is owed*, and it is the same dates read the other way — `/agenda`, a question asked of every dated node in the set, with nothing on disk that is the agenda (`format/src/agenda.ts`, ratified in [brainstorming/agenda.md](brainstorming/agenda.md)). **No new field, and no format change at all**: `date` says WHEN and a mark says whether it is work, so the two read together are the whole reading — `date` with no mark is an OCCURRENCE (a birthday, a delivery) that can never be late, and `date` with `todo` or `doing` is due work. A second `due` beside `date` would have been two dates answering one question. **`overdue` is the next `blocked`**: `overdue(n) ⇔ n carries todo or doing ∧ day(n.date) < today`, derived at view time, stored nowhere, spelled ONCE and read everywhere — the page's first section and the tone a date badge takes are the same predicate, the way blockedness is one predicate read at both ends of its arrow. It is a SECOND fact about a node, never a replacement for its mark; `done` extinguishes it by construction; and `doing` is in (2026-08-12 the human considered the narrower todo-only reading and declined it — started-but-unfinished is the most honest answer to "should this have happened by now"). The one thing the set cannot supply is what day it IS, so `today` is an argument at every entry point and the clock stays the client's one reading of it (`web/src/client/today.tsx` is how it reaches a row). Three sections, grouped by outline within each because that is the only heading that is true: **Overdue** (oldest first — the section that IS the feature, since a slipped task is on a day nobody visits), **Today** (what today's day page computes, minus finished work) and **Upcoming** (the next days that HAVE something, bounded by a count of populated days rather than a window of dates, since date arithmetic is exactly what this codebase does not do — each heading a link to that day's own page, where the note and the finished work the agenda leaves out are read). `done` never appears anywhere on it, undated tasks are absent entirely — they have no *when*, and inventing one is what this format refuses to do — and an empty agenda says "Nothing is due." and offers nothing to press: pressing it could only mean scheduling a task, and the writing surface for tasks is the tree, where a row is a place a node actually lives. Rescheduling is `set_date`; there is no snooze and no recurrence (recurrence would be a real format change and deserves its own debate). It is not `Now` either — Now is a person curating with mirrors, *chosen* work, and the agenda is derived, *dated* work; neither writes to the other. **And the directory says so before the page is opened**: the sidebar's Agenda entry wears the app's alarm — a filled chip counting what is late, on a washed and weighted row — when anything has slipped, the date badge's own quiet chip when work is merely on today, and nothing at all when neither; loud wins the row whole and prints the late count alone (one claim per readout), while the today count rides the entry's label and `data-today`. Overdue is the one answer no day page can give, and a page nobody opens cannot give it either. THE READING IS ONE: `agendaOf` is called exactly once in the client (`web/src/client/App.tsx`), by the composition rather than by the page model, and both things that show it read that value — the page lists the rows and the entry counts them (`owedOf`, `format/src/agenda.ts`), so the number beside the word cannot disagree with the rows behind it. It moves for the same reason every other reading does: a revision the store publishes (tick a late task off and the alarm goes down with no reload) and the one clock rolling `today` over at local midnight. The mark is on both faces of the column — the open one and the icon rail, where three rem takes a dot instead of a numeral — and on the phone it is inside the same sheet.
- **Search is one reading with several doors.** An agent's `search_nodes`, the `⌘K` palette and the header's search box (a magnifier opening that palette on a phone) are all callers of one `Query.search` over one snapshot — HACKING.md's consistency rule made structural, since the browser holds every node and deliberately runs no matcher of its own. The matching is case-folded substring over title/id/`#tag`/note, ranked by which field carried it, and it is the ONLY matching there is: recall by MEANING was built and then parked, because the implementation needed a model server on the reader's machine and olai requires no dependency outside Nix itself. What the browser adds is doors and a readable row (two lines, title then place, neither able to widen the panel), never a second answer. [search.md](search.md) is the reader's account; the parked design is [brainstorming/hindsight.md](brainstorming/hindsight.md) rec. 1.
- **Agents** (`packages/chat`): chat is one ACP session (`@agentclientprotocol/sdk`) over a subprocess, and the server owns exactly one — olai is a single-user app, so there is no session per tab or per outline, and every browser watching sees the same transcript. The agent's cwd is the served directory, which is what makes its stored conversations findable: boot asks `session/list` for that directory, and `claude --resume` in a terminal reaches the same sessions. WHICH of them the panel comes up in is olai's own note rather than a guess (`chat-restore-wrong`, the human's bug): the session id is written down when the panel enters a conversation and read back at the next boot, so a restart replays THAT one. It used to adopt the most recently updated session in the directory, which is an answer to "what moved last" standing in for "which one is mine" — so a terminal `claude` in the same directory, a `/clear` sibling, or an adapter touching a timestamp for a reason of its own would take the panel over silently. Newest-in-directory is the FALLBACK now, for the case it is actually an answer to: the remembered conversation is gone, or this olai has never served this directory. The note is one small file per served directory under `$XDG_STATE_HOME` (`~/.local/state/olai/chat/`, `packages/chat/src/memory.ts`) — not under the served root, which is the outline set the store probes and a commit would commit, and not in the agent's store, which has no field for whose panel a session is. It holds an id and a path and nothing else: olai still keeps no transcript store of its own. Failing to read or write it is a row in the transcript and never a failed boot — an unreadable note opens the newest conversation and says why, an unwritable one says this conversation will not come back. **The agent can ask a person a structured question**, because `initialize` advertises `elicitation.form` — without that capability the Claude Code adapter puts `AskUserQuestion` in `disallowedTools`, so an agent that wanted to check which of two things you meant had to guess or ask in prose and hope. Two methods reach a person and both are drawn as the same thing, a FORM IN THE TRANSCRIPT rather than a modal, so it is still there afterwards saying what was asked and what was chosen: `elicitation/create` in form mode (a JSON Schema of primitive-typed properties — the adapter renders its `AskUserQuestion` tool into one, a titled `oneOf` per single-select and a per-question free-text "Other" box beside it, and feeds the answers back as that tool's own `updatedInput`; MCP servers on the session reach the same method with schemas of their own), and `session/request_permission` (a list of named options for one tool call, which is a single-select with the options already spelled out). The projection of both payloads into that one form — and of the answers back, typed the way the schema asked — is `@olai/acp`'s, the package that owns the protocol's vocabulary; chat runs the subprocess and consumes the projection, translating that package's own refusal word into the domain's `UsageFailure` at the seam. A property whose type the panel has no control for makes the whole request UNDRAWABLE: it is declined and said out loud, because half a form is one somebody submits believing they answered all of it. A dismissal is a DECLINE on the wire — the agent is told a person would not say — and never a fabricated answer. Nothing times out; a pending question holds the ACP request open, which is exactly what a blocked turn is, and what the panel owes in return is that the block is impossible to miss (a count on the chat cell, drawn in the composer, the header and the permanent agent toggle). Every question is withdrawn when the conversation it belongs to ends — a new session, a load, a dead subprocess — so a live form is never a control that does nothing. **Permission requests are auto-approved for the tools olai handed the session** — its own mediated ops, kolu's terminals — and for nothing else, and that second half is the load-bearing one: the adapter maps plan mode's "Ready to code?" onto a permission request whose FIRST allow-flavoured option switches the session to `auto`, so a client answering every request with the first allow it found was silently taking that decision on somebody's behalf, every time. The rule is positive recognition, and a tool it cannot name is one a person is asked about. The name is read off the `tool_call` the adapter always emits before it asks — the request itself carries a display title rather than a name — which is the one agent-specific `_meta` the chat package reads. The session is handed olai's own MCP server, over an HTTP route on the same listener, because the tools it exposes are this process's ops over this process's store and a stdio server would mean a second olai with a second store. It is handed a SECOND one when this host is running [kolu](https://kolu.dev): `kolu mcp` over stdio, so the agent you are talking to about your outlines can also see the terminals your coding agents are running in. That is automatic and has no knob, and the two ways of being wrong do not cost the same: missing a kolu that is there costs a session some tools, while attaching one that is NOT there hands the agent a server whose every tool fails — it will try them, having been told they were available. So the bar is an answered read rather than a spawn. What is detected is the padi DAEMON rather than kolu's web server, which may be on another machine reaching this host as a remote. Detection is a PROBE and runs per conversation rather than once at boot: a `kolu` on PATH is not necessarily the host's kolu (a padi-spawned terminal prepends its own bundled copy, and one of those was an older build reporting the same version while missing most of the verbs), so the executable is started, handshaken with, and asked to read a resource only a live daemon can answer — and the absolute path that answered is the one the session is given, so the agent cannot resolve the word against a different PATH and spawn a different build. Socket discovery is not reimplemented: `PADI_SOCKET` is forwarded when olai was launched inside a kolu terminal, and kolu finds its own default when it was not (a host running two padis says so, and is left alone). Whole-file writes THROUGH OLAI are rejected by design: `fs` capabilities are false in both directions, so the only channel this process gives an agent to the disk is the ops layer. That is a statement about olai's channel and never was one about the agent, which is a coding assistant with its own tools and its own authority over the directory it was started in — and the honest thing to do about the difference is to SHOW it rather than to imply it away (`docs/chat.md` says so where an operator reads). **What a call CHANGED is drawn in the transcript, structured, in two vocabularies — and which one is decided by the FILE rather than by the tool.** An agent editing a `.md` or a source file is using its own tools, and ACP reports it as a `diff` content block: a path and two texts. The panel draws that as a diff, trimmed to a few lines and expanded in place on a click (Claude Code CLI's idiom), with unchanged stretches collapsed so the first rows are the change rather than the top of a document. It used to be flattened into the progress line as `— <path>` on the argument that a unified diff in a folded frame is a page of text and that the outline is where an olai edit shows up anyway; the second half is what inverted, since an edit like that shows up in NO outline and the answer to "what changed" was a terminal. An OUTLINE gets the opposite treatment whichever door the write came in by, for the commit panel's own reason — a `.jsonl` diff is one enormous line per node — so it is drawn as the node-level story in the same words the Commit panel uses (*marked done*, *note rewritten*, *moved*), plus the rollup's nudge for a write that went through the ops layer. A `.jsonl` the agent edited with its own tools is not the exception that proves the rule: its two texts are PARSED and compared as records (`web/src/client/chat/outline.ts`, the same `changesOf`), and a side that will not parse says so rather than falling back to lines — which is how hand-editing an outline goes wrong, and a text diff is not a better answer to it. That parity is structural rather than remembered: the classification is `@olai/format`'s one `Sort`, computed by the same `changesOf` a pending row is computed by (`ops`' `sorted.ts`, off the two readings a write is already made of) and worded by one table both panels read (`web/src/client/changes.ts`). The wire carries both shapes as DATA — `FileDiff` is path plus old and new text, declared by `@olai/acp` (whose `diffsOf` reads the protocol's diff blocks) and re-exported through the surface, and the line diff is derived in the browser like every other view-time derivation — because a change flattened into prose is a change no panel can draw and no browser should re-parse. WHICH MODEL is two facts, not one: the session's config option is what was picked, and the CLI's own `init` message — forwarded because `session/new` asked for it — is what is running. A `/model` is handled inside the wrapped CLI, so the picker never hears about it; whichever source moved last is what the header names, each debounced against its own previous value, and the first live id is a baseline rather than a change. A new conversation EMPTIES the panel: the agent's context is gone, so nothing above could be followed up, and a transcript you cannot refer to is history kept for its own sake. **A message can be about a NODE, and what that concretely is is an id** (`chat-node-context`). A row's `•••` offers *Ask agent*, which arms the composer with the node that row SHOWS — a mirror is a placement and the thing to ask about is what it is a placement of, which is the rule a fold and a mark verb already follow. What the browser sends is the id and only the id: a title or a `file:line` from a tab is that tab's account of a frame that is already old, so the SERVER resolves it, over the same reading a keystroke's write is judged against (`server/src/context.ts`), and hands the chat package the node as it IS — id, title, `file:line`, and the canonical ancestor titles that make a bare "order" mean something. That reaches the agent as one line under what was typed, the id in backticks, exactly where an attachment's `Attached file:` line goes and by the same argument: the agent is handed a HANDLE and reads the thing itself, because a subtree pasted into a prompt is a copy that stops being true the moment anything writes, and `read_node` is already in the closed table. An armed id the set no longer declares REFUSES the send in the ops layer's own `notFound` words, rather than sending a question whose subject is missing; a mirror id refuses the same way an op on one does. The nodes ride the user's transcript row as well as the prompt, so what a message was about survives a reload and reaches the other tab. **The other direction is the same ids, read backwards**: a node named in the panel is pressable and shows that node on the page (`web/src/client/focus.ts` — the row is scrolled to and toned with the same accent the row holding the caret takes, and a node that is not drawn on this page goes to its own address instead). Three things in a transcript are ids and none of them is an invented syntax: the chips on a message, the node an olai write was about (`Applied.id`, which the reply has always carried and which now crosses the wire on `Wrote`), and an id the agent wrote in BACKTICKS — which is how every one of these tools spells one in its own description, so it is what an agent already emits. A code span becomes a reference exactly when the loaded set declares what it says (`web/src/client/chat/refs.ts`), which is what makes a false positive unrepresentable: `notes.md` is looked up, is not a node, and stays a code span. What the span is MARKED with is the id the format RESOLVED — `nodeNamed`, the rule a `see` link and the chip already use — because a row carries the node it SHOWS: a placement id (which an agent writes, since `read_node` answers `mirrors` with them) marked as itself would name no row on the page and every press of it would leave for a node that is right there. The marking is a DOM pass over one message rather than a step in the markdown pipeline, because that pipeline is pure and cached by source text and this answer depends on the SET; the press is one delegated listener on the transcript pane, which is the arrangement a relative link between two documents already has on the main pane. A PICTURE can be pasted, dropped or picked into the composer, and what the agent gets is a PATH, as text: the bytes are chunked over `chat.attach` into a tmp directory of that conversation's own — deliberately NOT under the served root, so a screenshot stays out of the store's probe and out of anything the commit path would commit — and the prompt names the file, which Claude Code reads itself. So no base64 rides the prompt into the session the agent persists, and nothing here depends on the session's `promptCapabilities.image`; moving to ACP's `image` content block later is a change to one function. The directory goes when the conversation is left and when the server stops. A path that arrives over the wire is re-resolved against that directory, through symlinks, on both sides of the comparison — a chunk's `appendTo` is a continuation token that happens to be readable, never a capability. What the transcript carries is the file NAMES: the tab that pasted has the Blob and draws a thumbnail, every other tab draws the name, and `/media/*` cannot help either of them because it is guarded to the served root. A message sent while a turn is running QUEUES rather than being refused — a person watching an agent work has the next thing ready long before it finishes — and the queue is dropped, out loud, when what it was waiting behind stops meaning what it meant: a cancel, an agent that died, a conversation being left. **A CANCEL is judged by the turn, not by the write.** It is a notification — written and never answered — and a pipe does not tell its writer that the reader has gone, so the write succeeding is evidence of nothing and every way of failing looked like success: the button pressed, the turn streaming on, nothing said. The write's own failure refuses like any other verb, and the panel then watches the two facts that separate a slow agent from a deaf one — is the same turn still running, and has the agent said anything since — so one still streaming tool progress is left alone and one that has gone quiet with a cancel outstanding is reported as `trouble`, cleared by the turn ending.
- **The same tools are also a command anybody can launch** (`olai mcp <dir>`, `packages/server/src/mcp/`). A coding agent in a terminal is not olai's subprocess and has no listener to dial, so it gets what nearly every MCP client expects: a command, and JSON-RPC newline-framed over its own pipes. It is the SAME face the panel's agent talks to — `@kolu/surface-mcp` over olai's surface, with the ops table riding as tools and the outlines, documents, errors, git state and what is WAITING to be committed readable (and subscribable) as resources — differing only in the transport in front of it. That is the OPPOSITE conclusion from the bullet above out of the same argument — who owns the store. The panel's agent is a child of the server, so a stdio server there would have been a second olai for nothing; this one has to work with no server running at all, which is the ordinary case, and a bridge into a running instance would need that instance's port and its per-process token discovered from outside and would still have to do all of this on finding nothing listening. So two stores may watch one directory, and that is safe for the reason the write gate exists: it probes before it judges, and a base that has moved comes back as `StaleWrite` for the ops layer to re-plan against the newer snapshot — the same machinery a `git pull` under an open tab already goes through. What it is not is a lock: two writers landing on one file inside the same instant is last-write-wins, exactly as an editor and a `git checkout` are, and git is the recovery net for that as for everything else. It takes `--commit` on exactly the terms `olai web` does, `manual` included and by default, which is the whole of `mcp-commit-manual`: an agent in a terminal accumulates ops the way a person does, so its writes land and wait and the `commit` tool is what asks — and `surface://cells/pending` is how it knows there is anything to ask about, since an agent that had to shell out to `git status` for that would be reaching past the one surface it is given. Under the per-write behaviour this replaced, one orchestration beat put four commits into a human's log inside fifteen seconds. One rule belongs to the transport rather than to any caller — **stdout is the protocol** — so the whole program's logging is routed to stderr (`@olai/log`'s `toStderr`, one line at that composition root): a store's failed-probe warning on stdout is a frame that is not a frame, and no future writer should have to remember that.
- **The adapter is pinned, and it is the default on every launch path.** `nix/acp-agent.nix` builds the Claude Code ACP adapter from a committed npm lockfile; the packaged binary's wrapper bakes it in with `--set-default`, and the justfile recipes that run the tree directly (`just serve`, `just run`) resolve the same derivation on demand through `scripts/acp-agent.sh`. So no documented way of starting olai lands without an agent, and a person never has to learn that the variable exists. The `nix` CI lane asserts it: the wrapper must carry the assignment and the path it names must be executable, so dropping the `--set-default` fails a check rather than a browser.
- **`OLAI_ACP_AGENT` is the override, and empty is the off switch.** Point it at another ACP agent and that is what gets spawned — it is how the e2e suite points at a scripted one. Set it to the EMPTY string and there is deliberately no agent; that works through the packaged binary too, because `makeWrapper --set-default` emits `${VAR-default}`, which substitutes only when the variable is unset. (The one-dash form is asserted in the same CI lane: `:-` would swallow the off switch.)
- **With no agent, the panel says so.** Serving a directory has never depended on an agent being installed, and it still does not — but that principle is "the server is fine without one", not "hide the feature". The drawer draws, and its body names the variable and how to fix it. A capability that is silently absent cannot be told apart from one that is broken, or from one the reader has not found yet.
- **Logging is Effect's, and it is quiet by default** (`packages/log`). Every package says what it is doing with `Effect.logDebug` / `logInfo` / `logWarning` / `logError` — there is no `log` callback threaded through a constructor, which is what there used to be for the two packages a person actually hears from. **Two faces, one decision in the sink:** on a TTY the human gets Effect's pretty console logger (local time, coloured level, message first); when piped, under systemd, or in tests the face is [logfmt](https://brandur.org/logfmt) — one line per event, `key=value`, byte-identical to Effect's `formatLogFmt`, so the message is a short stable sentence and every value that varies is an ANNOTATION (`url=`, `root=`, `claimed=`, `agent=`) that can be grepped by field rather than matched out of a sentence. The e2e suite reads the bound address that way, which is also why pretty may only exist where no machine reads. **`OLAI_LOG=logfmt|pretty` forces either face**; harnesses that parse a line pin `logfmt`. `NO_COLOR` turns the pretty face's ANSI off. Annotations set with `Effect.annotateLogsScoped` are inherited by every fiber forked under that scope, so the store's own probe warning says which directory it was probing without the store ever learning what a served directory is; `Effect.withLogSpan` puts `serve=…ms` on every line, so a boot is timed and a later line says how long the server has been up. **The verbosity switch is Effect's CLI `--log-level`**, already parsed and already in `--help`: `Info` is the default, so the loudest thing in the program (a relayed agent stderr chunk, at `debug`) is off until asked for. A second spelling of that — a `--verbose` of ours, an env var — would be a second answer to one question, so there is not one. The one thing Effect cannot do by itself is log from a Node callback, where there is no fiber and the operator's chosen level would silently not apply: `@olai/log`'s `emitter` captures the fiber's services once and runs every later line under them.
- **`OLAI_ALLOWED_ORIGINS` is the CSWSH escape hatch**, comma-separated, empty by default (`packages/server/src/allowedOrigins.ts`, its own file for the same reason `OLAI_DIST_DIR` has one). Loopback and same-origin is the common case; the extra entries are for a front end whose browser origin is not the `Host` it forwards — a reverse proxy, or `tailscale serve`. The gate runs on the raw socket BEFORE the upgrade, because after it the browser has a connection to argue about, and the surface is unauthenticated: the origin is the only thing between a page somebody else served and every outline in the directory.
- **Git is the only history**: no sync protocol, no CRDT. It is one job and it is worth naming, because everything below follows from it — an AUDIT TRAIL OF WHAT THE TOOL WROTE. Chat auto-approves its ops and there is no web editor yet, so every write olai makes is one nobody typed; git is how you see what it did. Not for history (the notes carry their own dates), not for sync (a push shares what was recorded; nothing here merges, pulls or resolves), not for undo. **A commit is something somebody asks for** (`--commit=off | manual | auto`, `manual` by default; `--no-commit` still means `off`), and both subcommands take it: `olai web` and `olai mcp` are two faces of one ops layer, and a flag that meant different things on each would be exactly the divergence HACKING.md forbids. Writes land on disk and wait; a Commit button in the header and a `commit` MCP tool are two callers of one `Ops.commit`. `auto` is the old per-write behaviour, for a headless server with no browser to press anything. The control that asks is **always on screen** — a clean tree that has committed, one olai has never committed in, one with edits waiting, and a repository that is busy. That is the audit trail's own argument turned on itself: "there is nothing recording this directory" is the most important thing the feature can report, and a pill that disappeared is exactly how nobody would find that out (the connection dot's rule, for the same reason). Beside what is waiting it carries the LAST COMMIT olai made — `git log -1` through the audit filter, never the repository's HEAD — because what is pending says nothing about whether anything was ever recorded, and `null` there means "never", which an empty pending list cannot say. **What is waiting is DERIVED FROM GIT and stored nowhere** — the same discipline as node status: `git status --porcelain` names every dirty file in the REPOSITORY, `git show HEAD:<file>` is the committed side of each served outline, the store's own last-good parse is the working side, and comparing two parsed sets is a pure function beside the format (`format/src/changes.ts`) with no git in it. So a clean directory costs one `git status` and no parsing, an edit made in vim is in the panel like any other, and a commit made in a terminal takes itself out of it. **Never a text diff**: a `.jsonl` diff is one enormous line per node, so the unit is a NODE and what changed about it — *marked done*, *note rewritten*, *archived* — classified once into one `Sort` the panel and the commit body each have their own words for. WHO wrote it cannot come from git, so it is a per-writer counter the ops layer keeps in memory and clears on commit, explicitly allowed to be empty after a restart and never a substitute for the derived truth; the permanent record is an `X-Olai-Writer: chat-agent | mcp | web` trailer, without which an agent's commits are indistinguishable from a person's. Messages are prefixed `olai`, so `git log --grep '^olai'` is the audit view and `--invert-grep` gives back real history; a composed one names the biggest change by a fixed order, and the per-op words stay the racket reference's — `capture:` / `done:` / `doing:` / `move:` / `archive:` / `create:` / `see:` — with `date:` corrected off `move:`, which beside a real reparenting op read as a structural change that never happened. Committing checks that the repository is FREE first (merge, rebase, cherry-pick, detached HEAD): nothing used to, which is how an agent marking a node done mid-conflict could swallow a resolution, and that hole is what decided manual over automatic. A git failure never fails a write: the bytes are on disk and the browser has already seen them, so a refusal is an answer (`Failed`, with git's own words) rather than a failed op. **The scope is the WHOLE REPOSITORY, in two kinds of row** (`commit-whole-repo`, the human's bug: edit a `.md` by hand and the git part of the UI showed nothing pending). A dirty outline olai serves gets the node-level changes above; every other dirty file — a document, a source file, an outline outside the served root, anything untracked `.gitignore` does not cover — gets a path and the porcelain's own status letter, because the only richer thing available is the text diff this feature has never shown. What a commit NAMES is a SELECTION and never git's index: exactly the paths asked for (the panel's checkboxes, all ticked by default; the tool's optional `paths`), on both `add` and `commit`, so hand-staged work is undisturbed and what is left out stays waiting for its own commit and its own message. **And it PUSHES**, which was the last reason to leave olai for a terminal: one verb, the current branch to the upstream it already tracks, no remote to pick and no refspec, with git's refusal — authentication, a non-fast-forward — surfaced verbatim like a refused commit. How far ahead of that upstream the branch is comes off the `--branch` header the status call already prints, so "what is not recorded" and "what is not shared" cost one subprocess between them, and both are drawn on the one pill. Resolving a divergence stays in the CLI: no pull, no fetch, no branch UI. Design and the decisions behind it: [brainstorming/git-commits.md](brainstorming/git-commits.md).
- **And a reader is TOLD, which is the half that was missing** (`git-invisible`, filed by the human against his own vault): `committed: false` was four different pieces of news wearing one word — the opt-out, no work tree, no git on the service's PATH, a write that is simply waiting — and the actual reason went only to the server log, where somebody reading a browser never sees it. So every write's reply carries `why` when it was not committed, which is what the agent reads and what the transcript draws beside the call; under the default mode that sentence says the write is WAITING, because it is, and a reader who saw the git-error wording there would go hunting for a repository that is not broken. Beside it the header carries the Commit pill, whose faces cover what the `git` cell says — `off`, `repo`, `none`, `error` with git's own words — and the two classifications that keep it honest are exit codes and git's own sentences rather than guesses: a directory git will not answer about is an ERROR unless git said its own "not a git repository", because a broken git reported as "you have no repository" is the collapse that entry exists to have stopped. The `git` cell and the `pending` one are **one derivation published twice**, recomputed together by the server on the same three clocks (every revision, every landed commit, a slow sweep because nothing watches `.git`) — two probes would be two answers, and a page reading "Not a Git repo" beside a panel offering to commit four changes is the incoherence HACKING.md's consistency rule forecloses. They are now read into **one control** as well (`one-git-indicator`): the readout that used to draw the first of them beside the pill drawing the second is retired, because two chips answering one question is a redundancy a reader notices before anything else. Both values are still published, and the MCP face still reads the `git` cell as its own resource — what changed is a face, not a fact. The one thing remembered rather than derived is a commit that REFUSED, and it has to be: `rev-parse` answers happily in a repository with no `user.email`, so a state read from the directory alone would look healthy while every commit failed. None of it may make a write fail, wait or retry.

## Stack

- **Runtime**: TypeScript on Bun — Bun is the package manager, test runner and script runner; types are checked separately with `tsc --noEmit`.
- **Effect**: kolu's whole stack is Effect 4 (kolu PR #2101; the "Effect, everywhere" post) — Effect Schema at process boundaries, `RpcGroup` on the wire, `HttpRouter` layers for HTTP, `Schedule` for reconnect. oRPC, partysocket and hono are gone, and nothing olai writes uses zod. The `effect` version matches the pinned kolu's exactly (one copy fleet-wide, enforced via `package.json` overrides).
- **zod is in the tree, and it is not ours.** `@agentclientprotocol/sdk` declares it a peer dependency and imports it at runtime to validate ACP payloads, so it is a declared dependency of `packages/chat` — the one package that RUNS the protocol's subprocess — and comes back in the lockfile. (`packages/acp` imports the SDK's types only, so the runtime and its zod peer stay chat's.) That is the whole of it: no olai module imports zod, no schema of ours is written in it, and the format still has exactly one validator (Effect Schema, in `format`). Written down here rather than only in the manifest because "zod is gone" is the kind of claim a reader will otherwise carry forward — the honest version is that we do not write it, not that nothing in the closure has it.
- **Effect on Bun**: the proven odu/drishti pattern — `@effect/platform-node` under Bun's Node compatibility. One known seam: Bun's unix-socket async-connect-error contract needs odu's one-line shim, relevant only if we ever serve a unix socket.
- **Markdown**: remark + rehype-sanitize, rendered only at view time, and one pipeline for every piece of it — a node's note, a whole document, what the agent says, and a node's title are the same language read out of the same directory. Titles take one extra step after the pipeline has run: every block is unwrapped to its phrasing content (a fence becomes its `<code>`, a heading its words), so a title that contains block-level source cannot break a tree row's layout — racket parity, inline-only. GFM brings footnotes (whose ids are re-minted per rendered block, so two notes on a page cannot answer for each other); `rehype-highlight` paints fenced code, bundled with the client rather than fetched from a CDN, coloured with this theme's own tokens, and told which grammars it knows (lowlight's common set plus Nix, since this repository is built with it); relative images are rewritten to the `/media` route and everything else is dropped. Highlighting runs AFTER the sanitiser deliberately: the `hljs-` spans are ours and need no allowlist entry, while the `language-…` class that produced them is the reader's and is on the sanitiser's default one.
- **Styling**: Tailwind v4 — utilities inline in the components, and a CSS entry holding only the `@theme` tokens and the rules for markup this codebase does not author (a rendered note's tags come from a file on disk and can carry no classes). No `@apply`, which would recreate the problem utilities solve by inventing a second name for a set of them. Deliberately no class-validity scanner: kolu ships unguarded Tailwind and the silent-typo trade-off is accepted (decided 2026-08-09).
- **Theming**: the eleven tokens (paper, desk, panel, pill, plus ink/muted/rule and the four accents) are a *palette*, and there are fifteen of them (`web/src/client/theme/palettes.ts`, ported from the racket implementation). The table is the source: the build generates one unlayered `:root[data-theme="…"]` block per row and appends it to the stylesheet, and the preferences panel's Theme row draws one chip per row of it, so adding a theme is adding a row. A pick is CLIENT state — written on `<html>` by four inline lines in the shell before the first paint, stored in that browser, never sent anywhere, and carried into every other tab of that browser by its own `storage` event rather than waiting for a reload — and the OS's preference is not consulted at all: it used to choose the palette, which meant two ways to be dark that could disagree with each other and with the reader. One palette promises WCAG AA and a unit test holds it to that, pair by painted pair.
- **Type**: the three tokens (`--font-sans`, `--font-serif`, `--font-mono`) are a *typeface*, and there is a catalog of them — in `packages/fonts`, a package of its own, because the words for a face, the sheet generated from them and the derivation that produces the face were three answers to one question in three files and only one of them could be read at a time. Same shape as a theme: the table is the source, `@olai/fonts/build` generates `@font-face` plus one `:root[data-font="…"]` block per row, and the preferences panel's Font row draws one option per row. The default is Atkinson Hyperlegible (one voice); the Olai row is the one that keeps the three jobs distinct (Literata / iA Writer Quattro / iA Writer Mono). Hosted files come from nixpkgs and are converted to woff2 ONCE, by that package's own `default.nix`, in the Nix store — the conversion is a function of the font set, so the client build only copies out of `OLAI_FONTS_DIR` (it used to run 70 `woff2_compress` calls on every build, including every dev-shell rebuild, for bytes that were the same bytes every time). Generics download nothing. A pick is the same kind of client state as a theme — the shell's boot script writes `data-font` before the first paint — and is stored under `olai.font`, in `web`: the catalog is the words, the pick is the client's.
- **Dates**: validated as text, not through a date library — a writer must reproduce what it read verbatim. Reading them is text too: a day is a ten-character prefix and a month a seven-character one, so grouping, month boundaries and datetime→day are string comparisons. MINTING one is the other direction and has exactly one home, beside the rule that accepts it (`format`'s `stampOf`): every date value olai writes is a local ISO datetime carrying its offset, which is what the ops layer stamps a `done` with — local, because a mark is stamped where the person marking it is standing and a `Z` would file their evening under tomorrow. Only `done` is stamped (resolved 2026-08-11, human): a date on a mark places the node on that day, and filing or starting a task is not an event a day page is a record of, so `doing` and `todo` are written `true`. The one exception is where the days of a month land on a grid, which is integer arithmetic in the client (`web/src/client/calendar/month.ts`) rather than a `Date` — `new Date("2026-08-01")` is midnight UTC, which is the previous day for half the world, and a calendar that shifted a column by time zone is the bug that avoids. Temporal is still the intended tool if real date arithmetic is ever needed; nothing needs it yet. WHAT DAY IT IS is the client's one reading of a clock (`web/src/client/clock.ts`), in the reader's own time zone because the dates in the files are what a person wrote down, and it moves twice over: at the next local midnight, computed each time rather than assumed to be 24 hours later, and whenever the page becomes visible again — a laptop shut at eleven and opened at nine ran no timer while it slept, and a page whose promise is that it follows the files without a reload cannot have the day be the stale thing on it. The writer reads a clock too, when it stamps a `done`, and the two have to agree about where a local day ends — a mark made now must land on the day `/today` is showing — so that agreement is a test (`web/src/client/clock.test.ts`) rather than a rule two files each remember.
- **Nix**: flake + npins (kolu, nixpkgs) + justfile; `@kolu/*` packages hydrate as source from the Nix store.
- **E2E**: Cucumber + Playwright.

## Errors

Error kinds (`usage`, `validation`, `not-found`, `busy`) are `Schema.TaggedErrorClass`es — schemas that travel the wire and decode as themselves — surfaced as MCP tool errors and HTTP codes. Every validation error names `file:line`. Errors that teach are the product: a refused write carries the validator's own rows as structured data, and a write that LANDED can carry a nudge — what the rollup noticed, as advice rather than as a refusal (format.md's Status). There was a fifth kind, `derived`, and it went with status derivation.

Validation is staged, and the stage is part of the taxonomy (`stageOf`): a file is decoded whole or not at all, and the set-wide rules then run over the outlines that DID parse. What that costs the reader is one outline and, usually, nothing else — the hybrid error scope above, decided in the format ([format.md](format.md)) and published by the store.

**Not every failure is one of these kinds, and the ones that are not still have to reach somebody.** A refused write is an ANSWER, with rows a caller renders; a git that will not commit is not — the write happened, and nothing about the outlines is wrong — so it travels as two ordinary values instead: `why` on the reply of the write it concerns, and the `git` cell the header's one indicator draws. That is the rule HACKING.md now states, learnt here: never silently ignore an error, and most of them belong somewhere a person can see (`git-invisible`).

The staging still forbids guesses, and the catalogue is where each code answers for itself (`set-across-files`, read by `isGuessWhileUnreadable`). "`kitchen` is not a known id" is a guess when the line declaring `kitchen` is the one that failed to parse — so while any outline is unreadable, an unresolved `mirror`/`after`/`blocks`/`see` target is withheld rather than reported, and withholding one is itself a reason to refuse the whole set: its nodes point at ids nothing can resolve. Everything else is a finding whatever the missing file held, and is reported alongside the parse errors, because one pass should be enough to fix a directory. A report containing a per-line error says so (`reportStage`), and a second round is expected after those are fixed.
