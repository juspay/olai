
Olai serves one directory. Which files under it are part of the set is one table in `@olai/format` (`kinds.ts`, and [format.md](format.md)): `.olai` files are outlines, `.md` files are documents and `.html` files are hypertext, with the documents carried in the same snapshot as their text, because what is in one is content of the directory the way a note is — and hypertext carried as its PATH alone, because a saved page is megabytes that nothing in the set reads, so its body is read when somebody opens it and kept by nobody ([format.md](format.md)). Everything else there — a `README`, a picture, a source file — is not part of the set at all. There is one entrypoint and three write surfaces, not three products: `olai web <dir>` puts a browser in front of the ops layer, `/mcp` on that same listener puts an agent's HTTP client in front of the same one, and `POST /capture` on that same listener again puts a share sheet, a Raycast script or a `curl` in front of it with exactly one verb — a line into the directory's inbox, which is the one write worth a door of its own because the thing it costs is the five seconds between having a thought somewhere else and it being in the vault. There is no write CLI and there never will be — nothing on the command line adds a node, marks one or moves one, and the subcommand is a transport rather than a tool.


It reads that directory and keeps reading it: edit a file or `git pull`, and the open page follows without a reload. It also writes it, through one gate, from one layer: an agent asks for a node to be marked, or a person presses `Ctrl+Enter` on the row, and the tree in front of you follows — because both writes went to disk and came back through the same probe every other change does. Three writers now, one ops layer, and none of them can name a byte — the third is a line POSTed at `/capture` from somewhere that is not this app at all.

## Shape

```
files on disk ── load + validate ──▶ snapshot ── surface collection ──▶ browser (SolidJS)
      ▲                                                          │           │
      │                                                    chat panel     keyboard
   commit(baseRev)                                               │           │
      │                                       ACP session ◀──────┘           │
      │                                            │                         │
      │                                       MCP tools           edit procedures
      │                                            │                         │
      └── ops (create, add, mark, move, trash, untrash, see) ◀───────────┘
                                                 ▲
                                                 └── stdio ── an agent in a terminal
```

- **Store** (`packages/store`, generic — caller-supplied codec, no olai types; extractable to its own repo later): files load into a validated snapshot, revision-tagged, with errors on a second independent channel so a broken set does not blank what is on screen. A published snapshot also names WHAT MOVED to make it — the paths re-decoded and the paths the listing lost — which is the probe's own stamp diff kept rather than thrown away, and what lets a consumer publish per file without re-deriving the diff by comparing two whole snapshots. It spans the gap between two published revisions, not one probe: a probe the codec refuses publishes nothing, so what it found is still owed to the next revision that validates. It stays current by PROBE — re-list the tree, re-stat everything, diff against a table of mtime+size stamps — with a file watcher that only *triggers* the probe and whose event payloads are dropped unread, plus a settle delay that turns a `git pull` into one probe and a slow backstop for the events a watcher loses. The walk arms a watcher of its own on every directory made after the store booted, because the pinned runtime's recursive watch registers the tree it finds at arm time and never follows a new one — without it a folder made in a live vault stayed dark until the backstop swept it a minute later. So a file arriving via `git pull` appears without a restart, and only the files whose stamps moved are re-parsed. The walk prunes dot-directories and `node_modules`: a served directory is somebody's working tree, and `.git` is both the largest thing under it and the one git writes to constantly — an unpruned probe would do its most expensive work exactly when git is busy. Design and the decisions behind it: [brainstorming/architecture.live-store.md](brainstorming/architecture.live-store.md).
- **One brain per vault, and the kernel keeps it that way** (`packages/server/src/lock.ts`). Everything the store promises is a property of the DIRECTORY rather than of the process, and none of it survives two of them: whole-file writes are last-writer-wins, so one server's edit erases the other's with both reporting success; validation is per-store, so two individually valid writes put duplicate ids and after-cycles on disk that neither would have accepted; and two commit paths sweep one work tree. So the store boot takes an OS advisory lock (`flock`, through `bun:ffi` — the runtime exposes none) at `$XDG_RUNTIME_DIR/olai/<digest>.lock`, keyed on the served directory's REALPATH so a symlinked spelling is one vault, and a second olai refuses to boot naming the pid that holds it. An advisory lock rather than a pid file, because the kernel releases it on any death at all: no staleness protocol, nothing to clear after a crash, and no file left inside somebody's notes. What it excludes is another olai on THIS machine, and it says so about what it cannot: a share seen from two hosts, which no `flock` promises on both platforms.
- **The write gate is the same loop, run deliberately.** `commit({baseRev, changes, afterPublish?})` takes the probe's own permit, so a write and a `git pull` can never interleave over the stamp table they both read. Inside it: probe (so a change that arrived out of band is part of the revision this write is judged against), then the optimistic check — a `baseRev` the store has moved past is a typed `StaleWrite{currentRev}` — then validate the set the write WOULD produce, then stage every file beside its destination and rename them all, then re-probe and publish. Validation before any rename is what makes a refusal cost nothing on disk. The two outcomes travel on different channels because they mean different things: `StaleWrite` is a failure and the caller re-derives; a set the codec refuses is an *answer*, so the caller renders the errors rather than retrying. The changed files are re-read because the gate says so rather than because a stat noticed — stamps are deliberately coarse, and a write landing in the same second at the same length is exactly what they cannot see. What that re-read finds is the set the gate ALREADY judged, so the publish is that verdict rather than a second one about an identical set: the file is opened and its bytes compared with the ones the write promised, and the moment anything differs — a byte, a file that arrived — the codec is asked afresh. For olai's codec, whose validation builds a view of the whole corpus, that is the difference between one derivation per edit and two. The git commit rides `afterPublish`, an Effect the caller supplies, so the store never learns what git is.
- **A validation is offered what came before it.** The store knows two things no codec can work out for itself — the value it last published, and every path that has moved since — so it hands both over (`Codec.Since`) and a codec that can answer incrementally does. It is an offer and not an instruction: a codec that ignores the second argument validates the map it is given, exactly as before, and both answers are correct. What olai's does with it is PATCH the derivation instead of rebuilding it (`format/src/patch.ts`): the changed files' entries are swapped in the indexes and the rest is left standing, with reverse indexes saying which mirrors, edges and blockers have to be looked at again — and one more of them, filed by the TAG a title or a note writes (`#topic` and `@person` under keys that keep the sigil), which is what makes “what refers to this node” a lookup rather than a walk of the directory ([format.md](format.md)’s References) — and, since `mentions-index-one-sigil`, what makes the tag completion a lookup too (`format/src/vocabulary.ts`, which the browser asked of itself until `vault-in-browser` moved the question to the server). The patcher is held to `derive` by a property test — for any corpus and any delta the two views must be the same value — and it is free to DECLINE (a duplicate id, a delta that leaves nothing of the old view standing), which costs a rebuild and never an answer. It is two orders of magnitude on a vault-sized directory, and that figure is a HARNESS rather than a laptop sample nobody can re-run: `just bench` derives a generated 1,000-file / 21,552-record vault and then makes forty one-file edits, each to a DIFFERENT file, patching against rebuilding, and reports **0.42ms patched against ~49ms rebuilt, a ~115×** (`format/src/patch.bench.ts`; run-to-run variance on one machine is why the ratio is the honest figure rather than either number, and it is a leg somebody runs rather than a lane that fails on a busy machine — those two moved with `mentions-index-one-sigil`, which widened the tag fold a rebuild pays and left the ratio where it was, and they are medians of several alternating runs rather than one). What the patcher itself stopped paying is the copy-on-write it used to owe the corpus, in two goes. First `byId`, which has an entry per record in the directory: cloning it was the largest single line in a patch, and it became a LAYER over the map the last patch left standing (`format/src/overlay.ts` — same answers, same key order, nothing above it can tell). Then the rest of the residue (`perf-patch-residue`), which is where the layer's own argument got its rule: the reason the other ten stayed clones was written down as "a layer cannot DELETE a key", and that was a fact about the layer as built rather than about layers, so the layer learnt to delete and to append and the question became **who reads this index**. An index asked BY KEY gets one — `byId`, `children`, `status`, `after`, `blocked`, `mirrorsOf`, `edgesTo`, seven of the eleven — and an index read WHOLE stays a clone, because a walk through a layer costs more per entry than the copy it saves (`namedBy` for the validator's report, `taggedBy` for tag completion, `byDay` for the agenda and the calendar, `byFile` for whoever wants the corpus flat). The leg prints both halves rather than asserting either: the seven cloned on their own are ~0.73ms of a patch against ~0.12ms for the four, and `namedBy` walked whole is 0.062ms as a map against 0.208ms through a layer. In the same round the patcher stopped FLATTENING the corpus at all — `Derived.nodes` is `byFile` read the other way, so the patched view builds it when somebody asks and the validator, which used to flatten the set a second time just to check the patch was about it, checks the files instead. Design and the decisions behind it: [brainstorming/model-indices.md](brainstorming/model-indices.md).
- **Error scope is hybrid**, and the two halves answer different questions. A file that does not PARSE costs that one outline: the sidebar still lists it, opening it shows its own errors where its tree would have been, and every other outline stays live. A failure that no single file owns — a dangling cross-file reference, a duplicate id, a cycle — holds the whole last-good snapshot and raises a banner over it, because half a set is a set that was never on disk. The codec decides which of the two applies (`validate` is handed each file's `Result`, decode failures included) and the store only publishes the answer. A third failure is neither, and it travels the same channel for the same reason: the directory could not be READ — EACCES, a mount that vanished, no room to answer a stat. That one is the store's own rather than the codec's, so the codec is asked to translate it (`Codec.unreadable`) into the vocabulary its surfaces already draw, and it lands under the same banner over the same last-good tree. It used to be a log line and nothing else, which meant an outline that had stopped tracking the disk went on looking live — the exact failure a live store exists to prevent.
- **Git** (`packages/git`, a LEAF — `effect`, `node:child_process`, `node:fs`, and no workspace sibling at all): git as plumbing, and nothing that decides anything. One socket, `open(root)`, answering with a repository handle whose verbs are business questions rather than the commands behind them — what state the repository is in, what has moved in it, what HEAD had in a file, what was last recorded under a caller's own audit filter, commit exactly these paths, push the current branch — or with `NoRepo` for a directory that is not a work tree, or `Unusable` for a git that ran and could not answer, which are two different pieces of news and were one `null` until #108. It was `ops/src/git.ts` and moved out under `commit-whole-repo`, which is also the answer to "should olai take a git library": the handroll is a few hundred careful lines that work, and a package with one dependency is a smaller thing to own than an adapter over `simple-git`, a reimplementation of git (`isomorphic-git`) that can diverge from the one on your PATH, or a bundled binary (`dugite`). What it does NOT know is olai — who a writer is, what a commit message says, which dirty files matter — and both of the olai-isms it used to carry are handed in now: the audit convention (`olai:` and `X-Olai-Writer`) is an argument, and the trailer comes back verbatim for the ops layer to classify. Its `./state` subpath is the half with no subprocess in it — `RepoState` and `Reason` travel the wire, `@olai/format` re-exports them for its pending schema, and a browser bundle must never reach `node:child_process`. Two properties are its own rather than a caller's: a commit names only the paths it was given, and a commit that REFUSES puts the index back bit-identical — the `add` a commit needs writes the real index, and leaving it there meant a refused commit staged a selection nobody asked for.
- **Ops** (`packages/ops`): the only writer, and the only reader an agent gets. Between `format` and `store`, because it is where an EDIT lives — "mark this done", "put this under that", "start a new outline", "trash this", "point this at that" (`see`) — and neither of those two knows what one is. Every request names a NODE or a DOCUMENT (or, for the two creates, a relative path — `.olai` or `.md` — judged segment by segment the way `/media/*` is), never a free-form byte range, and three things follow from that: a retry against a newer snapshot lands cleanly, so no writer silently loses an update; a plan is whole RECORDS through the format's own writer, so a malformed file is unrepresentable through this path; and an answer carries structured detail rather than prose — a refusal brings the validator's own rows, each pinned to its `file:line`, and a write that LANDED can bring a `nudge` (what the rollup noticed: a branch ticked done over tasks still open, the last task under a parent finishing), which is advice on a success and never a reason nothing happened. `create` is the one op that mints a file the set does not yet hold — `add` refuses any path that is not already loaded — and it rides the same stage → validate → rename → commit gate, optionally seeding it with a capture. `add` takes a whole nested subtree in one request — with each node's `props`, `see` and `waitsOn` on it, so a plan arrives WITH the order its steps happen in and a target may point forward to a sibling the same call is about to mint — and `create`'s seed is that same capture, which is the same property read from the other side: one plan over N records is one validation and one all-or-none rename, so an outline is captured in one gesture and cannot half-land — and a new outline arrives holding its contents or does not arrive, rather than being created empty and filled by a second call that might refuse. `update` and `apply` are that argument made GENERAL (`olai-batch-verbs`): several fields of one node, or an ordered list of the write verbs themselves, folded into one plan by calling the planner once per op against the reading the op before it left behind — so every refusal is the single verb's own refusal in the single verb's own words (asserted literally, by comparing the two messages), while the gate still validates once, renames once and publishes one revision. A batch refused anywhere leaves the file byte for byte as it was and names which op it was; what a caller cannot build for itself out of a loop is exactly that. **The READS stopped looping too** (`mcp-read-batch`), and they were the half that still did: `read_subtree` took an id, so an outline of N top-level roots had no single-call read at all — `list_outlines` named the roots and the descent was one call each — and a search hit carried the whole `custom` map and not the note, so "every bug with its forensics" was one query and a `read_node` per hit. `read_subtree` takes an `id` OR a `file` now, exactly one, and the file arm answers `{file, roots}` — every top-level node walked, each saying for itself whether it stopped at the depth or at a leaf, with a top-level placement no more a root than it is a walked child. `search_nodes` takes `withDesc`, and that flag is the one asymmetry worth the sentence: every other field of a record rides a hit by default because each is bounded like the title beside it, where a note is unbounded prose — and this same request is what the ⌘K palette and two panels ask over the wire on every settled keystroke, so always-on would put the vault's notes on that wire per keypress, which is the cost `vault-in-browser` spent an arc removing. A `file` that is not an outline is REFUSED with the closest one that is (or with the outlines themselves when nothing is close), in `read_document`'s own words and through the same near-miss function — one typo, one answer, whichever verb it landed at, which is also why the write that places a node at a file's top level now says it too. `split` and `merge` are that same argument for the two edits that change how many rows there are: a split is a retitle plus a create and a merge is a retitle, a note, N reparentings and a trash, so composed by a caller each would be several writes at several revisions, able to stop in the middle and leave an outline saying something nobody wrote. They are one request each instead, which is also what keeps the faces equal — the keyboard's `Enter` mid-line and `Backspace` at line start ARE these ops, rather than a sequence the web can perform and an agent has to spell out four times. It also owns the codec that joins `format` to `store` — the same joint the write gate validates through — and the closed TABLE of what an agent may do, each entry carrying its own schema and, for a read, its own reader. How that table reaches an agent is not this layer's: `server` projects it onto `@kolu/surface-mcp` bespoke tools, which is what keeps the MCP SDK out of the closure of a package that knows nothing about a listener or a socket. The KEYBOARD reaches the same procedures by another projection, and the layer is unchanged by it: the browser's edit procedures are resolved into these same requests by `server/src/edit.ts`, so an op still does not know it is being called over a wire, and there is one writer rather than two things that both write.
- **Documents ride the snapshot, and reach a reader one at a time — and they are WRITTEN through the same gate** (`md-editing`). A document write is an op like a node's: the whole new text, validated with the set, staged and renamed atomically, audit-trailed with the same trailer, landing on its own revision — so a save in one tab reaches the other tabs the way a `git pull` does, and an agent's `write_document` is the same call the browser's editor makes. The write may carry `was`, what the caller read, refused on every retry when the disk has moved since; that refusal is the whole conflict story for a file edited in vim under an open editor, and the browser draws it verbatim with the draft kept. Creation is its own op (`create_document`), refusing a path that exists as write refuses one that does not, so a typo can never quietly mint a file. **Both are READ back through the same snapshot** (`md-second-class`, the read half): `list_documents` answers every served `.md` with the line it opens with, what it weighs, and the properties its frontmatter writes (omitted when none), `read_document` answers one body verbatim, and a path the set does not hold is refused with the closest one that is — the same near miss `write_document` gives, from the same `didYouMean`. That pair is what makes the `was` guard usable at all: before it, a caller was asked for the text it had read and had no tool that could read any. A `.md` decodes to its text through the same codec, is cached against the same stamp, and travels in the same revision, so an edited document reaches an open page by the mechanism that was already there and there is exactly one answer on screen to "what does this directory say right now". What CROSSES the wire is a `documents` collection keyed by path, `keys` + `get` and deliberately no `deltas`: the sidebar draws paths, so the key set is the whole of what a first paint needs, and a body travels to the tab that opens one. That is `snapshot-scale`, and it is a wire change only — the server still reads and validates every document, because a `doc` reference has to be checkable. What it replaced was the documents (text and all) on the `manifest` cell, which put every served body in the FIRST frame of every subscription: ~124 KB of a ~212 KB snapshot for this repo's own `docs/`, and O(corpus) for the directories of thousands olai has to serve. What a second read path would have cost — the reason a body still rides the live store rather than an HTTP fetch — is a second thing to invalidate and a page whose outline and document could be two different reads of the disk; a per-key `get` is the same store, the same revision, and an entry stamped with the revision it was published at. The one thing that cannot ride it is a PICTURE — the browser fetches an `<img src>` itself — so there is one HTTP route besides the bundle, `/media/*`, restricted to picture extensions, and its URL is declared in `surface` so the renderer that writes it and the route that reads it are one bijection rather than two spellings kept in step by hand. A relative LINK between two `.md` files goes through the same seam and lands at that document's own address, `/<path>`: `format` resolves it beside the file the link was written in (never beside the route the rendering is drawn under, which is what a browser would do and is wrong for a note on a day page), the client spells the address, and a click on one is answered in place by a single delegated listener on the main pane — rendered markdown arrives as HTML, so its anchors belong to no component and cannot be the app's own `<Link>`. Nothing else about a link is touched: a scheme goes where it says, a fragment stays the platform's, and a relative path to anything that is not a document is left as written.
- **Surface mapping** (kolu's surface framework, pinned via npins): the outlines are a `collection` keyed by root-relative file path, served with the batched `deltas` verb — one entry per file, so a probe tick that touched one outline sends that outline's slice and a `git pull` of forty is one coalesced `{upserts, removes}` frame, and the key is DECLARED in the protocol (`keySchema`) rather than inherited from a client library's default. The documents are a second collection on the same key, `keys` + `get` and no `deltas` — the batched verb opens with every entry, which for documents is every body, so its absence is what keeps the corpus off a first paint. A THIRD is EVERY served file with its content left off — `heads`, one revision, one face and one "did it parse" each — and it takes the `deltas` the documents cannot afford, because a path, an integer and a title per file is what the key set already cost: so a reader learns its file LIST, what each file is called and every file's revision on one stream, and asks for content only when it is going to draw it. A previewed `.html` never does — its frame fetches the file over HTTP — which is the case the member was built for; covering the OUTLINES as well is `vault-in-browser`'s PR 10, where it became the whole of what a browser knows about the directory. The set-wide facts are a `manifest` cell, and today it carries no value at all: it is the `null` that says a directory has never loaded, which an empty collection cannot say, and nothing else — a set revision there would move on every probe tick and wake every open tab for it. What the entries are, and what the store's per-publish change summary has to do with them, is [brainstorming/outlines-as-collection.md](brainstorming/outlines-as-collection.md). Error state is a `cell`; what git is doing for the directory is another (four states, moving at most twice in a serve — the probe, and a commit that refuses — which is why it is a cell and not a stream of anything); folding and the view toggles are on no member at all — they are client-local, and folding is this browser's own storage (`web/src/client/fold/`); chat is a `collection` with batched deltas for the transcript, a `cell` for where the conversation stands, and `procedures` for send/cancel/new/load/list — `send` carrying the nodes a message is ABOUT as bare IDS, because the set is the server's to read and a browser's account of it is a frame old — the two that answer a question the agent asked (a question's row key IS the id those verbs name, because it is the one entry a browser talks back about and two spellings would be a mapping to keep in step for nothing) — plus `attach`, the one member that carries BYTES, in bounded chunks: a pasted picture would otherwise be a frame that scales with the file, and an oversized frame is answered by closing the socket rather than by failing the call, taking every other subscription on that tab down with it. How big a chunk is, and why, is the framework's and not olai's — the arithmetic sits beside the frame cap it is derived from (`@kolu/surface/frame-chunking`, juspay/kolu#2158). Olai carried a copy of that derivation, taken from kolu's own padi where a 26 MB drop had proved it the hard way, and two copies of a margin is the shape of bug where a second `maxPayload` disagreed with the classifier above it and killed the frames in between. What olai keeps is the GATE, which no framework can decide: the two extension allowlists, the cap on a file, the tmp directory the bytes land in. A procedure rather than an upload route, because a procedure inherits the origin gate and the session the listener already enforces for the websocket; a sibling of `send` rather than a widening of it, because the two answer different questions and one picture is N calls to one send. EDITING is a `procedure` and deliberately nothing else — ONE of them, over a tagged union of what a keyboard may ask for (the shape the ops layer already uses for the same kind of thing, so the list of verbs is spelled once rather than five times), and the collections stay read-only on the wire, because an edit changes a FILE and a file reaches every open tab the way a `git pull` does. What they carry is the keyboard's own vocabulary rather than the ops requests re-spelled: `Tab` says "indent this", `Ctrl+Enter` says "toggle done", `Ctrl+Shift+Enter` says "walk this row's mark on" — and which answer that lands on is read off the snapshot as well, round a ring (bullet → `todo` → `doing` → bullet) that deliberately does not pass through `done`, since finishing something is a thing a person means rather than a thing to do on the way past, and a walk asked of finished work resolves to the request the ops layer refuses in its own words rather than to a rule the resolver would be inventing — and the placement each implies is read off the snapshot the write is judged against (`server/src/edit.ts`) rather than computed in a tab from a tree some frames old. What it answers with is the node the write was about, the ops layer's own `nudge` — advice on a success, which a person who pressed a key deserves as much as the agent that already gets it — and what would TAKE THAT WRITE BACK: the edits that reverse it, derived from the same reading the request was resolved against, because where a row sat and which mark it replaced stop being true the moment it lands, and a browser noting them down for itself would be the second reading of the set this whole seam exists to avoid. That is what ⌘Z spends (`web/src/client/edit/undo.ts`): an undo is the inverse REPLAYED through this same procedure, judged against the snapshot as it is now, never a restore of an older one — which is the difference between taking back your own edit and quietly taking back everything another writer has done since. The two verbs that only an undo sends (`place`, `remove`) are the only ones here that name an absolute placement or an id nothing on screen chose, and they are ids the SERVER derived; the `•••` menu speaks three more (`date`, `unmirror`, `trash`), the Trash view's `Put back` a fourth (`untrash` — born in the ops layer and exposed on both faces together, since no face had it), the Trash PAGE's own `Empty trash` a fifth (`emptyTrash` — `empty_trash`, born the same way and the only destructive write on either face; see below), the two EDGE fields two more (`see` and `after` — `set_see` and `set_after` in the ops layer's own shape, two optional lists rather than one target and a direction, because nothing is resolved behind them and a narrower spelling could not express its own inverse; the web had DRAWN both edges since edges-ui — the links under a node, the dim and the `blocked by` line of a blocked row — and could write neither, which is the same standing deviation the menu's verbs closed one field at a time, and what differs between the two is the planner's alone: an `after` add that would close a loop is refused NAMING the loop, in words both faces read verbatim), the OUTLINE one (`outlineNew` — `create_outline` from the sidebar, `docNew`'s twin, carrying no seed because a person's first row has a place to be typed and an agent's seed only saves it a second call), the MOVE-TO picker one (`under` — a row and the parent it goes under, `⌘⇧M` and the `•••`'s `Move to…`, resolving to `move_node` with that parent and no anchor so the row lands last among its new siblings; the fifth way a row moves and the only one that names where it is GOING rather than which step it is taking, which is why it is an arm of its own rather than a fifth `how`), the DOCUMENTS three more again (`doc`, which commits a document's editor and is the only verb here whose subject is a file rather than a node; `docNew` and `docDay`, the two creation doors — and the second of those carries a DATE rather than a path, because where a vault keeps its daily notes is a fact about the set and so is read on the server like every other placement), plus `mark`, which is BOTH theirs — a menu entry meaning "this is doing now" and an undo meaning "it carried `todo` before I ticked it off" are one request, so they are one arm. Those are the closing of a DEVIATION rather than growth: an agent could clear a date, retire a placement and trash a subtree, and a person could do none of them, which HACKING.md's consistency rule forbids. Each resolves to the request the equivalent tool would have sent, so a fence a menu wants — the trash confirm, which names how many rows go — lives in the panel and never in the schema, where it would be a rule the agent's own op does not have; the two TEXT verbs need no undo twin, because the inverse of setting a title is setting the title it replaced — what an undo adds there is `was`, the text it expects to find, so putting back what this tab replaced can never overwrite what somebody else has typed since (the human found the hole this closes by driving it: a committed title used to answer "nothing to undo"). One of them is the UN-CREATE and not a delete: nothing but an inverse produces a `remove`, no key sends one, the only row it can take back is a row that was just made and has nothing under it, and it resolves to the ops layer's own `trash`. Whether this face gets a delete KEY is still the deferral #109 recorded. EXACTLY ONE VERB HERE DELETES, and it is not the one that deferral is about: `emptyTrash`, the Trash page's `Empty trash`, which permanently removes every record in `_olai/Trash.olai`. It names no node and reaches no live outline — the only rows it can touch are ones somebody already put away and can still see — and it resolves to ONE `empty_trash` naming that file (leftover `Archive.olai` is not the trash and is refused). It carries the COUNT the confirm showed, checked in the planner on every attempt, so a record put away between the frame somebody read and the write landing is a refusal rather than something quietly deleted. It answers with NO inverse, and it is the second verb to do so — `unmirror`'s silence is about a placement this surface cannot spell, and this one's is about records that have left the set, which no op reaches; what still holds them is git, to exactly the extent git had already recorded them. TWO of them are COMPOUND — `split` (`Enter` with text on both sides of the caret) and `merge` (`Backspace` at offset zero) — and they are the one place this list grew by growing the OPS layer rather than by re-spelling it. Each changes an outline in several ways at once (a retitle and a create; a retitle, a note, N reparentings and a trash), and each is ONE request at the write gate, because a sequence assembled in the resolver would be two things at once: the web doing in one keystroke what MCP needs four calls for, which is the deviation HACKING.md forbids, and a write that can stop in the middle, which for a merge means an outline saying something nobody wrote. So they were born in `@olai/ops` and reached both faces in the same change (`split_node`, `merge_node`), which is `parity-unarchive`'s shape. `split` is the only verb here carrying text it did not read off the set — the two halves are the DRAFT's, and they cross as two TITLES rather than a caret index, because no verb on either face names a range into a field — and `merge` carries nothing but an id, since which sibling is above is a fact about the snapshot. Both name the ROW's own record rather than the node the row shows, which is where they part from every plain text edit: each puts a row on the page a reader has open, or takes one off it, so each is a question about where rows SIT — and asked at a mirror both are refused in the ops layer's `notANode` words, because a split named through a placement would mint its tail beside the TARGET, in a file the reader is not looking at (a mirror draws its target's children and never its siblings), leaving the two halves of one sentence unrelated on screen and the caret following the tail off the page. What a merge does with the rest of the row is the semantics and every line of it is a decision: the titles run together, the notes join a blank line apart, the children are adopted in order by the row above, and the mark, date, attached document and edges go with the RECORD into the trash — recoverable by id, and never silent, because the reply's `nudge` says what went. The transcript is a collection rather than an event because an event replays nothing: the `deltas` verb IS snapshot-then-deltas, so one subscription carries both the history a reloaded tab needs and the frames a live one is watching, with no dedup rule in the browser. Every subscription sends a full snapshot first, then deltas; a reconnect is just a fresh snapshot — no resume protocol, no optimistic UI. No raw wire code — Effect RPC, sockets, HTTP routes — exists outside surface's API, with four deliberate exceptions, and none of them is a surface member: everything an MCP CLIENT speaks (the internal route, and the HTTP `/mcp` a terminal agent posts at) — which is the same surface, re-projected by `@kolu/surface-mcp` rather than re-declared — whose consumer is an agent rather than an olai browser; `/media/*`, which the browser fetches itself — the URL of that one is still declared in `surface`, so the renderer that writes it and the route that reads it are one bijection rather than two spellings kept in step by hand; `GET /olai/who`, which the header chip fetches — who this REQUEST is, not a cell, and the path and JSON live in `surface` for the same bijection reason; and `POST /capture` (the bullet below), whose consumer is a share sheet or a shell script that has never heard of a websocket and must not have to — a surface member would have made every client a surface client, which is the opposite of a door anybody can write five lines against. (`POST /olai/resync` is a fifth route on the listener and is not one of these: it carries nothing and asks for nothing, it only tells the store to look at the disk now.) The websocket cannot see that value today: kolu's `serveSurfaceApp` owns the upgrade and does not hand request headers to the app.
- **The connection is a thing the page reports on.** A page that is live and a page whose server died look identical unless something says otherwise, so a pill in the app header reports the wire in every shape of the app on desktop, green only while a server is answering. On a phone a healthy wire is silent and a dead one is the freeze overlay. It reads `connectSurface`'s own `readout` — `connecting` / `live` / `degraded` / `reconnecting` / `retired` — and `retired` is the one that matters most: the server this page came from has been replaced, the link has stopped dialling for good, and the only recovery is a reload, which the page offers rather than pretending (and which it knows to offer because the readout carries `needsReload` rather than because a list of terminal states is kept here by hand). The handshake behind it is the framework's, not ours: the socket probes the reserved `system/identity` member on every open and echoes the server's process id back as `?pid` on the next dial, and `gateStaleSocket` on our side closes a tab presenting an id this process did not mint. Both halves used to be an app's to remember, and forgetting them is what shipped a tab that sat on a dead server looking healthy (juspay/kolu#2133 moved them into the seam and made the terminal state a required option). And green is a claim about what REACHES the page rather than about a socket, so it is the conjunction of the wire's status and the subscription-health fact, which knows what the transport cannot: a socket that is open and answering while a subscription over it is dead. That is a fifth state, `partly live`, and its detail NAMES the streams that stopped, because "something is not arriving" is the least useful true thing available. That conjunction was olai's own for one release — a `client.health()` walk in `status.ts` — and it is the framework's now (juspay/kolu#2160), for the reason the identity handshake became the framework's: it was a step every consumer had to remember, and the consumer that forgot it is exactly what left a dead `documents.keys` rendering as a directory with no documents in it under a green light. So the three rules travel with the readout rather than being restated here — `live` is the conjunction, `degraded` names what stopped and is non-empty by type, and a subscription still waiting for its first frame does NOT degrade, because that is what every page load looks like and a pill that is amber most of the time is a pill nobody reads. What did not graduate is the LOOK, and that is the whole of what `connection/status.ts` still holds: what this house CALLS `degraded`, and the sentence green makes about this directory. Folded into the pill rather than drawn beside it, for the same reason the git pill beside it is quiet when it is happy: one green claim per page. **And a wire that cannot carry a question now takes the app away**: an overlay covers everything, in the pill's own words, and nothing underneath is interactive until the connection returns (`connection/Offline.tsx`, the human's §5b ruling in `brainstorming/vault-in-browser.md`). It is the "live or nothing" doctrine — no service worker, deliberately — carried to its end: the browser answers nothing for itself since `vault-in-browser`, so a dead socket does not merely pause updates, it takes every door on the page with it, and a page left interactive under one would be doors that pretend. `connecting`, `reconnecting` and `retired` are the three it covers; `degraded` is not one of them, because that socket still lands a procedure. `retired` keeps its reload offer on the overlay itself. It is a modal `<dialog>`, so the browser puts it in the top layer and makes the rest of the document inert — the only way to promise nothing underneath is interactive, which no `z-index` can against a panel that portals to the body later.
- **So is git, and for the same reason — in ONE pill.** "Is this page still reading?" and "is what gets written to it being kept?" are the same shape of question about the same page, and both are facts a page can only get wrong SILENTLY — so the header carries an indicator for the second beside the connection pill answering the first. It is the **Commit pill**, and it is the only one: a separate `● git` readout sat beside it for a while, both answering "what is git doing here", which is what the human filed as `one-git-indicator`. They were already one derivation rather than two probes, so the fix was the face rather than the data — every state that readout drew is a face of the pill now, reading the `git` cell alongside the `pending` one. `commits off` under `--no-commit` and `no git here` are SETTINGS: dim, inert, no warning, because an owner's choice about a directory whose history is somebody else's job is not a fault. `git error` is the fault, and it carries git's own words on the tip AND on the `aria-label`, never hover-only. Healthy is quiet — `✓ committed · 3m ago`, with the tick deliberately not wearing the connection's green: one green claim per page, or neither is scanned. What the desktop pill may NOT do is disappear when all is well: an indicator that is only there when something is wrong cannot be trusted when it is absent, because healthy and not-rendered look identical. A phone banner can — it is only there when there is news, and the page itself is the healthy state. It also carries what is recorded HERE AND NOWHERE ELSE (`· 3 unpushed`), which is a second fact about the same work rather than a second control — an audit trail on one machine is one disk failure from not existing, and the panel behind the pill is where the Push button lives.
- **Web**: a SolidJS client over WebSocket, using surface's solid hooks (subscriptions land in Solid stores the framework owns). **A tab holds at most the page in front of somebody, and never the vault** (the human's ruling of 2026-08-19, landed whole in `brainstorming/vault-in-browser.md`'s PR 10). What it subscribes to is the DIRECTORY — `heads`, one entry per served file carrying its revision, its face and whether it parsed (`web/src/client/directory.ts`) — and, per open pane, the ADDRESS that pane is drawing (`web/src/client/reading.tsx`, over the `page` stream) — plus, for a pane somebody has NARROWED, that same address with the words in the box (`web/src/client/filter/asking.ts`, over the `narrowing` stream: which of the page's own nodes the query selects, re-read on the same pulse and sent only when it moved, where it was once a whole-vault search asked again per page frame — `filter-ask-carries-revision`, [brainstorming/filter-rides-the-page.md](brainstorming/filter-rides-the-page.md)). The heads become the sidebar's file tree (`fileTree.ts` — one walk mixing `.olai` and `.md` under the folders they live in; folders start collapsed, collapse is client-local and remembered by this browser like the outline tree's folds, and the open file's ancestors stay open so the selection is never hidden), the entries carrying a `broken` are the files that would not parse, and the manifest is what decides between waiting, never-loaded and reading. A page's rows, its crumbs, its backlinks, what its ids are called and what an archive of a row would move all arrive on that page's own reading, computed by `@olai/format`'s `page.ts` over the set the server already holds — the same `rowsOf`, `zoom`, `datedOn`, `agendaOf`, `backlinksOf`, `referrersTo` the browser used to call over a copy of its own, run on the side that has the set and re-sent when a published revision changes them by value. `web/src/client/document/documents.tsx` is what is left of the second collection, owning the documents member entirely because the rule about it (never a plain `.use()`, which would open a value stream per key) is enforceable only where the member is reached. **What that replaced was a second copy of the whole vault**: a tab subscribed to every outline's records and folded them with the same `derive`/`patch` the write gate validates against, so every page was a pure function over that copy and no navigation asked the server anything. Measured over a 40-outline × 200-row vault with the same driver on both sides (`packages/tests/wire.ts`'s `pages` session), the first frame went from **1,679 kB to 135 kB**, and a whole eight-step reading session — two outlines, a zoom, a document, a day, the agenda, the trash — from 1,679 kB to **641 kB**: navigation is no longer free, and it does not have to be, because the reader is never handed the corpus to make it so (§5a: round-tripping is acceptable, nothing is cached). What it costs when the wire drops is §5b's ruling, drawn as an overlay that freezes the app. **The client reads what it is sent and never writes to it — including now that it can EDIT.** A keystroke is a procedure call, and what comes back is the file on the next frame: there is no local model of the outline to keep in step, no optimistic row, and the only client-side state an edit involves is the DRAFT (`web/src/client/edit/`), which is the text in an open editor rather than a claim about the set. That is the same rule the chat composer follows, and it is what lets the paragraph below stay true. Committing is on blur / `Enter` / idle; a commit that would change nothing writes nothing; a commit that is REFUSED keeps the draft and shows the validator's own reason under the row, because a keystroke a person typed may not vanish into a rejected write. A NEW row is a draft too — `Enter` opens an editor where the row will go and the `add` lands when it has a title — so a blank record is never written. What a structural key costs is the caret: the row is redrawn where the file now says it is, which in a browser takes focus off it, so the editor follows its NODE across the frame and asks for the caret back (`edit/editing.tsx`). Which id an edit names is a rule: what a node SAYS names the node a row shows (so typing in a mirror edits its target), and where a row SITS names the row's own record (so moving a mirror moves the placement). A row's `•••` menu writes as well (`web/src/client/menu/`), and there is no draft in it: one op per click — any of the three marks, clearing a date, naming what this node points at or waits on, retiring a placement, trashing a subtree behind a confirm that names how many rows go with it — plus a plain-text copy of the subtree, which writes nothing, and *Ask agent*, which writes nothing either: it arms the composer with this row's node and opens the panel, and what happens to the node afterwards is whatever is typed next, through the same tools and the same gate. It is the established door for a row verb and deliberately the only one — a control in the gutter would cost title width on a phone (`touch.ts`), and a chord would cost an entry in a registry whose value is that it is short and collision-free (`keys.ts`). THREE of them cannot be a click, and they are one shape rather than three exceptions: a date, a `see` target and an `after` target are each a value somebody has to CHOOSE, so each opens a panel in place under the row rather than writing on the spot — the date picker (`web/src/client/date/`), reached from the menu entry and from the row's own date pill, whose pick is the same `date` edit the menu's `Clear date` sends — a native `<input type="date">`, whose value is the ten characters the record will hold, because a date is TEXT and this codebase does not parse one anywhere; and the edge panel (`web/src/client/edges/`), one panel for both fields because the ops layer plans them with one function, holding what the node says NOW with an `×` on each and the SERVER's own node search for what to add, so what it finds and what an agent's `search_nodes` finds cannot drift. A ZOOMED node reaches all three from controls of its own, because a heading has no `•••` to hang them off — which is also why the ⌘K palette's op rows stop exactly where a verb has a question to ask (`palette/ops.ts`): a palette drawn over the page has nothing to open. What each said is drawn beside the `•••` in the two moods every other write has, and what would take it back goes on the same ⌘Z stack a keystroke's does, so the chord means one thing whichever hand made the edit. What arrives on the wire is BORROWED: a row wrapper is minted fresh per frame but the records inside it are the served set's own objects, and Solid's `reconcile` mutates what it is given, transitively — so a page model reconciled into a store of its own rewrites the set in place, poisoning every other page and feeding the write back into the derivation that produced it (that was the day view, until it stack-overflowed on the second day opened). So there is no store in the client above the framework's: what a page draws is a memo, and identity across frames — the thing a store was reached for — is a keying question, answered by `<Key>` on `Row.key` and on a day entry's `file/id` — and, since juspay/kolu#2190, by the framework's own merge beneath them: a member DECLARES what identifies a row (`@olai/surface`'s `arrayKey` — the `page` stream by `key`, the `pins`, `pending` and `chat` cells by `id`, `path` and `name`), so a frame that merely repeats what a tab already holds notifies nobody at all, and a reorder MOVES the row objects a keyed view is following instead of rewriting every one of them. The client bundle is built by `Bun.build` via `@kolu/surface-app`'s helpers; the server is a Node `http` server with a `ws` upgrade. Started as `olai web <dir> [--port] [--host]` — a nix-built binary whose only job is serving; `just serve` and `nix run` wrap it — bound to loopback by default. The UI is an **app header** (wordmark, and when a trusted identity header is present who is looking; on desktop the connection, the one git pill, agent toggle, preferences; on a phone, identity and search) spanning every screen App draws and STICKING to the top of it — the document is what scrolls here, so a bar in flow took the connection dot, the commit pill and the agent toggle away from anyone reading past the fold, and it is the same fact that keeps the panels fixed at `top: var(--height-header)` (the drawer, its scrim, the chat dock and sheet) meeting the header's bottom edge rather than hanging 3rem below nothing — a **sidebar** of the directory (the agenda link — which carries what is owed as a mark, see below — the calendar, the file tree), PINNED under that bar on desktop by the same argument and with the same mechanism (`sticky` at the header's seam, exactly the strip below it tall, either face of it — open column or icon rail), which is also what gives the column a scroll region of its own so a directory taller than the screen scrolls inside it rather than lengthening the page — and one page in the main pane; mirrors render their target's subtree inline, marked. What a node cannot start until is derived from the edges and the marks together and answered in the MARK COLUMN (resolved 2026-08-11, human): a row that is waiting draws an hourglass where its box would be, toned with the mark it stands in for, and the row dims — because "has this started" and "can it start" are the same kind of question, asked of the same node, and a reader sorting rows is already looking there. The ordering graph both that and the acyclicity rule read is one graph in terms of NODES, mirrors resolved at both ends, so a deadlock closing through a placement is refused rather than drawn. There are seven routes, and the difference between them is what each is a property of: a FILE spells its own path and nothing else — `/Tasks.olai`, `/notes/README.md` — because the suffix already says which kind of page it opens and a prefix beside it would be that fact spelled twice, free to disagree with the name it carries (the prefixes `/o/` and `/doc/` were dropped on 2026-08-19, and a `#` after a document path is a heading in it); `/#<id>` names a node, and an id is all it may spell — ids are unique across the loaded set and survive renames and moves across files, so the permalink outlives every edit short of a delete, while a URL that also carried the outline could disagree with the file it named; `/d/<ISO-date>` names a day, which is not a thing on disk at all; `/today` names no day but the day it *is*, which is what an agent, a bookmark and a home screen can each keep; and `/agenda` names no day either and never will — it is those same dates read forward, so a horizon in the address would be a link that meant something else tomorrow; `/trash` spells nothing for the same reason — whether `_olai/Trash.olai` exists is the set's answer, and that file's own address opens the same view, because the trash is not a place you edit. A zoomed page is the node as heading, its note, its children as the same tree, above the *canonical* parent chain as breadcrumbs — derived, so the crumbs are the same however you arrived, and a mirror's id resolves through its chain to the one page its target has. Under all of it, the one place in this app a reference is read BACKWARDS: a `Referenced by …` section (`web/src/client/backlinks/`), shut by default, holding what SEES this node and what MENTIONS it by its `@id` — two rows of the same shape the forward relations draw, each entry opening the record that made the reference. It is a lookup rather than a walk (`@olai/format`'s `backlinksOf`, over two reverse indexes carried in the derivation and patched per changed file like the rest of it), so it costs a frame nothing and follows the disk the way every other page does — a note written in another outline adds a row to a section a reader already has open. A placement is not a reference and neither is an ordering edge, and a referrer in the trash is left out; the reasons are [format.md](format.md)'s References section, and `read_node` answers the identical reading as `referencedBy` so a person and an agent cannot be told different things about one id. Folds are stored by NODE ID under the file the node is defined in (2026-08-13, human — a reader with a real corpus was re-collapsing the same trees on every visit), so a fold survives a reload, a move, and zooming in and back out, and every mirror of a node is folded wherever that node appears — one node, one fold state. Nothing about it is committed and nothing crosses the wire. Ids are dropped as the entry is rewritten, and GONE MEANS GONE FROM THE SET rather than from the file the fold was filed under: `trash` is a move that keeps the id, so a node that has left one file is looked for in the others and re-filed under where it landed, and only an id no served file declares is forgotten — while a file that is broken or unserved keeps its folds rather than losing them to an absence. All of it is `format`'s date derivations — the one place both surfaces read from, so a dot and the day it opens cannot disagree, and since `perf-dates-index` three lookups into a day index the patcher maintains rather than three walks of the directory per call — and none of it writes about NODES: every cell is a link to `/d/<date>` — a day with something on it wears a dot, a day's NOTE a corner fold, today a ring, and the day being read is filled. A day with neither of the first two is quiet, not a write: the click never mints. Creating that day's note is the day page's **+ day note** (`md-editing`), shown on any day without a note, entries or not — minting at the path the vault's own convention names, the newest existing daily note's directory with its date segments re-spelled (`format`'s `dailyNotePathFor`), read on the SERVER against the same snapshot every placement is — landing in the new document's editor. A day is still a QUERY; what changed is only where the write is asked for. **The doctrine is knowingly amended in exactly one place, and only to ADD:** a document whose basename is exactly an ISO date (`2026-08-12.md`, wherever in the tree it sits — `2026-08-10-recap.md` deliberately not) is that day's NOTE, and it joins the query's answer rather than replacing it — drawn first on `/d/<date>` and `/today`, with the dated nodes below exactly as before, and marked in the month by a second and visibly different mark (a corner fold, against the node dot) so note-days and node-days are legible apart at a glance. Two documents claiming one date are both listed, in path order, because there is no conflict rule worth inventing over two files a person wrote. The derivation lives beside the other two in `format/src/dates.ts` for the reason they live beside each other: a calendar mark and the page it opens must not be two readings. Days remain queries, and a note is a document like any other now that documents are writable: its page edits (`md-editing`), and the day page's **+ day note** is how one is born.
- **The agenda is the same query, forward.** A day page answers *what is on*; the agenda answers *what is owed*, and it is the same dates read the other way — `/agenda`, a question asked of every dated node in the set, with nothing on disk that is the agenda (`format/src/agenda.ts`, ratified in [brainstorming/agenda.md](brainstorming/agenda.md)). **No new field, and no format change at all**: `date` says WHEN and a mark says whether it is work, so the two read together are the whole reading — `date` with no mark is an OCCURRENCE (a birthday, a delivery) that can never be late, and `date` with `todo` or `doing` is due work. A second `due` beside `date` would have been two dates answering one question. **`overdue` is the next `blocked`**: `overdue(n) ⇔ n carries todo or doing ∧ day(n.date) < today`, derived at view time, stored nowhere, spelled ONCE and read everywhere — the days above now on the page's spine and the tone a date badge takes are the same predicate, the way blockedness is one predicate read at both ends of its arrow. It is a SECOND fact about a node, never a replacement for its mark; `done` extinguishes it by construction; and `doing` is in (2026-08-12 the human considered the narrower todo-only reading and declined it — started-but-unfinished is the most honest answer to "should this have happened by now"). The one thing the set cannot supply is what day it IS, so `today` is an argument at every entry point and the clock stays the client's one reading of it (`web/src/client/today.tsx` is how it reaches a row). The reading is three stretches of ONE LINE: what has SLIPPED (oldest first, a day at a time — the stretch that IS the feature, since a slipped task is on a day nobody visits), TODAY (what today's day page computes, minus finished work) and what is AHEAD (the next days that HAVE something, bounded by a count of populated days rather than a window of dates — each day a link to its own page, where the note and the finished work the agenda leaves out are read). **It is DRAWN as one spine of time** (`agenda-spine`, ruled 2026-08-18, from a three-way design exploration): a 2px line down the gutter with NOW marked on it — drawn on a day nothing is due on, because now is a place on the line rather than a section that vanishes — each listed day a dot, what has gone above it and the future receding below in fading ink and fading rows. It replaced three flat boxes, whose three costs were the ruling: an item seventy-three days out shouted as loudly as one due on Monday, ISO dates demanded mental subtraction to feel any urgency, and the repeated chrome (a file heading and a crumb per day) outweighed the content about four to one. So days say FELT distance ("Mon, Aug 24", "in 6 days", "Yesterday"), the silences between listed days are named and take room that grows log-ish with the wait, the per-day file heading is gone, the ancestry is one muted line under each row, and a date pill survives only where it adds a fact the day heading cannot give — how late the work is, and the time on a datetime. That is the ONE PLACE this codebase counts days rather than comparing them (`format/src/calendar.ts`'s `daysBetween`, beside the weekday and the day-step it already held), and the counting stays below the client for the reason the rest of it does: the words on the page are the format's reading of the files, and a badge doing its own date arithmetic would be a second one. `done` never appears anywhere on it, put-away work is absent for the reason it is absent from a day (the same walk, one bullet up: putting something away is a reader saying they are done looking at it, so nothing in the Trash is owed), undated tasks are absent entirely — they have no *when*, and inventing one is what this format refuses to do — and an empty agenda says "Nothing is due." and offers nothing to press: pressing it could only mean scheduling a task, and the writing surface for tasks is the tree, where a row is a place a node actually lives. Rescheduling is `set_date`; there is no snooze. RECURRENCE was the one thing on that list that would be a real format change, and it has had its debate and landed: a `repeat` field, a closed four-shape grammar, and a completion that captures the next occurrence (the bullet below). Nothing about the agenda changed for it — the occurrence is a dated node, so it is owed, late or upcoming exactly as the one before it was. It is not `Now` either — Now is a person curating with mirrors, *chosen* work, and the agenda is derived, *dated* work; neither writes to the other. **And the directory says so before the page is opened**: the sidebar's Agenda entry wears the app's alarm — a filled chip counting what is late, on a washed and weighted row — when anything has slipped, the date badge's own quiet chip when work is merely on today, and nothing at all when neither; loud wins the row whole and prints the late count alone (one claim per readout), while the today count rides the entry's label and `data-today`. Overdue is the one answer no day page can give, and a page nobody opens cannot give it either. THE READING IS ONE: the page lists the rows and the entry counts them (`owedOf` over `agendaOf`, `format/src/agenda.ts`), so the number beside the word cannot disagree with the rows behind it. WHERE it is counted moved with `vault-in-browser`'s PR 4 — the entry's two numbers are a server answer now (the `owed` wire stream, `web/src/client/dates.ts`), counted at the day THIS reader is standing on, because the dates in the files are what a person wrote down and what is late is late where they are; the browser walks nothing for it. The page's own three stretches are still read in the tab, deliberately: `/agenda` is one of the seven routes, and that design's law forbids flipping routes one at a time, so every page reading moves in its PR 10 or none of them does. It moves for the same reason every other reading does: a revision the store publishes (tick a late task off and the alarm goes down with no reload) and the one clock rolling `today` over at local midnight, which re-asks because a new day is a new question. The mark is on both faces of the column — the open one and the icon rail, where three rem takes a dot instead of a numeral — and on the phone it is inside the same sheet.
- **One query language, ONE BOX — and the matcher is BELOW both of its scopes.** A person types into the FILTER over the page, which narrows what is on screen instead of listing hits beside it — an outline, a zoomed node, a day, the agenda or the trash, each pruned in the shape it draws, with a document the one page it has nothing to say about — and then WIDENS the same query to `/search?q=…`, which is that filter run over every file at once, as a page with an address (brainstorming/one-search-box.md, ruled 2026-08-21: the header's search box and the ⌘K palette's node hits are deleted, because two entry points at two scopes with two answer shapes could not list a tag written in three files). An agent's `search_nodes` and the app's PICKERS — the move-to panel, the edge panel, the `((` widget, the chat composer's `@` — are callers of one `Query.search` over one snapshot. What makes that one consistency rather than drift is where the matcher lives: `@olai/format`'s `filter.ts` says what a query MEANS — the case-folded substring over title/id/`#tag`/note, the operators (`is:`, `has:`, `date:`, the two stamps `created:` / `changed:`, `prop:`, and `-` to negate), the trash rule, and which field carried a hit — and every door is gated by that one function. It reads a CLOCK from nobody: `date:last-week` resolves against a day handed in and `changed:1h` against the whole instant that day text may carry, so the resolution stays a pure function two tests can pin a boundary on — and the day handed in is the SERVER's at every door now, which is the second half of what changed here. The browser used to RUN the matcher, over its own copy of the whole directory, because a filter over rows a tab already holds could not make a round trip per keystroke; that copy is what `vault-in-browser` is taking away, and `search-server-side` was its first step (brainstorming/vault-in-browser.md). So the filter and the composer's `@` list — the filter's shape with a shortlist on the end (docs/chat.md) — are questions too, behind a debounce and a rule that a stale answer never lands over a newer query. The matcher and the RANKING stay in `format` regardless (`ranked`, the done penalty and the order): what a query means and what order it answers in are one definition, and the day the browser holds a second one is the day `is:done` means two things. What the ops layer keeps is the SITUATING, the uncapped total behind a cap it applies itself, and carrying a REFUSAL back, since a known operator with a value it does not take is answered with the reason on every door rather than with an empty list. Recall by MEANING was built and then parked, because the implementation needed a model server on the reader's machine and olai requires no dependency outside Nix itself. [search.md](search.md) is the reader's account; the filter's design is [brainstorming/filter-in-place.md](brainstorming/filter-in-place.md), and the parked design is [brainstorming/hindsight.md](brainstorming/hindsight.md) rec. 1.
- **Agents** (`packages/chat`): chat is one ACP session (`@agentclientprotocol/sdk`) over a subprocess, and the server owns exactly one — olai is a single-user app, so there is no session per tab or per outline, and every browser watching sees the same transcript. The agent's cwd is the served directory, which is what makes its stored conversations findable: boot asks `session/list` for that directory, and `claude --resume` in a terminal reaches the same sessions. WHICH of them the panel comes up in is olai's own note rather than a guess (`chat-restore-wrong`, the human's bug): the session id is written down when the panel enters a conversation and read back at the next boot, so a restart replays THAT one. It used to adopt the most recently updated session in the directory, which is an answer to "what moved last" standing in for "which one is mine" — so a terminal `claude` in the same directory, a `/clear` sibling, or an adapter touching a timestamp for a reason of its own would take the panel over silently. Newest-in-directory is the FALLBACK now, for the case it is actually an answer to: the remembered conversation is gone, or this olai has never served this directory. The note is one small file per served directory under `$XDG_STATE_HOME` (`~/.local/state/olai/chat/`, `packages/chat/src/memory.ts`) — not under the served root, which is the outline set the store probes and a commit would commit, and not in the agent's store, which has no field for whose panel a session is. It holds an id, the model that conversation was running (below), and the path both belong to, and nothing else: olai still keeps no transcript store of its own. Failing to read or write it is a row in the transcript and never a failed boot — an unreadable note opens the newest conversation and says why, an unwritable one says this conversation will not come back. **The agent can ask a person a structured question**, because `initialize` advertises `elicitation.form` — without that capability the Claude Code adapter puts `AskUserQuestion` in `disallowedTools`, so an agent that wanted to check which of two things you meant had to guess or ask in prose and hope. Two methods reach a person and both are drawn as the same thing, a FORM IN THE TRANSCRIPT rather than a modal, so it is still there afterwards saying what was asked and what was chosen: `elicitation/create` in form mode (a JSON Schema of primitive-typed properties — the adapter renders its `AskUserQuestion` tool into one, a titled `oneOf` per single-select and a per-question free-text "Other" box beside it, and feeds the answers back as that tool's own `updatedInput`; MCP servers on the session reach the same method with schemas of their own), and `session/request_permission` (a list of named options for one tool call, which is a single-select with the options already spelled out). The projection of both payloads into that one form — and of the answers back, typed the way the schema asked — is `@olai/acp`'s, the package that owns the protocol's vocabulary; chat runs the subprocess and consumes the projection, translating that package's own refusal word into the domain's `UsageFailure` at the seam. A property whose type the panel has no control for makes the whole request UNDRAWABLE: it is declined and said out loud, because half a form is one somebody submits believing they answered all of it. A dismissal is a DECLINE on the wire — the agent is told a person would not say — and never a fabricated answer. Nothing times out; a pending question holds the ACP request open, which is exactly what a blocked turn is, and what the panel owes in return is that the block is impossible to miss (a count on the chat cell, drawn in the composer, the header and the permanent agent toggle). Every question is withdrawn when the conversation it belongs to ends — a new session, a load, a dead subprocess — so a live form is never a control that does nothing. **Permission requests are auto-approved for the tools olai handed the session** — its own mediated ops, kolu's terminals — and for nothing else, and that second half is the load-bearing one: the adapter maps plan mode's "Ready to code?" onto a permission request whose FIRST allow-flavoured option switches the session to `auto`, so a client answering every request with the first allow it found was silently taking that decision on somebody's behalf, every time. The rule is positive recognition, and a tool it cannot name is one a person is asked about. The name is read off the `tool_call` the adapter always emits before it asks — the request itself carries a display title rather than a name — which is one of the two agent-specific `_meta` readings the chat package makes. **The other is WHICH AGENT made a call**, and it is there because an agent can spawn agents and the protocol cannot say so: a subagent's tool calls arrive on the one feed every other frame arrives on, in the same shape, so a turn that sent three agents out reached the panel as one agent doing everything and nothing said a subagent had been started at all. The adapter knows — it keys a registry by the spawned task's own agent id and stamps the `Agent` call that spawned it onto every frame that comes out of one — so `parentToolUseIn` reads that stamp and the transcript stores it as the spawning call's ROW, in its own key shape, sticky like every other field on a tool frame (the adapter has a completion carrying only a status, and a row that read that silence as "no agent now" would step out of its lane at the moment the call finished). Both readings fail in the same safe direction: a frame that says nothing is the main agent's own, so an agent that is not that adapter has no subagents here and the transcript looks exactly as it did. What the panel does with it is the panel's — a row that names a parent is drawn indented behind a rail under that frame, and whether the lane NAMES itself depends on the row above it, which is a fact about a rendered list and belongs to the list (`web/src/client/chat/lanes.ts`) rather than to the transcript. **The other end of that is which call STARTED an agent** (`chat-subagent-live-face`, the human's bug, filed off a screenshot of a fan-out): the parent stamp is answered by frames a subagent PRODUCED, so it says nothing until it has produced one — and a spawned agent's first act is to read its instructions, which produces none, so the whole of the stretch a person watches a fan-out through had a pending row with an ordinary title on it and nothing saying an agent had been sent anywhere. The adapter says so at the spawn: it stamps `subagent: true` beside the tool name on every frame it builds for an `Agent`/`Task` call, and the kind of agent rides the call's own arguments (`subagent_type`), read THROUGH that flag as a gate (`spawnedIn`) and stored sticky a level down. Neither of the two payload-shaped fields is trusted on its own, and the second is not read at all: `subagent_type` is a name one tool gives one of its arguments on a session whose tools are not a closed set, and `toolResponse.subagentType` — which the adapter really does send for an Agent call's beats — sits in a `_meta` corner the adapter also uses to forward **any tool's own response verbatim** (`onPostToolUseHook`), so a server answering with that key was one string away from being drawn as somebody's spawned agent. So the panel draws the face from the spawn itself: who was sent, on the row that sent them, and a rail dropping out of it that says *working…* — one word, because the adapter announces every call `pending` and dispatches the subagent immediately, so splitting *starting…* off it reported olai's own ignorance and went on contradicting the subagent's calls drawn in the lane directly below until a heartbeat arrived. It comes off the moment the call stops — and the moment the CONVERSATION does, which is the half a row cannot answer: a status is sticky and a dead agent's rows are deliberately left on screen, so a subprocess that died between announcing an `Agent` call and reporting on it would otherwise leave a rail pulsing under a process that no longer exists. What the panel deliberately does NOT draw is the subagent's own prose: the adapter strips a spawned agent's text and thinking unless the client declares `subagent-transcript` in its `initialize` capabilities, and olai does not — so a subagent's narration cannot reach this feed, and cannot land in the main agent's voice either, which is the failure that would otherwise be reachable. **A QUESTION carries the same attribution**, and it is the row where being anonymous costs the most: a subagent's permission form drawn in the main column says the agent you are talking to is the one asking, at the moment somebody is about to press a button on that basis — and, being in no lane, it ENDS the stretch, so the lane re-opens and names itself again underneath the form and one agent's run reads as two. Both requests are answered by one thing (`calls.ts`) under one rule — **a frame refines, never retracts** — because both are about a CALL, and a call is what frames say things about. An `elicitation/create` carries no attribution at all: it names the tool call it was asked from, and the adapter guarantees that call was announced first (`ensureToolCallEmitted`), so the answer is a lookup. A `session/request_permission` does carry one, on the tool call it is about, in the shape every frame carries it — so it is folded in like a frame rather than read as a second kind of source, and precedence falls out of the order (the last frame in wins) instead of being a rule somebody has to apply the right way round. What the request said then stays known, for the next question about the same call. `@olai/acp` carries the call id onto the form it projects and stops there: which agent a call belongs to is an agent-specific `_meta` reading, and that package speaks ACP and nothing else. The panel then draws a form in its agent's lane like any other row — and names that lane wherever it sits, which is the one exception to *once per stretch* and is a drawing decision made for a drawing reason: a blocked question is pointed at from the composer and the header, so a reader arrives at it with no row above to have read. The session is handed olai's own MCP server, over an HTTP route on the same listener, because the tools it exposes are this process's ops over this process's store and a stdio server would mean a second olai with a second store. It is handed a SECOND one when this host is running [kolu](https://kolu.dev): `kolu mcp` over stdio, so the agent you are talking to about your outlines can also see the terminals your coding agents are running in. That is automatic and has no knob, and the two ways of being wrong do not cost the same: missing a kolu that is there costs a session some tools, while attaching one that is NOT there hands the agent a server whose every tool fails — it will try them, having been told they were available. So the bar is an answered read rather than a spawn. What is detected is the padi DAEMON rather than kolu's web server, which may be on another machine reaching this host as a remote. Detection is a PROBE and runs per conversation rather than once at boot: a `kolu` on PATH is not necessarily the host's kolu (a padi-spawned terminal prepends its own bundled copy, and one of those was an older build reporting the same version while missing most of the verbs), so the executable is started, handshaken with, and asked to read a resource only a live daemon can answer — and the absolute path that answered is the one the session is given, so the agent cannot resolve the word against a different PATH and spawn a different build. Socket discovery is not reimplemented: `PADI_SOCKET` is forwarded when olai was launched inside a kolu terminal, and kolu finds its own default when it was not (a host running two padis says so, and is left alone). Whole-file writes THROUGH OLAI are rejected by design: `fs` capabilities are false in both directions, so the only channel this process gives an agent to the disk is the ops layer. That is a statement about olai's channel and never was one about the agent, which is a coding assistant with its own tools and its own authority over the directory it was started in — and the honest thing to do about the difference is to SHOW it rather than to imply it away (`docs/chat.md` says so where an operator reads). **What a call CHANGED is drawn in the transcript, structured, in two vocabularies — and which one is decided by the FILE rather than by the tool.** An agent editing a `.md` or a source file is using its own tools, and ACP reports it as a `diff` content block: a path and two texts. The panel draws that as a diff, trimmed to a few lines and expanded in place on a click (Claude Code CLI's idiom), with unchanged stretches collapsed so the first rows are the change rather than the top of a document. It used to be flattened into the progress line as `— <path>` on the argument that a unified diff in a folded frame is a page of text and that the outline is where an olai edit shows up anyway; the second half is what inverted, since an edit like that shows up in NO outline and the answer to "what changed" was a terminal. An OUTLINE gets the opposite treatment whichever door the write came in by, for the commit panel's own reason — a `.olai` diff is one enormous line per node — so it is drawn as the node-level story in the same words the Commit panel uses (*marked done*, *note rewritten*, *moved*), plus the rollup's nudge for a write that went through the ops layer. A `.olai` the agent edited with its own tools is not the exception that proves the rule: its two texts are PARSED and compared as records (`web/src/client/chat/outline.ts`, the same `changesOf`), and a side that will not parse says so rather than falling back to lines — which is how hand-editing an outline goes wrong, and a text diff is not a better answer to it. That parity is structural rather than remembered: the classification is `@olai/format`'s one `Sort`, computed by the same `changesOf` a pending row is computed by (`ops`' `sorted.ts`, off the two readings a write is already made of) and worded by one table both panels read (`web/src/client/changes.ts`). The wire carries both shapes as DATA — `FileDiff` is path plus old and new text, declared by `@olai/acp` (whose `diffsOf` reads the protocol's diff blocks) and re-exported through the surface, and the line diff is derived in the browser like every other view-time derivation — because a change flattened into prose is a change no panel can draw and no browser should re-parse. WHICH MODEL is two facts, not one: the session's config option is what was picked, and the CLI's own `init` message — forwarded because `session/new` asked for it — is what is running. A `/model` is handled inside the wrapped CLI, so the picker never hears about it; whichever source moved last is what the header names, each debounced against its own previous value, and the first live id is a baseline rather than a change. That forwarding is asked for in the `_meta` of the call that MAKES the session, which is `session/load` as often as `session/new` — asked only at `new`, a restored conversation never heard the CLI at all, so a `/model` made in one moved nothing. **A model somebody switched to SURVIVES A RESTART** (`chat-model-reverts-on-restart`, the human's bug): the adapter resolves a resumed session's model as `ANTHROPIC_MODEL`, then `settings.json`, then the transcript — and re-asserts the first two over the third on resume, which is why a container pinning `"model": "sonnet"` took every `/model` back at each deploy, silently, with the panel truthfully naming what it was told. So the movement is written down beside the conversation id (`memory.ts`) and set back after `session/load`, through the picker's own config option (`session/set_config_option`), only when the restored session came up on a different model — judged in NAMES rather than strings, since a picker value (`fable`) and a live id (`claude-fable-5`) are the same model. The request is made in the picker's OWN words (`pickerValueFor`): what a `/model` reaches olai as is that live id, a config option takes a value the picker offers, and an agent that reads its own list rather than resolving aliases would refuse — which would leave the conversation on the pin. Only a movement is remembered, never the first value a source reports for a session: that one is what the agent decided, so a conversation nobody switched comes back on the agent's own answer and a fresh one still starts on the machine's default. The cost, written down in `docs/chat.md` because a person meets it: a `/model` made in a terminal `claude --resume` while olai was not running is indistinguishable on the wire from the pin this exists to overrule, and loses to olai's note. A refusal is a transcript row, not a failed boot, and the memory is left untouched so the next boot tries again. A new conversation EMPTIES the panel: the agent's context is gone, so nothing above could be followed up, and a transcript you cannot refer to is history kept for its own sake. **A message can be about a NODE, and what that concretely is is an id** (`chat-node-context`). A row's `•••` offers *Ask agent*, which arms the composer with the node that row SHOWS — a mirror is a placement and the thing to ask about is what it is a placement of, which is the rule a fold and a mark verb already follow. What the browser sends is the id and only the id: a title or a `file:line` from a tab is that tab's account of a frame that is already old, so the SERVER resolves it, over the same reading a keystroke's write is judged against (`server/src/context.ts`), and hands the chat package the node as it IS — id, title, `file:line`, and the canonical ancestor titles that make a bare "order" mean something. That reaches the agent as one line under what was typed, the id in backticks, exactly where an attachment's `Attached file:` line goes and by the same argument: the agent is handed a HANDLE and reads the thing itself, because a subtree pasted into a prompt is a copy that stops being true the moment anything writes, and `read_node` is already in the closed table. An armed id the set no longer declares REFUSES the send in the ops layer's own `notFound` words, rather than sending a question whose subject is missing; a mirror id refuses the same way an op on one does. The nodes ride the user's transcript row as well as the prompt, so what a message was about survives a reload and reaches the other tab. **The other direction is the same ids, read backwards**: a node named in the panel is pressable and shows that node on the page (`web/src/client/focus.ts` — the row is scrolled to and toned with the same accent the row holding the caret takes, and a node that is not drawn on this page goes to its own address instead). Three things in a transcript are ids and none of them is an invented syntax: the chips on a message, the node an olai write was about (`Applied.id`, which the reply has always carried and which now crosses the wire on `Wrote`), and an id the agent wrote in BACKTICKS — which is how every one of these tools spells one in its own description, so it is what an agent already emits. A code span becomes a reference exactly when the set declares what it says (`web/src/client/chat/refs.ts`), which is what makes a false positive unrepresentable: `notes.md` is looked up, is not a node, and stays a code span. WHO ANSWERS is the server, one batch per message (`nodes.named`, `web/src/client/chat/declared.ts`): the browser used to look it up in its own copy of the whole directory, and that copy is what `vault-in-browser` is taking away — so a span is plain until the answer lands, never marked on a guess, and a message's marks are what the set said when it was drawn rather than a standing view of it. What the span is MARKED with is the id the format RESOLVED — `nodeNamed`, the rule a `see` link and the chip already use — because a row carries the node it SHOWS: a placement id (which an agent writes, since `read_node` answers `mirrors` with them) marked as itself would name no row on the page and every press of it would leave for a node that is right there. The marking is a DOM pass over one message rather than a step in the markdown pipeline, because that pipeline is pure and cached by source text and this answer depends on the SET; the press is one delegated listener on the transcript pane, which is the arrangement a relative link between two documents already has on the main pane. A PICTURE can be pasted, dropped or picked into the composer, and what the agent gets is a PATH, as text: the bytes are chunked over `chat.attach` into a tmp directory of that conversation's own — deliberately NOT under the served root, so a screenshot stays out of the store's probe and out of anything the commit path would commit — and the prompt names the file, which Claude Code reads itself. So no base64 rides the prompt into the session the agent persists, and nothing here depends on the session's `promptCapabilities.image`; moving to ACP's `image` content block later is a change to one function. The directory goes when the conversation is left and when the server stops. A path that arrives over the wire is re-resolved against that directory, through symlinks, on both sides of the comparison — a chunk's `appendTo` is a continuation token that happens to be readable, never a capability. What the transcript carries is the file NAMES: the tab that pasted has the Blob and draws a thumbnail, every other tab draws the name, and `/media/*` cannot help either of them because it is guarded to the served root. **A message sent while a turn is running STEERS that turn, and olai holds nothing.** It went out refused, then queued — held in an array here until the turn ended, and dropped by the next cancel, which destroyed words with no copy anywhere (the transcript is not persisted; the agent's session is the persistence, and a queued message had never reached it). Now `send` puts every prompt on the wire immediately and the AGENT decides the lane: idle takes a `session/prompt`, and a turn in flight takes `_session/steering`, the extension the pinned adapter delivers at `now` priority, so the message pre-empts the current generation rather than queueing behind it (a concurrent `session/prompt` would queue — verified against the adapter, which answers a mid-turn steer `injected` and changes course inside the same prompt). Whether the agent CAN steer is never predicted from the advertisement `initialize` carries: the request is what proves it, and an agent without the method refuses it in its own words like any other failure. Two things fall out. Cancel means stop the agent and nothing else, because everything typed was already delivered. And a delivery that did not land marks its own `user` row — with WHICH of two things happened, because they are not the same thing and only one of them may be offered a button (`unsent-discriminate`). A `refused` row is a certainty: something answered no while the message had taken no effect (a method the agent does not have, a session it does not know, a process that was not there, a turn its own sender had stopped), so the exact prompt is kept beside the row for `chat.resend`, which only a person's click runs. An `unanswered` row is not: the steer went out and nothing came back before the deadline, or the connection died with it in flight, and an agent that took a message and then went quiet is indistinguishable from one that never took it — so the row says exactly that, keeps no prompt, and offers nothing to press, because a retry there is a duplicate offered to somebody with no way to tell. The reading is made where it is a FACT rather than a guess: `AgentGone` carries `Gone`, decided at the wire off the SDK's own shapes — an error RESPONSE is its `RequestError` and everything else it rejects with (a closed connection, an interrupted deadline) is silence — so nothing downstream infers a certainty from a sentence. `Gone` is THREE values where the row is two, because a caller has two questions: *may I offer this again* is anything but `unanswered`, and *is the agent still there* is `refused` — the agent answered, so it exists — as against `unreachable`, which is this end never reaching the wire at all (no process, a spawn that failed, no session open). Those last two shared a word until a second ACP implementation made the difference matter: a `session/prompt` can be answered with a JSON-RPC error rather than a stop reason, and read as the agent having gone it left a live agent's panel saying `not running`, in a conversation it was still in, until some later turn happened to succeed. A turn the agent REFUSED now ends the turn — the reason in the conversation, the message marked undelivered like any other that did not land, the panel back to idle — and splitting the value rather than adding a second field is what keeps "the agent answered, and it is not there" unspellable. The same reading covers the two OTHER places a conversation is opened: `session/new` and `session/load` can be refused by a running agent, which used to report a dead one, and the panel now has a third body for it (`web/src/client/chat/face.ts`) — the agent's own words where the conversation would be, the header still naming the model, and a `reopen` that asks for the SAME attempt again, kept beside the reason because a boot picks its own conversation. Entering one is recorded AFTER the agent agrees: `load` wrote the session id and the restart note before sending the request, so a refusal left the server pointing at a conversation the agent had just rejected — every later verb aimed at it, the next boot asking for it again, and the retry short-circuiting on a session it only believed in. Recording it late leaves its own window — a load on the wire with the server in no conversation — so the two verbs that OPEN one hold the boot's own permit for the whole of it: anything that booted in that window found nothing open and started a second one against the first, which with the composer never disabled is a person's next keystroke rather than a race. A concurrent verb waits, because the conversation its message belongs in is the one being opened. And a refusal does not outlive the agent it was about: the open verbs and the exit event drop it through one door, with the browser stating the same precedence a second time for the path that sets `gone` with no event behind it. The same reading covers a turn that never started, which used to mark nothing at all: a `prompt` that failed with the agent having said NOTHING is a delivery that failed too, and the panel's own count of what the agent has said is what separates that from a turn that was worked on and then died. A silence also lands in the transcript as a notice, since it is the one of the two nobody will act on and the banner it would otherwise live on is cleared by the next turn. **A CANCEL is judged by the turn, not by the write.** It is a notification — written and never answered — and a pipe does not tell its writer that the reader has gone, so the write succeeding is evidence of nothing and every way of failing looked like success: the button pressed, the turn streaming on, nothing said. The write's own failure refuses like any other verb, and the panel then watches the two facts that separate a slow agent from a deaf one — is the same turn still running, and has the agent said anything since — so one still streaming tool progress is left alone and one that has gone quiet with a cancel outstanding is reported as `trouble`, cleared by the turn ending.
- **The same tools are also an HTTP client anybody can point at the running server** (`POST /mcp`, `packages/server/src/mcp/`). A coding agent in a terminal is not olai's subprocess, so it gets what nearly every MCP client expects: a URL, and JSON-RPC over HTTP. It is the SAME face the panel's agent talks to — `@kolu/surface-mcp` over olai's surface, with the ops table riding as tools and the outlines, documents, errors, git state and what is WAITING to be committed readable (and subscribable) as resources — differing only in who holds the connection. That is the SAME conclusion as the bullet above out of the same argument — who owns the store. The panel's agent is a child of the server; a terminal agent is not, but it still talks to THIS process, because a second olai on the same directory is a second store and the thing this design retired. Requests from loopback skip the bearer; off-loopback the token the session was handed is still required. `--commit` is the serving process's setting, `manual` included and by default, which is the whole of `mcp-commit-manual`: an agent accumulates ops the way a person does, so its writes land and wait and the `commit` tool is what asks — and `surface://cells/pending` is how it knows there is anything to ask about, since an agent that had to shell out to `git status` for that would be reaching past the one surface it is given. Under the per-write behaviour this replaced, one orchestration beat put four commits into a human's log inside fifteen seconds.
- **And one HTTP door that is not a tool table at all** (`POST /capture`, `packages/server/src/capture.ts`). A thought arriving while you are somewhere else — a phone, a terminal, a mail client on another machine — should cost five seconds, and every client after this door is somebody else's few lines: a Raycast script that asks Mail.app what is selected, an Apple Shortcut on the share sheet, a `curl`. So it is ONE VERB with no id, no file and no target: a title, the text that becomes the note, the URL that goes under it as a link, and the `props` a caller already knows (`from`, `message-id`, so de-duplicating a captured mail is one `prop:` query). WHERE it lands is not a parameter and never will be in this shape — it is the top level of the directory's inbox, and where a capture BELONGS is a decision made in the app afterwards, which is what an inbox is. It is the SAME write as everything else: `@olai/format`'s `captureInto` (`inbox.ts`, beside the count the sidebar's door wears) resolves the inbox convention against the reading the write is judged on and hands back one ops request — the identical function the palette's `⌘K` `+` resolves through, which is why it lives in the format rather than in whichever face needed it first: "which outline is the inbox and is there one yet" spelled twice is two answers about one directory. AUTH IS THE TAILSCALE IDENTITY HEADER AND NOTHING ELSE (`Tailscale-User-Login`, required; human, 2026-08-21): `tailscale serve` injects it, the transport is tailnet-gated, and so there is no token to mint and no secret in any client — which is the whole reason a share sheet can be five lines. It buys two things beyond the refusal. It is the ATTRIBUTION, written onto the node as a `captured-by` property (a fact in the file, queryable beside whatever else the client sent, and refused if a client tries to send it itself) — which is a different question from the `X-Olai-Writer: capture` trailer beside it, because that one records a DOOR. It is NOT the CSRF gate, and saying it was is the one thing review had to send this door back for: `tailscale serve` STRIPS a client’s `Tailscale-*` headers and injects its own, so behind the deployment the docs recommend a page on another origin does not need to name the header — the proxy names it, and a `POST` with a safelisted `text/plain` body is CORS-SIMPLE, so there is no preflight for the missing `Access-Control-Allow-*` to fail and CORS hides only the response. The gate is the CONTENT TYPE: `application/json` is required and checked before the body is read, which is not safelisted, so a cross-origin `fetch` must preflight and the preflight is refused — with `Sec-Fetch-Site` (a header no page can forge, and one a script never sends, so its absence may not refuse) turning away a browser that owns up to another site. What it does NOT buy is said out loud where an operator reads it (docs/running.md): the header is a claim the TRANSPORT makes, so anything that can reach the port can make it — the same bargain the unauthenticated surface already takes, and why the ruling pairs "no token" with "no public exposure". A capture arrives DATED, so it is on the day's journal page as well as in the inbox, which is the half a line sent while nobody was looking actually needs; a date with no mark is an occurrence, on the day and never overdue. That is the one thing that differs from `⌘K` `+`, and it is a difference between two GESTURES rather than between two faces — both are an ops `add` and the gate judges them identically. FILES ARE NOT IN IT (`capture-files`, split out so v1 ships text-only): a photo or a PDF needs a binary write-into-vault path this codebase does not have, and the endpoint change would be the small half.
- **The adapter is pinned, and it is the default on every launch path.** `nix/acp-agent.nix` builds the Claude Code ACP adapter from a committed npm lockfile; the packaged binary's wrapper bakes it in with `--set-default`, and the justfile recipes that run the tree directly (`just serve`, `just run`) resolve the same derivation on demand through `scripts/acp-agent.sh`. So no documented way of starting olai lands without an agent, and a person never has to learn that the variable exists. The `nix` CI lane asserts it: the wrapper must carry the assignment and the path it names must be executable, so dropping the `--set-default` fails a check rather than a browser.
- **`OLAI_ACP_AGENT` is the override, and empty is the off switch.** Point it at another ACP agent and that is what gets spawned — it is how the e2e suite points at a scripted one. Set it to the EMPTY string and there is deliberately no agent; that works through the packaged binary too, because `makeWrapper --set-default` emits `${VAR-default}`, which substitutes only when the variable is unset. (The one-dash form is asserted in the same CI lane: `:-` would swallow the off switch.)
- **With no agent, the panel says so.** Serving a directory has never depended on an agent being installed, and it still does not — but that principle is "the server is fine without one", not "hide the feature". The drawer draws, and its body names the variable and how to fix it. A capability that is silently absent cannot be told apart from one that is broken, or from one the reader has not found yet.
- **Logging is Effect's, and it is quiet by default** (`packages/log`). Every package says what it is doing with `Effect.logDebug` / `logInfo` / `logWarning` / `logError` — there is no `log` callback threaded through a constructor, which is what there used to be for the two packages a person actually hears from. **Two faces, one decision in the sink:** on a TTY the human gets Effect's pretty console logger (local time, coloured level, message first); when piped, under systemd, or in tests the face is [logfmt](https://brandur.org/logfmt) — one line per event, `key=value`, byte-identical to Effect's `formatLogFmt`, so the message is a short stable sentence and every value that varies is an ANNOTATION (`url=`, `root=`, `claimed=`, `agent=`) that can be grepped by field rather than matched out of a sentence. The e2e suite reads the bound address that way, which is also why pretty may only exist where no machine reads. **`OLAI_LOG=logfmt|pretty` forces either face**; harnesses that parse a line pin `logfmt`. `NO_COLOR` turns the pretty face's ANSI off. Annotations set with `Effect.annotateLogsScoped` are inherited by every fiber forked under that scope, so the store's own probe warning says which directory it was probing without the store ever learning what a served directory is; `Effect.withLogSpan` puts `serve=…ms` on every line, so a boot is timed and a later line says how long the server has been up. **The verbosity switch is Effect's CLI `--log-level`**, already parsed and already in `--help`: `Info` is the default, so the loudest thing in the program (a relayed agent stderr chunk, at `debug`) is off until asked for. A second spelling of that — a `--verbose` of ours, an env var — would be a second answer to one question, so there is not one. The one thing Effect cannot do by itself is log from a Node callback, where there is no fiber and the operator's chosen level would silently not apply: `@olai/log`'s `emitter` captures the fiber's services once and runs every later line under them.
- **`OLAI_ALLOWED_ORIGINS` is the CSWSH escape hatch**, comma-separated, empty by default (`packages/server/src/allowedOrigins.ts`, its own file for the same reason `OLAI_DIST_DIR` has one). Loopback and same-origin is the common case; the extra entries are for a front end whose browser origin is not the `Host` it forwards — a reverse proxy, or `tailscale serve`. The gate runs on the raw socket BEFORE the upgrade, because after it the browser has a connection to argue about, and the surface is unauthenticated: the origin is the only thing between a page somebody else served and every outline in the directory.
- **Who is looking is a request, not a cell.** A reverse proxy can inject a login (and optionally an email) on each HTTP request. olai trusts one configurable pair of header names (`OLAI_IDENTITY_LOGIN_HEADER` / `OLAI_IDENTITY_EMAIL_HEADER`; default `tailscale serve`'s `Tailscale-User-Login` for both — the same pair covers Caddy+OAuth, Authelia, and Pomerium). The PERSON is `@olai/identity` (`identityOf` the one reading) — a leaf, no HTTP, so a later `POST /capture` does not import the composition root. `GET /olai/who` is `@olai/server`'s door over that function. Absent (direct access, a local serve) is a state: the header draws anonymous, top right, nothing is invented. It is not a surface member because a cell is one value for the process and this value is one value for the request. The websocket cannot see it today: kolu's `serveSurfaceApp` owns the upgrade and does not hand request headers to the app. **Trust:** the names are only meaningful when the proxy is the only way in (olai bound to loopback or the tailnet) and strips client-supplied copies. Documented beside the config in [running.md](running.md).
- **What a reader KEEPS is in the directory too, and it is nodes.** The sidebar's pinned shelf is `Pins.olai` — one ordinary node per pin, whose title is an ADDRESS this app would spell (`/#<id>`, `/<path>`, `/agenda?q=…`; [format.md](format.md#pins)) — so it is read off the same snapshot every page is drawn from, committed with everything else, and reachable by an agent through the tools that already exist: `add_node` pins, `move_node` reorders, `trash_node` unpins. WHO reads it off that snapshot is the SERVER since `vault-in-browser`'s PR 5: the shelf a browser draws — the file's rows, with every pinned node's live title on them — is one cell recomputed per published revision and sent when it changed (`@olai/format`'s `shelfOf`, the surface's `pins`), because resolving a shelf means reading a whole vault and the browser is giving that up (brainstorming/vault-in-browser.md). What the browser still reads is the TITLE it was handed: which page an address opens is this app's own bijection, at view time, which is the seam [format.md](format.md#pins) rules. That is the deliberate line between it and a FOLD, which is browser-local and written nowhere: a fold is what one reader is looking at right now, and a shelf is what the directory is FOR. No field was added for it and no placement is used for it, because a pin says *go there* where a mirror says *draw it here too* — and half the things worth pinning are not nodes at all.
- **Git is the only history**: no sync protocol, no CRDT. It is one job and it is worth naming, because everything below follows from it — an AUDIT TRAIL OF WHAT THE TOOL WROTE. Chat auto-approves its ops and there is no web editor yet, so every write olai makes is one nobody typed; git is how you see what it did. Not for history (the notes carry their own dates), not for sync (a push shares what was recorded; nothing here merges, pulls or resolves), not for undo. **A commit is something somebody asks for** (`--commit=off | manual | auto`, `manual` by default; `--no-commit` still means `off`), and `olai web` takes it, and every MCP consumer is a client of that one process, and a flag that meant different things on each would be exactly the divergence HACKING.md forbids. Writes land on disk and wait; a Commit button in the header and a `commit` MCP tool are two callers of one `Ops.commit`. `auto` is the old per-write behaviour, for a headless server with no browser to press anything. The control that asks is **always on screen** — a clean tree that has committed, one olai has never committed in, one with edits waiting, and a repository that is busy. That is the audit trail's own argument turned on itself: "there is nothing recording this directory" is the most important thing the feature can report, and a pill that disappeared is exactly how nobody would find that out (the connection dot's rule, for the same reason). Beside what is waiting it carries the LAST COMMIT olai made — `git log -1` through the audit filter, never the repository's HEAD — because what is pending says nothing about whether anything was ever recorded, and `null` there means "never", which an empty pending list cannot say. **What is waiting is DERIVED FROM GIT and stored nowhere** — the same discipline as node status: `git status --porcelain` names every dirty file in the REPOSITORY, `git show HEAD:<file>` is the committed side of each served outline, the store's own last-good parse is the working side, and comparing two parsed sets is a pure function beside the format (`format/src/changes.ts`) with no git in it. So a clean directory costs one `git status` and no parsing, an edit made in vim is in the panel like any other, and a commit made in a terminal takes itself out of it. **Never a text diff**: a `.olai` diff is one enormous line per node, so the unit is a NODE and what changed about it — *marked done*, *note rewritten*, *trashed* — classified once into one `Sort` the panel and the commit body each have their own words for. WHO wrote it cannot come from git, so it is a per-writer counter the ops layer keeps in memory and clears on commit, explicitly allowed to be empty after a restart and never a substitute for the derived truth; the permanent record is an `X-Olai-Writer: chat-agent | mcp | web | capture` trailer, without which an agent's commits are indistinguishable from a person's — and the fourth of those is the door rather than a person, a line POSTed at `/capture` from a share sheet while nobody was watching (WHO sent that one is a different question, answered on the node itself as a `captured-by` property, because git records only the repository's own user).| mcp | web` trailer, without which an agent's commits are indistinguishable from a person's. Messages are prefixed `olai`, so `git log --grep '^olai'` is the audit view and `--invert-grep` gives back real history; a composed one names the biggest change by a fixed order, and the per-op words stay the racket reference's — `capture:` / `done:` / `doing:` / `move:` / `trash:` / `create:` / `see:` — with `date:` corrected off `move:`, which beside a real reparenting op read as a structural change that never happened. Committing checks that the repository is FREE first (merge, rebase, cherry-pick, detached HEAD): nothing used to, which is how an agent marking a node done mid-conflict could swallow a resolution, and that hole is what decided manual over automatic. A git failure never fails a write: the bytes are on disk and the browser has already seen them, so a refusal is an answer (`Failed`, with git's own words) rather than a failed op. **The scope is the WHOLE REPOSITORY, in two kinds of row** (`commit-whole-repo`, the human's bug: edit a `.md` by hand and the git part of the UI showed nothing pending). A dirty outline olai serves gets the node-level changes above; every other dirty file — a document, a source file, an outline outside the served root, anything untracked `.gitignore` does not cover — gets a path and the porcelain's own status letter, because the only richer thing available is the text diff this feature has never shown. What a commit NAMES is a SELECTION and never git's index: exactly the paths asked for (the panel's checkboxes, all ticked by default; the tool's optional `paths`), on both `add` and `commit`, so hand-staged work is undisturbed and what is left out stays waiting for its own commit and its own message. **And it PUSHES**, which was the last reason to leave olai for a terminal: one verb, the current branch to the upstream it already tracks, no remote to pick and no refspec, with git's refusal — authentication, a non-fast-forward — surfaced verbatim like a refused commit. How far ahead of that upstream the branch is comes off the `--branch` header the status call already prints, so "what is not recorded" and "what is not shared" cost one subprocess between them, and both are drawn on the one pill. Resolving a divergence stays in the CLI: no pull, no fetch, no branch UI. Design and the decisions behind it: [brainstorming/git-commits.md](brainstorming/git-commits.md).
- **And a reader is TOLD, which is the half that was missing** (`git-invisible`, filed by the human against his own vault): `committed: false` was four different pieces of news wearing one word — the opt-out, no work tree, no git on the service's PATH, a write that is simply waiting — and the actual reason went only to the server log, where somebody reading a browser never sees it. So every write's reply carries `why` when it was not committed, which is what the agent reads and what the transcript draws beside the call; under the default mode that sentence says the write is WAITING, because it is, and a reader who saw the git-error wording there would go hunting for a repository that is not broken. Beside it the header carries the Commit pill, whose faces cover what the `git` cell says — `off`, `repo`, `none`, `error` with git's own words — and the two classifications that keep it honest are exit codes and git's own sentences rather than guesses: a directory git will not answer about is an ERROR unless git said its own "not a git repository", because a broken git reported as "you have no repository" is the collapse that entry exists to have stopped. The `git` cell and the `pending` one are **one derivation published twice**, recomputed together by the server on the same three clocks (every revision, every landed commit, a slow sweep because nothing watches `.git`) — two probes would be two answers, and a page reading "Not a Git repo" beside a panel offering to commit four changes is the incoherence HACKING.md's consistency rule forecloses. They are now read into **one control** as well (`one-git-indicator`): the readout that used to draw the first of them beside the pill drawing the second is retired, because two chips answering one question is a redundancy a reader notices before anything else. Both values are still published, and the MCP face still reads the `git` cell as its own resource — what changed is a face, not a fact. The one thing remembered rather than derived is a commit that REFUSED, and it has to be: `rev-parse` answers happily in a repository with no `user.email`, so a state read from the directory alone would look healthy while every commit failed. None of it may make a write fail, wait or retry.

## Split panes

A pane is a route: the same page (an outline, a zoom, a day, the agenda, the trash, a document), the same filter, the same chrome. The workspace is a **layout tree** — a leaf (one route) or a split (an axis and children with fractions; a `0` is collapsed). Today's product writes only a lone leaf or a one-level **row**. That row still serializes as the flat `/s/<encoded-route>/…` list (`?w=` fractions, `?f=` focus) so every existing link stays. Axis and nesting have room in the codec (`?a=`, `?t=`) and are not written yet. Reload restores the layout; Back walks it; sharing the URL shares the workspace.

Exactly one pane is focused (a visible ring when there are two or more). Keyboard shortcuts, the palette and filter typing act on that pane. A plain click navigates the pane the link was in; Alt+click opens the target in the pane to the **right** (reusing one that is already there; Alt+Shift+click forces a new one). No rule targets "leftmost". Closing the second-to-last pane returns to a plain page. Below a minimum width a pane collapses to a labelled rail — collapse and close are different verbs. On a narrow screen the same list is a tab strip over one column.

Panes are sibling views over the one store. Dragging a node from one pane to another is the outline's own `place`, and is not wired yet: the drag measures one page's rows. Saved layouts (a node whose children restore a split) are a follow-up. The design as built is [brainstorming/second-pane.md](brainstorming/second-pane.md).

## Stack

- **Runtime**: TypeScript on Bun — Bun is the package manager, test runner and script runner; types are checked separately with `tsc --noEmit`.
- **Effect**: kolu's whole stack is Effect 4 (kolu PR #2101; the "Effect, everywhere" post) — Effect Schema at process boundaries, `RpcGroup` on the wire, `HttpRouter` layers for HTTP, `Schedule` for reconnect. oRPC, partysocket and hono are gone, and nothing olai writes uses zod. The `effect` version matches the pinned kolu's exactly (one copy fleet-wide, enforced via `package.json` overrides).
- **zod is in the tree, and it is not ours.** `@agentclientprotocol/sdk` declares it a peer dependency and imports it at runtime to validate ACP payloads, so it is a declared dependency of `packages/chat` — the one package that RUNS the protocol's subprocess — and comes back in the lockfile. (`packages/acp` imports the SDK's types only, so the runtime and its zod peer stay chat's.) That is the whole of it: no olai module imports zod, no schema of ours is written in it, and the format still has exactly one validator (Effect Schema, in `format`). Written down here rather than only in the manifest because "zod is gone" is the kind of claim a reader will otherwise carry forward — the honest version is that we do not write it, not that nothing in the closure has it.
- **Effect on Bun**: the proven odu/drishti pattern — `@effect/platform-node` under Bun's Node compatibility. One known seam: Bun's unix-socket async-connect-error contract needs odu's one-line shim, relevant only if we ever serve a unix socket.
- **Markdown**: remark + rehype-sanitize, rendered only at view time, and one pipeline for every piece of it — a node's note, a whole document, what the agent says, and a node's title are the same language read out of the same directory. Titles take one extra step after the pipeline has run: every block is unwrapped to its phrasing content (a fence becomes its `<code>`, a heading its words), so a title that contains block-level source cannot break a tree row's layout — racket parity, inline-only. GFM brings footnotes (whose ids are re-minted per rendered block, so two notes on a page cannot answer for each other); `rehype-highlight` paints fenced code, bundled with the client rather than fetched from a CDN, coloured with this theme's own tokens, and told which grammars it knows (lowlight's common set plus Nix, since this repository is built with it); relative images are rewritten to the `/media` route and everything else is dropped. Highlighting runs AFTER the sanitiser deliberately: the `hljs-` spans are ours and need no allowlist entry, while the `language-…` class that produced them is the reader's and is on the sanitiser's default one. The ALLOWLIST is rehype-sanitize's default plus exactly two named additions, each a single value, and its own module so a feature that widens it has to come there to do it (`web/src/client/markdown/sanitise.ts`, held against the default by its own test so an upstream bump that reshapes it is red rather than quiet): the anchor's class on an `a`, and `message:` on an `href` — a captured mail keeps Mail.app's own address for the message instead of a copy of it (`POST /capture`, above), and the default's href protocols do not include the scheme, so the pointer was being stripped out of the note that was written to hold it. On `href` alone: a scheme admitted where a person CLICKS is not the grant a scheme admitted where a browser FETCHES would be.
- **Styling**: Tailwind v4 — utilities inline in the components, and a CSS entry holding only the `@theme` tokens and the rules for markup this codebase does not author (a rendered note's tags come from a file on disk and can carry no classes). No `@apply`, which would recreate the problem utilities solve by inventing a second name for a set of them. Deliberately no class-validity scanner: kolu ships unguarded Tailwind and the silent-typo trade-off is accepted (decided 2026-08-09).
- **Theming**: the eleven tokens (paper, desk, panel, pill, plus ink/muted/rule and the four accents) are a *palette*, and the table of them lives in `web/src/client/theme/palettes.ts` — ten of our own (reef, leaf, manuscript, bloom, sky, chalk, aurora, pitch, ember, dusk). The WorkFlowy ports that used to pad the table are gone: they were another app's colour values, and olai paints a different app (the frame is ink, the page is paper). The table is the source: the build generates one unlayered `:root[data-theme="…"]` block per row and appends it to the stylesheet, and the preferences panel's Theme row draws one chip per row of it, so adding a theme is adding a row. A pick is CLIENT state — written on `<html>` by four inline lines in the shell before the first paint, stored in that browser, never sent anywhere, and carried into every other tab of that browser by its own `storage` event rather than waiting for a reload — and the OS's preference is not consulted at all: it used to choose the palette, which meant two ways to be dark that could disagree with each other and with the reader. Every palette is held to a reading floor; `chalk` additionally promises WCAG AA over every pair this client paints, and a unit test holds both claims, pair by pair.
- **Type**: the three tokens (`--font-sans`, `--font-serif`, `--font-mono`) are a *typeface*, and there is a catalog of them — in `packages/fonts`, a package of its own, because the words for a face, the sheet generated from them and the derivation that produces the face were three answers to one question in three files and only one of them could be read at a time. Same shape as a theme: the table is the source, `@olai/fonts/build` generates `@font-face` plus one `:root[data-font="…"]` block per row, and the preferences panel's Font row draws one option per row. The default is Olai (Literata / iA Writer Quattro / iA Writer Mono); Atkinson Hyperlegible remains a pick, for a page that wants one voice. Hosted files come from nixpkgs and are converted to woff2 ONCE, by that package's own `default.nix`, in the Nix store — the conversion is a function of the font set, so the client build only copies out of `OLAI_FONTS_DIR` (it used to run 70 `woff2_compress` calls on every build, including every dev-shell rebuild, for bytes that were the same bytes every time). Generics download nothing. A pick is the same kind of client state as a theme — the shell's boot script writes `data-font` before the first paint — and is stored under `olai.font`, in `web`: the catalog is the words, the pick is the client's.
- **A write may not produce a file olai cannot read back.** The set ABSORBS an unreadable file on load — the survivors are clean, so the directory serves with that one outline's errors drawn in its place — and that is right for a line somebody hand-edited and exactly wrong for a line this software just wrote: the caller hears "done" while the records leave every page. So the write gate refuses a write whose own changed files will not decode (`store/src/store.ts`, before the set-wide validation and before any bytes move). It is P5 read literally — the gate is the only thing that knows which files are THIS write's, the codec the only thing that knows what reading one means — and it is what puts every per-line rule behind every verb at once, in one wording, instead of a bespoke predicate per rule wired into each op that can touch its field: a `date` that is not a date used to LAND, silently, and take its outline with it.
- **A dated node can repeat, and the decision lives in ONE place.** `repeat` is a field holding the rule in the format's own words — `every day`, `every week on <weekday>`, `every month`, `every year`, spelled in the file because a `.olai` is read by people and a cron field is a dialect that has to be learned (format.md's [Repeating](format.md#repeating)). The grammar is CLOSED and deliberately small: no intervals, no end dates, no counts, and the picker offers exactly the list the validator takes, read off the grammar itself so a browser and a validator cannot come to disagree about what a rule is. What makes it a feature rather than a field is `set_done`: completing a node that repeats stamps it AND captures the next occurrence as a FRESH node at the next date, so the journal keeps the honest history of each completion instead of one row whose date kept moving. THAT DECISION IS THE PLANNER'S (`ops/src/plan.ts`'s `recurring`), which is the whole of the layering argument here — the browser's `Complete` and an agent's `set_done` are the same request planned by the same function, so it is a fact about the OP and there is nowhere else both faces could be true at once. **The rule rides the occurrence that is NEXT**: completing one hands it forward, so a finished record is a plain dated node, a recurrence has exactly one live head, and un-done/re-done churn is unrepresentable rather than policed — there is no flag anywhere remembering whether a spawn has happened. The next date counts from the node's OWN date rather than from today, so nothing here reads a clock and a late completion spawns the occurrence that was genuinely next; a catch-up rule would need both a clock inside a derivation and a second modifier in the grammar, which is the dialect arriving one character at a time.
- **Dates**: validated as text, not through a date library — a writer must reproduce what it read verbatim. Reading them is text too: a day is a ten-character prefix and a month a seven-character one, so grouping, month boundaries and datetime→day are string comparisons. MINTING one is the other direction and has exactly one home, beside the rule that accepts it (`format`'s `stampOf`): every date value olai writes is a local ISO datetime carrying its offset, which is what the ops layer stamps a `done` with — local, because a mark is stamped where the person marking it is standing and a `Z` would file their evening under tomorrow. Only `done` is stamped (resolved 2026-08-11, human): a date on a mark places the node on that day, and filing or starting a task is not an event a day page is a record of, so `doing` and `todo` are written `true`. The one exception is COUNTING — which weekday a day falls on, the day before or after one, the days a month holds, and the moment so many minutes before another one — and it has one home too, `format/src/calendar.ts`, integers only and never a `Date`: `new Date("2026-08-01")` is midnight UTC, which is the previous day for half the world, and a calendar that shifted a column by time zone, or a `date:yesterday` that answered with today, is the bug that avoids. It lived in the client while a calendar grid was its only reader; the query grammar's relative words are the second, and two copies would have been two answers to which day a week starts on (Monday). The REPEAT rule is the third reader of that module and the first one that is not a view — `every month` from the 31st of January is the 28th of February, which is the month-length and leap arithmetic already sitting there — so recurrence cost this codebase no new date handling at all, which is most of why the grammar could stay four shapes. Temporal is still the intended tool if real date arithmetic is ever needed; nothing needs it yet. WHAT DAY IT IS is the client's one reading of a clock (`web/src/client/clock.ts`), in the reader's own time zone because the dates in the files are what a person wrote down, and it moves twice over: at the next local midnight, computed each time rather than assumed to be 24 hours later, and whenever the page becomes visible again — a laptop shut at eleven and opened at nine ran no timer while it slept, and a page whose promise is that it follows the files without a reload cannot have the day be the stale thing on it. The writer reads a clock too, when it stamps a `done`, and the two have to agree about where a local day ends — a mark made now must land on the day `/today` is showing — so that agreement is a test (`web/src/client/clock.test.ts`) rather than a rule two files each remember.
- **Nix**: flake + npins (kolu, nixpkgs) + justfile; `@kolu/*` packages hydrate as source from the Nix store.
- **E2E**: Cucumber + Playwright.

## Errors

Error kinds (`usage`, `validation`, `not-found`, `busy`) are `Schema.TaggedErrorClass`es — schemas that travel the wire and decode as themselves — surfaced as MCP tool errors and HTTP codes. Every validation error names `file:line`. Errors that teach are the product: a refused write carries the validator's own rows as structured data, and a write that LANDED can carry a nudge — what the rollup noticed, as advice rather than as a refusal (format.md's Status). There was a fifth kind, `derived`, and it went with status derivation.

Validation is staged, and the stage is part of the taxonomy (`stageOf`): a file is decoded whole or not at all, and the set-wide rules then run over the outlines that DID parse. What that costs the reader is one outline and, usually, nothing else — the hybrid error scope above, decided in the format ([format.md](format.md)) and published by the store.

**Not every failure is one of these kinds, and the ones that are not still have to reach somebody.** A refused write is an ANSWER, with rows a caller renders; a git that will not commit is not — the write happened, and nothing about the outlines is wrong — so it travels as two ordinary values instead: `why` on the reply of the write it concerns, and the `git` cell the header's one indicator draws. That is the rule HACKING.md now states, learnt here: never silently ignore an error, and most of them belong somewhere a person can see (`git-invisible`).

The staging still forbids guesses, and the catalogue is where each code answers for itself (`set-across-files`, read by `isGuessWhileUnreadable`). "`kitchen` is not a known id" is a guess when the line declaring `kitchen` is the one that failed to parse — so while any outline is unreadable, an unresolved `mirror`/`after`/`blocks`/`see` target is withheld rather than reported, and withholding one is itself a reason to refuse the whole set: its nodes point at ids nothing can resolve. Everything else is a finding whatever the missing file held, and is reported alongside the parse errors, because one pass should be enough to fix a directory. A report containing a per-line error says so (`reportStage`), and a second round is expected after those are fixed.
