## To fable, press 1 — the wire bill: a projection, and here is the invoice

The question: does the Meaning socket pay for declarations on the wire (vocabulary copied to every tab) or a `names`-table-style projection (answers computed where the set is)? **Projection — and I should have said which one on r1's face, because the bill was already itemised in the codebase.**

The precedent is exact. `door.ts` today consumes `Vault.names`: *"an id-shaped value… resolved where the set is (`@olai/format`'s `page.ts`'s `namesFor`) and arrive[s] in the names table"* (`door.ts:30-32`; `web/src/client/names.ts` — one table per page, carried on the page reading, rebuilt only when membership changes). The door's rule 3 is *already* a projection plug: the tab does not resolve ids; it holds the page's table of answers. My candidate 1 extends the same pattern down the door's own rules 1–5: the page reading gains a **doors table** beside `names` — per page, keyed by the value that names something, carrying `{ kind, target, face }` — computed once per revision by the standing views (`ops/src/standing.ts`, one question one answer per revision however many tabs watch), shipped on the existing page pulse. `door.ts` thins to what it should always have been: a map from answer to `Route`.

Itemised, so the price is stated and not waved:

- **Zero new wire shape.** The doors table rides `page`'s reading the way `names` does — no new cell, no new subscription, no vocabulary. *#395's own stated exclusion survives*: declarations stay server-side (`narrowing.ts:159` reads them where the set is; the browser's filter box was deliberately refused them). A declarations cell would **revoke a deliberate design decision of the very feature this debate is about**; the projection costs it nothing. This is the decisive argument, and it is the house's own.
- **The vault test passes in the strong reading.** Vocabulary churn — the axis that moved three times in one afternoon (`1c30daf5`, `24f80b2d`) — changes the projection's *input*, not its *schema*. Tabs receive different answers from the same wire type. "If the next vocabulary change must touch a wire format, the socket leaks": under the projection the wire format is `Meaning`, and `Meaning` changes only when the app grows a *new kind of openable thing* — the same genuinely client-coupled event that grows `Door`'s union today. Stable under the volatile axis; coupled only to the display axis, which is where the client legitimately lives.
- **The cheapest reading of the divergence bug.** The alternative keeps a derivation alive in every tab. Today's bug is, in one sentence, one derivation too many. Option B — vocabulary on the wire — pays more bytes to keep the disease.

And the cost I owe honestly, not underneath the table: the projection must be *computed*, once per page per revision, and the wiring must move `doorFor`'s three lookups (`from`, `serves`, `names`) server-side — which is a simplification, because the set knows what it serves without a `served.tsx` mirror at all. The frontmatter chips (#302, #322) and search-row chips (#195) ride the same readings and inherit the same table.

## To fable, press 2 — the basis rule: you are right, and here is the tooth it grows

Accepted as policy, not as compromise: **the basis is a declared fact on the declaration's row, or the two premises fight again.** Taking it to the end of the thought, where it gets sharper than either of our openings had it:

So the amendment:

One honest leftover, stated so it can't be mistaken for a fight: the **fallback arm** (undeclared keys keep today's shape-guessing) has no row either, so it inherits the markdown premise and will be wrong for a root-relative text prop the board writes undeclared.
