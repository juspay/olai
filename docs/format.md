# The outline format

One `.olai` file per outline. One JSON object per line; one line per node. Every `.olai` file under the served directory is an independent tree: no cross-file parents. Cross-file relations are mirrors and edges, by bare id.

```jsonl
{"id":"order","parent":"kitchen","ord":"a1","title":"order the new cabinets","date":"2026-08-10","after":["demo"]}
```

The extension is what changed; the CONTENT is the same JSON lines it always was. A vault written before the rename is renamed by hand, once — olai does not read `.jsonl` any more, and a `.jsonl` left in a served directory is simply an unclaimed file, like a `.txt`:

```sh
git ls-files '*.jsonl' | while read -r f; do git mv "$f" "${f%.jsonl}.olai"; done
```

(`mv` instead of `git mv` outside a repository.)

## Two record shapes

A line is a **regular node** or a **mirror**, and which one it is decided by whether it carries `mirror`. They are two shapes, not one shape with optional fields: a mirror is a second *placement* of a node that already exists, so any field describing the node itself has an authoritative copy at the target, and a second copy here could only ever disagree with it.

A mirror is exactly `{"id", "parent"?, "ord", "mirror"}`. Any other field on it is an error.

## Fields

In canonical order (writes always re-serialize the whole record in this order; absent fields are omitted, never `null` or `[]`). **Required** means the record is rejected without it.

| field | required | meaning |
|---|---|---|
| `id` | both shapes | Stable identity: a chosen slug (`[A-Za-z0-9_-]+`) or a minted short string. Unique across the whole loaded set; survives renames and moves. |
| `parent` | no | Parent id, same file. Absent at top level. |
| `ord` | both shapes | Sibling order: a fractional-index string over base62 (`0-9A-Za-z`). Plain string comparison is the sort; never a float. |
| `title` | regular nodes | Verbatim text. Inline tags live here and are extracted at view time — `#topic` and `@person`, two sigils over the same alphabet (`[A-Za-z0-9_/-]+`, so `#work/olai` is one tag) and two NAMESPACES: `#alice` and `@alice` are different tags. `@` is claimed only where a word starts, so `srid@srid.ca` is an address; `#` is claimed anywhere, unchanged since the format's first day. Rendered as **inline-only** markdown (bold, links, code — no block elements) through the same sanitised pipeline a note uses. |
| `done` / `cancelled` / `doing` / `todo` | no | The four MARKS: `true` or an ISO date/datetime string, which is WHEN that state was reached. At most ONE of the four — they are four answers to one question. Storable on ANY node, children or not. A node carrying none of them is not a task at all — see [Status](#status). `done` and `cancelled` are the two that **settle** — nobody is waiting on either — and both are written with the instant they were made at, so both put the node on that day; a dated `doing` or `todo` puts it nowhere — see [Days](#days). |
| `date` | no | ISO date/datetime: what the node is SCHEDULED for. A node with a `date` is a day node, and so is one carrying a dated `done` — see [Days](#days). |
| `repeat` | no | How this node COMES BACK, written in the format's own small grammar — `every day`, `every week on monday`, `every month`, `every year`. Needs a `date` beside it, which is what it repeats FROM; a `repeat` without one is a `bad-repeat`, as is text this grammar cannot read. Carried by the occurrence that is NEXT and by no other — see [Repeating](#repeating). |
| `desc` | no | The note: one string, embedded newlines. Markdown, rendered only at view time; stored verbatim. |
| `doc` | no | Relative path to an attached `.md` document, resolved against the directory of the outline that names it. |
| `after` / `blocks` / `see` | no | Arrays of target ids (any file in the set). Closed set of relations. `blocks` is sugar: `a blocks b` means `b after a`. `after` (with normalized `blocks`) must stay acyclic, and is what a node being **blocked** is derived from ([Status](#status)); `see` is a free cross-reference, and what it lands ON reads it back — see [References](#references), which also says what an `@<id>` written in a title or a note means and what is deliberately not a reference at all. Each is a **set**: a target named twice is named once. Nothing refuses the repeat — a `.olai` is plain text and a hand or a merge can write one — but `set_see` / `set_after` take a re-add as a no-op (and so does `add_node`'s `see` / `waitsOn`, which is those two verbs written at capture time), and a reading of the RELATION collapses it — the links a page draws, the derived blockedness — so a file saying the same thing three times says it once. The exemption is the reads that hand back the RECORD: `read_node` and `search_nodes` answer `see` / `after` **verbatim**, exactly the array the line on disk holds, because what those answer is the record a writer is about to edit rather than what the relation means. |
| `created` / `changed` | no | ISO datetimes the ops layer STAMPS: `created` when a node is captured, `changed` on every write to it afterwards. No verb writes either, and `set_prop` refuses both. Absent on a node written before olai stamped anything — nothing invents a past it did not see, and `git log` is the archaeologist's tool. A `created` with no `changed` beside it means nothing has been written to that node since it was made. |
| `custom` | no | The one OPEN field: a map of named facts olai gives no meaning to — see [Properties](#properties). |
| `mirror` | mirrors | Makes this record a mirror: it shows the node with that id at a second location. The target may live in any file of the set, and may itself be a mirror — the chain is followed to the regular node at its end. |

There are no include records; the served directory is the only composition mechanism.

## Properties

Every field above is one this format declares, and the top level is **closed**: a key olai has no meaning for is a `bad-record` naming it, so a typo'd `titel` is caught rather than kept. `custom` is the one exception, and it is an exception in one direction only — the field is declared, what goes *inside* it is not.

```jsonl
{"id":"lane","ord":"a1","title":"the chat header goes stale","doing":true,"custom":{"agent":"claude-opus","pr":"https://github.com/juspay/olai/pull/176"}}
```

**Any key, holding text or a list of text.** Nothing here gives a key a meaning: a URL is a string that looks like a URL, and no reading in olai turns a value into anything. What a vault MAY do is declare that one key's values have a shape — see [Typed properties](#typed-properties) below, which is a fence around a value and never a meaning given to a key.

**One open field rather than an open record.** Letting unknown top-level keys through would buy the same expressiveness by giving up the refusal that catches typos — and it would put `pr` and `title` in one namespace, where a key called `done` reads as a mark and is not one. Two namespaces in two places: which is which is a fact about where the key sits, not a rule to remember.

**Nothing in olai reads a key in here.** That is the whole difference between a system field and a custom key. The journal reads `date`, the checkbox reads the marks, the blocking graph reads `after`; these are read by the person who wrote them, by `prop:` in a query ([search.md](search.md)), and by the run of chips the web draws under a node's title. That run asks one question of a VALUE — does this string name a file, a node, a day or a URL this app can open, so that the chip can be a link ([editing.md](editing.md#what-a-node-says-about-itself)) — and that is not the same thing: no key gets a meaning, and a value that names nothing is drawn as the text it is. (A key the vault DECLARES has its values fenced — [Typed properties](#typed-properties) — which is still not a meaning: the fence says what a value may be, and no reading here turns it into anything.) Every read that situates a node hands the map back verbatim — a search hit as much as `read_node` — so the query that selects on a property answers with the rest of them beside it.

**Written with `set_prop`** — `{id, key, value}`, and `null` (or `""`) removes it. A key spelled like a field this format already has (`done`, `cancelled`, `date`, `see`, `title`, `id`, `created`, `changed`, or the word `status`) is refused toward the verb that writes that fact: the two namespaces are two places, so `{"done":true,"custom":{"done":"yesterday"}}` is a legal record and an unreadable one. **Three verbs write it and they are one writer**: `add_node`'s `props` puts a map on a node being captured, `update`'s `props` merges one key by key onto a node that exists, and both reach `set_prop`'s own planner — so the shadowed-key refusal is the same sentence whichever one met it.

**The stamps are not compared as changes.** Every write stamps `changed`, so a commit that named it would name it in every line beside the field somebody actually changed — and a write that changed nothing would report as a change, since the stamp would be the difference. What a reader is owed is what they wrote; when they wrote it is the log's own answer.

**Keys are written alphabetically**, and a key holding nothing is not written at all — the same two rules the fields above follow, one level in. A map with no keys left is no `custom` field rather than `{}`. **A read answers the same map a write would produce**, so a key holding nothing is absent from a hit and from `read_node` exactly as it is absent from the line on disk, and `prop:` — which asks the same question — cannot disagree with the answer beside it.

## Typed properties

A key with no declaration is **text**, and that is nearly every key. A vault may declare that one key's values have a shape, and then the write gate refuses a value that does not fit — the same fence `set_doing` and the duplicate-id rule already are. **Typing constrains the value; it grants no meaning**: a `date`-typed property still does not put its node on a day page, because a property is not a mark.

The problem it is for, from a live board:

```
merge       AUTO: grok review folded + CI green; gate = index≡scan differential
dispatched  2026-08-25 10:06 (sweep queue #5; the slot freed by #387's merge)
```

`merge` is a word a driver switches on and this value matches neither of the two it may be; `dispatched` is a date with a story stapled to it. **The value is the value**; the story belongs in the node's note.

**Declarations live in `_olai/Properties.olai`** — read by NAME, wherever it sits, exactly as `Pins.olai` and `Inbox.olai` are. One node per key, the **title IS the key**, the type is written in that node's own props, and an enum's variants are its **children**:

```jsonl
{"id":"prop-merge","ord":"a0","title":"merge","custom":{"type":"ref"}}
{"id":"auto","parent":"prop-merge","ord":"a0","title":"automatic"}
{"id":"human","parent":"prop-merge","ord":"a1","title":"the human merges"}
{"id":"prop-dispatched","ord":"a1","title":"dispatched","custom":{"type":"date"}}
{"id":"prop-pr","ord":"a2","title":"pr","custom":{"type":"int"}}
{"id":"prop-agent","ord":"a3","title":"agent","custom":{"type":"ref","under":"agents-roster"}}
```

**Data, not config.** Editing the vocabulary is editing an outline: adding a variant is adding a child row, the file opens in olai like any other, and nothing restarts. Per-outline declarations were considered and rejected — props are ONE namespace across the vault, so `merge` on a lane and `merge` anywhere else mean one thing or a key's meaning depends on where the reader is standing.

**The seven kinds:**

| kind | what a value is |
| --- | --- |
| `text` | anything. The default, and a DECLARED `text` is the durable blessing for a key whose values are deliberately prose (`from`). |
| `date` | an ISO day (`2026-08-25`) or an instant written as a mark records one (`2026-08-25T10:06:00-04:00`). Nothing else. |
| `int` | a digit run: no sign, no leading zeros, no separators, nothing after them. |
| `path` | one run of characters with no whitespace in it. May point anywhere. |
| `doc` | a path that resolves — against the naming outline's own directory, as `doc` does — to an `.md` this directory serves. |
| `ref` | the **id** of one of a parent's children. `under` names the parent; absent, it is the declaration's own children. |
| `node` | the id of any node in the set. A mirror is not one. |

**There is deliberately no `sum` — an enum IS a ref.** The variants are nodes, so adding one is adding a child rather than editing a pipe-separated string inside a property, which is exactly the sloppiness this refuses. A roster that happens to live elsewhere (`{"type":"ref","under":"agents-roster"}`) is the same mechanism pointed at a different place, and it stays data: add a node under the roster and the sum grows, with no declaration to edit.

**A ref value is an ID** — the pin and mirror rule, for the pin and mirror reason: names rename, ids don't. Variant ids are chosen short at declaration time (`auto`, `human`), which is safe because the duplicate-id fence makes a clash loud at add-time, and short because **the id is what is drawn**: nothing resolves a ref value to its variant's title yet. Where a chip shows `auto`, `auto` is what the file holds. Resolving one for display is the same door work `pr` is waiting on (a repo and a number into a URL) and lands with it, not here.

**One rule, two doors.** A live write is REFUSED, with the allowed values named and the closest one offered:

```
set_prop {"id":"lane","key":"merge","value":"AUTO: grok review folded + CI green"}
→ `merge` is `auto` | `human` — got "AUTO: grok review folded + CI green"

set_prop {"id":"lane","key":"agent","value":"clade"}
→ `agent` names a node under `agents-roster` — those are `claude`, `grok`, `pi` —
  got "clade" — did you mean `claude`?
```

A hand edit that lands a bad value makes the file **broken, naming the key** (`bad-prop`), exactly how every other validation rule reports. Every door that writes a property is covered, because the check sits at the plan/validate seam: `set_prop`, `add_node`'s `props` (children included), `apply`, `update`, `capture`. `duplicate_node` needs no rule of its own — a copy is isomorphic to a subtree the validator has already approved.

**A `date` has TWO WIDTHS and one spelling each** (Converged #8 as amended, 2026-08-25): a DAY stays a bare day, and an INSTANT is written the way a mark records one. Inventing a clock face for a value that named a day would be the same lie the format already refuses when it validates dates as text — a date-only `2026-08-10` round-tripped through an instant comes back a datetime — so "one name, one spelling" is held per width rather than by flattening the two.

**Within a width, the obvious spellings fold into one.** Surrounding space, a single-digit month or day, a space where ISO writes `T`, missing seconds, a fraction after them — all fold into the canonical spelling, and a datetime with no zone is stamped with the offset of the clock the write is made on. `Z` and `+00:00` are one offset and two spellings, so the numeric one — which is what a mark's own stamp writes for every offset, zero included — is the one held. Prose stapled to a date is not a spelling and is refused. On disk the canonical form is the only legal one, so a hand-written `2026-08-25 10:06` is a broken file naming the key rather than a value quietly accepted.

**A `ref` or `node` value is a REFERENCE, and the removals read it.** `empty_trash` and `remove_mirror` refuse to delete a record a live one still names through a declared key, naming the record and the key — the same sentence they already say about a `see` or an `after`. It is a fact about what the VAULT declares rather than about the format, so no index built from the record's own fields could hold it.

**Dangling ref values are flagged like dangling edges.** Delete a roster node while lanes still name it and the validator says so, with a did-you-mean — the same treatment an `after` target that went away gets.

**A key is folded for case.** `pr` and `PR` are one key — to the fence, to `prop:` in a query, and to the shadowed-key refusal, all of which folded already. A property is something somebody typed into a map that gives no key a spelling, so a declaration of `pr` fences a record that wrote `PR`, and declaring both is declaring one key twice.

**Where the recursion grounds.** A declaration is a node carrying properties, so `type` and `under` would need declaring too. They do not: a **built-in table** in code types those two words, applied to the records of `_olai/Properties.olai` and nowhere else. A vault may not declare `type` or `under`; outside that file, a property called `type` is somebody's own vocabulary and none of this format's business. `under` names a NODE and never a mirror: a placement has no children of its own, so a declaration pointed at one would be accepted, find no variants, and then refuse every value of that key for a reason nobody could act on — it is refused where the mistake is written instead.

**What typing does NOT do.** No required keys, no schema per node kind, no defaults. A node may carry any subset of keys, as today. This is one rule about values.

Typed keys gain **spans** in search (`prop:pr=190..200`) — see [search.md](search.md).

## Status

A node is either **marked** or it is not, and one that is not has **no status at all**. There are four marks — `done`, `cancelled`, `doing`, `todo` — and a node carries at most one of them. There is no value for "unmarked", and in particular no `open`.

**Two of them SETTLE.** `done` and `cancelled` are the marks that end the wait: nobody is owed anything by a node carrying either. That is one property and it is the whole of what they share — `done` is work that HAPPENED and `cancelled` is work that WILL NOT — and it is what every derived reading below asks about rather than asking which mark: what a day still owes, what a date badge burns for, what an `after` arrow blocks, what a branch holds up. `doing` and `todo` are the two that do not settle, which is the same list read the other way.

The distinction that whole design turns on is between a **mark** and a **default**. `open` was a default: status derived as done → doing → *otherwise open*, so `open` was simply what a node got for carrying nothing. That made every node a task, and left one value answering two different questions — "a task nobody has started" and "not a task at all". Nothing had ever argued for it; the only outline olai served was its own roadmap, which really is all tasks, so "everything is open" never looked wrong. A corpus of notes is where it shows: every paragraph in it renders as an unfinished to-do, and a search for what is unfinished matches the whole file.

`todo` answers the first of those two questions and answers nothing else, because **someone has to put it there**. That is what makes it a mark rather than the residual coming back: a bullet stays a bullet unless it is marked, and the model forbids a default rather than a third face. Dropping `open` and dropping the *concept* of unstarted work were two changes, and only the first one was the fix — the gap showed the moment someone wanted to say "this is work I have not started" and had nothing to say it with.

**`cancelled` is that same gap, found once more** (the human, 2026-08-25). "This is not happening" was said by CLEARING a mark, and clearing a mark leaves a bullet — a line indistinguishable from one nobody ever called work, carrying no instant, landing on no day. A reader coming back in a month could not tell a task somebody decided against from a note somebody jotted, and could not tell you when the decision was taken. The mark says it, and says when.

It settles because "not happening" ends the wait exactly as finishing does. Concretely, and these are the two halves of the ruling:

- **a parent's `set_done` is not refused over a cancelled child**, anything `after` a cancelled target **unblocks**, a cancelled node stops being overdue and leaves what its day owes, and it drops out of the rollup's denominator (below). Nobody can finish a task somebody has called off, so a mark that went on blocking would be an obstacle with no way past it;
- **it records the INSTANT** — the same local-ISO stamp `done` writes — **and shows on that day's journal page, struck through**, labelled `cancelled`. A day tells the whole story of itself, and a decision to stop is part of that story: a Tuesday on which three things shipped and two were dropped is not a Tuesday on which three things shipped. `date:` selects it the way it selects `done`'s instant ([search.md](search.md)).

What it is NOT is a second spelling of `done`. Everything that asks WHICH mark still answers differently: the glyph is a crossed box rather than a checked one, the day page names the occasion, the commit line says `cancelled:` rather than `done:`, and `is:cancelled` and `is:done` are two questions.

**A node's status is the mark it stores, and nothing else.** Leaf or parent, it says what it says; a node with children is marked exactly like one without. `read this book` can be ticked with three notes hanging off it.

That is a change (resolved 2026-08-11), and the thing it deleted was **derivation**: a parent used to take its status from the children that were tasks — all done → done, all `todo` → todo, anything else → doing — and was forbidden from storing one of its own. It went for the reason `open` went. Derivation reads outline containment (notes under an item) as task decomposition (subtasks), and it makes every parent-of-tasks a task **by structure**, which is exactly the default this model exists to refuse: *a node is a task because someone said so, never because of where it sits*. The two failures it produced were one bug: a parent whose finished children were its only tasks derived `done`, so hiding finished work took the branch with unmarked findings inside it — and the obvious escape, marking the branch, was the one thing the rule forbade.

What follows from the marks on disk:

- **An unmarked node is not an unfinished one.** It is a bullet: nothing to finish, nothing outstanding, and nothing that makes anything else a task.
- **A mark on a parent is a claim about the branch**, not a summary of it, and nothing recomputes it behind whoever wrote it. A `done` therefore says "this whole branch is finished", and because hiding honours that claim by taking the subtree with it, the claim has to be true when it is made: the ops layer will not write a `done` over a branch that still holds a task nobody finished, and will not let one come to stand over work that arrives later (the two doors, below). "This is finished, and what is left under it is not happening" is still a thing people mean — it is said by CANCELLING those rows, which settles them and clears the way, and leaves a truer record than a `done` two levels up that nobody can see from them. (Clearing the marks says it too, and the refusal offers both; the difference is that a cancelled row keeps a mark, an instant and a day, where a bullet keeps none of the three.)
- **Cancelling a parent is not a cascade.** A mark is a stored fact, never computed from what hangs below — so a `cancelled` on a branch settles that node and says nothing about the rows under it, which keep their own marks, stay on the page, stay owed, and go on blocking. **`set_cancelled` is therefore not gated on the branch at all**, where `set_done` is, and the asymmetry is exactly the sweep: done-hiding takes a done row off the screen WITH its subtree, so a false `done` hides work, and nothing hides a cancelled row. There is nothing for a refusal to protect. What the answer does instead is NAME what it left standing, so the contradiction is said out loud rather than either refused or hidden. For the same reason, **open work arriving under a `cancelled` ancestor leaves that mark alone** — door two exists because a stale `done` above an arrival would sweep it away, and a stale `cancelled` sweeps nothing.
- **Rollup survives as DISPLAY.** A node with task children may show how far they have got — `3/5`, beside the title, never in the checkbox. It is an annotation: it decides nothing, hides nothing, blocks nothing, and a node with no tasks under it shows none rather than `0/0`. Mirrors are not counted, for the reason they never were — a mirror is a second view of a node, not a second obligation. **A cancelled child leaves the DENOMINATOR**: `3/5` counts what is happening, so a called-off row is neither a finished thing (which would make the numerator a lie about how much got done) nor an outstanding one (which would make the rollup unfinishable, the very reading a settling mark ends). A parent whose every task child was cancelled shows no rollup at all, which is the "nothing under it is a task" sentence read once more — nothing under it is happening.
- **Hiding what is done means what it says.** A row whose node STORES `done` is not drawn, and its subtree goes with it. The sweep is honouring a claim somebody made rather than inferring one: a parent nobody marked is never hidden, however finished the things under it are, so the findings under it stay on screen. That is the whole of `hide-done-scope`. The other half of the bargain is that the claim stays true — a mark that is right when it is written and goes stale as the branch grows under it hides exactly the work a reader came to see, which is `done-over-open-work` and what the two write-time gates below exist for.
- **A checkbox is drawn for a mark, not for a node.** Done is a checked box, cancelled a **crossed** one, doing a half-filled one, `todo` an **empty** one — and an unmarked node gets no box at all, only the blank that keeps the titles in a column. Those last two are the pair worth keeping apart: an empty box on every row is the claim that every paragraph is an unfinished to-do, and an empty box on a `todo` is someone saying so about one node. The absence of a box is an answer, not a missing one. The check and the cross are the other pair: both rows are struck through, because a strike says nobody is waiting on this line, and the box is where the two are told apart.
- **A mirror asks everything of what it SHOWS.** A mirror stores no mark of its own — it may not carry one — so its row draws its target's mark, its target's rollup, its target's blockedness, and is hidden with finished work exactly when its target's own row is. A box that disagreed with the one at the target would make mirrors unusable. A `see` is not a placement and never inherits any of it: a node carrying `see` is a node in its own right, with its own mark or none, and a row that points at finished work while storing nothing itself is a bullet — correctly, because nobody marked it.

**A `done` may not come to stand over unfinished work, and the ops layer gates both doors onto that state** (`done-over-open-work`, resolved 2026-08-16). The state is one state — a node storing `done` with a `todo` or `doing` anywhere in the branch below it — and it is work that has vanished from the view whose whole job is showing what is left, because hiding takes the subtree with the row. (**"Open work" below is that pair, `todo` or `doing`, and nothing else.** It is prose rather than a value: the status `open` is the default this model abolished, an unmarked bullet is not open work — it is not work — and neither is a `cancelled` node, which has settled.) It is reachable two ways, and the incident that filed this walked through the second: a mark written over open work, and open work arriving under a mark that was true when it was written. So:

- **`set_done` over a branch that holds an unfinished task is REFUSED**, naming them — title, id and the mark each carries, the same shape the `after` refusal has. A BULLET never stands in the way: it is not a task, so there is nothing under it to finish. Nor does a CANCELLED one, which is the fourth mark's first ruling and the refusal's own advice made sayable: the way past this gate is to settle what is not happening, and `set_cancelled` is how that is said. What was lost with the old allow-and-nudge is "shipped, dropping the rest" in one gesture; what replaced it is two, and the second one leaves a truer record on the rows themselves than a `done` two levels up that nobody can see from them.
- **Open work ARRIVING under a `done` ancestor takes that ancestor's mark off**, and says so on the answer. A capture carrying a `todo`, a `set_todo` or `set_doing`, a move that lands a task under it, a merge handing its rows to a finished sibling, a subtree coming back out of the trash: every one of them is somebody saying the branch is not finished after all, and the ancestor's mark is the older and staler of the two facts. A `set_done` or a `set_cancelled` is NOT one of them — the node it lands on settles, so no work arrived and nothing above it went stale. Refusing them would be a capture flow that says no because of a sentence somebody else wrote last week, and the price of that is not a tidy outline — it is work that never gets written down. Every `done` in the chain comes off, each one stamped like any other write, and the commit subject names them too.

Marks the write did not make are never touched: a `done` that is not in the arriving node's own parent chain stays exactly as it was, and so does a `doing` or a `todo` anywhere. Two exemptions, and both are rules this document already has. **Trashed work is exempt at both doors** — a subtree in an `_olai/Trash.olai` is over, so nothing in it is unfinished and nothing in it is hidden by a mark, the same reason blockedness exempts it at both ends of an arrow. It ends where the trash does, and it ends in BOTH directions: work coming back out re-opens what it comes back under **and every stale `done` inside what is coming back**. That second half matters because an exemption is a place where the state can legally be born — marking a trashed branch done over a trashed `todo` is refused nowhere — so `untrash` is the one write that has to ask the question twice. Reopened rather than refused, for door two's reason and one more: the trash is deliberately not a place you edit, so "clear those marks first" would be advice nobody could take, and the subtree would be stranded there by the rule that exists to keep work visible. And **a placement is not containment**, at both doors: a mirror of an open task under a branch neither stops that branch being marked done nor takes a mark off anything, because the work it draws keeps its own row where the node really lives, and hiding a second view of something hides no work. Which is why `add_mirror` is not gated at all.

**Nudges are policy, and they are the writer's, not the format's.** When a mark lands the ops layer may say what the rollup noticed — the last open task under a parent going done, which is the moment to consider ticking the parent, and every mark the second gate above took off (the first one only ever refuses, so it has nothing to remark on). It travels on the answer to a write that HAPPENED, in a field of its own, so nobody has to read it out of the agent's prose. **None of it is ever a load invariant**, gates included: a set that arrives from a git merge — a mark written in one branch, a task added under it in another, both merged cleanly — has nobody to refuse and nobody to nudge, and a file that will not load is a worse answer to "these two disagree" than a file that loads and says so. The gates are about what may be WRITTEN through this software; a set that got there some other way loads, draws, and is fixed by the first write anybody makes to it.

**Merge safety is better for it.** Marks merge line-wise, and there is no longer a cross-line invariant a clean textual merge can break. The one that existed did break: mark a leaf in one branch, add a task child under it in another, and git merges both edits cleanly into a set nothing will load. **The fourth mark kept that property**, which is what makes it a word rather than a rule: the only per-line thing it grew is the exclusion — a record carrying `cancelled` and any other mark is a `several-marks`, exactly as any other pair is — and that is answerable from the one line it is on, so two branches that break it between them CONFLICT in git rather than merging into a set nothing loads.

**Blocked** is the same kind of answer, computed from the edges and the marks together and stored nowhere: `a after b` means `b` blocks `a` while `b` is a task nobody has SETTLED — with the four marks there are, while `b` is `doing` **or** `todo`, read off `b`'s own record. A target with no status **never blocks**: it is not a task, there is nothing to finish, so there is nothing to wait for — and to block on a branch, mark the branch. A `cancelled` target never blocks either: it is not going to happen, so nobody can finish it and nothing can be waiting for it. The trap the rule is written against is spelling it `status !== "done"`, which reads every plain bullet as an obstacle that can never be cleared — and, once there are two settling marks, reads work somebody called off as an obstacle with no way past it at all, since the way past is the very mark being ignored.

That is ONE predicate and it is read at BOTH ends of the arrow, which is the racket reference's own shape: "a node this can be said about" and "a node that still stands in the way" are the same question asked from either side, and two spellings of it would be two chances to disagree about what unfinished work is. So a `done` node is waiting on nothing whatever it is after — it has happened, and the order it happened in is no longer a question — a `cancelled` one is waiting on nothing either, for the mirror-image reason, and an unmarked node is neither blocked nor blocking, because a bullet is not work. **Trashed** work is exempt at both ends for the same reason from the other side: a subtree put away in an `_olai/Trash.olai` is over, so nothing waits on it (a live node that did would wait forever) and nothing tells it that it cannot start.

The exemptions stop at the validator: `after` must stay **acyclic** whatever the marks say and wherever the nodes live, because a loop is a claim about the file rather than about what is on anyone's plate. Both rules read one graph — `blocks` normalised into `after`, with each edge filed under the node its target NAMES, so an edge written at a mirror and an edge written at the node it stands for are one edge. A deadlock that closes through a placement is a deadlock. An edge NAMED TWICE is one edge too, however the set says it twice — a field repeating a target, both spellings of one arrow written down, or a placement named beside the node it stands at — so what a node waits on is a set of nodes, each named once, in the order the set first names it.

Being blocked is a SECOND fact about a node, never a replacement for the first: a blocked task keeps the mark it carries and the date it is due on. A view is free to draw the two together — olai answers both in one column, since "has this started" and "can it start" are the same kind of question about the same node — but nothing may make a node's mark depend on what it is waiting for.

**Both faces are told it, off the one derivation.** A page dims a blocked row and names what it is waiting on; `read_node` answers `blockedBy`, every blocker situated with its title, its `file:line`, its ancestors and the mark that makes it one; `search_nodes` selects on it with `is:blocked` ([search.md](search.md)). None of that is a second reading of the rule above — an agent handed the record's `after` alone would have to re-derive it, and would count a `done` target and a plain bullet as obstacles and miss the edge the other record wrote as `blocks`. The field is absent when nothing is in the way, which is nearly every node, the same way an empty list is absent everywhere else.

**One verb is gated on it, and only one.** Marking a node `doing` is REFUSED while anything is in its way, and the refusal names what — titles and ids, with the mark each carries. Starting is not a report about the world, it is an instruction about what to pick up next, and `a after b` is the set's own statement that `b` comes first; a tool that lets a machine start what the graph forbids has turned its own law into a drawing. `set_done` is not gated on the ORDER at all — finishing out of order is sometimes simply what happened, and a tool that will not record that is a tool that gets lied to. (What that verb *is* gated on is the branch below it, which is a different question about a different set of edges: above.) `set_todo` is not gated at all: filing work is not starting it, and un-starting a blocked node is exactly what should be possible. Neither is `set_cancelled` — calling work off is a decision rather than an instruction to start, and a blocked node is exactly the sort of thing somebody decides against. The gate asks what a node's `after` targets hold up rather than what the node is *drawn* waiting on, because the two differ for a plain bullet — nothing tells a bullet it cannot start, and the write is about to make it work.

## References

**Every reference points one way on disk, and the reverse of it is derived.** Two things in this format are a reference to a node:

- **`see`**, the free cross-reference — the one edge nothing else reads. `a` seeing `b` says only that somebody thought the two belonged together.
- **`@<id>` in prose**, in a `title` or a `desc`. `@` is a tag sigil ([Fields](#fields): `#topic` and `@person` are two namespaces, extracted at view time), and `@herbs` is a tag whether or not anything is called `herbs`. What makes one a REFERENCE is that some record claims that id — a question asked when the reference is READ and never when it is written. So a node minted today turns every `@its-id` already written in the directory into a reference to it, and nothing has to go back and rewrite a note.

The reverse reading — **what refers to this node** — comes out of two indexes kept beside the rest of the derived view and patched per changed file like everything else in it (`@olai/format`'s `derive.ts` and `patch.ts`, [architecture.md](architecture.md)). It is what the browser draws under a zoomed node and what `read_node` answers as `referencedBy`: one reading, so a person and an agent cannot be told different things about one id.

**The prose index files BOTH sigils, and this section reads half of it.** `taggedBy` is keyed by the tag as WRITTEN, so `#herbs` and `@herbs` are two keys — which is what lets one index answer two questions that have nothing to do with each other: what refers to a node (the `@` half, here) and what vocabulary the set uses (both halves, which is the tag completion's list — `format/src/vocabulary.ts`, asked of the server since `vault-in-browser`). A `#herbs` is never a reference, however exactly it spells somebody's id.

**Three things are deliberately not references, and each is already answered elsewhere:**

- **A `mirror` is not.** A placement is a second VIEW of a node rather than a claim about it — the record says nothing except *draw it here too*, it carries no prose of its own, and where else a node is drawn is `read_node`'s `mirrors`. Counting placements would put one fact under two names, and would fill the section on exactly the nodes a curated list points at with entries that say nothing about them.
- **An `after` or a `blocks` is not.** Those are the ordering graph, and both directions of it are already read: what a node is waiting on is [derived blockedness](#status), and what it declares for itself is the field. Collecting the other end under "referenced by" would say one edge twice, under a word that means something else.
- **A record naming a node from an `_olai/Trash.olai` is left out**, the same way it is left out of search, of a day and of blockedness. What is put away is drawn on the Trash and nowhere else, and a section is not a query — there is no `is:trashed` to say otherwise at this door.

**A reference to a PLACEMENT of a node is a reference to the node.** A `see` naming a mirror of `herbs` draws the herb bed's title and opens the herb bed's page, so the reverse reading agrees: the ids a node answers to are its own and every mirror standing for it. And a record never refers to itself — a note saying its own `@id` is talking about the page it is on.

**One record referring twice is one referrer.** A node that both `see`s another and names it in its note is one thing pointing, saying two things — the rule the edge fields already keep about a target named twice.

**A note is read as TEXT.** A `desc` is markdown and the browser parses it before it styles a tag, but `@olai/format` is the floor the validator stands on and holds no markdown parser: deciding what a reference IS out of one would put a parser under the write gate. So what the record SAYS is the answer here, which is the same answer the search grammar's tag facet gives about the same text.

**What that costs is a disagreement with the browser, and it runs BOTH ways.** One rule decides every case and it is inherited rather than invented: `@` is claimed only where a WORD STARTS — the beginning of the text, or after a space, `(`, `[` or `{` — because `@` sits inside ordinary words all the time. So:

| | here | drawn as a tag |
|---|---|---|
| `` `@herbs` `` — a tight code span | no | no |
| `` `see @herbs here` `` — a space inside the span | **mention** | no |
| a fenced or indented code block, `@herbs` after a newline | **mention** | no |
| `[@herbs](…)` — a link's text | **mention** | no |
| `*@herbs*` / `**@herbs**` — emphasis | no | **styled** |

The tight span is the only row where the two agree, and the agreement is an accident of the sigil rule rather than knowledge — nothing here has to know what a code span is. The last row is the one worth knowing about: a reader can see `@herbs` styled as a tag on a record's own page and not find that record in the herb bed's referenced-by section, because `*` does not open a word. Every row is pinned by a test (`format/src/backlinks.test.ts`), so the table cannot drift from the code without something going red.

## Days

The journal, the calendar and the today view are derived from dates AT VIEW TIME, over the whole served directory: there is no journal file, no stored year→month hierarchy and no OUTLINE whose filename means anything. A day is a question asked of every node in every outline.

**One filename does mean something, and it is a document's.** A `.md` whose basename is exactly an ISO date — `2026-08-12.md`, wherever in the tree it sits — is that day's NOTE, and the day page draws it above the query's answer (`2026-08-10-recap.md` is a document about a day and deliberately not one; two files claiming one date are both shown, in path order). It is a view convention over the directory rather than a rule about records: nothing here validates it and no field records it. Olai WRITES one on request now — the day page's **+ day note** mints into that day's note where the newest existing daily note says the vault keeps them — and the convention stays exactly this paragraph's: the file is named for its day, and nothing else says so. Clicking a calendar day never writes. What it changes about the sentence above is only that a day now has two halves — what somebody wrote about it, and what the set says was on it — and never that a node's dates are read differently.

**Two outline filenames mean something too, and both are conventions rather than rules.** `_olai/Trash.olai` is the ONE trash for the whole served directory — a node put away from any outline lands there, and the outermost scaffold title records which outline it came from so `untrash_node` can put it back. It is the one file the set has a verb for EMPTYING — `empty_trash` rewrites it holding no records at all, which is the only write in olai that removes a record from the set rather than moving it, and is refused while anything outside that file still names something in it ([editing.md](editing.md)). There used to be one `Archive.olai` per directory, beside the outline it left; those files stay on disk, parsed as outlines so a human can open one and hand-move, but they are dormant: not the trash, not drawn on the trash page, `is:trashed` does not reach them, and they re-enter no live reading — calendar, day, agenda, default search, blockedness. No migration. An `Inbox.olai` is where a capture lands when the caller names no file. The inbox is read by NAME: whichever outline is called `Inbox.olai`, case-insensitively, wherever in the tree it sits — shallowest first, then path order, so a directory that already keeps `notes/inbox.olai` captures into the file it has — and a directory with none gets `_olai/Inbox.olai`, minted by the same single operation that writes the first line into it. **That mint MOVED, and this page used to say the opposite** (ruled 2026-08-20, reversing 2026-08-19): the inbox is beside the shelf and the trash now, because all three are files olai made because somebody pressed something and the top level of a served directory is the reader's own. Only the MINT moved — the reading above is untouched, nothing migrates, and a vault keeping an `Inbox.olai` at its root goes on capturing into the file it has. Nothing validates either name and no field records them; `@olai/format` spells both (`TRASH` / `isTrashed` / `TRASH_FILE` / `isLeftoverArchive`, `INBOX` / `inboxIn`) so every face resolves them identically. Every face reaches the inbox the same way: the browser's `⌘K` `+` sends a line and no file and the server resolves it, `olai surface capture` from a terminal or a script sends the same thing ([running.md](running.md#quick-capture-from-a-terminal)) and is resolved by the identical function, and an agent reads the outlines and calls `add_node` or `create_outline` itself.

**The sidebar leaves `_olai/` out of its file tree**, and that is a DRAWING rule in the app rather than anything about the set: every file olai names for itself has a door of its own in that column — the shelf IS `Pins.olai`'s face, Inbox sits beside Agenda (wearing how many top-level captures still await processing — a finished branch does not count), and Trash sits at the foot — so a row for each of them as well was a second way in stacked on the reader's own outlines (ruled 2026-08-20). A **Prefs** switch draws them again for somebody who wants to open `Pins.olai` as an outline. Search, a day, the agenda, `list_outlines`, the trash page and the shelf read the same directory whichever way it is set ([editing.md](editing.md), [running.md](running.md)); `@olai/format` spells which files those are (`inOlaiDir`).

**Three fields put a node on a day**: `date`, which is what it is scheduled for, a dated `done` — `{"done":"2026-08-11T15:40:03-04:00"}` is work someone finished at that instant — and a dated `cancelled`, which is work someone CALLED OFF at that instant. All three place identically: a node finished on the 11th, and one called off on the 11th, are both on the 11th's page and both light the 11th in the calendar exactly as a node scheduled for it is. (The second was resolved 2026-08-11 — only `date` used to be read, and the consequence was that finished work, the thing a journal is most often asked about, was the one thing not in it. The third is the same argument one mark over, resolved 2026-08-25: a day that showed what got done but not what got dropped would be missing the decisions, which are the other thing a day is a record of.)

**A dated `doing` or `todo` places nothing.** The format lets any of the four marks carry a date and these views read neither of those two (resolved 2026-08-11, from seeing a day page under the other rule). A journal is narrower than the format on purpose: a day answers *what is on, what got done, and what got called off*, while "this was picked up on Tuesday" and "this was filed on Tuesday" are facts about a task's own history — read as days they bury the day's real answer under everything that was captured that morning. The values stay legal, stay on disk untouched, and a node's own row still shows the mark it carries.

- **A node with two dates is on two days**, once each. Scheduled for the 10th and finished on the 11th is a true statement about both days.
- **Two dates on one day are one row.** It is one thing that happened, and a day claiming two of it would be counting the record rather than the event. The row names which of its dates it is there for — `date`, `done` or `cancelled`, printed in front of the time — and `date` wins that naming: which kind of mark it is, the checkbox has already said.
- **A settling mark holding `true` is on no day.** It says the state was reached and declines to say when — which is legal, and is the shape of everything written before `done` carried instants. There is nothing to put on a calendar, and inventing a day for it would file years of settled work under whatever day it was read on.
- **The day is the first ten characters**, here as everywhere: dates are text, and a `2026-08-10` parsed into an instant comes back a datetime. So an offset is part of the day it names — a stamp is written in the zone of the person who made it, and the day is theirs.
- **Work that was put away is on no day** (ruled 2026-08-17, reversing 2026-08-11). A node in an `_olai/Trash.olai` lights no day in the calendar, is on no day's page and is owed on no agenda, whichever of the two date fields it carries. What is put away is drawn on the **Trash** and nowhere else: putting something away is somebody saying they are done looking at a thing, and a day that went on listing it would be handing back what that reader had just swept off the page. The earlier rule read a journal as "what happened, trash included"; what it cost was that putting something away changed nothing about where it was drawn. Nothing on disk moves for this — the record keeps both its dates and its mark, `untrash_node` brings it back to a day as well as to an outline, and `is:trashed` reaches it from every door ([search.md](search.md)). It is the same exemption blockedness already takes at both ends, read once more: nothing can be waiting on work that is over, and nothing is owed of it either ([Status](#status)).

What a WRITER does with that is policy, not format ([Writing](#writing)), and olai's ops layer stamps **the two settling marks**, each with the instant it was made, local and with its offset (`done` resolved 2026-08-11, `cancelled` 2026-08-25). `doing` and `todo` are written `true`. The two rules are one rule read twice: a settling instant is what a day page shows, so a settling instant is what the writer records. Nothing writes a `doing` or `todo` date, and nothing reads one — a value a view ignores is a value no writer should be minting. Scheduling has a field of its own, and that is what `date` is for.

It is only ever the record being marked that is rewritten, so `true` and day-only values elsewhere keep the spelling they were read with — and every view and every derivation goes on accepting all three shapes, whoever wrote them.

**Due dates are the same two fields read together, and there is no third one.** A `date` says WHEN; the mark says whether it is work — so a node carrying a `date` and no mark is an OCCURRENCE (a birthday, a delivery, a note pinned to a day) and a node carrying a `date` with `todo` or `doing` is DUE WORK. Only the second can be late: `overdue(n) ⇔ n carries todo or doing ∧ day(n.date) < today`, derived at view time and stored nowhere, the way [blocked](#status) is — a second fact about a node, never a replacement for its mark, and one either settling mark extinguishes by construction (`done` because the work happened, `cancelled` because it is not going to). A day passing is not a failure of a bullet, which is the crown rule of this format read once more, and a `due` field beside `date` would have been two dates answering one question. **The agenda is that collection: dated `todo` and `doing` only.** An occurrence stays on its day page and in the calendar dots — it is not owed, so it is not on `/agenda`. The view that reads the predicate, and the page that collects the answer, are [architecture.md](architecture.md)'s.

## Repeating

A dated node may say how it **comes back**, and completing it makes the next occurrence.

```jsonl
{"id":"bins","ord":"a0","title":"put the bins out","todo":true,"date":"2026-08-17","repeat":"every week on monday"}
```

**The grammar is small, closed, and spelled in the file.** Four shapes and no fifth:

| rule | the next occurrence |
|---|---|
| `every day` | the day after |
| `every week on <weekday>` | the next `monday` … `sunday`, strictly after |
| `every month` | the same day of the next month, clamped to one that exists (the 31st of January repeats on the 28th of February) |
| `every year` | twelve months on, clamped the same way (the 29th of February repeats on the 28th) |

Written as the words a person would write, because a `.olai` is read by people: `0 0 * * 1` says the same thing in a dialect that has to be learned, and the moment a dialect exists the pressure is to grow it. What is deliberately absent, each of them a real feature somebody will ask for: intervals (`every 2 weeks`), end dates, counts, several weekdays, days of the month. Reading is forgiving about SPELLING and strict about grammar — case is folded, runs of whitespace collapse, `mon` is `monday` and `every monday` is `every week on monday` — and **a write stores the canonical spelling**, whichever of them was typed. That asymmetry is the [Writing](#writing) section's rule about absence read once more: two files that mean the same thing must not differ byte for byte, because a conflict over which way somebody spelled Monday is a conflict about nothing. What is already ON DISK is left exactly as it was found until somebody writes that field — the rule a `done: true` keeps beside the instants olai now stamps.

**A rule needs a `date`, which is what it repeats FROM.** The rule says how often and the date says when the next one is, so a `repeat` without a `date` answers nothing and is refused per line, beside "at most one mark". Both halves are `bad-repeat`: text this grammar cannot read, and a rule with nothing under it. Nothing else anywhere repeats that rule — `set_repeat` with a rule the grammar does not have, and `set_date` clearing the day out from under one, are both refused by the write gate in the validator's own words, because a write may not produce a file it cannot read back ([Validation](#validation)).

**The rule rides the occurrence that is NEXT.** A recurrence is a chain of occurrences and exactly one of them is pending; the rule lives on that one. Completing an occurrence hands the rule forward to the occurrence it spawns, so a finished record is a plain dated node — it does not go on claiming to repeat, and the set never holds two live heads of one recurrence. Every other rule here falls out of that sentence.

**Completing one stamps it AND captures the next**, as a FRESH node rather than by moving the date forward, so the journal keeps the honest history of each completion: eleven finished occurrences are eleven records on eleven days, where one row whose date kept moving could prove none of them. The new node is placed immediately after the one that was finished, among the same siblings, and carries:

- the **title**, the **note** and the **rule** — the intent, which is what recurs;
- the **date** the rule names, counted from the completed node's own date;
- the mark `todo`, because it is work that has not started — and because an unmarked occurrence could never be [overdue](#days), so a recurring chore that spawned a bullet would be a thing that silently stopped being owed.

It carries nothing else, and each omission names something particular to the occurrence that just ended: the **edges** (an `after` naming tasks already done would be a new task born blocked on history), the **children** (a subtree is where that occurrence's work was recorded), the **document** (`doc` is a path, and two nodes naming one file would both be editing the same text) and the **properties** (a `pr` or a `stage` is a fact about the occurrence that carried it). Anything a person wants carried forward they put there; nothing guesses.

**The rhythm is the file's, never the clock's.** The next occurrence is one period after the node's OWN date, whatever day it is when somebody ticks it off — so a chore finished three weeks late spawns the occurrence that was genuinely next, which may itself be overdue. A catch-up rule that skipped to the first occurrence after *today* would need a clock inside a derivation, whose answer would change with the machine it ran on, and a second modifier in the grammar to choose between the two readings (org-mode's `+1w` against `.+1w`) — which is the dialect above arriving one character at a time. A backlog is cleared by completing those occurrences or by clearing them, and either way the file says what happened.

**Un-doing a completion does not un-spawn, and re-doing makes no second occurrence.** The rule travelled, so the node that was completed has none left to spawn from: the churn is unrepresentable rather than policed, and there is no "have I already spawned this?" flag for anything to remember. What un-doing leaves is a recurrence with one live head — the occurrence that was made — and a node beside it that no longer repeats. Stopping either is `set_repeat` with `null` on whichever one was meant.

**Where it is drawn.** Nowhere special: the next occurrence is a dated node like any other, so the agenda, the calendar and the day pages read it exactly as they read the one before it. What is drawn extra is the rule itself, as a badge beside the date on the row and on the node's own page.

**Everything else is a mark and a date read as they always were.** No occurrence is expanded, no future dates are materialised, and nothing is derived from a rule but the one node the completion makes: a set with a hundred repeating chores holds a hundred records, not a hundred years of them.

## Documents

A `.md` file under the served directory is a **document**, and documents are part of the loaded set for the same reason the nodes are: `doc` points into them, so a reference the validator cannot see is one it cannot check, and a document read out of band would be a second read of the disk, at a different moment from the outline that named it.

**A served file is one of three shapes, and every one of them has a face** ([first-class documents](brainstorming/first-class-documents.md), ruled 2026-08-19): an **outline** carrying its records, a **markdown** document carrying its body, or one of the four kinds olai only **shows** — hypertext, a table, a picture, a printed document — carrying neither. What they share is a path, a **title**, the **addresses** their content points at and the **tags** their prose writes — all of it derived, none of it a change to what is on disk, and all of it TOTAL, so a feature cannot handle one kind and skip the other for want of a field. The nodes are the substructure of the outline arm rather than a collection beside it, which is why there is no node-only list for a feature to reach for.

- A document is **called** by its first non-empty line with the heading marks off, and by its filename when the body has none. That is the closest a `.md` has to a name: it has no record for one to be written on.
- Its **elements** are the slugs of its headings, in document order — what `README.md#install` names, and the reason a `.md` is addressable below the file at all. Derived from the words, so rewording a heading breaks the address that named it; an opt-in explicit `## Install {#setup}` is the later evolution and is not this round.
- What it **points at** is where its `[…](…)` land, read by the same rule a node's note is read by — so a link means the same thing in a body and in a note. Read backwards, that is what lets a document's page say who points at it.
- Its **properties** are its YAML **frontmatter**: a `---` block on the very first line, closed by another `---`, holding `key: value` lines. It is the one thing a `.md` writes about ITSELF rather than a fact derived from its prose, and it is the document's answer to `prop:` in the query grammar ([search.md](search.md#properties)) — the same open namespace a node's `custom` map is, so `prop:agent=claude-opus` answers with both kinds in one list. The block is not rendered, not a heading, not the document's title, and not prose a word search looks through; ONE reading decides all of that, and the browser spends the same one, so the page and what the app knows about the file cannot disagree. Where it ends is the rule every other reader of your vault applies — three dashes on line one, closed by three dashes; an unclosed fence is a thematic break and not frontmatter. A NOTE on a node is not a file and has none: a `---` at the top of one is the thematic break markdown says it is, drawn and indexed as written.
  - **A value is text, or a list of text** — the same two shapes a node's property has. A number, a boolean or a date is the text somebody typed; `[a, b]` and a `- ` block sequence are lists. A key whose value is a nested map, a block scalar (`|`, `>`), a flow map or an anchor is **not read**, and is therefore not a property that document carries — one key at a time, never the whole block.
  - **Properties are not a record.** A frontmatter `date:` is a property named `date` and not the day the journal reads; a `done:` is a property and not a mark; a `tags:` is a property and not one of the tags above, which this format writes with a sigil in prose. So `is:done`, `has:date` and `date:today` still select no document ([search.md](search.md)) — a document with a real day would have to be drawn on the day page, the agenda and the calendar, all three of which read a node.
  - **The document's own page draws them as the same run a node's does** — a chip per fact, key small and muted, value first-class, under the path heading and above the body ([editing.md](editing.md)). A file that wrote no block draws nothing there. The editor is the YAML; the run is off while it is open, so the record is not spelled twice. `list_documents` reports the same map, omitted when empty.

- A document's text is **content, like `desc`**: stored verbatim, interpreted as markdown only at view time. Nothing about it is validated; a `.md` cannot make a set invalid.
- A document is **written the way everything else is** ([Writing](#writing)): whole, through the one write gate, never as a byte range. The two ops are create (a relative `.md` path judged segment by segment, refused if it exists) and write (the whole new text, refused if the path does not exist — so a typo cannot mint a file). A write may carry `was`, the text the caller read, and is refused if the file has moved since — checked on every retry, which is the conflict story for a document edited in vim under an open editor.
- **The whole set loads; a body travels when it is read.** Those are two rules, and only the first one is about this format: every document is decoded, cached and revised with the rest of the directory, whatever a reader asks for. What crosses a wire is the transport's business — olai's serves the paths to everyone and one document's text to whoever opens it, because a directory of thousands of `.md` files cannot put every body in a first frame. It is still ONE read of the disk: the body comes off the same live set at a named revision, not from a second reader that could disagree with it. That is a `.md`'s story and it is deliberately not a `.html`'s, whose body the set does not keep at all ([Hypertext](#hypertext)) — a document's text is what a conditional write is judged against and what a writer must reproduce, so the set has to be holding it.
- `doc` **attaches** one to a node, relative to the outline that names it — a node names a file beside itself, not beside whoever is reading it. The rule is one function (`docOf`), read by the validator and by the view.
- A document may point at **pictures** beside itself: a relative `![](art/shot.png)` resolves against the document's own directory (a note's resolves against its outline's) and is served from `/media/`, restricted to picture extensions. A `..` is clamped at the served directory rather than escaping it, and nothing else is drawn at all — no remote host, no `data:`, no absolute path, no `.svg`, since an SVG is a document that can script. The same route serves a `.html` preview, a picture's own page, a `.pdf`'s, and the parts a preview draws with ([the kinds olai only shows](#the-kinds-olai-only-shows)) — one answer to "which files may be fetched over HTTP", not two, and one traversal guard in front of it. What markdown may *name* is still a picture and nothing else, `.svg` excluded: that is a rule about what markdown means, and it did not widen when the route did or when a picture became a kind. Pictures ARE part of the set now — they are listed, addressed and drawn on pages of their own — but only their paths are: nothing loads a picture's bytes.
- A document may **link** to another: a relative `[the deck](../projects/deck.md)` is rewritten at view time to that document's page (`/<path>`). A filename with a space in it is still that file: `[the brief](the%20brief.md)`, `[the brief](<the brief.md>)`, and `[the brief](the brief.md)` all name it. A relative link to any file with a page is rewritten the same way — a `.html`, a `.csv`, a picture, a `.pdf` — since a link is asked of the registry rather than of a list kept beside it. A `[shot](art/handle.png)` opens that picture's page; an `![](art/handle.png)` is still an embed, drawn from `/media/`, which is the distinction those two rules keep. An `http:`/`https:` link is left as written and opens in a new tab. Everything else — a fragment, a path that is not a served file — goes where it says, in this tab. The same pipeline draws a node's note and what the agent says, so the rule is one.

## Pins

**A pin is an ordinary node, in an ordinary outline, whose title is an ADDRESS.** The sidebar draws a shelf of them above the file tree — one click back to a node, a document, or a page with the query it was narrowed by ([editing.md](editing.md#pinning-a-page-to-the-sidebar)). Nothing in this format is new for it: no field, no record shape, no op.

**The file is `Pins.olai`, by NAME**, wherever in the directory it sits — the third filename that means something, read the way the [inbox](#days) is (case-insensitively, shallowest first, then path order; `@olai/format`'s `pinsIn`). A directory without one has an empty shelf, which draws nothing.

**Where olai MINTS one is `_olai/Pins.olai`**, and that is a different question from where it finds one. The reading above is unchanged: a directory that already keeps a `Pins.olai` at its root, or under `notes/`, goes on using the file it has. What changed is only the file olai creates when there is none — `_olai/` is where olai puts the files it names itself, because a file made because somebody pressed something is not one of the reader's own and the top level of a served directory is theirs. An underscore rather than a dot: a dot-directory is not walked at all, so a shelf under one would never be read back. The trash and the inbox are minted here too (`_olai/Trash.olai`, `_olai/Inbox.olai` — the inbox's move ruled 2026-08-20, reversing the day before).

**The top level of that file is the shelf, in `ord` order.** One node per pin. What is nested under a pin is that pin's own business — notes about it, a checklist — and is not a second row in the sidebar.

**The title is the address this app would spell for that page.** An address is `[document]#[element]`, the format's own grammar (`@olai/format`'s `address.ts`), with a slash in front of it: `/#<id>` a node, `/<path>` a document — a `.md`, a `.html` or an outline, the suffix says which page it opens — and `/<path>#<slug>` a heading inside one. Beside them are the pages that name nothing on disk, which are the app's own ([architecture.md](architecture.md)): `/d/<ISO>` a day, `/today`, `/agenda`, `/trash`. Each may carry `?q=<filter>`, which is how a **saved query** is a pin at all ([search.md](search.md)).

```jsonl
{"id":"p-herbs","ord":"a0","title":"/#herbs"}
{"id":"p-late","ord":"a1","title":"[What is late](/agenda?q=is%3Atodo)"}
```

**A bare address has no name stored beside it, and that is the point.** What the shelf draws for `/#herbs` is that node's title *right now* — so a node renamed anywhere, by anyone, says its new name on the shelf, because there was never a second copy of it to go stale. That is the same argument [Two record shapes](#two-record-shapes) makes about a mirror. A file's pin is called by its own filename; the pages that are not files are called what a reader calls them.

**A title that names a place is DRAWN as that place** — wherever it is drawn, in either spelling. The shelf resolves its rows, and so does `Pins.olai`'s own page, and so does any other outline holding such a title: a row reading `/orchestrator/instructions.md` draws the pin mark, the file's name, and the query if it carries one. That is a rule about TITLES rather than about the shelf, which is what keeps the file browsable — it is an ordinary outline, and it reads like one. What the EDITOR opens is the address exactly as it is stored, the same trade a markdown title already makes: the face is what you read, the address is what you edit.

**A markdown link is a NAMED pin** — `[What is late](/agenda?q=…)`. A name written there is somebody's, not a copy of anything, so nothing can disagree with it later, and **renaming a pin is editing that row's text** — no op, no field. Both spellings draw the same face: the mark, the name, and the query when there is one. Three things follow, and each was ruled rather than fallen into:

- **the label is drawn as the words somebody chose.** A `#home` in it stays those four characters rather than becoming a tag pill: the label names a door, and restyling part of it would be making a claim about the directory out of somebody's punctuation.
- **the query is drawn either way.** A name renames the PIN and never the destination, so `[Overdue](/agenda?q=is%3Atodo)` reads *Overdue* with `is:todo` beside it — a door onto a narrowed page that did not say so would promise something it does not open.
- **pressing the label opens the address**, because it was written as a link and goes on being one. A BARE address is not a link: pressing that row opens the editor, where the address is what you see and edit.

**Olai writes a named one only when somebody TYPED a name**, which is the other half of that sentence and the reason nothing here goes stale now that the app can. What it asks about is a page carrying a `?q=` — the one address whose name cannot be derived from anything, since every narrowing of the agenda is still called *Agenda* — and an empty answer is the bare address it has always written ([editing.md](editing.md#naming-one-where-the-thought-arrives)). Nothing DERIVED is ever written into a link, so a stored name is always somebody’s own; and the row it writes is the row a hand writes, so renaming is `set_title` on that node whichever face asks for it — the shelf’s `✎`, an agent, or vim.

**What a pin promises, and what it does not.** It promises the ADDRESS is what somebody kept, and that a node's name is read live. It does not promise the target is still there, and the three ways that shows are worth knowing: a pin to an id nothing declares draws its own address (`/#gone`) — an honest dead row rather than a blank; a pin to a node that was TRASHED goes on drawing that node's title and opening its page, because the record is still in the set, and the shelf does not say it was put away; and a pin to a DOCUMENT is a path, so a renamed or deleted `.md` leaves a row named for a file that is no longer there. That is the cost of path identity, which ids do not have — an unpin is one click, and re-pinning is the fix.

**A row that is not an address is not a pin.** `Pins.olai` is an ordinary outline: a heading in it, a note, a title that merely begins with a slash — none of them is a door, and the shelf simply does not draw them. The test is whether the app's own parser recognises a page rather than a list of prefixes, so `/etc/passwd` reads as text — and so does an address no escape could have written (`/%`), which is refused rather than thrown at: this file is one a hand and an agent are invited to edit, and a parse that threw would take the sidebar down instead of skipping a row.

**A mirror in there is not a pin either.** A placement means *draw it here too*, so a shelf built out of mirrors would pull every pinned node's whole subtree into `Pins.olai`. A pin says *go there*, which is a different thing, and the difference is why this convention is titles rather than placements.

**Which half of this convention lives where is deliberate.** *Which file the shelf is* is a fact about the DIRECTORY, so it is `@olai/format`'s (`pinsIn`, beside the inbox's rule) and both faces read it there. *What a title MEANS* is two facts with a seam between them. What an ADDRESS is — `[document]#[element]`, and what each half names — is the format's, because it is a statement about the directory (`address.ts`). WHICH PAGE one opens, and what a `?q=` on it means, is the browser's, at view time, through the same bijection that wrote it. The `pin` verb carries the address across as an opaque string; nothing between the affordance and the file parses one. A NAME rides beside it on the same verb and is wrapped round it where the file is chosen, by the exact inverse of the reader that draws one (`@olai/format`'s `pinTitle`, beside `linkedTitle`) — so the address is still never read on the way, and where the brackets go is one expression rather than two that must agree.

**That seam is also where the shelf is ANSWERED**, since the browser stopped holding the vault ([brainstorming/vault-in-browser.md](brainstorming/vault-in-browser.md)). Reading a shelf means reading a whole directory — finding the file, sorting its top level, and looking up a title that may live in any other file — so the server does it (`shelfOf`) and the browser is handed the answer: the rows as the file holds them, and, for each row that addresses a node, that node's id and what it is called at this revision. Every revision re-answers it, which is what keeps a bare pin's name live; a revision that moves no pin sends nothing. The browser reads its own half of each title as it always did, and spends the answered name only where the two agree the row addresses that node — a name is drawn on a door, and a name for somewhere else is the one wrong thing a door can say.

**Both faces write it with the tools they already have.** An agent pins with `add_node` into `Pins.olai` (or `create_outline` when the directory has none), reorders with `move_node`, and unpins with `trash_node` — which is exactly what the browser's own gestures resolve to, one op each ([architecture.md](architecture.md)'s one write gate). The web has one verb of its own, `pin`, and all it saves a browser is the READING: which file the shelf is is a fact about the directory, so it is resolved where the write is judged, the same way a quick capture finds the inbox.

## The kinds olai only shows

What is in a vault is not only outlines and notes: a saved article, a report a build wrote, the bank's export, the screenshot of the thing that broke, the diagram somebody drew, the receipt. Four kinds of file are those, and olai treats all four the same way — it claims them, lists them, addresses them and **draws** them, and never writes one.

Which files olai claims at all is one table, in `@olai/format`'s `kinds.ts`: an outline is a `.olai`, a document is a `.md`, hypertext is a `.html`, a table is a `.csv`, a **picture** is any of `.png` `.jpg` `.jpeg` `.gif` `.webp` `.avif` `.bmp` `.ico` `.svg`, a printed document is a `.pdf` — and everything else in the directory, a `README`, a `.json`, a source file, is not part of the set. A suffix is matched **exactly as the table writes it**, for every kind: `IMG_1234.JPG` is a file olai walks past, the same way `a.OLAI` is. Adding a kind is one entry there, and the type checker then names every surface that owes it a glyph and a page.

A picture is the one kind with more than one spelling, and that is what a kind with a list of suffixes is for: `.png` and `.webp` are not two names for one thing, they are two encodings of the one thing olai does with either, which is draw it in an `<img>`. A kind per encoding would be nine rows owing nine identical glyphs, nine identical faces and nine identical nouns.

**All four are drawn and never written.** No editor, no create verb; `create_document` and `write_document` take a `.md`, and MCP's `list_documents` and `read_document` answer for a `.md` and refuse the rest exactly as they already refused a `.html`. What each is drawn AS is the whole of what differs:

- a **`.csv`** is parsed when a reader opens it and drawn as a table, the first row as the header — which is a convention every tool that writes one keeps and nothing in the file marks. It is a table and never a spreadsheet: nothing here writes one back. A file bigger than a page draws is **bounded and the bound is said** — "Showing the first 500 rows." — because a table showing a fraction of a file with nothing saying so is a lie the reader cannot see. The bound is on the READING rather than on a slice taken afterwards: the scan stops at five hundred rows, at a hundred columns, and at two thousand characters of any one cell (the third is the axis the other two cannot cover, since a file that is one quoted field is one row and one column). That is also why the sentence says "the first 500 rows" and not "of 12,431" — a total is a number only a full scan knows, and reading a million-row export to print a figure the bound exists to avoid reading is the defect wearing an honest sentence;
- a **picture** is an `<img>` pointed at `/media/<its path>`, at its own size up to the width of the column. `.svg` is among the picture suffixes and is drawn in that same `<img>`, which is exactly the element that will **not** run one — and the response the media route answers an SVG with carries `default-src 'none'; sandbox`, so a reader who reaches the URL another way (typing it, a link, a previewed page pulling it into a frame) gets an inert document rather than script on this app's origin. That is the same permission split markdown keeps: a relative `![](…)` may still name a picture and **not** an `.svg`, because markdown pointing at one is this app promising to draw a file it has not read;
- a **`.pdf`** is the browser's own viewer, embedded as an `<object>` pointed at `/media/<its path>` — zero dependencies, because every browser a person actually runs ships a viewer and bundling one would be megabytes of somebody else's code to draw a worse one. An `<object>` rather than an `<embed>` for one word: **fallback**. A browser that will not draw a PDF gets a sentence and the file itself, where an `<embed>` leaves an empty rectangle and says nothing. What sandboxes it is the browser's own out-of-process viewer: a PDF never executes in this page's context, so an `<iframe sandbox>` around it would add no boundary it is not already behind while being the ordinary way to stop the viewer loading at all.

**None of their bodies is in the set** — the table's `kept` column, which is what a saved page taught. The set holds the path; the content is read, or fetched, when a reader opens it and kept by nobody. Where that content comes FROM is the table's other new column, `fetched`: hypertext, a picture and a `.pdf` are drawn by pointing an element at the file's own URL on `/media/`, and a `.csv` is not — its text crosses the wire like a document's body, read for whoever is holding it open and let go. So the media route answers the first three and still refuses a `.csv`, which already has a page that is handed its content.

## Hypertext

A `.html` file under the served directory is **hypertext**, and it was the first of those four — the sidebar lists it under the folder it lives in with a glyph of its own, and it has a page at `/<path>` like a document does.

- It is **shown, and it runs** (resolved 2026-08-16). It used to be shown and never run: the seal admitted exactly one script by its hash — olai's own tape measure — and refused the file's, so a saved dashboard, an exported report or any page that draws itself was a heading over an empty box. That rule is gone. **The file's own JavaScript runs**, and what decides the consequence of running is unchanged: the frame is sandboxed **without `allow-same-origin`**, so its origin is nobody's — no `document.cookie`, no `localStorage`, no reading the page around it, no reaching this app at all.
- **An inline script and a classic `<script src>` run; a MODULE does not**, and neither does `fetch`. Module scripts and `fetch` are CORS-mode requests always, and this document's origin is nobody's, so a response with no `Access-Control-Allow-Origin` is discarded by the browser. That is deliberate: a CORS grant is what would let a page in there READ this vault's files as data rather than only draw them, which is a different promise from the one this makes. `@olai/server`'s `media.ts` records the shape to reach for if a saved page ever needs modules badly enough — never a blanket allow-origin.
- **The seal is about bytes, not about code.** The file is served at its own address (below) behind a content policy on the **response**: `sandbox allow-scripts; default-src <host>/media/; script-src <host>/media/ 'unsafe-inline' 'unsafe-eval'; style-src <host>/media/ 'unsafe-inline'; frame-src 'none'; form-action 'none'; base-uri 'none'`. Every fetching directive names one place — this vault, on the host the reader asked for — and everything that merely *computes* is allowed, because what may run was settled by the sandbox. Three of those lines are worth their own sentence: `sandbox` is on the response because a `<meta>` cannot carry it and because the address is one a person can type, so a page opened directly is in an opaque origin too, never in this app's; `form-action` is spelled out because it is one of the few directives that does **not** fall back to `default-src`; and `base-uri 'none'` refuses the `<base href>` a saved page carries of its own, which would otherwise point every relative address in the file at the server it was saved from.
- **What it cannot stop, said plainly.** A script can navigate its own frame, and no CSP directive covers that — `navigate-to` was specified and then removed, `form-action` is forms only, and the sandbox's absent `allow-top-navigation` protects the tab rather than the frame. So a page that *wants* to tell somebody else's server what it is can, once, by leaving. What the seal still guarantees is that nothing a page fetches leaves this vault: an image, a font, a stylesheet, a script or a `fetch` is answered from `/media/` or refused, and a nested frame or a form post is refused outright — which covers the ordinary case the promise was written about: a saved page that merely *carries* a stranger's addresses reaches nobody.
- The frame **comes home.** A sandbox is a fact about the browsing context and survives navigation; the policy is a fact about one response and does not. So a page that walks the frame off the vault — a `<meta http-equiv="refresh">`, a link to a stranger — lands somewhere with no `default-src` over it. Every document olai serves greets the app as it parses, so a navigation to a file of this vault that the frame does make for itself — a script assigning `location`, a `refresh` naming a neighbour, a link carrying a fragment — is kept, and anything that says nothing is replaced by the file — a bounded number of times, and then by an empty frame, so no served file can put the tab in a reload loop. That greeting is a *bound* rather than a proof, and the reason is the new rule: a page that runs script can send the same greeting from anywhere, so nothing said from inside the frame can prove where the frame is.
- The frame is **as tall as its page**, within bounds. A short receipt gets a short frame instead of two thirds of a screen of white; a long article gets a tall one and is read by scrolling the page around it instead of a scrollbar inside a scrollbar. The reported height is a claim from an untrusted frame, so it is clamped rather than obeyed: never under `6rem`, never over two screens — past that the page scrolls inside the frame as it used to — and `70dvh`, the old fixed guess, is what a frame that never reports keeps. A page is measured whenever it changes — as it parses, as it reflows, when its pictures land — and the frame follows every reading that says something the reading before it did not. What it refuses is its OWN height coming back: a page sized in `vh`, whose height IS the frame's height plus its own margins, stands the same distance above the frame at every height the frame is given, so a report at that same distance is the container handed back rather than a page that grew. A page that really grew — a chart drawn from a fetch, a `<details>` a reader opens, a `loading="lazy"` picture whose bytes were late — stands a different distance above it, and is followed however late it arrives. What that costs, and it is a decision rather than an oversight: a page that grows by exactly as much as the frame just grew is sending the same two numbers a `vh` page sends, so it loses that step and wins it back at the next one out of step; and a page that asks for MORE than the frame's height (`min-height: 120vh`) has no height that satisfies it at all and rides up to the two-screen clamp. A page whose height moves the OPPOSITE way from the frame's — an element taller when its viewport is shorter, or a page simply posting two heights in a loop — has no satisfying height either and does not run out of room, so the frame may be sent back the other way only a few times without a quiet moment in between: it changes its mind for about a second and a half and then stops, rather than flickering for as long as the file is open. A height is the FILE's rather than one fetch of it, so re-fetching the file — which is what a revision moving does — leaves the frame the size it was until the new reading arrives: dropping it back to `70dvh` for the length of a round trip took a thousand pixels out of the page around it and clamped whoever was reading the end of it to the top. It goes only where the frame is no longer showing this file at all — a page that walked off, and the empty frame a page that would not stop leaving is finally given.
- It **fetches nothing off this vault**, which is a rule about privacy rather than about scripts: a saved page full of remote images would tell somebody else's server what this reader is reading, with no script involved. It is the same rule markdown already lives by here — a relative picture or nothing, and a vendored highlighter.
- **It is served at its own address**, `/media/<its path>`, and that is what makes everything relative in it correct: the vault's directory shape IS the URL space. `<img src="art/shot.png">` in `notes/report.html` is `/media/notes/art/shot.png` — the exact URL a markdown `![](art/shot.png)` beside it is rewritten to — and `<a href="other.html">` is the file next door (the old `<base>` at the route's directory made pictures work and left links 404ing). Everything that is not vault-relative resolves somewhere the policy refuses: a remote host is not this one, a `data:` URI is not this scheme, and a climb out of the directory is normalised out of `/media/` by the URL parser before any of it is fetched. The one place a preview and a document beside it differ is worth naming: a `..` that climbs past the served root is CLAMPED for a document (the address resolves to the root's own file) and REFUSED for a preview (the parser normalises the climb out of `/media/`, where the policy cannot follow). Both stay inside the vault; the preview is the stricter of the two. `@olai/surface`'s `media.test.ts` asserts the agreement and that one divergence against the browser's own resolver, so a change to either side has to come past it.
- **A link to a page of this vault opens that page in olai** — that is `html-preview-relative-links` closed. A folder holds `foo.html` and `bar.html` and one links to the other; clicking that link takes the reader to `bar.html`'s own page — its own address, its heading, its entry lit in the sidebar — which is exactly where clicking `bar.html` in the sidebar lands. The seal puts a click handler in the previewed page: a plain left click on a link that resolves to this vault's `/media/` space and names a file olai has a *page* for — **every kind the registry claims**, which is a `.html`, a `.md` (whose page is the note it renders), an outline (whose page is the tree), a `.csv`, a picture or a `.pdf` — is not followed — the address is posted out to the app instead, and the app navigates. A `.md` and a `.csv` are on that list even though the route refuses to serve either, because the two rules answer different questions: what a browser may be **served**, and where a reader may be **taken**. Everything else keeps the behaviour above: a link to a picture, a stylesheet or a font is a link to a file and the frame follows it; a link to a stranger and any navigation the page makes for itself are untouched; and an in-page `#top` is still the frame's own jump, because a page scrolling itself is not a navigation. A fragment naming ANOTHER file — `other.html#beds` — is carried: the document page can land on a section now, so the address the app opens keeps the `#`, which is what makes a section something a reader can copy out of the bar and send. The two kinds land by two mechanisms with nothing in common — a `.html` gets the fragment on the frame's own URL and the browser scrolls it, while a `.md` needs translating, since the format's own rule gives `## Beds` the id `beds` — the same slug the document's face promises — and the renderer then moves it into the block's own namespace so that two notes opening `## Shape` cannot answer for each other. A fragment naming no id leaves the reader at the top, which is what a browser does with the same address. And a landing is spent ONCE, on arrival: coming back to that address restores where the reader had scrolled to rather than the section, and a file rewritten under them — an agent's write, a `git pull`, another tab — redraws the page they are reading without dragging them back to the heading. It is spent by the READER and not by the page's own geometry, which is the same sentence one turn further out: a preview goes on correcting where it put somebody while the frame is still settling to the height of what is in it, and stops the moment they have scrolled somewhere of their own choosing — or, at the latest, two seconds after the act it is correcting, which is the ending that answers for a pane the reader is not looking at, where nothing they do moves that frame at all. So a window dragged narrower, or a page that draws a chart from a fetch a minute later, moves the frame and moves nobody. What crosses is a **lookup key, never an instruction** — a page that runs script can post any string it likes, so the app decodes it through the same traversal guard the route stands behind and then looks the result up in the files it is actually serving — the documents, then the outlines, which is also what decides which of the two pages it opens. A name the vault does not hold moves nothing at all — and neither does the name of the page ALREADY OPEN. That one is refused for a different reason: the channel needs no gesture, and a message naming another file navigates once and takes the frame with it, while one naming the file on screen would leave the sender sitting there able to send again, spending history and the tab's scroll with no reader in it. It is refused silently, unlike a miss: a self-open names a page olai has and is drawing, so an alarm about it would be contradicted by the screen it was drawn on. That list is the store's, and the store's walk skips dot-directories and `node_modules` while the route's guard is lexical, so a `.html` under one of those is servable and unlistable at once: a link to it is claimed and then dropped — and the reader is TOLD so, in the same voice every refused act in this app speaks, because a click that does nothing and explains nothing is what the never-silently-ignore rule is about. Nothing became unreachable — olai has no page for such a file either — but the frame no longer draws it, and that is the one thing this change costs. The notice does not quote the path: the string came from a document running somebody else's JavaScript, and echoing it would let that page put words of its own into olai's chrome.
- **What the route answers** is the page, its pictures, its stylesheet, its script and its font — `@olai/format`'s `isAsset`, a closed list, in front of which stands the traversal guard markdown's pictures already went through. The `.html` is on it because it IS the page — the frame's own address — and everything else on it is a part that page draws itself with. A `.md` or an `.olai` is not: nothing draws a page out of one, they have pages of their own, and handing them over raw would be a second way to read them with no argument for the first. Data (`.json`, `.csv`) is not on it either, because a page reading FILES is a different permission from a page drawing itself and nothing has forced that question — a `.csv` becoming a KIND did not force it, since that kind's page is handed the text over the wire and never fetches this route. **`.svg` used to be off the list and is now on it**, and that is the one entry whose argument changed rather than widened: an SVG is still a document that can script, and what stops it is now the RESPONSE rather than a suffix withheld — the route answers one with `default-src 'none'; sandbox`, so a reader who reaches the URL any other way gets an inert document ([the kinds olai only shows](#the-kinds-olai-only-shows)). Withholding the suffix also withheld it from the `<img>` a picture's own page draws, which the ruling never meant to stop.
- **The file is handed over whole**, after a prefix. Nothing of the file is parsed, stripped, rewritten or re-encoded: the response is a doctype, a colour scheme and the tape measure, and then the file byte for byte, its own `<script>` and its own `<base>` included. That is deliberate rather than lazy — rewriting each `src` needs a tokeniser that agrees with the browser's about what an `<img>` is (inside a comment, inside `<script>`, inside `<template>`, unquoted, `<img/src=…>`), and every disagreement between the two is a place where what was checked is not what runs. It is also what makes a `srcset`, a `<picture><source>` and a `background: url(…)` in the page's own CSS work without a second mechanism each: they are all relative URLs, so they all resolve in the same place. Two costs come with the prefix and are named where they are taken: the response is not the file's length, so the route does not offer byte ranges; and the charset travels on the response as UTF-8 rather than being read out of the file's own `<meta>`, which the prefix would push past the 1024 bytes a parser looks in.
- It is **read, not written.** There is no editor on its page and no create op: `create_document` and `write_document` take a `.md`, and a `.html` in the directory belongs to whatever wrote it. The agent's document READS take a `.md` too, and for a second reason: the set keeps a `.html`'s path and not its body, so `list_documents` leaves one out and `read_document` refuses it — a page is fetched by URL, by whoever is showing it.
- It is part of the loaded set the way a document is — same probe, same revision, and it updates on an open page when the file changes on disk — and its text crosses the wire the same way when anybody asks for it, one body at a time. Nobody drawing it asks, which is the next bullet. What the set keeps of it, though, is **the path and not the body**, and that is the one place hypertext differs from a document. A saved page can be megabytes with its pictures inlined, and holding every one of them for the life of the process made resident memory the directory's *content* rather than its size. Nothing in the set ever read those bytes: a `.html` is not validated, no op writes it, and a `doc` reference is checked against the paths. So the body is read **when a reader opens the file**, handed to that reader, and kept by nobody — the probe does not open a `.html` at boot, does not re-read one that changed unless the server is watching it (below), and a vault of a thousand saved pages costs a thousand paths. Which kinds are kept is one entry in the registry (`@olai/format`'s `kinds.ts`), the same table that says which files olai claims at all.
- **The PREVIEW does not read that body, and does not ask for one** (resolved 2026-08-17). The frame fetches the file over HTTP from `/media/` (above); what the page needs from the wire is to know the file on disk MOVED, which is what re-points the frame. So that is all it asks for: the file's HEAD, a revision and nothing else, off a member that carries one for every bodied file and no bodies at all. It used to ask for the BODY and read the revision off it — which made the server read the whole file (a body is read for whoever opens the key), sent a copy of it to a page that draws none of it, and did not create the frame until that unused copy had landed. Two full transfers of a saved dashboard, serialized, on every open and on every edit. Measured before and after on a one-megabyte page opened and rewritten three times: the websocket carried 3.9 MB and now carries about half a kilobyte, and what the frame fetches is unchanged. A `.md` is untouched — it is DRAWN from its body, so its page asks for one — and so is an agent, which has no frame and reads a saved page's bytes off the same collection it always did.
- **Live update is not bounded, and a body is not bounded either.** A `.html` on an open page follows the file, however many other files are opened anywhere: a revision moves that file's head, and the head reaches every reader on one batched stream with nothing to read from a disk and nothing to age out. The other question — a reader that asks for a saved page's BYTES (an agent, today) — is answered the same way now. Such a body is re-read on every later revision that touches the file for exactly as long as that reader is READING it, because the wire's own per-key subscription is the lifetime: the server counts the readers holding each path, the first one starts the re-reads and the last one to leave ends them, and there is no capacity, no eviction and no number anywhere. It used to be the sixteen most recently OPENED paths across every reader at once, and the reason was an absence — the wire said when a reader opened a key and never when the last one let go, so "who is watching" was inferred from opens and aged out by capacity. What that cost, plainly: sixteen newer opens elsewhere could stop a body being refreshed for somebody who asked for one and was still holding it, and that reader then had **what the file said when it was asked for** until it asked again (stale, never wrong — a body only ever arrives from a read of that file). Both halves of that are gone: the seventeenth file somebody is reading the BYTES of is as live as the first, and a reader that stops asking stops costing re-reads at that instant instead of after sixteen newer opens have pushed its path out. (A person's open preview is not one of those readers and has not been since it stopped asking for bodies — that is the bullet above, and this one is about the readers that do ask.)
- **What that costs otherwise.** A page arrives one fetch later than a document's body does — the heading is drawn, the frame is created with the file's address already on it, and the file follows. Two readers of one file are two reads. And a `.html` that cannot be READ (not gone — unreadable) says so on the page, in the same words a `doc` reference says so on its line: *This file could not be read.* The route that could not open it still logs the disk's own sentence, and so does the body reader on the wire; the two tell one story. Which of the ways the file is unavailable is still not said — saying would describe the disk to anybody who can reach the port — but that it is served and will not open is. Before this, one unreadable saved page failed the whole probe and put a banner over the entire directory: quieter about the one file, and no longer the wrong blast radius.

## Validation

One validator checks the loaded set — on load and after every write. Nothing is checked anywhere else.

It runs in two stages, and the staging is part of the contract:

1. **Per line.** Everything a single record answers on its own: JSON, the record shape (required fields present, no unknown field, a mirror carrying nothing but its four), the id's spelling, ISO dates, the mark exclusion, and the repeat rule with the date it repeats from (all of them, per the rules below).
2. **Per set.** Everything that needs to know what else exists: uniqueness, references, cycles, documents, and the property values a key's declaration fences.

A file is decoded whole or not at all. The set-wide rules then run over the outlines that did parse, and one that did not costs **that outline and nothing else**: if the survivors are clean, the set loads with the broken file's errors carried inside it, shown in that outline's place while the rest stay live. If anything else is wrong, the set is refused and the parse errors are reported alongside it.

**That absorption is about LOADING, and a WRITE is refused instead.** The rule above exists so one hand-edited line cannot take a whole vault off the screen; applied to a file this software just produced it would mean the opposite — the caller told the write landed while the records left every page, and the repair somebody's text editor. So the write gate refuses any write whose own changed files will not decode ([architecture.md](architecture.md)), which is where every per-line rule reaches the ops layer at once: a `date` that is not a date, an `id` that is not a slug, two marks on one record, a `repeat` the grammar cannot read or one with no `date` under it. The refusal is a `validation` one carrying the validator's own rows — the code, the `file:line` and the message — so the rule has one wording however it was reached.

Guesses are still not reported. "`kitchen` is not a known id" is a guess when the line declaring `kitchen` is the one that failed to parse, so an unresolved `mirror`/`after`/`blocks`/`see` target is withheld while any outline is unreadable — and withholding one is itself a reason to refuse the set rather than serve nodes whose targets cannot be resolved. Nothing else can be invented by an unreadable file: `parent` may not cross files, so an unresolved one is refused whichever file the id was going to be in, and a duplicate or a cycle can only be *hidden* by a missing file. A report containing any per-line error says so, and a second round is expected after fixing the first.

The rules:

- ids: valid shape, unique across the whole set. The duplicate is reported on the *second* record, pointing at the first, which stays the one every reference resolves to.
- References resolve: `parent` (same file, must be a regular node, no cycles), `mirror` targets, `after`/`blocks`/`see` targets (any file). Unknown targets get a did-you-mean suggestion.
- `after` is acyclic (counting normalized `blocks`); mirror placement may not create a containment cycle — a mirror inside the subtree it shows would expand forever.
- Dates (the marks and `date`) are valid ISO; the four marks are mutually exclusive, and a record carrying two is refused whichever two they are. Validated as text, because a writer must reproduce what it read: a date-only `2026-08-10` round-tripped through an instant would come back a datetime.
- `repeat` is a rule the grammar holds, and the node carries a `date` for it to repeat from. Both are `bad-repeat`, and both are per-line for the reason the mark exclusion is: the whole question is on one line, and two branches that broke it between them would conflict in git rather than merging into a set nothing loads ([Repeating](#repeating)).
- `doc` resolves, against the naming outline's own directory, to an `.md` file that is actually served.
- Every property value fits what its key DECLARES, and every declaration in `_olai/Properties.olai` says a type the built-in table knows ([Typed properties](#typed-properties)). Both are `bad-prop`, and both name the key. A ref or a `node` value resolves a bare id across files, so the code is withheld while any file is unreadable — the same staging rule an unknown target gets, and a withheld finding still refuses the set.

There is deliberately **no rule about a mark and the children under it**, and the fourth mark added none: `set_cancelled` is not gated on the branch at all ([Status](#status)), so the format grew a word without growing a cross-line invariant. There was one — no stored derived state, which refused any mark on a node with children — and it existed only to keep a computed status and a written one from contradicting each other. Nothing computes one now, so it has nothing to defend: it dissolved with derivation rather than needing an exception ([Status](#status)). What replaced it is a pair of write-time gates and a nudge ([Status](#status)), which are the ops layer's policy and never a reason a set fails to load: a merge can write a mark in one branch and a task under it in another and both land cleanly, so this file has to read that set, and the next write through the ops layer is what fixes it.

## Errors

Every error names its location: `file:line` of the bad record (one node per line — the line is the whole story). Errors carry a kind — `usage`, `validation`, `not-found`, `busy` — surfaced as MCP tool errors and HTTP codes, with structured detail (e.g. a `validation` refusal carries the validator's own rows as data, not prose). There were five: `derived` refused a write that would have stored a computed status, and went when derivation did.

## Writing

The server is the only writer; git merges are the only edits that bypass it, and validation on load catches those. A write goes: re-validate the whole edited set → same-directory temp file(s) → atomic rename (all files or none) → commit. Validation comes FIRST, over the set the write would produce, so a refused write costs nothing on disk: the bytes are under names nothing reads, or they were never written at all.

Writers emit canonical field order, literal UTF-8 (no `\uXXXX` escaping beyond JSON's structural escapes), no blank lines, exactly one trailing newline. Readers tolerate blank lines.

**There is one writer, and callers do not assemble bytes.** A writer is handed the records of a whole file and hands back the whole file, so every separator — the newline between two records, the one at the end, the absence of a blank line — has exactly one owner. That is not tidiness: a caller that built its own bytes once produced two records glued onto one line, out of a write that every layer above believed had succeeded, and the file that came out was one no reader could parse. The shape is what makes it unrepresentable, and there is a test that says so.

**Absent has one spelling, and the writer is what enforces it.** An optional field holding nothing — `undefined`, `null`, `[]` or `""` — is not written, so `{"after":[]}` cannot reach a file however a writer arrived at it. Two files that mean the same thing must not differ byte for byte: the format's whole bet is that a line-based git merge is safe, and a conflict over `after: []` against no `after` is a conflict about nothing. A REQUIRED field is written whatever it holds, and the asymmetry is deliberate — dropping one produces a line the reader rejects outright, which is worse than handing an odd value to the validator that is about to see it anyway.

**A record is one line by construction**, not by care: a `desc`'s embedded newlines are escaped by JSON itself, which is the whole reason the format is JSONL rather than indented JSON.

**Sibling order is an insert, not a renumbering.** `ord` is a fractional index over base62, so a node placed between two neighbours mints a key that sorts between them and touches neither — a one-line diff, which is what keeps line-based git merges worth having. The one case with no answer is arithmetic rather than a gap: nothing sorts between `x` and `x0`, because every string above `x` begins with `x` and the least of those IS `x0`. The writer renumbers that row rather than guessing.

Because each node is one line with a stable id, plain line-based git merges are safe; a merge driver keyed by node id can be added later if concurrent-edit conflicts become painful.

## Relation to the Racket reference (PR #54 on `master-racket`)

PR #54 is the working reference implementation of this format — read it, don't extend it. Three of its features are deliberately **not** part of the new format: `include` records (glob or literal), the stored year→month journal scaffolding with day-titled nodes (replaced by the `date` field), and `.scrbl` docs.
