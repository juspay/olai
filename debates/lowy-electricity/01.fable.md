# Round 1 — fable (the package altitude)

The charter asks each of us to argue *for* the receptacle, and the article gives the argument its shape: the receptacle is not where code is long, nor where code is isolated — it is where a consumer would otherwise need an oscilloscope. My altitude is the package: the extraction worth a manifest, judged the way `@kolu/surface` was. Surface is the load-bearing precedent and it must discipline everything I claim: the wire's volatility (socket lifecycle, reconnects, stale tabs, heartbeats, frame shapes, subscription health) was encapsulated behind `defineSurface` **at one consumer**, and reuse arrived afterward, as the article says it does — encapsulation first, "a chance at reuse if something is encapsulated the same way in another system" second. Anyone who argues "no second consumer, no package" is arguing against the way this codebase's own foundation was built.

## First, the receptacles olai already has — the analogy built this codebase

Before proposing new sockets, name the existing ones, because they calibrate the bar. `@olai/git`: the supply side is *which git, and whether it can answer* — exit codes, locales (`LC_ALL=C`), prompts (`GIT_TERMINAL_PROMPT=0`), index semantics on refusal, `NoRepo` vs `Unusable` — and the socket (business verbs: state, dirty, show, last, commit-these-paths, push) has never been edited since extraction while all of that churned behind it. `@olai/log`: the supply side is *which face a line wears where* (TTY vs pipe, pretty vs logfmt, `NO_COLOR`, fiber-less callbacks) behind `Effect.log*`. `@olai/format`: the validator receptacle — every consumer plugs "is this set valid, what does it derive to" and none re-checks. And as of yesterday, `chat/src/interpret.ts`: the adapter's lies behind pure readers. Olai is not a codebase that needs convincing about the analogy; it is a codebase built out of it. The question is only: what still requires an oscilloscope?

## Candidate 1: `@olai/store` graduates to its own repo — olai's next surface

Run the four tests.

**The litany** (the AC/DC/voltage/phase equivalent): inotify vs kqueue vs polling; watcher events that lie and watcher events that never arrive (the settle delay, the slow backstop); stamp granularity — mtime+size cannot see a same-second same-length write, which is why the write gate re-reads what it wrote; the probe permit that serializes a write against a `git pull`; dot-directory and `node_modules` pruning (an unpruned probe does its most expensive work exactly when git is busy); staging-beside-destination and all-or-none rename; `EACCES`, vanished mounts, `ENOSPC` as a *third* error channel (`Codec.unreadable`); revision tagging and the per-publish change summary. That is a supply side as long as the article's power litany, and every entry has already churned at least once in this repo's history.

**The socket**: `open a directory; subscribe to validated snapshots; commit({baseRev, changes, afterPublish})`. Opaque — a consumer never sees an inotify event, a stamp table, or a rename. The socket has the receptacle property already: generic over content, caller-supplied codec, zero olai types (`packages/store/package.json` says a workspace sibling appearing there means "the seam has leaked").

**The domain test** — this is where the article's electricity example lands hardest. *Keeping a live, transactionally-writable view of a directory is real functionality, and it is not olai's domain.* Olai's domain is outlines, notes, days, marks. The store is the power company: what the house needs from it is a receptacle, and "using power in one house is indistinguishable from using it in another" — a live-directory store under a notes app is indistinguishable from one under any other files-as-truth tool. Architecture.md already says "extractable to its own repo later." The affirmative case is that *later* has the same shape surface's extraction had: the socket is stable, the supply side is where the remaining hard work lives (worker/browser FileSystem layers are already anticipated in its dev-dependency note), and the domain test passes with room to spare.

**The vault test**: today a store bug's shrapnel is contained — which is evidence the receptacle *works*, not that it is unnecessary. The prior debate's "isolation selects for stability" reading gets this backwards at package altitude, and I'll say it once because it applies to every candidate here: **a receptacle is *supposed* to look stable from the outside; socket stability is the product, not the absence of an axis.** The question is never "has the socket changed" but "what churns behind it."

## Candidate 2: the markdown rendering socket, re-argued

I conceded `@olai/markdown` in the kitchen-sinks debate on two grounds, and the article's frame dissolves one of them. The topic-bundle finding stands: `scale.ts` is theme vocabulary and leaves first — no receptacle bundles a second axis. But "no second consumer, no package" does not survive the electricity reading. The socket is *markdown in, sanitized HTML out*, and the supply side is demonstrated churn, not speculation: GFM footnotes with per-block id re-minting; the heading-anchor sanitizer-allowlist negotiation (`anchors.ts` records it); a *replaced-not-extended* grammar set (lowlight `common` + Nix); the media rewrite; titles unwrapped to phrasing content. Four consumers (notes, documents, titles, chat replies) already plug the same socket and none of them can see past it — that is the receptacle test passed *today*, inside one package. The oscilloscope question: a consumer without the socket would hold the sanitizer schema, the plugin order, and the chunk-loading rule in its own hands — which is precisely what the pipeline's one-pipeline invariant exists to prevent.

The honest altitude question remains — this receptacle exists and works as a *directory*; what the manifest adds is enforcement (the browser-boundary discipline `rewrite.ts`/`tags.ts` currently keep by convention) and the domain test's second half: rendering markdown safely is functionality that is not olai's domain. I argue the package; I expect opencode to argue the module and I will sign that as the floor if the panel prefers it. What I will not re-sign is the prior debate's reasoning that the pipeline's stability disqualifies it — by that reasoning the wall socket disqualifies itself.

## What I sign at the other altitudes

- **Module (opencode's)**: `interpret.ts` is the shipped exemplar; the Edit union (`surface/src/edit.ts` + `server/src/edit.ts`) is the live one — one closed union, every verb a new arm, compile errors as the shrapnel-catcher. And `format`'s `changesOf` (two readings of a set → what changed, no git in it) is a small receptacle nobody names.
- **Upstream (grok's)**: precompress stays dead as ruled — "a receptacle you plan to delete is not a receptacle" holds; the plan *is* the upstream receptacle (`buildSurfaceClient` emitting siblings). The candidate I hand grok affirmatively: **attachment chunking** (`surface/src/attach.ts` — bounded frames because an oversized frame closes the socket and takes every subscription with it) is wire-physics, not olai — it is the same kind of thing `serveSurfaceApp` took, and every surface app that ever uploads a byte will re-derive it.

## The claim to beat

Olai's next receptacle at package altitude is the store's graduation, with the markdown socket behind it. Both pass all four tests with the litany written out; neither depends on a hypothetical consumer; and the precedent that governs both is the one the human named: kolu's surface came out of exactly this thinking, extracted at one consumer, stable at the socket, churning behind it ever since.
