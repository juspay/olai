# OpenCode, as a chat agent

The ACP engine olai **finds**. Put [opencode](https://opencode.ai) on this server's agent search path and chat offers it as **OpenCode**. When it is missing, its enabled plugins row moves to **Needs you** with installation advice and a link. It is not offered in the agent menu while it is missing. After installing it, switch the plugin off and on to probe again without restarting olai. Olai ships no pin or adapter override for it; `OLAI_AGENT_PATH` (defaulting to the server's `PATH`) selects the build.

This page is one engine's own account of itself. What a conversation IS — how you choose an agent, what a turn looks like, which conversation you come back to, what the servers strip says — is the same for every engine and is [chat.md](../chat.md).

## How olai finds it

A probe for a runnable `opencode` on the **agent search path**, spawned as `opencode acp` with the served directory as its working directory.

There is no `--cwd` on the command line: opencode 2 removed the flag and answers it with its usage text, which is not ACP. The child's own working directory is the one opencode reads for *which sessions this directory has* as well as for where to run — `session/list` now filters by the request's `cwd` of its own accord, and olai still filters the answer on its own side, because a client that stopped checking would be trusting an agent to keep doing something it only started doing in this major version.

**Olai's PATH is not your shell's.** Run as a systemd user service (the home-manager unit) olai inherits neither your profile nor your login shell, so an `opencode` you can run in a terminal is not necessarily one this process can see. `OLAI_AGENT_PATH` is where to say otherwise; set, it REPLACES the search path rather than adding to it.

Turn this row off with `on: no` on the `opencode` node in `_olai/Settings.olai`, or its durable switch on the plugins panel. The row stops probing and its browser contribution is withdrawn.

## Which opencode

**OPENCODE 2 ONLY. The 1.x line is not supported**, and that is a statement about correctness rather than about effort. Every reading below was captured live against **opencode 2.2.7** (2026-11-11), and the old line answers three of them the other way round: it put the tool's name at the head of the call id (`bash:0`), announced every MCP tool as `<server>_<tool>`, and held a mid-turn prompt behind the running turn instead of taking a steer. A reader written for 2.2.7 does not merely go blind on 1.x — it would be WRONG, which is the direction nothing in olai is allowed to fail in. So there is no dual leg and no shim: a 1.x `opencode acp` matches nothing this engine knows, which means every call is unnamed, every permission question reaches a person, and nothing is ever auto-approved. It will work, in the way a conversation with a stranger works.

## What is only true of this wire

Each reading is safe to lose in one direction only — an agent that says none of it matches nothing, and what happens then is that **a person is asked**.

- **the tool's name is a FIELD ON THE FRAME.** `tool_call`, `tool_call_update` and the `toolCall` of a permission request all carry `name` beside `title` — `shell` (the builtin is `shell`, not `bash`), `execute`, `subagent`, `read` — and the three agree. The `toolCallId` is an opaque `chatcmpl-tool-<hex>` and says nothing (a child session's is that behind the child's own session id), so a reader still splitting it would name a call after a hash. The `title` is display text and MOVES over a call's life — `shell` while it starts, `sleep 20` once the command is known, and a child's titles carry the child's own title in front of them (`Summarise note.txt: read`) — so it is never what a row is named by.
- **olai's own tools never arrive as tool calls at all.** opencode 2 hands every MCP tool to the model as **Code Mode**: one `execute` call whose `rawInput.code` is JavaScript against a `tools.<server>.<tool>` object — `return await tools.olai.outlines_done({ id: "n1" })` — and whose completion reports what it actually ran in `rawOutput.metadata.toolCalls` (`{ tool: "olai.outlines_done", status, input }`), with `metadata.error: true` when anything threw or was refused. The script's RETURN VALUE comes back as a `content` text block, and that is where olai reads a tool's answer from: there is no `structuredContent` and no `output` on this wire. `tools` also carries opencode's own builtins, under `tools.opencode.*`.
- **one `execute` can be several calls, and the row names every one of them.** Three `tools.olai.*` calls in one script is an ordinary thing for a model to write, so a row that could only name a script that ran exactly one would lose the friendly title, the outline link and the write story for the commonest case there is. The row is COMPOSED instead: each call's advertised title on one line (*Read a node · Mark done*), and the engine's own `execute` under the fold. What the completion REPORTED beats what the script said it would do, for the same reason a frame beats a guess. What a batch does NOT get is the **reply**, and with it the outline link and the write story that are drawn off it — a Code Mode script returns ONE value and which of three calls it belongs to is said nowhere, so a row drawing them would be filing one answer under three questions. Nor is a script whose calls are not ALL servers olai handed named at all, because a row naming two of the three calls a script made is a row claiming the third did not happen.
- **the auto-allow rule is written over the SCRIPT, and it is the one thing about this engine that must not be written loosely.** Every MCP tool — olai's own, a foreign server's, opencode's builtins — is dispatched through `execute`, so the `name` on a permission request is `execute` for all three and the only thing that tells them apart is the code. And **ONE APPROVAL COVERS THE WHOLE SCRIPT**: opencode asks once per inner tool call and sends THE SAME FRAME each time — the three requests a three-call script produced were byte-identical in every field, differing only in the JSON-RPC request id — so answering one of them is answering all of them and nothing says which one you answered. Four conditions, every one of them positive, and any one missing means a person is asked:
  1. the request is about an `execute` — a `shell`, a `subagent`, a `read`, an unnamed call, anything else, is a person's;
  2. its `rawInput.code` PARSES under a closed grammar (`src/script.ts`): a sequence of `tools.<server>.<tool>(literal)` calls, optionally bound to names and returned. Anything else — a comment, a string literal, an operator, a variable argument, a template, a property read, a `Promise.allSettled`, any token the grammar has no rule for — means the script has NOT been read, and is a person's. SCANNING FOR WHAT LOOKS FAMILIAR WAS TRIED AND IS UNSOUND: `await tools.olai.read({}); return await globalThis.tools.opencode.shell({command:"rm -rf ~"})` reads as "one olai call" to a scan, as does a mention of one of olai's tools inside a comment or a string. Every one of those is outside the grammar now, and each is a unit case;
  3. it calls at least one tool, and EVERY server it names is one olai handed this session — olai's own, plus whatever optional server answered this session's probe. `tools.opencode.*` is never one of those. A server whose name is not a JavaScript identifier is reached as `tools["xyne-spaces"]`, which the grammar accepts for a LITERAL key and for nothing else (opencode spells a hyphenated server with its hyphen in the table, captured);
  4. the request offers an allow-flavoured option.
- **permissions are allow-first.** The options arrive as `once`/`always`/`reject` with kinds `allow_once`/`allow_always`/`reject_once`, where the Claude adapter's ordinary list leads with the refusal — so the rule is read off each option's own `kind` and never off its position. A rejected inner call does not fail the turn: the `execute` completes with `Permission.DeclinedError` as its content and `metadata.error: true`, and the model reads that as the answer it got. A script that calls no tool is never asked about at all.
- **opencode CAN be interrupted, and will not queue.** `initialize` answers `_meta.steering.supported: true`, so the composer draws the interrupt gesture from a positive handshake fact; `_session/steering` answers `{"outcome":"injected"}` when the words went into the running turn and `{"outcome":"promptRequired","reason":"noRunningTurn"}` when there was no turn to put them in. Those are the only two outcomes in the binary. The other half has to be read with it: a second `session/prompt` while a turn runs is REFUSED — `-32603 "Session already has an active ACP prompt: <sessionId>"` — so nothing here promises that a mid-turn message waits its turn, and olai does not send one: **with steering advertised and no queue, an ordinary send while this agent is busy IS the steer**, and the words reach the turn in flight. The refusal is reached only when the steer was not taken — the turn ending in the same instant — and then the words come back on the row with *send again* under them and the next send lands as an ordinary first message.
- **its subagents are real child sessions, and they draw behind doors of their own.** The spawning call is `name: "subagent"`, kind `think`, `rawInput: { agent, description, prompt }` — so the row that sent an agent out says which agent and what it was sent to do from its first titled frame. Its completion carries `rawOutput.metadata.sessionID`, and that is the ONLY frame that does: the in-progress updates carry `rawOutput: null` (captured twice), so nothing joins the spawning row to the child's lane until the child is over. The consequence is visible and is the honest cost: while a subagent is out there are TWO live rows for it — the `subagent` call in the main agent's column, with its rail saying an agent is out, and the child's own card with its door — and they are not merged, because merging them at the end would make a row a person was reading disappear. The child's own work arrives on a notification of opencode's own, `opencode/session/child_update`, carrying `{ rootSessionId, childSessionId, parentSessionId, depth, title }` and either a `status` (`created`, `running`, `completed`, `interrupted`, `failed`) or a nested `update`; at depth 2 the root stays the root and `parentSessionId` becomes the first child's. **ASKED FOR, OR IT DOES NOT HAPPEN**: opencode sends these only to a client whose `initialize` advertised `clientCapabilities._meta["opencode/child-session-updates"]`, and `agentCapabilities._meta` says it will. Without the opt-in a child's frames are flattened into the parent's stream with no `created`/`completed` pair anywhere, so the opt-in is not an optimisation — it is the difference between lanes and a flat fan-out. One thing has to be corrected on the way past: a permission request about a CHILD's call arrives stamped with the ROOT session, because that is the connection opencode is asking on, while the call itself carries `_meta["opencode/child-session"]`. Left alone, a child's question would be drawn in the main agent's name, so it is re-stamped with the child's session here rather than branched on in the panel. A REOPENED conversation has none of this: `session/load` replays the `subagent` call and its report and nothing on the channel, so a stored fan-out comes back as the record of the delegation with no lane.
- **there is no bypass mode.** `session/set_mode "bypassPermissions"` is refused (`-32602 mode not found`); the modes are `build` and `plan`. Unattended auto-approval for opencode lives in its own `opencode.json`, outside ACP — olai answers what it is asked and never widens what it answers.
- **a failure inside a turn is LOUD.** A provider opencode cannot reach is a JSON-RPC error on `session/prompt` — `-32603 "Internal error: Insufficient balance…"`, with `data: { service: "session", errorName: "provider.quota" }` — not a quiet successful end of turn. The turn ends with the agent's own words on the banner and the message marked undelivered, like any other that did not land.
- **its picker offers the ids it reports**, so the agent line names a model with the picker's own label (`opencode/claude-sonnet-5` under *opencode/Claude Sonnet 5*) and needs no alias arithmetic. `session/new` offers three entries — `model`, `effort` (the thought level) and `mode` (`build`, `plan`) — and `session/set_config_option` answers with the updated `configOptions` in the RESPONSE rather than pushing anything, for the model and for the mode alike.
- **its `session/list` rows are the protocol's four fields** — `sessionId`, `cwd`, `title`, `updatedAt` — and no `_meta` corner on a row. It answers the WHOLE directory in one page: a `limit` is ignored and the `nextCursor` beside the rows answers zero rows when it is followed (captured over three stored conversations). Olai sends no limit and follows no cursor, which on this version loses nothing.
- **signing in is something you do in a terminal, and olai shows you the line.** Its one method is `opencode-login`, offered as a `terminal` kind — the kind olai normally runs for you. It cannot run this one. opencode's login is an interactive wizard: `opencode acp --login` and `opencode auth login` both answer *Pass an integration ID or name when running without an interactive terminal* and exit 1 the moment they find no TTY, and `auth login <target> --method key` answers *API key input requires an interactive terminal* — `--answer` fills a provider's form, never the key itself (captured against 2.2.7). A sign-in card is a pipe and a paste box, so **no button is drawn**: the card names the method and the exact command, with the binary the probe found in front of it as an absolute path — `/nix/store/…/bin/opencode auth login --standalone` — because the bare `opencode` its own `_meta` corner asks for is not on this server's `PATH` and, on a deploy where the engine was reached through `OLAI_AGENT_PATH`, is not on your shell's either.
  - **`--standalone` is in that line on purpose.** The credential store is `$XDG_DATA_HOME/opencode/opencode.db` (`~/.local/share/opencode/`), and `--standalone` is the path PROVEN to write where the `opencode acp` olai spawns reads: a dummy OpenRouter key connected that way makes `session/new` offer `openrouter/*` models to a freshly started `acp` in the same home, where before it offered 12. The default path goes through opencode's per-machine background service on `127.0.0.1:49374`, a singleton that cannot be stood up twice and so could not be tested in isolation; whether what it stores is what `acp` reads is unproven here.
  - **Then put the chat to sleep and open it again.** An `opencode acp` reads its credentials when it starts and never again — a NEW session inside the running process does not see an account connected after it started, which is why *Fresh start* on the same engine is not enough. *Put to sleep* (the Chats row's `•••`, the node's row menu, ⌘K) is the one gesture that ends the process and keeps the chat; opening the chat again continues it on a new one. The card says so.
- **no harness memory built in.** opencode's memory is opt-in plugins, and olai installs none — the node's subtree is the only memory.

## Where to get it

<https://opencode.ai>, then make sure it is on the PATH the olai **server** has.

It declares no MCP prefix, and that is structural rather than an omission: an MCP tool's name on this wire is a path inside a script (`tools.<server>.<tool>`), not a word at the head of a call's own name, so there is no spelling to hand anybody. The leg reads a tool's answer out of the `execute` completion's own content block.
