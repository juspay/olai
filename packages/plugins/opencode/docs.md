# OpenCode, as a chat agent

The ACP engine olai **finds**. Put [opencode](https://opencode.ai) on this server's agent search path and chat offers it as **OpenCode**. When it is missing, its enabled plugins row moves to **Needs you** with installation advice and a link. It is not offered in the agent menu while it is missing. After installing it, switch the plugin off and on to probe again without restarting olai. Olai ships no pin or adapter override for it; `OLAI_AGENT_PATH` (defaulting to the server's `PATH`) selects the build.

This page is one engine's own account of itself. What a conversation IS — how you choose an agent, what a turn looks like, which conversation you come back to, what the servers strip says — is the same for every engine and is [chat.md](../chat.md).

## How olai finds it

A probe for a runnable `opencode` on the **agent search path**, spawned as `opencode acp` with the served directory as its working directory.

There is no `--cwd` on the command line: opencode 2 removed the flag and answers it with its usage text, which is not ACP. The child's own working directory is the one opencode reads for *which sessions this directory has* as well as for where to run — `session/list` now filters by the request's `cwd` of its own accord, and olai still filters the answer on its own side, because a client that stopped checking would be trusting an agent to keep doing something it only started doing in this major version.

**Olai's PATH is not your shell's.** Run as a systemd user service (the home-manager unit) olai inherits neither your profile nor your login shell, so an `opencode` you can run in a terminal is not necessarily one this process can see. `OLAI_AGENT_PATH` is where to say otherwise; set, it REPLACES the search path rather than adding to it.

Turn this row off with `on: no` on the `opencode` node in `_olai/Settings.olai`, or its durable switch on the plugins panel. The row stops probing and its browser contribution is withdrawn.

## Which opencode

**OPENCODE 2 ONLY. The 1.x line is not supported**, and that is a statement about correctness rather than about effort. Every reading below was captured live against **opencode 2.2.7** (2026-11-11), and the old line answers three of them the other way round: it put the tool's name at the head of the call id (`bash:0`), announced every MCP tool as `<server>_<tool>`, and held a mid-turn prompt behind the running turn instead of taking a steer. A reader written for 2.2.7 does not merely go blind on 1.x — it would be WRONG, which is the direction nothing in olai is allowed to fail in. So there is no dual leg and no shim: a 1.x `opencode acp` matches nothing this engine knows, which means every call is unnamed, every permission question reaches a person, and nothing is ever auto-approved. It will work, in the way a conversation with a stranger works.

## What is only true of this wire

Each reading is safe to lose in one direction only — an agent that says none of it matches nothing, and what happens then is that **a person is asked**.

- **the tool's name is a FIELD ON THE FRAME.** `tool_call`, `tool_call_update` and the `toolCall` of a permission request all carry `name` beside `title` — `shell` (the builtin is `shell`, not `bash`), `execute`, `subagent`, `read` — and the three agree. The `toolCallId` is an opaque `chatcmpl-tool-<hex>` and says nothing (a child session's is that behind the child's own session id), so a reader still splitting it would name a call after a hash. The `title` is display text and MOVES over a call's life — `shell` while it starts, `sleep 20` once the command is known, and a child's titles carry the child's own title in front of them (`Summarise note.txt: read`) — so it is never what a row is named by.
- **olai's own tools never arrive as tool calls at all.** opencode 2 hands every MCP tool to the model as **Code Mode**: one `execute` call whose `rawInput.code` is JavaScript against a `tools.<server>.<tool>` object — `return await tools.olai.outlines_done({ id: "n1" })` — and whose completion reports what it actually ran in `rawOutput.metadata.toolCalls` (`{ tool: "olai.outlines_done", status, input }`), with `metadata.error: true` when anything threw or was refused. The script's RETURN VALUE comes back as a `content` text block, and that is where olai reads a tool's answer from: there is no `structuredContent` and no `output` on this wire. `tools` also carries opencode's own builtins, under `tools.opencode.*`.
- **one `execute` can be several calls, and a batch is drawn as the batch it is.** Three `tools.olai.*` calls in one script is an ordinary thing for a model to write, and a row has one title, one outline link and one reply. A row that named itself after the first of the three would be claiming to be a third of what ran, and the fold under it would show one answer out of three. So olai names a row for one of its own tools only when the `execute` names EXACTLY ONE of them — what the completion REPORTED beats what the script said it would do, for the same reason a frame beats a guess — and everything else is drawn as the plain `execute` it is, with its whole script as the row's detail and its whole returned value in the fold.
- **the auto-allow rule is written over the SCRIPT, and it is the one thing about this engine that must not be written loosely.** Every MCP tool — olai's own, a foreign server's, opencode's builtins — is dispatched through `execute`, so the `name` on a permission request is `execute` for all three and the only thing that tells them apart is the code. And **ONE APPROVAL COVERS THE WHOLE SCRIPT**: opencode asks once per inner tool call and sends THE SAME FRAME each time (a script with three calls produces three identical requests), so answering one of them is answering all of them. Four conditions, every one of them positive, and any one missing means a person is asked:
  1. the request is about an `execute` — a `shell`, a `subagent`, a `read`, an unnamed call, anything else, is a person's;
  2. its `rawInput.code` is a string olai can read EXHAUSTIVELY. The grammar is the narrow one — `tools` as a whole word, a dot, an identifier, a dot, an identifier — and a script that reaches the table any other way (`tools[name]`, a destructured `const { ping } = tools.olai`) is a script olai has NOT read all of. That is not a parser being fussy: an approval it could not read in full is an approval of the call it could not see;
  3. it names at least one tool, and EVERY server it names is one olai handed this session — olai's own, plus whatever optional server answered this session's probe. `tools.opencode.*` is never one of those;
  4. the request offers an allow-flavoured option.
- **permissions are allow-first.** The options arrive as `once`/`always`/`reject` with kinds `allow_once`/`allow_always`/`reject_once`, where the Claude adapter's ordinary list leads with the refusal — so the rule is read off each option's own `kind` and never off its position. A rejected inner call does not fail the turn: the `execute` completes with `Permission.DeclinedError` as its content and `metadata.error: true`, and the model reads that as the answer it got. A script that calls no tool is never asked about at all.
- **opencode CAN be interrupted, and will not queue.** `initialize` answers `_meta.steering.supported: true`, so the composer draws the interrupt gesture from a positive handshake fact; `_session/steering` answers `{"outcome":"injected"}` when the words went into the running turn and `{"outcome":"promptRequired","reason":"noRunningTurn"}` when there was no turn to put them in, which falls back to an ordinary prompt because that is what the person meant. Those are the only two outcomes in the binary. The other half has to be read with it: a second `session/prompt` while a turn runs is REFUSED — `-32603 "Session already has an active ACP prompt: <sessionId>"` — so nothing here promises that a mid-turn message waits its turn. A plain send into a running turn comes back as the refusal it is, on the row keeping your words, with *send again* under it; the interruption is the gesture that gets words into the turn in flight.
- **its subagents are real child sessions, and they draw in lanes.** The spawning call is `name: "subagent"`, kind `think`, `rawInput: { agent, description, prompt }` — so the row that sent an agent out says which agent and what it was sent to do from its first titled frame — and its completion carries `rawOutput.metadata.sessionID`. The child's own work arrives on a notification of opencode's own, `opencode/session/child_update`, carrying `{ rootSessionId, childSessionId, parentSessionId, depth, title }` and either a `status` (`created`, `running`, `completed`, `interrupted`, `failed`) or a nested `update`. **ASKED FOR, OR IT DOES NOT HAPPEN**: opencode sends these only to a client whose `initialize` advertised `clientCapabilities._meta["opencode/child-session-updates"]`, and `agentCapabilities._meta` says it will. Without the opt-in a child's frames are flattened into the parent's stream with no `created`/`completed` pair anywhere, so the opt-in is not an optimisation — it is the difference between lanes and a flat fan-out. One thing has to be corrected on the way past: a permission request about a CHILD's call arrives stamped with the ROOT session, because that is the connection opencode is asking on, while the call itself carries `_meta["opencode/child-session"]`. Left alone, a child's question would be drawn in the main agent's name, so it is re-stamped with the child's session here rather than branched on in the panel.
- **there is no bypass mode.** `session/set_mode "bypassPermissions"` is refused (`-32602 mode not found`); the modes are `build` and `plan`. Unattended auto-approval for opencode lives in its own `opencode.json`, outside ACP — olai answers what it is asked and never widens what it answers.
- **a failure inside a turn is LOUD.** A provider opencode cannot reach is a JSON-RPC error on `session/prompt` — `-32603 "Internal error: Insufficient balance…"`, with `data: { service: "session", errorName: "provider.quota" }` — not a quiet successful end of turn. The turn ends with the agent's own words on the banner and the message marked undelivered, like any other that did not land.
- **its picker offers the ids it reports**, so the agent line names a model with the picker's own label (`opencode/claude-sonnet-5` under *opencode/Claude Sonnet 5*) and needs no alias arithmetic. `session/new` offers three entries — `model`, `effort` (the thought level) and `mode` (`build`, `plan`) — and `session/set_config_option` answers with the updated `configOptions` in the RESPONSE rather than pushing anything, for the model and for the mode alike.
- **its `session/list` rows are the protocol's four fields** — `sessionId`, `cwd`, `title`, `updatedAt`, with a paging cursor beside them — and no `_meta` corner on a row. Its rows say as much about a conversation as the protocol alone says.
- **no harness memory built in.** opencode's memory is opt-in plugins, and olai installs none — the node's subtree is the only memory.

## Where to get it

<https://opencode.ai>, then make sure it is on the PATH the olai **server** has.

It declares no MCP prefix, and that is structural rather than an omission: an MCP tool's name on this wire is a path inside a script (`tools.<server>.<tool>`), not a word at the head of a call's own name, so there is no spelling to hand anybody. The leg reads a tool's answer out of the `execute` completion's own content block.
