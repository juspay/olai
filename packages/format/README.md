# @olai/format — the format, and the only place it is enforced

The format core ([docs/format.md](../../docs/format.md)): `parseOutline` per file, `validate` per set, and the derivations — sibling order, tags, mirror expansion, the rollup a parent displays, what is dated a given day, what is overdue as of one — that both the validator and the view read from. It is the bottom of the layering: it knows about records, files and rules, and nothing about disks, servers or browsers.

Nothing outside these two functions may reject an outline. Not the reader, not the store, not the web layer. A second interpretation of the format would be free to disagree with the one that decides whether a file is legal at all.

## Which files a served directory is made of

`src/kinds.ts` is the one table that says it: a kind per row, each with the suffixes that claim a file, whether its content is a tree of RECORDS the validator judges, a BODY OF TEXT carried verbatim, or BYTES nothing here reads at all; whether the loaded set KEEPS that content or only the path; and whether the READER'S OWN BROWSER fetches the bytes off `/media/` rather than being handed the content. `fileKind` reads it, and so does everything downstream — the store's walk is handed it as `match`, the codec decodes by it, the set sorts decoded files by it, and the client's sidebar, glyphs and routes are `Record`s over the union it exports. It was four spellings before, which is what made the outline rename (PR #177) and the file glyphs (PR #174) each a hunt; a new kind of served file is now one entry here, and the type checker names every surface that owes it a drawing. `packages/tests/kinds.test.ts` holds both halves as sweeps: nothing outside this file decides by spelling a suffix, and every registered kind is drawn everywhere kinds are drawn. Four exports hand out the SPELLING rather than the verdict, for the callers that cannot ask a function — `OUTLINE_EXT` and `DOCUMENT_EXT` for the ops layer's path mints, `SVG_EXT` for the one rule that has to subtract a single suffix from a kind (markdown may point at a picture and deliberately not at an SVG), and `FILE_EXTS` for the click handler `@olai/surface` puts inside a previewed page, which is text in a template literal running in a frame that imports nothing and still has to know which links name a file olai has a page for — every suffix of every kind, since all of them have a page. `stemOf` is the same table asked one step further: the file's NAME with the suffix that claims it taken off, and the bare name for a file no kind claims. Two callers were answering that for themselves with opposite rules — a commit subject spelling the outline suffix and leaving every other name whole, a daily note cutting at the last dot and so answering `READM` for `README` — and they agreed on outlines and nowhere else, so neither could absorb the other. `src/stem.test.ts` holds both retired rules beside the one that replaced them and shows, row by row, that on every name the two disagreed about the merged answer is *one of the two* — never a third reading — and that it is the one belonging to whichever caller can reach that name: the daily-note rule for a `.md`, the commit-subject rule for a name no kind claims. What no caller passes is the row where the merged rule would have moved it.

The table holds only what EVERY kind has an answer to. A fact one kind has — where an archive goes, which files a `doc` may point at, what a day's note is named — stays with that kind's rule, because a column that is empty for most rows is a union wearing a table's clothes.

A PICTURE is the one kind claimed by more than one suffix, and that is what the list is for rather than a convenience: `.png` and `.webp` are two encodings of the one thing olai does with either, which is draw it in an `<img>`, so they are one row owing one glyph, one face and one noun. `.htm` is still deliberately not a second spelling of hypertext — one spelling per kind where the kind really has one — and every suffix is matched exactly as written, so `IMG_1234.JPG` is a file olai walks past.

`kept` is the third column, and what it decides is what one loaded directory COSTS. `unkept(path)` is how every layer asks it — the same move `bodyKind` is one row up, so nobody derives it in two steps of their own. An outline's records are the set and a document's text is what a conditional write is judged against, so both are kept; the four kinds olai only SHOWS are not — nothing validates one, no op writes one, and a saved page with its pictures inlined, or the pictures themselves, is megabytes. So the set keeps the path and the content is read when a reader opens it (`@olai/store`'s `Codec.byName` is how the probe is told not to read it at all, and `@olai/server`'s `bodies.ts` is what reads the ones that are text). That is why `Document.text` is nullable: `null` is a state — *this file is served and its body is not here* — and never an empty file.

`fetched` is the fourth, and it is the one question the other three cannot answer between them: WHERE a reader's copy comes from. Hypertext, a picture and a `.pdf` are drawn by pointing a frame, an `<img>` and an `<object>` at the file's own URL, so `/media/*` answers them (`isAsset` in `src/documents.ts` is that allowlist, and `@olai/server`'s `media.ts` is the route). A `.csv` holds text, is not kept, and is still `false`: its page is handed the file's text on the wire like a document's, so serving the raw bytes as well would be a second way to read a file that already has a page.

`src/csv.ts` is what a `.csv` SAYS: RFC 4180's grammar in one forward scan (a quoted field may hold a comma, a newline and a doubled quote; a blank line is not a row), squared off to the rectangle a table needs, and BOUNDED — on the scan itself rather than on a slice taken afterwards. Three axes, because a `.csv` can be enormous along three: rows, columns, and the length of one cell — the last being the one the others cannot cover, since a file that is one quoted field is one row and one column and both other bounds stay silent while the whole thing lands in a `<td>`. Past the row bound the scan runs on only far enough to answer *is there another row*, and stops at the first character that says yes; past the column bound a row's fields are consumed and not kept, since the quoting still has to be tracked to find where the row ends. So what it can report is `moreRows` / `moreColumns` / `longCells` and deliberately not a total: a total is a number only a full scan knows, and reading a million-row export to print a figure the bound exists to avoid reading is the defect wearing an honest sentence. `src/csv.test.ts` states the stopping as a property no timing test could — a five-thousand-column row and a two-hundred-thousand-character cell sit past the row bound, and both flags come back false because the scan never reached them. The sentence a reader is told is deliberately NOT here: it is the client's vocabulary (`@olai/web`'s `document/clamped.ts`), the way what a reader calls each kind of file is, and nothing else in this package writes a sentence for a person.

`src/set.ts` is what those decoded files amount to — one collection in path order, with the files that would not read holding their place — and three things about it are worth naming because callers kept building them. **The READINGS are held with the set they describe**: which outlines the directory serves (`outlinePaths`, and `outlineNames` for the callers that want a membership test), and which files hold nothing (`brokenBy`, which `brokenIn` is one key of). Each is a pure function of the set, built when somebody asks and kept against that set in a `WeakMap` — so a fold click that used to allocate a `Set` of every path and a map of every broken file per call costs a lookup, and a write that asks whether its file is writable at half a dozen gates asks once (`perf-homes-files`, `perf-batch-assemble`). A set is a VALUE, so there is no moment at which a held reading could describe a directory that has moved. **And `withDocuments` is the set with files written into it**, spliced into the order it already holds rather than re-assembled from a map — what the batch fold does between two ops, equal to `assemble(apart(set) + the written files)` by a differential over generated directories (`src/set.walks.test.ts`), and a binary search where that was a pass over every served path.

## What a place in the directory is CALLED

`src/address.ts` is the one grammar: **`[document]#[element]`**, with a branded half for each thing a name can be — a `DocumentPath` (a path whose suffix the table above claims), a `NodeId`, a heading `Slug`, and a written `Tag`. Three arms come out of it: a whole document (`Tasks.olai`, `notes/README.md`), a node (`#a1b2c3`, location-free, because an id survives renames and moves between files), and a heading inside a body (`README.md#install`).

What a `#` MEANS is read off the document in front of it — an outline has nodes and no headings, a body has headings and no nodes — which is why the document half insists on a suffix the registry claims, and why `Tasks.olai#a1b2c3` parses and NORMALISES to the bare node it names. `printAddress` is total over an address and `parseAddress` is total over any string, answering `null` for text that names no place: what reads one is an address bar, a title in `Pins.olai` that a hand and an agent are invited to edit, and an href written in somebody's note, and a throw out of any of those is a blank page rather than a bad address.

THREE SMALLER READINGS sit beside the grammar because a title and a URL are how an address is WRITTEN, and both are now read on two sides of a wire: `splitAddress` (path, query and fragment, cut fragment-first because a `#` ends a query), `linkedTitle` (a title written as one markdown link, cut into its two halves — the shape a named pin takes), its inverse `pinTitle` (the title a pin carries for a name somebody typed: the bare address for a blank one, a link around it otherwise, and a refusal rather than a mangling for words a label cannot hold — two WRITERS cut this too, the server resolving a `pin` and the browser renaming one) and `addressWritten` (the address a title carries, either way). Each was spelled once in the browser until the shelf's reading moved to the server (`shelf.ts`) and was about to spell it a second time. What is NOT here, and stays the browser's, is what the halves MEAN — which page a pathname opens, and that the query is a filter (docs/format.md's Pins).

It is HERE rather than in the browser because it is a statement about the directory, the same reason `kinds.ts` is — the design that rules it is [first-class-documents.md](../../docs/brainstorming/first-class-documents.md). What the browser adds is a slash in front of it and the pages that name nothing on disk (`@olai/web`'s `routes.ts`).

## Staged, and the stage is part of the answer

Validation is two phases, and the seam is load-bearing rather than tidy.

`parseOutline` sees one line at a time and checks everything a single line can answer alone — shape, id spelling, ISO dates, the two exclusivity rules. `validate` sees the whole set and owns every rule that needs to know what else exists: parents, mirror targets, `after` cycles, documents.

What `validate` ANSWERS with is a `Reading`: the set, the one `Derived` its rules were run over, and the LINKS INDEX over the set's own documents (`src/pointing.ts`, `perf-doc-backlinks-index` — what a link NAMES, backwards). Every rule needs the same indexes, so it builds them once and shares them — and used to drop them at the door, which meant the next reader of an approved set (the store publishing it, the planner judging the next keystroke) walked the corpus again for a value that had just been in hand. The three travel together for the reason `Derived` carries its own nodes: a caller holding one revision's set against another's indexes draws a plausible tree rather than failing. The links index is a member here rather than a thirteenth index inside the derivation because `derive` is handed the RECORDS and `patch` a delta of them — neither has ever been shown a face — while the set and the reading this one follows are exactly what is in hand at the one place a `Reading` is made.

A file is decoded whole or not at all. The set-wide rules then run over the files that DID parse, and what happens to the one that did not is the error scope (resolved 2026-08-09, and the reason `validate` is handed each file's `Result` rather than only the successes):

- if the survivors are clean, the set is accepted with that file's errors embedded in it (`OutlineSet.broken`). The browser renders them in that one outline's place and everything else stays live;
- if anything else is wrong, the set is rejected and the report carries the parse errors alongside whatever else was found.

Guesses are still not reported. "`kitchen` is not a known id" is a guess when the line declaring `kitchen` is the one that failed to parse — so `unknown-target` is withheld while any file is unreadable, and withholding one is itself a reason to reject the set rather than publish nodes whose targets are unresolvable. Nothing else can be *invented* by a missing file: `parent` may not cross files, so an unresolved one is refused whichever file it was going to be in, and a duplicate or a cycle can only be hidden by a missing file, never conjured. A report containing a per-line error says out loud (`reportStage`) that a second round is expected.

Within a phase, every rule runs and every error is collected. Stopping at the first would turn "fix this file" into a loop of load-fix-load, which is the workflow the format exists to remove.

An unknown reference is nearly always a misspelling, so an error about one ends with the closest declared id — within a typo's distance (`src/suggest.ts`: a third of the id's length, never less than two), and nothing further away, since a guess that is merely NEAREST teaches a reader to distrust the offer. That rule is exported (`didYouMean`, and `nearestId` for a caller that wants the candidate rather than the wording) for one reason: the ops layer refuses the same unknown `mirror` / `after` / `see` target one moment EARLIER, at the plan, and a second copy of the budget — or of the sentence — would let the write and the load disagree about what a typo is. The pair to reach for over IDS is `didYouMeanDeclared` / `nearestDeclared`, which answers the identical offer — ties included, held to the walk by a differential over generated corpora — over the MAP a derivation keeps them in: the offer is a nearest neighbour, so a stale tab replaying twenty refused edits used to walk the vault twenty times and a hand-edited file with a dozen dangling references paid it per write (`perf-didyoumean`). Held against that map, the candidates are bucketed by LENGTH and by the characters they are made of, and both of those are exact lower bounds on an edit distance — so what is ruled out could never have won, and what a burst costs is one pass over the ids for the revision rather than one per refusal. The plain pair stays for the candidates that are not a map: a directory's outlines, its documents, the handful of ids a capture is minting. `chainOf` (`src/errors.ts`) is the same argument about a LOOP: the validator names one it found on load, the ops layer names the one a write is about to close, and the arrow between the ids is written once — and `drawingPath` (`src/derive.ts`) is that argument one turn further, about the WALK rather than the wording. The containment graph `drawnFrom` was shared and the walk over it was not, so each rule that asked "would this placement expand for ever" wrote its own; three ask now, at three moments — the validator on load, the ops layer at the write (a new mirror, and a move that carries one into what it shows), and the move-to picker at the aim, before the key — and a rule that walked a shared graph its own way was a second answer with extra steps.

## The view is patched, not rebuilt

`validate` takes an optional second argument: the reading it FOLLOWS, and what has moved since (`Previous`). With it, the view its rules run over is the previous one with the changed files' entries swapped into the indexes — `src/patch.ts` — rather than a derivation of the whole corpus. What that costs is what the edit touched: a title edit dirties one record, and the reverse indexes (`mirrorsOf`, `edgesTo`, `namedBy`, `taggedBy`, `byDay`) say which placements, edges, blockers, referrers and DAYS elsewhere have to be looked at again. It is two orders of magnitude on a vault-sized directory, and `just bench` measures this patcher directly (`src/patch.bench.ts` — forty one-file edits over a generated 21,552-record vault, each to a different file, patched on the view the last edit left: **0.42ms against ~49ms rebuilt, a ~115×**, medians of several alternating runs — the rebuilt half moved with the tag index below, which widened the fold a rebuild pays, and again with the day index, which added one more: on the same machine and the same run that pair read 36.8ms before that index and 44.0ms after it, the fold's ~7ms landing where it was expected to. The patched half moved with `perf-patch-residue`, which is the two paragraphs after the next one). The browser used to fold the SAME function over the frames it received, and that is over: a tab holds at most the page in front of somebody, so the derivation runs on the server alone and the browser is handed a page's reading (`./src/page.ts`, and `docs/brainstorming/vault-in-browser.md`'s PR 10). What a FRAME cost a tab was a figure this README quoted beside the two above — 4.33ms for the fold, 4.44ms for the whole composition, on this same vault — and it is history now, along with the older pair (a frame 64ms against 330ms) from the slice-4 harness this tree no longer carries. What replaced it is a wire measurement rather than a fold one: the same reading session over a 40-outline vault costs a first frame of 135 kB where it cost 1,679 kB (`packages/tests/wire.ts`). One generated vault feeds the legs that quote one (`src/fixtures.testlib.ts`'s `vaultOf`, shared with `src/vocabulary.bench.ts` and `src/dates.bench.ts`), so their numbers are about one directory. That vault gained PROSE with the backlinks index — a note on every fifth record, every tenth naming another by its `@id` — and `#tags` in the titles when that index gained the second sigil, and DATES with the day index (a quarter of the records, half the SETTLED ones — `done` since that index, `cancelled` since the fourth mark — carrying the instant they were settled at, spread over two years: 6,517 dated records over 637 days), because a corpus with no notes in it measures none of what a derivation does with notes, a corpus whose titles hold no `#` measures the sigil nobody writes, a corpus where nothing is scheduled measures no day at all, and a new index that nothing exercises prints as *costs zero* when what it printed was *was never asked*. All of them are counted rather than drawn, so the corpus stays one directory (981 files, 21,551 records) and the added work is the only thing that moved. It moved by a record when `cancelled` went in — the marks are drawn from one stream, so a fourth draw shifts it — and `src/vault.test.ts` is the fence that makes those numbers a checked fact rather than a claim beside them.

**There are TWO doors onto that pair without the rules, and they differ by who is making a claim.** `reading(set, previous?)` is `validate`'s first line and its last with the six whole-set rules taken out from between them, for a reading that is speculative and validated once, later — and its guard, `isSet`, walks the corpus to check that the view a delta produced really is a view of the set in hand. That guard is worth the walk when the two halves came from different places: the store's set is a directory of decoded files and its delta is a probe's claim about which of them ticked, and a delta that missed a file makes every record look like a duplicate of itself. `following(read, written)` is the other door, for the caller that is WRITING files into a reading it holds — `@olai/ops`' batch fold, which plans op two against the set op one would leave. It builds both halves out of the one argument, so there is no second source to disagree with the first, and what it checks is what it did: the written records are filed under the written paths, in that order. That is `perf-reading-patched-check`, and what it took out was the one per-op cost the batch work before it left scaling with the VAULT rather than with the op — measured as **zero records read per write against 2,496 over a 500-file directory** (`src/validate.walks.test.ts`, which tripwires the records themselves, since a walk is measured by asking the things it walks over), and **1.6–2.0× on the whole door** — the `one op's DOOR` row of `@olai/ops`' `walks.bench.ts`, six alternating runs over the 980-outline vault, which read 0.27ms/0.17ms checked-against-carried on a quiet machine and 0.82ms/0.50ms on a busy one. The ratio is the claim and the absolute pair is one machine's mood, which is the paragraph two below this one arriving early. The equality is a differential rather than a paragraph: the batch's reference fold still comes through `reading` with the full guard, and `@olai/ops`' `following.equivalence.test.ts` holds the two to one another — set, grouping and id table — at every op of a scripted every-op run, and asserts of each arm outright that its view is a view of its own set.

**That claim was false for a whole review cycle, which is why `src/vault.test.ts` now exists.** The first spelling put the mention on `which % 25 === 0` inside a loop that runs `which` from 1 to 20, so it never fired: 3,920 notes, not one `@`, `taggedBy` empty, and the patcher's own `keys.size === 0` early return firing on every bench edit — under a paragraph saying the opposite. A reviewer derived the corpus and counted. The fence asserts, at the size the benches run, that every index they print a number about has something in it; a fixture that quietly stops producing one now fails a test rather than a sentence.

**The absolute numbers are one machine's and the ratios are the claim.** These were re-measured on a slower, busier box than the ones they replaced, and the run-to-run spread on the patch arm alone is 0.71–1.12ms across four runs — which is why the pair is reported as a ratio and why `patch.bench.ts` is a leg somebody runs rather than a lane that fails on a busy machine.

The copy-on-write is where the patch's own cost sat, and `src/overlay.ts` is what it costs now. Every index a patch changes used to be cloned so that the revision a reader is holding cannot move under them — one `new Map` per index per edit, one entry per key in the directory for the largest of them. Seven of them are LAYERS now — the entries this edit changed and the keys it dropped, over the map the last patch left standing — with the same answers, the same size and the same key order, which is not a detail, because the did-you-mean behind every unknown-target error walks `byId`'s keys and four of them promise a key order of their own. Nothing above it knows: sealing a layer answers with a `ReadonlyMap`, and it flattens back into a plain one when it has grown past half the map.

**WHICH seven is decided by the index's READERS, and that rule is what the second round of this work bought.** The first layer kept its base's key set exactly, so `size`, `has` and `keys` were the underlying map's own answers and cost nothing — and the price was that only `byId` could have one, since a patch DROPS keys from the others (a tag nothing writes any more has to leave `taggedBy` rather than stand there empty). This file used to say so and stop there, which was a fact about the layer as built and not about layers. A tombstone set beside the changed values is what it costs to say properly, and it is paid per READ — so the question became who reads the index, and every one of them now says which it is at the call. Asked BY KEY: `byId`, `children`, `status`, `after`, `blocked`, `mirrorsOf`, `edgesTo` — the six a drawn row spends, plus the corpus-sized one. Read WHOLE: `namedBy` (the validator's report), `taggedBy` (tag completion), `byDay` (the agenda and the calendar), `owedByDay` (what each day owes, added up to today), `byFile` (whoever wants the corpus flat) — and those stay clones, because the leg prints `namedBy` walked whole at **0.062ms as a map against 0.208ms through a layer**, which is more per entry than the copy it would save. A map read whole is not made into a layer and then flattened, either: the word is taken when the writer is made, so those are written straight into one clone — taken on the FIRST WRITE, so an edit that touches no key of them still hands back the map that stood. `byFile` was the one close enough to have to be timed rather than argued: the clone and the flat read together are 0.174ms, and a layer with the same read through it is 0.241ms.

**And that carrying is what `src/tape.ts` spends, one layer up.** A copy-on-write patch leaves a promise a reader can act on: an index the edit wrote no key into is the map that stood, a key it re-filed nowhere holds the members it held, and a record in a file nothing touched is the object it already was. So a reading of the set can be TAPED — run the answer over a recording view, keep every key it asked for and what each one said, and ask the next revision whether any of it moved. That is a `could-this-have-changed` test that runs BEFORE the rebuild rather than an equality that runs after it, and its one consumer is `@olai/ops`' `standing.ts`, which is where the five standing views a browser holds open are answered (`perf-streams-per-tab`). Two rules make it safe rather than merely fast, and both are about which way its mistakes go: a lookup that found NOTHING is taped like any other, so an answer that asked for an id and was told nothing is held against the revision where something starts claiming it; and a WALK of an index is not taped key by key but as a dependency on that whole index, which is stricter than the walk needed and is one comparison per index per revision that every open question shares. What it can be wrong about is being too WIDE — a rebuild that was not needed, which is what every revision cost before there was a tape.

**And the corpus is not flattened by a patch at all.** `Derived.nodes` is `Derived.byFile` read the other way — the same records, never a second copy of them — and building it cost one array per record in the directory on every write, for a reading none of the patch's own work asks for. The view a patch hands back builds it when somebody asks, which on a keystroke is never; the one caller that asked for it only to check the patch was about the right corpus stopped asking, and compares the FILES instead (`validate.ts`'s `isSet`, which is the stronger question as well as the cheaper one — the flat lists agreeing said the records were the same objects in the same order, and this says that *and* that the view files them under the paths the set spells). So a validated write flattens the corpus once where it used to flatten it twice and walk both.

The bench prints the before/after rather than quoting one: a `patch+residue` arm pays, inside the same timed window, the two corpus-sized costs a patch used to owe whatever the edit was — the `new Map(byId)` the first round replaced, and the flat list the second one did — reading **1.28ms against 0.42ms, a 3.0×**. It is a reconstruction of the old cost and the file says which two ways: the layers are built and thrown away, and the reads inside the patch go through them — both of which make the arm slower than the code it stands for, so the saving is a ceiling. It also leaves the six other clones out, and says why: reconstructing those means cloning the layers this patcher produced, and `new Map(layer)` walks a generator where the old code walked a plain map, so the arm would be slower than the thing it stands for by an amount that is about the reconstruction. The id map's own step is timed beside it at **0.48ms cloned against 0.010ms layered** (0.002ms when the edits are one file typed in, which is the case that never grows the layer). The six are priced on their own instead, as the indexes cloned — **~0.73ms for the seven a patch layers now against ~0.12ms for the ones it still clones** — and so is the corpus read flat, **~0.07ms to build the list a patch used to hand on against 0.011ms to walk the grouping for the length it wanted it for**. Those isolated arms are a ceiling too; the whole-patch A/B against the branch point reads **0.78ms against 0.42ms**, medians of four and nine runs of the leg (the arm's own spread is 0.68–1.22ms before and 0.30–0.72ms after, which is why the ratio is the claim). What the layer costs a reader is one extra lookup on `get`, and a corpus-wide walk of `byId` puts the layered view and the rebuilt one within each other's noise in both directions.

`derive` does not go away — it becomes the ORACLE. `src/patch.test.ts` generates corpora and deltas (duplicate ids, mirrors of mirrors, chains that dangle, edges naming a placement, cross-file siblings whose `ord` ties, records swapping lines, records moving between files) and asserts that `patch(derive(before), delta)` is the value `derive(after)` is, index by index. The patcher may also DECLINE — a duplicate id, a delta that leaves nothing of the old view standing — and a decline costs a rebuild, never an answer; the suite counts them from both sides, so a patcher that quietly stopped patching fails rather than passes. The one rule `patch.ts` re-spells is the ordering graph, because one pass over every record and one pass per disturbed key are different loops over the same rule; both files say so and the property test is what holds them together. Everything else it needs — sibling order, the FOUR FOLDS that build the reverse indexes (`parentInto`, `nameInto`, `tagInto`, `dateInto` — each asked of BOTH sides of the edit, over what arrived for the members and over what left for the keys they held), mirror resolution, blockedness — it calls in the module that owns it. Re-filing an index across an edit is itself one function (`refiled`) rather than one copy per index: what a key keeps is whatever of it is not in a touched file, what it gains is whatever arrived, and a key left holding nothing GOES AWAY rather than standing empty where a rebuild would have had no key at all. The argument, and what building it taught: [docs/brainstorming/model-indices.md](../../docs/brainstorming/model-indices.md).

`patch` is exported, and PATH ORDER is why that mattered more than it sounds. The browser folds the same function over the frames it receives, so where an arriving file LANDS is now a question two ends have to answer identically — and they did not: `assemble` sorted paths with a plain code-point compare while the client sorted segment by segment, which disagree for a file and a directory that share a name (`.` is 0x2E, `/` is 0x2F, so `wing.olai` compares before `wing/kitchen.olai` while a walk that descends into `wing` reads the nested file first). `src/paths.ts` is the one answer now — the walk's, spelled as "the separator sorts below every other character", which IS segment-by-segment comparison with no allocation — and `assemble`, the patcher, the browser and the five places this package asked which file comes first (a report's order, where a cycle's report starts, which of two inboxes, which of two daily notes is the example, what order a day lists its notes in) all read it.

## The rules are narrowed too, and the narrowed verdict is the ANSWER

Patching the view left the six rules walking it. Five of them visit every record on every write (`reportDuplicateIds`, `reportParents`, the two cycle walks under them, and `reportDocs`); only the unknown-target rule reads an index. `src/incremental.ts` is the other way to reach the same verdict — the previous verdict, the previous view and a delta naming what moved are enough to say which findings could possibly be different — and since `perf-validate-flip` it is **what a write pays**: `validate` asks that arm first and answers with what it says, and the whole-set rules run only for a validation that has nothing to narrow from (`src/validate.ts`'s `wholly`, reached on a boot, on a rebuilt view, on a reading nobody validated, and on the three doors the narrowing turns back at).

**It shipped as a SHADOW first, and that is how the flip was earned.** For three days (#383, 2026-08-25 → 2026-08-27) every write ran BOTH validators: the full one's verdict was what the product obeyed, the narrowed one's was compared and dropped, and every disagreement shouted at error level and appended a line of JSON to a log an orchestrator read each morning. The gate was machine-checkable — that log empty, and at least three quiet nights — and it was met with the log absent throughout. The shadow came out with the flip, because a shadow of an authoritative thing is meaningless; `src/incremental.ts`, its property test and its bench were always going to stay either way, since the harness is the durable artifact.

The narrowing rests on four facts, and each rule says which already-maintained index it reads. **Duplicate ids** cost nothing at all: `patched` hands a corpus with two claims on one id straight back to `derive` and refuses to let an arriving record claim an id an untouched file holds, so a patched view has exactly one record per id and the rule's answer is the empty list (`claimsAreUnique`, `O(files)`). **Parents** re-ask the edited records plus the children of every id whose claimant moved — `Derived.children` is `parent` read backwards and is keyed by the id *as written*, dangling ones included. **Unknown targets** re-ask every id the edit named on either side plus every id whose claimant moved, against `Derived.namedBy` and `Derived.byId`; the ids it finds are put back in `namedBy`'s key order, because that order is what decides which of two findings at one site comes first. **The three cycle walks** are not narrowed by asking them about fewer records — a global visited set means a walk seeded from a subset can find a *different* set of simple cycles — but by how often they run: an edit that left every `parent`, `mirror`, `after` and `blocks` in the corpus where it was left the graph where it was, so a keystroke, a mark, a date or a re-ordering pays no cycle walk at all. **Documents** carry the `.md` path set forward from the last validation and keep it current from the delta's file names; only a `.md` that *went away* can break a record nobody edited.

**Fact 4 — "nothing outside the delta moved" — is checked in two places, and that split is not tidiness.** `isSet` compares a view against a set, and a view holds no documents, so it is structurally unable to witness the half the `doc` rule spends: a `.md` the delta failed to name would leave the outlines matching, the patch taken, and the carried list quietly wrong. So the carry is held against the set it is about on every write (`carriedDocuments` — membership *and* a count, which together are set equality and neither of which is on its own; a count alone is the proxy that let a bug through one PR earlier), and a disagreement **declines** rather than answering. One pass, no allocation, against the three arrays `markdownPaths` would build. It is a DOOR and not an alarm, which is exactly what made it survive the shadow: it is the one class the log watched for that no comparison could have caught once the comparison came out.

`just bench` prints all three arms (`src/validate.bench.ts`, over the same 21,552-record vault with 500 `.md` beside it, 40 edits per row): a **keystroke 23.8ms full against 0.09ms narrowed**, an **edge added 24.5ms against 23.9ms** — the row that says what this did not buy, since the graph moved and all three cycle walks run — and a **`.md` deleted 24.1ms against 0.4ms**. The first column is what a write paid before the narrowing and what a validation with nothing to narrow from still pays; the second is what a write pays now. The third is a record of the soak — **both, 24.6ms / 48.4ms / 24.3ms** — kept because it is the one number that says what the flip gave back.

`src/incremental.test.ts` is what the equivalence rests on, and the flip changed its weight rather than its shape: a wrong answer there used to cost a log line and now costs a write accepted or refused differently. It replays *sequences* rather than pairs — the narrowing follows a reading, so nearly everything that can go wrong with it goes wrong across three revisions: a ledger carried past a refusal, a delta spanning several probes, an id that leaves and comes back. **Both arms are now `validate` itself**: `validate(set, previous)` is the write the store makes, and `validate(set)` with nothing to follow is the whole-corpus validator by construction — so the claim is stated in the product's own vocabulary and the second arm is reached through the same exported door as the first, rather than through a function only the shadow called. Three corpora: nineteen hand-written corners, each an edit a lazier narrowing gets wrong; generated sequences over the same corpora and edits the patcher is held to (`src/corpora.testlib.ts`, moved out of `patch.test.ts` verbatim so there is one generator and not two opinions about what an awkward set looks like), repaired as they are written because a stream that is always refused never publishes a reading for anything to follow; and this repository's own `docs/`, edited. The gate is an equality to the empty divergence list plus floors that say the run was not vacuous — a revision the narrowing *declined* runs the whole-corpus arm on both sides, which is the full validator agreeing with itself, so the suite counts which revisions really narrowed and which doors the rest went through (`src/validate.ts`'s `Reached`, the one channel that can tell them apart).

**The two arms of that suite ask different halves, and the refusal count is not a coverage figure.** The repair that makes a generated stream publishable takes duplicate ids, parent loops, foreign parents, placements-as-parents, mirror containment and ordering loops out of it on purpose — so what the eight hundred generated refusals drive is `unknown-target`, `missing-doc` and the unreadable file, at size and in sequence, and every class the repair removed lives in a corner of its own (including a `blocks`-only loop, which is the ordering arrow read from the end the `after` corner does not write). The duplicate is not even a narrowed refusal: it is a **decline**, which is the right answer and therefore no differential of that rule at all. The floors say which *doors* a run reached rather than summing them, because one word for a first load, a rebuild and three doors of the narrowing is a floor a run can meet without exercising any of them.

**The comparator has its own table**, and that is the shadow's own suite surviving the file it lived in: a differential whose comparator is blind is a green suite that means nothing, so `differing` is a function of two lists of report lines and `src/incremental.test.ts` hands it differences directly rather than writing a validator that is wrong in exactly one way. It sees a set one arm accepted and the other refused, a finding one had and the other did not (counting repeats, so a sentence said twice where the other said it once is a difference), and the same findings in a different order — with the first index they part at rather than both reports whole. The `.md` carry and the property vocabulary are compared straight out of the validator's ledger table beside it.

**And a throw is no longer caught.** The shadow ran inside one `try` because it decided nothing, and a write that failed because its own understudy failed would have been a strictly worse product than one that shipped without an understudy. That premise went with the flip: the narrowing decides now, it has a word for every case it knows it cannot answer, and a validator that swallowed its own defects and quietly answered a different way would make the verdict depend on whether a bug threw or was merely wrong.

## Entry point

`main`, `types` and `exports` all point at `src/index.ts`, and its header states the whole contract: the codec (`parseOutline`, `validate`), what they produce (`OutlineSet` and the records in it), what a set MEANS (`derive` with `rowsOf`, `zoom` and `withoutDone`), how a set is WRITTEN BACK (`serializeOutline` and `ordBetween`), what went wrong (`OutlineError`), what a write says when it refuses (`OpFailure`), and the two vocabularies that cross this floor because both the ops layer and the wire spec speak them — what a pending commit is spoken in, and what a search asks and answers. Everything else under `src/` is internal — the id regex, the edge-field list, the path resolver are spellings a rule happens to use, not contract, and a consumer reaching for one would be re-implementing a rule that lives here.

The derivations are exported for exactly this reason: the browser draws the tree with the same code the validator judged it with.

`src/custom.ts` is the record's one OPEN field, and the reason it is one field rather than an open record: the top level stays closed, so a key this format has no meaning for is still a `bad-record` naming it — which is what catches a typo'd `titel` — while `custom` takes any key a person wants. Two namespaces in two places, so which is which is a fact about where a key sits rather than a rule to remember. Beside it in `src/node.ts` is `shadowFor`, keyed by the record's own field names: a custom key spelled like a field is refused toward the verb that writes that fact, and a field added to the format without a sentence there is a compile error. What the map HOLDS — pruned of keys holding nothing, keys sorted — is `src/write.ts`'s `heldCustom`, beside `nothing` and on the surface for the same reason: a file, a `prop:` query and an ANSWER all ask that question, and three copies of the rule is how a key becomes a thing to search for and no thing to write.

`src/filter.ts` is the newest of them and the one whose placement is worth arguing: it says what a QUERY means — the words, the `"quoted phrases"`, the operators (`is:`, `has:`, `date:`, `created:`, `changed:`, `prop:`, `-`), the `OR` that joins two tokens into one alternative, which nodes they all select, and the transforms that narrow a PAGE to what matched, siblings of `withoutDone`: `keeping` for a tree (the matches, their subtrees and the ancestors that lead to one) and `keepingDated` for the flat rows a day and each stretch of the agenda's line are made of, where nothing is kept as context because every one of those rows already carries its own ancestry. The three operators that take a span of DAYS are one list (`DAY_READINGS`) rather than three — `date:` over the journal's two dates, `created:` and `changed:` over the record's own stamps — and that list is the choke point every table and every reader is built off, `dayWithin` included, which is where both the rule and the argument for it are written. What a reader of this file should take away is only that the three are one grammar and that ABSENCE IS NOT A PAST: a node written before the stamps is found by no span however wide, and by the negation of one, which is the law `-has:date` has always followed ([../../docs/search.md](../../docs/search.md)). `Scope` says which corner of the set is being asked, and its third field is the one exception to the archive rule — a caller whose scope IS the page that shows what was put away rather than a search of the directory. That is the TRASH, plus the one other reading whose rows are already archived ones — a zoom onto an archived node, where an `is:trashed` hit lands (`Scope.archived`'s own doc names both callers). The trash is the one page an archived node is drawn on by a page's own reading of the set (ruled 2026-08-17): `dates.ts` leaves the archive out of the walk every date reading is built from, so a day, the calendar's dots and the agenda draw none of it and have nothing for the flag to be true about. What the ruling did not touch is the grammar — `is:trashed` still selects what was put away at every door, `date:` beside it included, since that clause reads a record's own dates rather than asking a day for its rows. It is here rather than beside the search procedure in `@olai/ops` because a matcher spelled once is the only way `is:done` means one thing to an agent and to the box a person types in; it arrived here when the browser's filter ran on every keystroke over rows the tab already held, and it stays here now that the filter is a question to the server (`search-server-side`, the first step out of `vault-in-browser`) — what moved was WHO CALLS it, not what it says. Both halves are called from the server side now: `ranked` for the shortlists, and the per-node `matchOf` behind `selecting` for the whole membership a page prunes itself by — which since `filter-ask-carries-revision` is asked of the PAGE rather than of the set. That is `src/narrowing.ts`, a reading of its own beside `page.ts`'s: it walks the records one page draws, which are mirror-resolved already, so the answer is bounded by the page and the archive question is read off the page instead of being told to the matcher by a browser ([../../docs/brainstorming/filter-rides-the-page.md](../../docs/brainstorming/filter-rides-the-page.md)). One matcher, five callers — the fifth is the chat composer's `@` list, which completes a NODE into a message — and the RANKING is here with it: `ranked` is the done penalty a finished node takes, the stable sort and the cap, which used to be `Query.search`'s and would have been a second opinion the moment a browser ranked anything. `Query.search` calls both as its gate and keeps the situating, the uncapped total and the refusal; `Query.narrowing` is the envelope over `narrowingOf` and keeps nothing, because the page that asks it is looking at the rows already. The file also answers WHERE, since 2026-08-18, and that is what lets a filtered row say why it is drawn: `needlesOf` is a parsed query's positive words (already folded, since the tokenizer folds as it reads) and `litBy` is where each of them lands in a piece of text, merged and mapped back onto the source. Here rather than in the browser for the reason everything else in this file is — an offset found under some other case rule would light up a stretch of title the matcher never looked at — and the prunes took a widening with them: `keeping` and its siblings now ask `Selected`, the one membership question they ever asked, so the browser can hand in the map of id → `Match` it needs anyway instead of keeping a second `Set` beside it. It is PURE and takes the day as an argument, which is what the relative words (`date:yesterday`, `date:last-week`) cost: a clock read inside it could not be tested against a boundary, and what day it is is a fact about who is asking — each door hands over the one clock it already has. The DURATIONS (`changed:1h`, `created:30m`, `duration-values`) count from the same argument and read the whole of it rather than the day in front, which is the one thing that value kind cost the matcher: a bound may now be a MOMENT as well as a day, so each bound is compared at its own width instead of every value being cut to ten characters first. Four units and no month or year one (`m` is minutes), a bare duration is the range it opens, and everything else it needed — the arithmetic in `src/calendar.ts`, the refusal in `teaching` — was already the shape it had to be. Since `search-index` the file also answers what an INDEX outside this package may hold and may narrow by, which is three exports and no new rule: `hayOf` and `documentHayOf` are the same folds run together into one string per record and per document, and `narrowableBy` is which of a query's words a table may look up, with the query's own and/or shape kept. Both halves are here for the reason the matcher is — a second lowercasing of the text or a second reading of the groups is exactly how an index comes to answer a question the matcher is not asking, and flattening the words would answer `chen OR remo` with the records holding both. `matching` and `matchingDocuments` take those candidates as a last argument and are otherwise unchanged: the ids are resolved through the set's own `byId`, put in the set's own order and run through the same `selecting`, so what an index buys is a smaller reading and never a different answer ([`@olai/index`](../index/README.md)). Since `perf-filter-scope` the SCOPE is a smaller reading too, and for the same reason it had to become one: `Scope` was applied as a predicate INSIDE the whole-corpus walk, so a query about one outline read every record in the directory to throw all but one file's away, and an `under:` walked each record's ancestry as well — narrowing a search cost strictly more than not narrowing it. Both scopes name a corner the derivation already indexes, so `inScopeOf` reads one: `byFile` for a file, and `children` DESCENDED from the named node for a subtree (`descendedFrom`, which is `ancestorsOf` read backwards and inherits its stopping rules — a placement is not walked through, so a record written beneath a mirror is under nothing above it, and a scope rooted at a placement is empty). The predicate stays for the other caller, and that is the division rather than a leftover: handed candidates something else already narrowed, a scope has to TEST them and the cost is the list's, so an index and a scope compose instead of fighting. The equivalence is a DIFFERENTIAL rather than a paragraph — `src/scope.testlib.ts` keeps the old walk as a reference implementation and `src/scope.test.ts` runs the two against each other over generated corpora, over the corners no generator reaches (a record beneath a placement, a parent loop, a child in another file, a root nothing claims), over this repository's own `docs/` vault, and again after each of four writes against a PATCHED view — which is the one thing a fresh derivation cannot ask, since the descent reads an index the patcher maintains and the walk it is held to reads only `byId`. `@olai/index`'s `scope.index.test.ts` is the same harness with the table in front of it. What it buys is `src/scope.bench.ts`: on a 20,000-record vault of trees, **one file of 200 at 2.5ms → 0.3ms (9×), a file'"'"'s whole tree at 39.1ms → 0.3ms (116×), a small subtree at 36.4ms → 0.02ms (1,632×)**, with an unscoped control that reports 1.0× because it is the same walk on both sides. The milliseconds are one laptop'"'"'s and move with what else is running on it — a busier reading of the same tree said 64.7ms and 150× for the second row — which is why both arms are in the tree and the ratio is the claim.
`src/calendar.ts` under it is the one place in this repo a date is COUNTED rather than compared: which weekday a day falls on, the day before or after one, the days a month holds, and — since the query grammar's durations — the moment so many MINUTES before another one, which is the day step composed with a clock face and the first reading here narrower than a day. That last one carries the zone offset through verbatim rather than recomputing it, so it is a wall-clock subtraction: the alternative is a time-zone database in a module whose whole header is a refusal to become one, and `filter.ts` names what the trade costs a query. Every other date reading here is text — a day is a ten-character prefix and a range is two string comparisons — and these two questions genuinely are not. It was the browser's (`calendar/month.ts`, which drew the month with it) and came down when the grammar needed the same Monday; the alternative was two answers to which day a week starts on, drawn on a calendar and selected by a query. Never a `Date`: `new Date("2026-08-01")` is midnight UTC, which is the previous day for half the world. The seven weekday NAMES live here too, beside the count that orders them — they came down the same road for the same reason, when the repeat grammar needed them one layer below a client this package may not import, and the browser now takes both its capitalised names and its two-letter column headings off that one list rather than keeping a second Monday.

`Status` is the four `MARKS` — `done`, `cancelled`, `doing`, `todo`, declared once in `node.ts` because the per-line rule, the ISO check and the index all read that one list — and it is OPTIONAL wherever it appears: a node nobody marked has no status, and `derive`'s status index is partial over the set rather than total. A node missing from it is a bullet, and `todo` is how a node says the other thing, which someone has to put there (docs/format.md's Status section).

**Two of the four SETTLE**, and `SETTLED` beside that list is the one place saying which: `done` and `cancelled` are the marks that end the wait, `settles` is that question asked of one mark, and `Unfinished` is `MARKS` with them filtered out. That indirection is what made the fourth mark ONE seam rather than a hunt through the readings — `derive.ts`'s `unfinishedWork` carries the contract in its header, and naming `cancelled` in `SETTLED` is what made a cancelled task un-owed on the overdue count, the agenda, the date badge and the blocker arrow at once. The trap it is written against is spelling any of those `!== "done"`, which is exactly right for one settling mark and silently wrong for two.

`Site` is the same argument about WHERE. A place in the loaded set is `{file, line}` — `file` relative to the served directory so it reads the same in a browser, a test assertion and a report from another machine, `line` 1-based and the whole address because there is one node per line. Four things in this package are AT a place and carry it: an error's site (`OutlineError`, and the `related` rows beside it), a record in the set (`Located`), the flattened node every read answers with (`Found`) and a mirror's location (`Placement`). They stay four — an error, a record, an answer and a placement are different things, and folding them into each other would be a lie — but the PLACE is one thing, declared once in `node.ts` beside `Located` and spread into the other three.

It was declared four times, once per carrier, which #170's review round noticed and [declined as a drive-by](https://github.com/juspay/olai/pull/170) because it reaches the public surface. Four spellings of one fact is not four names for a type: it is a fact that can be extended in one of four places and compile clean past the other three. Adding a required field to the old `errors.ts` `Site` failed at `OutlineError` producers and nowhere else — not one `Found`, not one `Located`, not one `Placement`. Adding it to this one fails at all four. WHICH carriers a place's new field reaches is the property; how many packages happen to go red is a fact about today's consumers, and this file does not pretend to know it.

A status is STORED, on whatever record carries it, parent or leaf; the index resolves exactly one hop, a mirror standing for its target's mark because that is what it shows. Nothing is computed from a node's children — that was derivation, deleted 2026-08-11 with the rule that existed to defend it, because it read containment as decomposition and made a parent a task nobody had called one. What survives is `progressOf`: how many of a node's child tasks are done, `3/5`, an annotation carried on `Row` and `Situated` for the view to draw beside a title. It feeds nothing — not `withoutDone`, which reads the stored mark, and not blocking.

**Blocked** is the other thing the marks are read for, and it is derived beside them: `after` (with `blocks` normalised into it in the one place that happens, so the acyclicity rule and this see one graph) says `a` comes after `b`, and `b` is in the way while it is a TASK that is not done. A target with no status never blocks — it is not work, so there is nothing under it to finish — and spelling the test `status !== "done"` is the trap docs/format.md writes the rule against. One predicate at both ends of the arrow, racket's own shape: a done node is waiting on nothing, a bullet is neither blocked nor blocking, and archived work is out of it in both directions because it is over. What a blocker IS is `InTheWay`: a node and the mark that makes it unfinished — and "unfinished" is not a sentence this says twice, it is `unfinished`, the one exported predicate that `blockage` here and `unfinishedWithin` over a branch are both built from, about the two different kinds of edge. The ordering graph is built in two passes — every node's own `after` first, then the `blocks` pointing back at it — so the order a reader with room for ONE blocker sees is a promise rather than an accident of where in the directory somebody wrote an unrelated edge; and both halves are filed under the node their target NAMES, mirrors resolved, so the acyclicity rule and this cannot disagree about whether two records mean one edge. It is a SET per source, which is the last thing that normalisation owes its readers: an edge named twice — a field repeating a target, both spellings written down, a placement named beside the node it stands at — is one edge, so a node is never told that one thing is in its way twice. Nothing outside this package asks for the index to DRAW with: what is in a node's way rides on the `Row` and the `Situated` it belongs to, the way its mark does.

**`Derived` is indexes, and five of them read backwards** (plus two LISTS that are readings of one of them — see the end of this paragraph). Everything above is a lookup rather than a walk, which is why the nodes travel WITH their tables rather than beside them: two parameters would let one revision's nodes be read against another's indexes, and the symptom would be a plausible tree rather than a failure. Six answer forwards — `byId` (first claim wins, the validator's own duplicate rule), `children`, `status`, `after`, `blocked`, and `byFile`, one file's records in DISK order, which is what "what does this outline hold" and "what are its roots" are now instead of a filter over every node in the directory — and, since `perf-filter-scope`, what a `file:` scoped search READS, with `children` descended for an `under:` one, so a scoped query stops costing the vault as well. Five answer backwards, and the first three are the ones that know what an edit REACHED: `mirrorsOf` (the placements standing for a node — `follow` reversed, chains followed, so a mirror of a mirror is filed at the node and not at the hop before), `edgesTo` (`after` reversed, canonicalised by the same act that built it, so the two readings cannot disagree about whether two records mean one edge), and `namedBy` (the format's own `targetsOf` reversed — RAW, what the records SAY, because a refusal has to quote a field and the id somebody wrote rather than what it resolves to, and because `see` is a relation no derivation reads). The last two are not about reaching at all. `taggedBy` files every record under each tag its title or its note writes, keyed by the tag AS WRITTEN — `#herbs` and `@herbs` are two keys, never one, because they are two namespaces in every other reader of this format. Keyed by the tag rather than by a node, because `@alice` and `@order` are the same thing to a title and what makes the second a REFERENCE is that some record claims that id. Asking existence in the index would mean re-reading every note in the directory whenever a node was minted or dropped, so it is asked at the READ instead (`src/backlinks.ts`, `backlinksOf` — which also rules that a placement is not a reference, that an ordering edge is not one either, and that an archived referrer is left out; [docs/format.md](../../docs/format.md)’s References argues each). It has a SECOND reader now, and that is what the written-form key bought: `src/vocabulary.ts` asks it which tags the set uses and how many records carry each (the row editor's completion, answered over the `vocabulary.tags` procedure since `vault-in-browser` took the set out of the browser), where it used to walk every node of the corpus per derivation — **18.5ms walked against 0.47ms read** on the bench vault, and **12.2ms** for the title-only walk that was literally there (a smaller answer: 60 tags against 1,052, since it never looked at a note). All three are arms of one leg, because a ratio quoted against a reconstruction that does more work than the code it stands for is a flattering ratio. Filing the other sigil is not free — the corpus-wide fold goes **6.5ms → 18.6ms per REBUILD**, which `src/patch.bench.ts` prints as its own pair — and the trade is that a rebuild is the fallback path while the completion is asked per keystroke. That same leg prints what the WALK under both costs, because the widening made it the largest single thing a rebuild does: `titleParts` over the corpus's prose is ~12ms stepping its regex with `exec` (which is how it is written, since #249), ~16ms asking `matchAll` for an iterator per call (which is how it was), and ~9ms for the tag-only private loop this package declines to have — three arms checked to find the same tags before any of them is timed, so the decision not to take that last one is a number somebody can re-take rather than a sentence. `byDay` is the fifth, and the newest (`perf-dates-index`): a DAY → the dates that land on it, which is `src/occasion.ts`'s `datesOf` read backwards over the set — the journal, as an index. It is the one index here whose KEYS are promised in an order, ascending by day, because three readings step them and none may sort to get it: the calendar's month walks into the month and stops at its end, and the agenda walks back from today for what has slipped and forward for the next days that have anything. A decade of daily notes is three and a half thousand keys, and sorting them per read was the cost the node was filed over — the patcher pays for the promise the way `byFile` pays for path order, re-sorting only when an edit ADDS or EMPTIES a day. It is also the one index that leaves the trash out AT THE FOLD rather than at each read, and that is a considered difference from `taggedBy` above: that one is about what prose SAYS, so a storage rule inside it would be out of place; this one is about what a journal SHOWS, and a journal does not show what was put away (ruled 2026-08-17). The exclusion therefore stays spelled once for all three readings, which is what the walk it replaced was written to hold, and a month with a thousand archived records on it costs a reader nothing. What the three readings cost now, each against the walk it replaced, is `src/dates.bench.ts`: **the month's dots 0.00ms against ~6.5ms, a fourteen-row day page 0.01ms against ~7ms, the agenda PAGE ~1.7ms against ~10ms (≈6×)** on the bench vault. The agenda's six is the honest one — finding its days is a lookup now, but drawing them is still an ancestry walk per row, and 242 days owe something in that corpus.

**`owedByDay` and `days` are the sixth and the seventh, and they are not a sixth fold** (`perf-agenda-history-walk`). Both are readings of `byDay` kept beside it: a DAY → how much unfinished dated work sits on it (days owing nothing absent, keys in the same day order), and that map's keys as an ARRAY. The patcher recounts only the days an edit touched, out of the buckets it has just re-filed, and re-lists the array only when the key set moved — which is the same one edit in many that already re-sorts those keys, so a keystroke in an outline nobody scheduled anything in pays nothing for either. They answer the two things `byDay` alone could not. First, the two COUNTS a mark outside the agenda prints (`owedNow`) used to be `owedOf(agendaOf(…))` — the whole agenda assembled, every overdue node in the directory situated with its ancestry, its blockers and its rollup, and the answer counted and thrown away, per subscriber per published revision — and they are an addition over this index now: **0.02ms against ~2ms**, a hundredfold, on the same vault (the leg's reconstruction of the old path reads 1.3–2.9ms across runs, and the branch point's own agenda-and-count arm reads ~2.1ms). Second, a map's keys can only be stepped from the front, so a reading that begins at a month or at tomorrow reached its start by skipping every earlier day one at a time; the array makes that a binary search (`dayAt`), and the calendar's month is **0.00ms against 0.01ms stepping** — tens of microseconds either way on a corpus with 618 days in it, because what the jump takes off is proportional to the days BEFORE the month, which is what the ten-year vault the node was filed on has a lot of. The price of the second reading is that the counts and the page are two spellings of one number where they used to be one, and what holds them together is a differential rather than a shape: `src/occasion.test.ts` asks both over generated corpora and `@olai/ops`' `src/owed.index.test.ts` asks both after every write of a real gate, at every day the corpus can be read on.

The fold costs **~7.4ms per rebuild** for all three together, up from ~7.0ms for the day index alone, and one WRITE pays **~0.36ms against ~0.30ms** patched (`src/patch.bench.ts`, medians of five alternating runs, spreads that overlap) — which is the whole of the trade, and it is a trade rather than a saving on both sides: the fold and the patch each got a little dearer so that a reading answered per subscriber per published revision got two orders of magnitude cheaper. An edit that changes no day's tally still hands back the map that stood, which is what keeps a keystroke free. The plan the first three are the first slice of is [docs/brainstorming/model-indices.md](../../docs/brainstorming/model-indices.md).

One caller asks the other end of it. `standingBefore` is what a node's `after` targets hold up whether or not the node is work yet, and `@olai/ops` refuses `set_doing` with it. The two readings part at exactly one place — an unmarked source, which `blockersOf` reports as waiting on nothing because a bullet is not being told it cannot start, and which a write that is about to MAKE it work has to hear about. They share `inPlay` and they walk the same graph, so the target side — bullets, done work, the archive — cannot come out two different ways.

`zoom` is the same claim about one node as a page — which record an id resolves to (following a mirror chain to the regular node at its end, so a node has one page and not one per placement), the canonical parent chain above it, and the rows beneath it. Where a node lives and what it is under are facts about the set, so they are answered here rather than carried in a URL that could disagree with the files.

`dates.ts` is the same claim about a DAY. There is no journal file and no stored year→month hierarchy: a day is a question asked of every dated node in every outline, so `datedDays` (which days of a month have something on them, in day order) and `datedOn` (everything on one day, grouped by outline, with each node's ancestry and mark) are one reading of the set that the calendar and the day view both read from — a dot that disagreed with the page it opened would be worse than no dot. Both are LOOKUPS into `Derived.byDay` since `perf-dates-index`, where they were passes over every record of every outline: the month's own keys taken and stopped at, and one key taken. Getting TO the month was the half that node left standing — a map's keys can only be stepped from the front, so paging to March cost every day of every year before it — and `perf-agenda-history-walk` made it a binary search over `Derived.days`, which is those same keys as an array. WHAT puts a node on a day is one module below them (`src/occasion.ts`) — the two fields, the mirror that carries neither, the trash that is on no day, and the fold the index is built with — because a fold cannot live above the reading it feeds. Dates stay TEXT here as everywhere else: a day is a ten-character prefix, a month a seven-character one, and a datetime counts for its own day (`occasion.ts`'s `dayOf`, `monthOf` and `timeOf`, which is where the slicing lives). Two SHAPES sit beside those readings and travel rather than compute — `DatedRequest` / `DatedAnswer`, what the calendar's dots are asked and answered with. They are here for `searching.ts`'s reason: since [vault-in-browser](../../docs/brainstorming/vault-in-browser.md)'s PR 4 the dots are walked on a server and drawn in a browser, so the question crosses a wire and a vocabulary spelled in the wire spec would be a second spelling free to drift from this one. `sameDated` beside them is the schema's own equivalence — what lets a server keep quiet on a revision that moved no dot.

TWO fields are read, not only `date`: a dated `done` (`{"done":"2026-08-11T15:40:03-04:00"}`) places a node too, because a journal without the work that was finished is missing the half of the day that happened. A dated `doing` or `todo` is read by neither question (2026-08-11, human): the format allows it, a journal is narrower than the format, and "picked up on Tuesday" buried the day under everything filed that morning. So a node with two dates is on two days, two dates on one day are one row, and each row says which of the node's dates put it there (`Occasion`), because scheduled-on and finished-on are two different sentences and only the reader can be told which one they are reading. A `done` holding `true` is on no day: it declines to say when, and inventing an answer would file every old `true` under today. The ARCHIVE IS FILTERED OUT, at the one FOLD every date reading here is built from (`src/occasion.ts`'s `dateInto`; ruled 2026-08-17, reversing 2026-08-11): what was put away is drawn on the trash page and nowhere else, so a day, the calendar's dots and the agenda all lose it together and cannot come to disagree about it. It is the exemption blockedness already takes at both ends — nothing waits on what is over — read once more for the question a journal asks. `is:trashed` still reaches the node itself at every door (`filter.ts`), because that clause asks a record for its dates rather than asking a day for its rows.

The same module answers the one question about a day that is not about nodes at all: which DOCUMENT is that day's note. `noteDateOf` is the whole convention — a `.md` whose basename is exactly an ISO date is that day's note, wherever in the tree it sits, and `2026-08-10-recap.md` deliberately is not — with `dailyNotesOn` (the notes of one day, in path order, both of them when two files claim one date) and `dailyNoteDays` (the days of a month that have one) reading it for the day page and the calendar's second mark. It is here rather than beside whatever draws a calendar for the reason the two questions above are one module: a mark and the page it opens must be one reading. Those two take the document PATHS rather than a derived set, which is the shape of the wire — a browser holds every path and only the bodies of what is on screen. Nothing about this is a rule the validator enforces: a daily note is a view convention over filenames, and no record mentions it.

THREE OTHER FILENAMES MEAN SOMETHING here, read the same way and for the same reason — by NAME, with no record saying so, in this package because a rule about what a file IS, spelled in two places, is two answers about one directory. `ARCHIVE` is what was put away; `inboxIn` finds where a captured line lands; `pinsIn` finds the SHELF the sidebar draws — a `Pins.olai` whose top-level nodes are pins, each an ordinary node whose title is an address the app would mint (docs/format.md's Pins). The last two are one walk, `outlineCalled`, because the rule is not "where the inbox is" but "how this format finds the file a directory named" — a running minimum over whatever the caller can iterate (a list, a map's keys), shallowest first then path order, allocating nothing per file it rejects. WHO ASKS IT, AND HOW OFTEN, is `conventions.ts`, added with `perf-filename-conventions`: the answer moves only when a file is added, removed or renamed, and the two readings below were asking it per published revision — which is per keystroke. A `Convention` is the answer held with the path set it was read from, and whether that set moved is asked of the STORE'S OWN DELTA (the `changed` / `removed` a snapshot carries) rather than by comparing two directories, because a comparison the size of the walk would have bought a rename of the cost. It fails towards the walk in every direction it can be wrong, including the one the delta cannot name: a departure a `resync` swallowed shows in the COUNT, which is the one comparison that makes the check exact rather than usually right. WHERE olai MINTS one when a directory has none is a different question and stays a different function — `mintedInto`, which puts every file olai names for itself under `OLAI_DIR` (`_olai/`: the shelf, the trash, and since 2026-08-20 the inbox, reversing the ruling of the day before). `inOlaiDir` is that mint read backwards, for the one face that draws a LIST of files: the sidebar leaves those rows out of its tree because each of them has a door of its own in that column, which is a drawing rule and never a reading of the set. What a pin's title MEANS is deliberately NOT here: which PAGE an address opens and what a `?q=` on one means is this app's address space, which the format has no business knowing — so that half is the browser's, at view time. What an address IS, on the other hand, is this package's own (`address.ts`): `[document]#[element]`, one grammar for every feature that names something.

`shelf.ts` is that seam spent: the SHELF as a reading of the set — `pinsIn` for the file, its top level in `ord` order, and for each row `pinTargetIn` (the node an address names, asked of the grammar above, so the bare `#id` and the qualified `garden.olai#id` land on one id) resolved through `nodeNamed`. It is here because it is a walk of a whole directory, and the browser stopped doing those ([brainstorming/vault-in-browser.md](../../docs/brainstorming/vault-in-browser.md)): the server re-reads it per published revision and the sidebar is handed the answer, which is what keeps a bare pin's name live with no copy of it stored anywhere. `shelfIn` beside it is the same reading with the convention walk lifted out — the file named by the caller, which is how the server spends a carried answer (`conventions.ts`) instead of re-deriving which file the shelf is on every keystroke; `shelfOf` stays the plain reading and is the differential's reference arm. It reads no title as a PAGE and never will — every row of the file travels, the browser's own parser decides which are doors — and `sameShelf` beside it is what keeps a revision that moved no pin from sending a frame.

`inbox.ts` is the same seam read TWICE, and the two readings are there together because they are one fact from two sides. `inboxHeldOf` counts the top-level regular nodes of whichever outline `inboxIn` names over the set's paths that still await processing — the same list capture walks; nested children, placements, done rows and finished branches (a bare-bullet header whose every descendant is done) left out, zero when there is none or every capture is already processed; `sameInboxHeld` keeps a revision that moved no capture from sending a frame, and `inboxHeldIn` is that count over a file the caller names — the shelf's lifted twin, for the same carrier (`conventions.ts`). Its list is the SET'S paths and not `byFile`'s, which is why the two readings need two carriers: `byFile` groups parsed records, so an empty or torn `Inbox.olai` has no entry in it and a count read off that list would name a different file from the one a capture lands in. `captureInto` is the other side: what a captured line BECOMES, which is one write request — an `add` into the inbox the directory has, or the `create` that mints `_olai/Inbox.olai` holding exactly this capture, so a refused capture leaves no file behind. It is here rather than in a face because TWO doors resolve through it (the browser's `⌘K` `+` in `@olai/server`, and the `capture` TOOL in `@olai/ops`, which is what an agent and `olai surface capture` both land on) and a directory with no inbox has to be a `create` for one and a `0` for the other — two spellings of that would be two answers about one directory. It came down from `@olai/server` the day it got its second caller, which is `message.ts`'s own move in the same words.

`agenda.ts` reads those same dates FORWARD: what is owed rather than what is on. `Owed` — the two numbers a mark outside the page prints — is a SCHEMA here for the reason its sibling next door is, and it carries `OwedRequest` and `sameOwed` with it: the counting happens where the set is and the counts travel, and the one thing the set cannot give the reading is the day it is counted against, so the READER's own today rides the request rather than being read off a server's clock. It adds no field and no rule — `date` says when, the mark says whether it is work, and the two together are the whole reading, so `date` with no mark is an occurrence that can never be late and is not on this page — it stays on its day and in the calendar — and `date` with `todo` or `doing` is due work, which is the only thing the agenda lists. `isOverdue(node, today)` is that predicate spelled ONCE (`todo ∨ doing`, and `day(date) < day(today)` by plain string order, because dates are text here too — both sides through `dayOf`, so it answers about a day whichever shape of ISO value it is handed), and it is read by the days above now on the page's spine and by the tone a date badge takes, the way `blocked` is one predicate read at both ends of its arrow. `agendaOf` assembles the three stretches of one line — what has gone, today, the next days that have anything — out of `Derived.byDay`, read back through the same `groupedOn` and `byOutline` a day page is built from, so the agenda and the day it links to cannot be two readings. It WALKS the days that OWE something, back from today for what has slipped, and JUMPS to tomorrow for what is coming, which is what the promised key order and the day line bought between them: it used to sort every day the set has, twice, per read, and then to visit every day that has gone whether or not it owed anything — and since `vault-in-browser`'s PR 4 that read happens on the server, once per published revision for everybody watching it — it was once per SUBSCRIBER until `perf-streams-per-tab`, which is what `@olai/ops`' `standing.ts` fixed and where the sentence about it now lives. WHAT SLIPPED ARRIVES AS DAYS, like what is coming (`behind`, ruled with `agenda-spine` 2026-08-18): the page draws one continuous line of time rather than three boxes, so a day is where a node goes and late work has to bring the day it was owed on with it — the outline grouping stays INSIDE each day, for the page that still draws it. `done` is filtered from all three, and so is an occurrence: this question is what is OWED, and what happened — and what is merely ON a day — is the day view's. The ARCHIVE is out of all three as well, and not by a rule of this module's — it reads the index `occasion.ts`'s fold already left it out of, so a task put away after somebody scheduled it stops being owed on the same revision it stops being on its day. `keepingOwed` is the same answer with rows taken out of it — the filter over the page, applied to each of the three, so a day left with nothing stops being drawn and nothing is re-derived; the silences between the days that remain are not filtered but RECOMPUTED, because how long a wait is, is a fact about the days still on the line rather than data (`web/src/client/agenda/spine.ts`). `owedNow(derived, today)` is the two numbers a mark outside the page prints — how many NODES are late and how many are due today, never how many outlines they were grouped under. Upcoming is deliberately no part of it: a task due next Tuesday is not news today, and a count that included it could never fall to nothing. It reads them off `Derived.owedByDay` (the days that have gone, added up; today's own tally read off a key), where until `perf-agenda-history-walk` it was `owedOf` over a whole `agendaOf` — which meant situating every overdue node in the directory, with its ancestry, its blockers and its rollup, to produce two integers, per subscriber per published revision. `owedOf` is still here and still exported: it counts an agenda a caller ALREADY has, and it is the reference arm the differential and the bench hold the index read to. That the two are two readings of one directory is the price of the change and is met with a gate rather than an argument — `src/occasion.test.ts` over generated corpora, `@olai/ops`' `src/owed.index.test.ts` after every write of a real gate, and `src/agenda.test.ts` at the two boundaries either can move on (the day rolling over, and work finished on the day it was owed). TODAY IS AN ARGUMENT, never a clock: a derivation that read one would answer differently on the machine it ran on, and what day it is belongs to the reader (`web/src/client/clock.ts`).

`repeat.ts` is the smallest module here and the one with the most argument per line: the closed grammar a dated node says it COMES BACK in — `every day`, `every week on <weekday>`, `every month`, `every year`, and nothing else — plus the arithmetic that says when the next one is. It is text in and text out: `parseRepeat` reads a record's field, `printRepeat` writes the canonical spelling, and `./repeat.test.ts` holds the two to each other over the whole vocabulary, so what the picker offers and what the validator takes are one list read from either end. FOUR names leave the package — `isRepeat` and `REPEAT_GRAMMAR` for the two rules a write is judged by, `nextOccurrence` for the answer a completion needs, `REPEAT_RULES` for the surface that offers the vocabulary as a list — and the parser, the printer and the `Repeat` union stay inside, reached only by the tests beside them: a grammar with a parser on its surface is an invitation to a second reading of it. `nextAfter` counts with `calendar.ts` above and never leaves integers, which is the one reason this feature could be added to a package whose stance on dates is that they are strings. THE RULE RIDES THE OCCURRENCE THAT IS NEXT — completing one hands it forward (`@olai/ops`' `recurring`), so a finished record is a plain dated node and a recurrence has exactly one live head; that single sentence is what makes un-done/re-done churn unrepresentable rather than policed, and it is argued at length in the module header. The rhythm is the FILE's and never the clock's: one period after the node's own date, so nothing here reads a clock and a late completion spawns the occurrence that was genuinely next (docs/format.md's Repeating).

`stamp.ts` is the other direction, and every date value olai WRITES is minted there: `stampOf` produces a local ISO datetime carrying its offset, which is what the ops layer marks a node with. It lives beside the rule that ACCEPTS one so that what olai writes and what olai reads are two functions in one package rather than a writer above guessing at a shape. (The browser's clock turns an instant into date text too, for the question "which day is `/today`" — nothing it mints is stored, and that the two agree about where a local day ends is a test in `@olai/web` rather than an argument.)

A day's nodes and a zoomed page are built from the same `Situated` — a node, its mark, its rollup, what is standing in its way and its canonical ancestry — because that is one concept with several readers, not a shape two surfaces happened to agree on. A title torn out of its outline says nothing, wherever it is being drawn.

`documents.ts` is the third such claim, about the `.md` files beside the outlines. A document's text is content — verbatim on disk, markdown at view time, nothing about it validated — so what lives here is only what has to be answered the same way twice: where a node's `doc` lands (`docOf`, resolved against the outline that named it, which is the rule the validator checks and the view links with), and what a relative `![](…)` may name (`pictureOf`, `isPicture`). That last one is asked by two packages that cannot import each other — the renderer that rewrites a picture into a URL, and the route that answers it — and two allowlists that drifted apart would mean either a broken image or a served file nobody meant to serve. `isAsset` is the same question asked once more and one step wider: what the media route may ANSWER at all, which is a page and the parts a page draws itself with (a stylesheet, a script, a font) as well as a picture, because a previewed `.html` is fetched by URL and draws itself. The two are deliberately not one list — markdown may still name a picture and nothing else, which is a rule about what markdown MEANS. `bodiedOf` is the third thing markdown can point at, and the third reading of the same arithmetic: where a relative `[…](…)` to another `.md` lands. A vault linking between its own files writes those by the dozen, and resolving one beside the file it was WRITTEN in is what keeps it from being resolved against whatever page it is being drawn on — which is the same reason `doc` is resolved against the outline that named it. Whether the directory actually holds the answer is nobody's business here: this package knows the arithmetic, and the page that opens the address already has a screen for a document that is not there. Two things here are not arithmetic. **`linksIn`** is every ADDRESS a piece of prose points at, spent on a document's body and on a node's note alike, so a `[…](…)` means the same thing wherever it is written. **`firstLine`** is the closest a `.md` has to a title — its first non-blank line with the heading marks off — a DERIVATION because a document has no record for a name to be written on; it was `@olai/web`'s while the browser was the only caller, and moved here whole when `list_documents` wanted the same answer the row beside a `doc` draws. **`bytesOf`** is beside it as the other thing sayable about a document without walking its markdown: its size in UTF-8 bytes rather than in the UTF-16 units JavaScript holds it in, so olai reports the number every other tool a person has reports for the same file. The number is remembered on the document at decode (`bodiedDocument`), so a listing is O(documents) rather than a re-encode of every served body.

What is deliberately NOT here is the SENTENCE a path that is not a document is refused with. This package declares what a refusal *is* (`failure.ts`); `@olai/ops` is the only layer that raises one, and it keeps that one too (`noSuchDocument`, beside `notFound`), because a floor that started composing agent-facing prose would be a second voice for the same "no". The facts the sentence is made of — `markdownIn` and `didYouMean` — are here, which is the line: facts down, voice up.

## What a served file IS

`src/document.ts` is the type the [first-class documents](../../docs/brainstorming/first-class-documents.md) arc exists to make, and `src/set.ts` serves it as the directory's ONE collection:

```
data Document = Outline   Face [Node]
              | Markdown  Face Text Bytes [Slug]
              | Hypertext Face
```

A sum of products, one arm per kind the registry claims, discriminated on the registry's own word for the file. Every arm carries the same **face** — a `DocumentPath`, a title, the `Address`es its content points at, the `Tag`s its prose writes and the `props` it writes about itself — and all of it is TOTAL. There is no `Maybe` to branch on, which is exactly what made "handle the nodes, skip the rest" the shortest way to write a feature: a document had no addressable identity below the file, so everything keyed on ids excluded it by construction, and graph view drew no `.md`, search walked past every body, backlinks could not name one.

Nodes did not become documents. They became the SUBSTRUCTURE OF ONE ARM — `Node` keeps every field it ever had, and what changed is its standing. The set no longer serves a `nodes` collection beside a `documents` one, so a feature has no node-only list to import; the records are reachable through the outline they are written in, and the one flattening left is the validator's, for the derivation.

The FACE IS DERIVED and it is built at the DECODE (`@olai/ops`' codec), once per file per change, which is where a walk of somebody's prose belongs — `assemble` is a collect. A markdown document's title is its first line, its links are where its `[…](…)` land, its tags are the `#topic` and `@person` in its prose read by the walk a note is read by, its elements are the slugs of its headings (`src/slug.ts`, whose rule the browser's renderer spends too, because a slug spelled twice is an address this app writes and cannot open), and its weight is `bytesOf` of its body, remembered so a listing does not re-encode every served `.md`. Hypertext is a face and nothing else, and the emptiness is the registry's `kept: false` showing through: its `links` are empty because nothing read it, which is not the same claim as "a saved page points nowhere".

**Frontmatter is a document's own record, and it is `src/frontmatter.ts`.** A `---` block on the very first line, closed by another — micromark's rule, spelled out there because a vault is read by other tools too, and held to it by a test that renders every corner through `remark-frontmatter` and through this function (`@olai/web`'s `markdown/frontmatter.test.ts`) — read into the face's `props`, which is `Custom`: the same open map a node carries, answered by the same `prop:` clause through one `propKeyOf`. It is a stated SUBSET of YAML and not a parser: text, quoted text, flow and block sequences of text, and a refusal for everything else, one key at a time. What the block is NOT is prose — one `proseIn` is the skip `firstLine`, `headingsIn`, `tagsIn`, `linksIn` and the search's body fold all spend, and the BROWSER spends it too (the three faces that draw a whole file strip it before the markdown pipeline sees it), so the page and the face are one function rather than two rules. That is what keeps a `---` off the title, off the page, out of the heading list and out of the tag index — and what keeps it ON the screen in a node's note, which is not a file and has no frontmatter to hide. And it is not a RECORD: a frontmatter `date:` is a property named `date`, so `is:done`, `has:date` and `date:today` still select no document — the honest answer, since a document with a real day would have to be drawn on the day page, the agenda and the calendar.

`src/backlinks.ts`'s `referrersTo` is the reverse reading the face made possible: every document's forward `links`, read backwards, so a document's page can say who points at it. It is a lookup in the LINKS INDEX and then a walk of ONE file, through `recordLinks` — the same function that BUILT the face, because two walks of the same fields would be two answers to "does this record point there". That index is `src/pointing.ts` and it rides on the `Reading` (`perf-doc-backlinks-index`): what a link NAMES, written the way the grammar writes an address, against the faces that write one — in path order, a face once per key however many of its links land there, and a link onto a HEADING filed under the heading AND under the document it is in, because that is the rule the reader downstream applies and collecting it out of a document's headings at the read would mean knowing every heading anybody had ever written. It was a WALK of every face in the directory until then, per revision, per tab sitting on any page with a body — the one direction of the graph that had no reverse index while the node-to-node direction next door had two. Kept the way `patch.ts` keeps the derivation and held to the same kind of oracle: `pointingOf` is the definition, `repointed` steps the two path-ordered document lists and re-files only the files whose FACE moved, and `src/pointing.test.ts` holds them to each other — and both to the walk, which is kept as this lane's reference arm (`src/pointing.testlib.ts`) — over generated corpora and over this repository's own `docs/`. Reading the SETS rather than the delta is what makes it exact for a `.md` written inside a batch, which the delta the ops layer folds names no records for at all. `just bench` prints both halves of the trade, because an index that costs a read little and a revision something is a trade (`src/pointing.bench.ts`). On a `.md`-heavy generated vault — 1,801 files, 300 outlines × 21 records and 1,500 bodies, 5,020 keys, a median of 6 referrers per body — ten open document pages read **3.98ms walked against 0.53ms indexed**, and a page NOTHING points at (which is most pages in most directories, and the row where the shape shows rather than one corpus's density) **0.194ms against 0.001ms**. The write side is what it now costs to carry: **0.15ms per revision against 3.87ms to fold the directory again**, with 3 of 20 edits handing the index straight on uncloned. What a read still pays is the walk of the files that really DO point here, which the old code paid too; what it stopped paying is opening every other file in the directory, so the ratio rises with the vault and falls with how thickly the vault points at itself.

## Two readings of a set, and what they differ by

`src/changes.ts` takes two sets of records and answers with what CHANGED, node by node — created, archived, marked done, note rewritten. It is here for the same reason the writer is: it is a statement about records, and it has no idea where either side came from. That is what lets it serve two callers whose inputs are nothing alike — what is pending is HEAD against the working tree, a past change is a commit against its parent — with no git anywhere near this package.

It is never a text diff, and that is the format paying for itself in the other direction: a `.olai` diff is one enormous line per node with everything on it changing at once, which is exactly the shape that made line-based merges safe and exactly the shape nobody can read. Matching is by ID ACROSS FILES, so archiving reads as one change to one node rather than as a removal and an unrelated arrival.

`src/committing.ts` is the values that answer travels in — what is waiting, what was last recorded, what git is doing for the directory (`GitState`, with its before-first-frame `GIT_OFF`), the policy this server runs under and what the operator pinned of it, whether the repository can take a commit, what asking for one answers with. Git plumbing is `@olai/ops`'s, and so is everything that never crosses the wire: how olai spells a commit message. What is here is exactly what `@olai/surface` imports, which is why it is here at all — this package is the floor both that layer and the wire spec stand on, as the refusal vocabulary already is. Design: [docs/brainstorming/git-commits.md](../../docs/brainstorming/git-commits.md).

`src/window.ts` beside it is the QUIET WINDOW as a rule and nothing else — the span, what counts as a flurry, and `armedOn`, the one expression that says whether what is waiting would record itself right now. No timer, no git, no I/O: `@olai/ops` runs it (the debounce and the two verbs) and `@olai/server` prints the span in `--help`, but the caller that puts it on this floor is the BROWSER, whose panel promises "Auto-commit will record all of this" and may only promise it when this answers with something. A browser cannot import the layer that runs the loop — its next module down reaches `node:child_process` — so a panel that re-derived a shorter version of the rule is exactly what happened, and the shorter version had already dropped the term that says anything is waiting.

## What a read of the set asks, and what it says back

`src/reading.ts` and `src/searching.ts` are the same argument applied to the other vocabulary that crosses this floor. There are seven reads: four over NODES with one atom between them, one that is a BATCH of ids and shares that atom with nothing, and two over the other kind of file.

| declaration | what answers with it |
|---|---|
| `Site` | not a read at all — the `{file, line}` under all of them, `src/node.ts` |
| `Found` | every read. One node SITUATED — id, title, a `Site`, mark, ancestor titles, the edges it writes, and the `custom` properties it carries |
| `OutlineSummary`, `OutlineAnswer` | `list_outlines` — a count and the top-level titles, per file; or, for a file that did not parse, its errors and nothing else |
| `Detail`, `NodeAnswer` | `read_node` — the record, its tags, its children, its stamps, and a placement from both ends (`mirrors`, `placed`) |
| `Subtree`, `OutlineRoots`, `SubtreeAnswer` | `read_subtree` — nested, and saying where a walk stopped. THREE arms, because the read takes two kinds of subject: a node walked, a whole OUTLINE walked (`{file, roots}` — every top-level node in it, each walked, each with its own `truncated`, and a placement at the top level is not one of them), and the id the set does not hold |
| `SearchHit`, `SearchAnswer` | `search_nodes` and the ⌘K palette |
| `DocumentSummary`, `DocumentAnswer` | `list_documents` — every served `.md` with the line it opens with, what it weighs, and the properties its frontmatter writes; or, for a file that could not be read, its errors and nothing else |
| `DocumentRequest`, `DocumentBody` | `read_document` — one body, whole and verbatim |
| `Pinned`, `Shelf` | the `pins` cell — the rows of `Pins.olai`, each with the node its address names and what that node is called at this revision (`shelf.ts`). The one shape here that is a READING rather than an answer to a request: nobody asks for it, the server sends it when it changed |
| `InboxHeld` | the `inbox` cell — how many top-level captures still await processing (`inbox.ts`); a finished branch does not count. The shelf's twin, one integer over |
| `NamedRequest`, `NamedAnswer` | `nodes.named` — which of these ids the set declares, and the node each one names. The one read that shares no atom with the others, because it says nothing about a node except that it is there: the chat panel asks it once per message about the ids an agent wrote in backticks, and what it needs back is a lookup rather than a record |
| `HomesRequest`, `HomesAnswer` | `nodes.homes` — WHERE these ids are, and which of these files this directory has READ (served, and not among the ones that would not parse — never "declares a record", which would read an emptied outline as unreadable and keep its folds for good). The other read that carries no node: the browser's fold memory asks it about what it has collapsed, so a node that was archived keeps its fold under the file it moved to and a node that is gone stops being remembered. It is not the row above with a `file` on it — that one FOLLOWS a mirror chain, because a backtick means the node a reader would be shown, and this one is the plain record lookup, because a fold is of a record |


`OutlineSummary` is a UNION, and the second arm is the file that did not parse.
It used to be flat, with an optional `unreadable` beside a `nodes: 0` and a
`roots: []` — a count nobody counted and a claim that the outline is about
nothing, on the one file where neither could be known. Every field read honestly
alone; the untruth was in the combination, held apart by a convention a reader
had to know. The dependent facts now exist only on the arm that grounds them
(ruled 2026-08-22: `{file, unreadable}`), which is also what the neighbouring
`Missing` already does for a `read_node` of an id the set does not hold. The
torn arm is one declaration, shared with `DocumentSummary`, so the two listings
cannot answer a file nobody read two different ways.

The document pair shares no atom with the four above it, and that used to be the `md-second-class` asymmetry in one line. What can be said about one is its path, its title, its size and — when it wrote any — the properties its frontmatter holds. The title is READ OFF THE FACE the decode built rather than derived again here, so this listing, a search hit, a palette row and the page's own heading say one name; the properties are that face's too, omitted when empty, the same map a search hit carries and the document page draws. Its torn-file row is the same two-arm shape `OutlineSummary` now is — `{file, unreadable}` — so one listing answering a torn file one way and the other listing answering it another cannot come apart. And `DocumentBody` has no `{ missing }` arm on purpose: an id is guessed at and worth answering, a path is not — a typo gets the near miss, which only a refusal can carry.

Plus what each one ASKS — `NodeRequest`, `SubtreeRequest`, `SearchRequest`, `DocumentRequest` — and the two numbers an omitted field MEANS, `DEFAULT_SEARCH_LIMIT` and `DEFAULT_SUBTREE_DEPTH`, which are here because the agent-facing prose beside each request quotes them.

The walks are `@olai/ops`' (`Query`) and stay there: which nodes match, how hits are ordered, which mirrors resolve to a node, how far a subtree descends. What is here is only the SHAPE — because the shape travels. Search's travels four ways at once already: an agent reads it off `search_nodes`, the `search.nodes` procedure carries it, the ⌘K palette draws it, and the header's search box draws it again.

It was spelled twice before — three times counting `Query.search`'s own parameter — once in each of the two packages that stand on this floor, and `@olai/surface`'s header claimed the two could not drift. They could: a field added to the ops-side hit and produced type-checked clean across every package, reached the agent, and was dropped by the wire schema's encoder on the way to a browser. One declaration is why that is now unrepresentable rather than merely detected — see [docs/brainstorming/surface-mcp-positions.md](../../docs/brainstorming/surface-mcp-positions.md).

Every field of a hit is a statement about records in this package's own terms: an id, a title, a `file:line`, a mark, the ancestor titles `ancestorsOf` walks, the edge lists a record carries — and, when the query said `withDesc`, the note. That one is the only record field a hit does not carry by default, and the reason is its SIZE rather than its meaning: every other field is bounded like the title beside it, where a note is unbounded prose, and this same request is what the ⌘K palette and two panels ask over the wire on every settled keystroke. It travels whole or not at all; `src/searching.ts` carries the ruling and the argument against a length. The three fields that are not statements about the record — `matched`, which field carried the words; `matchedProps`, which custom keys a `prop:` clause selected the node on; and the `refusals` an unreadable query answers with — are facts about a QUERY, and they sit on the hit and the answer rather than on `Found` for exactly that reason. The first two are two fields because both can be true of one hit and because `matched`'s four values are a closed, weighted list where a property key is an open namespace; `src/searching.ts` carries the ruling. `Refusal` itself is declared next door in `src/filter.ts`, beside the `parseFilter` that produces it, and is a Schema rather than an interface because it does not stay there: the filter over the tree draws its own, and the three doors that ask the server get theirs on the answer.

**The filter grammar is what the single declaration was for, and it proved it one day later.** #168 extended search with `file`, `under`, an optional `matched` and `refusals` — four fields the previous arrangement would have needed spelled twice and kept in step by hand, in two packages that cannot import each other. Seated here instead, they are spelled once: removing `refusals` from this file fails in `@olai/ops` (which produces them), `@olai/web` (which draws them) and `@olai/server` at the same moment, where before it would have failed on one side and compiled on the other. Dropping `path` from `Found` does the same across the same three packages, which is what makes the atom an atom.

**The other three moved BEFORE anything carried them**, which is the cheap end of the same lesson: they were TypeScript interfaces in `@olai/ops`' `query.ts`, so no wire spec could declare them and the second spelling was still ahead rather than behind. What the compiler cannot check on its own is a producer putting a key on an answer the declaration has never heard of — object-literal freshness is lost through a `.map`, so a field DROPPED here still compiles at the one place it is built — and `@olai/ops`' `tools.test.ts` closes that by walking the tool table, calling every read's own reader, and decoding each answer through the declaration that entry carries with `onExcessProperty: "error"`, the same setting `parseOutline` reads records under.


`src/vocabulary.ts` is the seventh read, and the one that is not a query at all: **which tags this set already uses, and how many records carry each.** It is the reading over `taggedBy` that `src/backlinks.ts` is over the pair — the keys of that map, the length of each entry, the trash taken off, most-used first — plus the prefix test one popup applies to it, and it carries its own three shapes (`TagsRequest`, `TagCompletion`, `TagsAnswer`) for `searching.ts`'s reason. ONE export, `completingTags`: the enumeration and the match are two functions inside because they cost differently, and a consumer composing them by hand would be a consumer holding the composition. It ran in the browser until `vault-in-browser`'s PR 2, which took the set out of the browser; it now answers the `vocabulary.tags` procedure, memoised once per revision so a settled keystroke pays the match and nothing else. No grammar and no score: nothing here can disagree with `search_nodes`, because nothing here is asked of the matcher. The cap rides the REQUEST rather than living in the shape, because a row count is a fact about the door that asked.

## What a write ASKS for, and what one that landed says

`src/writing.ts` is the third time this move was made — after `committing.ts` and `reading.ts`/`searching.ts`, and for the identical reason. It holds the twenty-two request schemas, the `WriteRequest` union over them, and `WriteResult`, which is what an op that succeeded answers with.

**Twenty-two schemas, twenty-five write tools**, and the gap is not a typo: the four marks share `MarkRequest`, because the format allows at most one mark and `set_done` / `set_cancelled` / `set_doing` / `set_todo` differ only in the `op` their own NAME fixes. `@olai/ops`' table generates those four off the format's own `MARKS` list — which is the point of keying them, since a mark that was plannable and writable everywhere and had no tool would otherwise be silently missing. `set_cancelled` is what that keying is FOR: it arrived as a tool, an `apply` op, an undo and a `Status` literal the day the list grew, and every table that had to say something about it said so as a compile error.

It moved here from `@olai/ops` when the writes went onto the surface: `ops.run` is a procedure now, so the request an agent sends and the answer it gets back are values that CROSS this floor. The ops layer produces them, the surface carries them, and `@olai/ops` re-exports the two under its own names — `Request` and `Applied` — the way `Pending` and `CommitRequest` are already re-exported by their consumers rather than declared twice.

Both are renamed at the move, and the second rename is the load-bearing one:

- `Request` → **`WriteRequest`**, because among `NodeRequest`, `SubtreeRequest`, `SearchRequest` and `CommitRequest` a bare `Request` is the one that does not say which question it is;
- `Applied` → **`WriteResult`**, because `@olai/surface` exports an `Applied` of its own and it is a DIFFERENT type — the keyboard's answer, which adds `undo` and drops `summary`, `sort`, `captured` and `rev`. Two things called `Applied`, both about a write that landed, both carrying `id`/`title`/`nudge`, is the `Outline`/`OutlineSummary` trap again: not a rename away from a compile error, a rename away from a plausible one.

The PLANNER stays in `@olai/ops`, exactly as the matcher and the walks did. What is here is only the shape, plus the two numbers the shapes impose — `NESTING`, the depth to which `add_node`'s `children` is unrolled, and `BATCH_AT_MOST`, how many ops one `apply` may carry. Both live beside the schema that quotes them, and both are facts about what an agent READS (a JSON Schema an MCP host can hold; a refusal a reader can hold) rather than about the format.

**Two of the twenty carry the others** (`olai-batch-verbs`): `UpdateRequest` names several fields of one node, and `ApplyRequest` an ordered list of the write verbs. `ApplyRequest`'s arms are the request schemas THEMSELVES — each already carries the `op` literal that names it, so a batched `set_done` and a called one decode against one declaration and a parallel list of "batch forms" never exists to fall behind. What is taken off on the way in is only the top-level PROSE (`arm`, `TERSE` one level up): every one of those sentences is already in the same `tools/list` frame, on the tool that takes the request, and leaving them doubled cost 8 kB of the first frame of every agent session. Left out of the list are the three writes whose subject is a FILE rather than a node, and `apply` itself.

## Writing is here too, and for the same reason reading is

`src/write.ts` is the only thing in olai that turns records back into bytes, and `src/ord.ts` is the only thing that decides where a node sits among its siblings. Both are statements about the format rather than about whoever is writing, so they live beside the rules that judge them.

The writer takes the records of a WHOLE FILE and gives back the whole file, so every separator has exactly one owner: the newline between two records, the one at the end, the absence of a blank line. That shape is the point. A caller that built its own bytes once produced two records glued onto one line — a file no reader could parse, out of a write every layer above believed had succeeded — and `write.test.ts` asserts the invariant directly, by parsing back what the writer produced for every shape of record the format has.

It also gives "absent" ONE spelling. An optional field holding nothing — `undefined`, `null`, `[]` or `""` — is not written, so `{"after":[]}` cannot reach a file however a writer arrived at it. That is the same bet as the line format itself: two files that mean the same thing must not differ byte for byte, or a line-based git merge conflicts over nothing. A *required* field is written whatever it holds, because dropping one makes a line the reader rejects outright — worse than handing an odd value to the validator that is about to see it anyway.

`ordBetween` is a fractional index over base62 in ASCII order, so the plain string comparison the format promises IS numeric order in this encoding. It answers `null` for the one pair with no answer — nothing sorts between `x` and `x0` — rather than inventing a key in the wrong place; the ops layer renumbers that row instead.

`src/failure.ts` is the other half of the error story: the four KINDS a write refuses with (`usage`, `not-found`, `validation`, `busy`), as schemas, so a refusal travels the wire and an MCP tool result as itself. Four classes rather than one with a `kind` string because they carry different things — only `validation` has a verdict to show, only `not-found` names what was missed — and a single struct would make every field optional and push "which fields are meaningful" back into prose. There were five: `derived` refused a write that would have stored a computed status, and went with derivation itself.

`src/verdict.ts` is what a refused VALIDATION answers with, and it stopped being a flat `ReadonlyArray<OutlineError>` on 2026-08-25 (the lowy-electricity debate's finding 2). The rows are still the product and still travel whole; what changed is that the questions consumers used to re-derive from them — and got wrong three different ways — are answered here, once. `admits(files)` is the write gate's, and it is per FILE: `admitted` or `implicated(file, rows)`, with no whole-set member, so a set that will not validate can no longer freeze a write to a file it has nothing to do with and a refusal names its blocker. `summary(n)` is a BOUNDED per-file face — state and counts, no rows — for a surface drawn over something still live; the enumeration stays where a reader asked for it. `implicating` / `implicatedBy` are which files a finding is about, which is `errors.ts`'s `Reach` axis read per finding rather than per code. And `tierOf` is what a class costs a LOAD — `refuses` or `carried` — which is the per-line tier the error scope has had since 2026-08-09, with the set half finally spellable. It ships at exactly what the validator already did (`verdict.test.ts` pins that equivalence over generated broken sets); which classes brick a boot is a policy call and stays the vault owner's.
