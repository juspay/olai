# @olai/format — the format, and the only place it is enforced

The format core ([docs/format.md](../../docs/format.md)): `parseOutline` per file, `validate` per set, and the derivations — sibling order, tags, mirror expansion, the rollup a parent displays, what is dated a given day, what is overdue as of one — that both the validator and the view read from. It is the bottom of the layering: it knows about records, files and rules, and nothing about disks, servers or browsers.

Nothing outside these two functions may reject an outline. Not the reader, not the store, not the web layer. A second interpretation of the format would be free to disagree with the one that decides whether a file is legal at all.

## Which files a served directory is made of

`src/kinds.ts` is the one table that says it: a kind per row, each with the suffix that claims a file, whether its content is a tree of RECORDS the validator judges or a BODY carried verbatim, and whether the loaded set KEEPS that content or only the path. `fileKind` reads it, and so does everything downstream — the store's walk is handed it as `match`, the codec decodes by it, the set sorts decoded files by it, and the client's sidebar, glyphs and routes are `Record`s over the union it exports. It was four spellings before, which is what made the outline rename (PR #177) and the file glyphs (PR #174) each a hunt; a new kind of served file is now one entry here, and the type checker names every surface that owes it a drawing. `packages/tests/kinds.test.ts` holds both halves as sweeps: nothing outside this file decides by spelling a suffix, and every registered kind is drawn everywhere kinds are drawn. Three exports hand out the SPELLING rather than the verdict, for the callers that cannot ask a function — `OUTLINE_EXT` and `DOCUMENT_EXT` for the ops layer's path mints, and `FILE_EXTS` for the click handler `@olai/surface` puts inside a previewed page, which is text in a template literal running in a frame that imports nothing and still has to know which links name a file olai has a page for — every kind, since all three have one. `stemOf` is the same table asked one step further: the file's NAME with the suffix that claims it taken off, and the bare name for a file no kind claims. Two callers were answering that for themselves with opposite rules — a commit subject spelling the outline suffix and leaving every other name whole, a daily note cutting at the last dot and so answering `READM` for `README` — and they agreed on outlines and nowhere else, so neither could absorb the other. `src/stem.test.ts` holds both retired rules beside the one that replaced them and shows, row by row, that on every name the two disagreed about the merged answer is *one of the two* — never a third reading — and that it is the one belonging to whichever caller can reach that name: the daily-note rule for a `.md`, the commit-subject rule for a name no kind claims. What no caller passes is the row where the merged rule would have moved it.

The table holds only what EVERY kind has an answer to. A fact one kind has — where an archive goes, which files a `doc` may point at, what a day's note is named — stays with that kind's rule, because a column that is empty for most rows is a union wearing a table's clothes.

`kept` is the third column and the newest, and what it decides is what one loaded directory COSTS. `unkept(path)` is how every layer asks it — the same move `bodyKind` is one row up, so nobody derives it in two steps of their own. An outline's records are the set and a document's text is what a conditional write is judged against, so both are kept; a `.html` is the one file olai only ever shows — nothing validates it, no op writes it — and a saved page with its pictures inlined is megabytes, so the set keeps its path and its body is read when a reader opens it (`@olai/store`'s `Codec.byName` is how the probe is told not to read it at all, and `@olai/server`'s `bodies.ts` is what reads it). That is why `Document.text` is nullable: `null` is a state — *this file is served and its body is not here* — and never an empty file.

## What a place in the directory is CALLED

`src/address.ts` is the one grammar: **`[document]#[element]`**, with a branded half for each thing a name can be — a `DocumentPath` (a path whose suffix the table above claims), a `NodeId`, a heading `Slug`, and a written `Tag`. Three arms come out of it: a whole document (`Tasks.olai`, `notes/README.md`), a node (`#a1b2c3`, location-free, because an id survives renames and moves between files), and a heading inside a body (`README.md#install`).

What a `#` MEANS is read off the document in front of it — an outline has nodes and no headings, a body has headings and no nodes — which is why the document half insists on a suffix the registry claims, and why `Tasks.olai#a1b2c3` parses and NORMALISES to the bare node it names. `printAddress` is total over an address and `parseAddress` is total over any string, answering `null` for text that names no place: what reads one is an address bar, a title in `Pins.olai` that a hand and an agent are invited to edit, and an href written in somebody's note, and a throw out of any of those is a blank page rather than a bad address.

THREE SMALLER READINGS sit beside the grammar because a title and a URL are how an address is WRITTEN, and both are now read on two sides of a wire: `splitAddress` (path, query and fragment, cut fragment-first because a `#` ends a query), `linkedTitle` (a title written as one markdown link, cut into its two halves — the shape a named pin takes), its inverse `pinTitle` (the title a pin carries for a name somebody typed: the bare address for a blank one, a link around it otherwise, and a refusal rather than a mangling for words a label cannot hold — two WRITERS cut this too, the server resolving a `pin` and the browser renaming one) and `addressWritten` (the address a title carries, either way). Each was spelled once in the browser until the shelf's reading moved to the server (`shelf.ts`) and was about to spell it a second time. What is NOT here, and stays the browser's, is what the halves MEAN — which page a pathname opens, and that the query is a filter (docs/format.md's Pins).

It is HERE rather than in the browser because it is a statement about the directory, the same reason `kinds.ts` is — the design that rules it is [first-class-documents.md](../../docs/brainstorming/first-class-documents.md). What the browser adds is a slash in front of it and the pages that name nothing on disk (`@olai/web`'s `routes.ts`).

## Staged, and the stage is part of the answer

Validation is two phases, and the seam is load-bearing rather than tidy.

`parseOutline` sees one line at a time and checks everything a single line can answer alone — shape, id spelling, ISO dates, the two exclusivity rules. `validate` sees the whole set and owns every rule that needs to know what else exists: parents, mirror targets, `after` cycles, documents.

What `validate` ANSWERS with is a `Reading`: the set, and the one `Derived` its rules were run over. Every rule needs the same indexes, so it builds them once and shares them — and used to drop them at the door, which meant the next reader of an approved set (the store publishing it, the planner judging the next keystroke) walked the corpus again for a value that had just been in hand. The two travel together for the reason `Derived` carries its own nodes: a caller holding one revision's set against another's indexes draws a plausible tree rather than failing.

A file is decoded whole or not at all. The set-wide rules then run over the files that DID parse, and what happens to the one that did not is the error scope (resolved 2026-08-09, and the reason `validate` is handed each file's `Result` rather than only the successes):

- if the survivors are clean, the set is accepted with that file's errors embedded in it (`OutlineSet.broken`). The browser renders them in that one outline's place and everything else stays live;
- if anything else is wrong, the set is rejected and the report carries the parse errors alongside whatever else was found.

Guesses are still not reported. "`kitchen` is not a known id" is a guess when the line declaring `kitchen` is the one that failed to parse — so `unknown-target` is withheld while any file is unreadable, and withholding one is itself a reason to reject the set rather than publish nodes whose targets are unresolvable. Nothing else can be *invented* by a missing file: `parent` may not cross files, so an unresolved one is refused whichever file it was going to be in, and a duplicate or a cycle can only be hidden by a missing file, never conjured. A report containing a per-line error says out loud (`reportStage`) that a second round is expected.

Within a phase, every rule runs and every error is collected. Stopping at the first would turn "fix this file" into a loop of load-fix-load, which is the workflow the format exists to remove.

An unknown reference is nearly always a misspelling, so an error about one ends with the closest declared id — within a typo's distance (`src/suggest.ts`: a third of the id's length, never less than two), and nothing further away, since a guess that is merely NEAREST teaches a reader to distrust the offer. That rule is exported (`didYouMean`, and `nearestId` for a caller that wants the candidate rather than the wording) for one reason: the ops layer refuses the same unknown `mirror` / `after` / `see` target one moment EARLIER, at the plan, and a second copy of the budget — or of the sentence — would let the write and the load disagree about what a typo is. `chainOf` (`src/errors.ts`) is the same argument about a LOOP: the validator names one it found on load, the ops layer names the one a write is about to close, and the arrow between the ids is written once — and `drawingPath` (`src/derive.ts`) is that argument one turn further, about the WALK rather than the wording. The containment graph `drawnFrom` was shared and the walk over it was not, so each rule that asked "would this placement expand for ever" wrote its own; three ask now, at three moments — the validator on load, the ops layer at the write (a new mirror, and a move that carries one into what it shows), and the move-to picker at the aim, before the key — and a rule that walked a shared graph its own way was a second answer with extra steps.

## The view is patched, not rebuilt

`validate` takes an optional second argument: the reading it FOLLOWS, and what has moved since (`Previous`). With it, the view its rules run over is the previous one with the changed files' entries swapped into the indexes — `src/patch.ts` — rather than a derivation of the whole corpus. What that costs is what the edit touched: a title edit dirties one record, and the reverse indexes (`mirrorsOf`, `edgesTo`, `namedBy`, `taggedBy`, `byDay`) say which placements, edges, blockers, referrers and DAYS elsewhere have to be looked at again. It is an order of magnitude on a vault-sized directory, and `just bench` measures this patcher directly (`src/patch.bench.ts` — forty one-file edits over a generated 21,552-record vault, each to a different file, patched on the view the last edit left: **0.79ms against 44.0ms rebuilt, a 55×**, medians of four alternating runs — both moved with the tag index below, which widened the fold a rebuild pays, and again with the day index, which added one more: on the same machine and the same run the pair reads 0.72ms against 36.8ms before that index and 0.79ms against 44.0ms after it, which is the fold's ~7ms landing where it was expected to). The browser used to fold the SAME function over the frames it received, and that is over: a tab holds at most the page in front of somebody, so the derivation runs on the server alone and the browser is handed a page's reading (`./src/page.ts`, and `docs/brainstorming/vault-in-browser.md`'s PR 10). What a FRAME cost a tab was a figure this README quoted beside the two above — 4.33ms for the fold, 4.44ms for the whole composition, on this same vault — and it is history now, along with the older pair (a frame 64ms against 330ms) from the slice-4 harness this tree no longer carries. What replaced it is a wire measurement rather than a fold one: the same reading session over a 40-outline vault costs a first frame of 135 kB where it cost 1,679 kB (`packages/tests/wire.ts`). One generated vault feeds the legs that quote one (`src/fixtures.testlib.ts`'s `vaultOf`, shared with `src/vocabulary.bench.ts` and `src/dates.bench.ts`), so their numbers are about one directory. That vault gained PROSE with the backlinks index — a note on every fifth record, every tenth naming another by its `@id` — and `#tags` in the titles when that index gained the second sigil, and DATES with the day index (a quarter of the records, half the finished ones carrying the instant they were finished at, spread over two years: 5,939 dated records over 618 days), because a corpus with no notes in it measures none of what a derivation does with notes, a corpus whose titles hold no `#` measures the sigil nobody writes, a corpus where nothing is scheduled measures no day at all, and a new index that nothing exercises prints as *costs zero* when what it printed was *was never asked*. All three are counted rather than drawn, so the corpus itself is the one it has always been (980 files, 21,552 records) and the added work is the only thing that moved.

**That claim was false for a whole review cycle, which is why `src/vault.test.ts` now exists.** The first spelling put the mention on `which % 25 === 0` inside a loop that runs `which` from 1 to 20, so it never fired: 3,920 notes, not one `@`, `taggedBy` empty, and the patcher's own `keys.size === 0` early return firing on every bench edit — under a paragraph saying the opposite. A reviewer derived the corpus and counted. The fence asserts, at the size the benches run, that every index they print a number about has something in it; a fixture that quietly stops producing one now fails a test rather than a sentence.

**The absolute numbers are one machine's and the ratios are the claim.** These were re-measured on a slower, busier box than the ones they replaced, and the run-to-run spread on the patch arm alone is 0.71–1.12ms across four runs — which is why the pair is reported as a ratio and why `patch.bench.ts` is a leg somebody runs rather than a lane that fails on a busy machine.

The copy-on-write is where the patch's own cost sat, and `src/overlay.ts` is what it costs now. Every index a patch changes is cloned so that the revision a reader is holding cannot move under them — cheap for nine of them, and not for `byId`, which has an entry per record in the DIRECTORY. It is a LAYER now — the entries this edit changed, over the map the last patch left standing — with the same answers, the same size and the same key order, which is not a detail, because the did-you-mean behind every unknown-target error walks those keys. Nothing above it knows: `overlaid` returns a `ReadonlyMap`, and the layer flattens back into a plain one when it has grown past half the map.

The bench prints the before/after rather than quoting one: a `patch+clone` arm pays the `new Map(byId)` this branch replaced, inside the same timed window, and the pair reads **1.50ms against 0.69ms — a 2.2×**, with the step itself timed on its own at **0.444ms cloned against 0.014ms layered** (0.002ms when the edits are one file typed in, which is the case that never grows the layer; the gap between the arms is larger than the step's own cost because a 21,552-entry allocation leaves garbage for later work to collect). It is a reconstruction of the old cost and the file says which two ways: the layer is built and thrown away, and the reads inside the patch go through it — both of which make the arm slower than the code it stands for, so the saving is a ceiling. What the layer costs a reader is one extra lookup on `get`, and a corpus-wide walk of `byId` puts the layered view and the rebuilt one within each other's noise in both directions.

`derive` does not go away — it becomes the ORACLE. `src/patch.test.ts` generates corpora and deltas (duplicate ids, mirrors of mirrors, chains that dangle, edges naming a placement, cross-file siblings whose `ord` ties, records swapping lines, records moving between files) and asserts that `patch(derive(before), delta)` is the value `derive(after)` is, index by index. The patcher may also DECLINE — a duplicate id, a delta that leaves nothing of the old view standing — and a decline costs a rebuild, never an answer; the suite counts them from both sides, so a patcher that quietly stopped patching fails rather than passes. The one rule `patch.ts` re-spells is the ordering graph, because one pass over every record and one pass per disturbed key are different loops over the same rule; both files say so and the property test is what holds them together. Everything else it needs — sibling order, the FOUR FOLDS that build the reverse indexes (`parentInto`, `nameInto`, `tagInto`, `dateInto` — each asked of BOTH sides of the edit, over what arrived for the members and over what left for the keys they held), mirror resolution, blockedness — it calls in the module that owns it. Re-filing an index across an edit is itself one function (`refiled`) rather than one copy per index: what a key keeps is whatever of it is not in a touched file, what it gains is whatever arrived, and a key left holding nothing GOES AWAY rather than standing empty where a rebuild would have had no key at all. The argument, and what building it taught: [docs/brainstorming/model-indices.md](../../docs/brainstorming/model-indices.md).

`patch` is exported, and PATH ORDER is why that mattered more than it sounds. The browser folds the same function over the frames it receives, so where an arriving file LANDS is now a question two ends have to answer identically — and they did not: `assemble` sorted paths with a plain code-point compare while the client sorted segment by segment, which disagree for a file and a directory that share a name (`.` is 0x2E, `/` is 0x2F, so `wing.olai` compares before `wing/kitchen.olai` while a walk that descends into `wing` reads the nested file first). `src/paths.ts` is the one answer now — the walk's, spelled as "the separator sorts below every other character", which IS segment-by-segment comparison with no allocation — and `assemble`, the patcher, the browser and the five places this package asked which file comes first (a report's order, where a cycle's report starts, which of two inboxes, which of two daily notes is the example, what order a day lists its notes in) all read it.

## Entry point

`main`, `types` and `exports` all point at `src/index.ts`, and its header states the whole contract: the codec (`parseOutline`, `validate`), what they produce (`OutlineSet` and the records in it), what a set MEANS (`derive` with `rowsOf`, `zoom` and `withoutDone`), how a set is WRITTEN BACK (`serializeOutline` and `ordBetween`), what went wrong (`OutlineError`), what a write says when it refuses (`OpFailure`), and the two vocabularies that cross this floor because both the ops layer and the wire spec speak them — what a pending commit is spoken in, and what a search asks and answers. Everything else under `src/` is internal — the id regex, the edge-field list, the path resolver are spellings a rule happens to use, not contract, and a consumer reaching for one would be re-implementing a rule that lives here.

The derivations are exported for exactly this reason: the browser draws the tree with the same code the validator judged it with.

`src/custom.ts` is the record's one OPEN field, and the reason it is one field rather than an open record: the top level stays closed, so a key this format has no meaning for is still a `bad-record` naming it — which is what catches a typo'd `titel` — while `custom` takes any key a person wants. Two namespaces in two places, so which is which is a fact about where a key sits rather than a rule to remember. Beside it in `src/node.ts` is `shadowFor`, keyed by the record's own field names: a custom key spelled like a field is refused toward the verb that writes that fact, and a field added to the format without a sentence there is a compile error. What the map HOLDS — pruned of keys holding nothing, keys sorted — is `src/write.ts`'s `heldCustom`, beside `nothing` and on the surface for the same reason: a file, a `prop:` query and an ANSWER all ask that question, and three copies of the rule is how a key becomes a thing to search for and no thing to write.

`src/filter.ts` is the newest of them and the one whose placement is worth arguing: it says what a QUERY means — the words, the `"quoted phrases"`, the operators (`is:`, `has:`, `date:`, `created:`, `changed:`, `prop:`, `-`), the `OR` that joins two tokens into one alternative, which nodes they all select, and the transforms that narrow a PAGE to what matched, siblings of `withoutDone`: `keeping` for a tree (the matches, their subtrees and the ancestors that lead to one) and `keepingDated` for the flat rows a day and each stretch of the agenda's line are made of, where nothing is kept as context because every one of those rows already carries its own ancestry. The three operators that take a span of DAYS are one list (`DAY_READINGS`) rather than three — `date:` over the journal's two dates, `created:` and `changed:` over the record's own stamps — and that list is the choke point every table and every reader is built off, `dayWithin` included, which is where both the rule and the argument for it are written. What a reader of this file should take away is only that the three are one grammar and that ABSENCE IS NOT A PAST: a node written before the stamps is found by no span however wide, and by the negation of one, which is the law `-has:date` has always followed ([../../docs/search.md](../../docs/search.md)). `Scope` says which corner of the set is being asked, and its third field is the one exception to the archive rule — a caller whose scope IS the page that shows what was put away rather than a search of the directory. That is the TRASH, plus the one other reading whose rows are already archived ones — a zoom onto an archived node, where an `is:trashed` hit lands (`Scope.archived`'s own doc names both callers). The trash is the one page an archived node is drawn on by a page's own reading of the set (ruled 2026-08-17): `dates.ts` leaves the archive out of the walk every date reading is built from, so a day, the calendar's dots and the agenda draw none of it and have nothing for the flag to be true about. What the ruling did not touch is the grammar — `is:trashed` still selects what was put away at every door, `date:` beside it included, since that clause reads a record's own dates rather than asking a day for its rows. It is here rather than beside the search procedure in `@olai/ops` because a matcher spelled once is the only way `is:done` means one thing to an agent and to the box a person types in; it arrived here when the browser's filter ran on every keystroke over rows the tab already held, and it stays here now that the filter is a question to the server (`search-server-side`, the first step out of `vault-in-browser`) — what moved was WHO CALLS it, not what it says. Both halves are called from the server side now: `matching` for the whole membership a page prunes itself by (`@olai/ops`' `Query.matches`) and `ranked` for the shortlists. One matcher, five callers — the fifth is the chat composer's `@` list, which completes a NODE into a message — and the RANKING is here with it: `ranked` is the done penalty a finished node takes, the stable sort and the cap, which used to be `Query.search`'s and would have been a second opinion the moment a browser ranked anything. `Query.search` calls both as its gate and keeps the situating, the uncapped total and the refusal; `Query.matches` calls `matching` alone and keeps nothing, because the page that asks it is looking at the rows already. The file also answers WHERE, since 2026-08-18, and that is what lets a filtered row say why it is drawn: `needlesOf` is a parsed query's positive words (already folded, since the tokenizer folds as it reads) and `litBy` is where each of them lands in a piece of text, merged and mapped back onto the source. Here rather than in the browser for the reason everything else in this file is — an offset found under some other case rule would light up a stretch of title the matcher never looked at — and the prunes took a widening with them: `keeping` and its siblings now ask `Selected`, the one membership question they ever asked, so the browser can hand in the map of id → `Match` it needs anyway instead of keeping a second `Set` beside it. It is PURE and takes the day as an argument, which is what the relative words (`date:yesterday`, `date:last-week`) cost: a clock read inside it could not be tested against a boundary, and what day it is is a fact about who is asking — each door hands over the one clock it already has.
`src/calendar.ts` under it is the one place in this repo a date is COUNTED rather than compared: which weekday a day falls on, the day before or after one, the days a month holds. Every other date reading here is text — a day is a ten-character prefix and a range is two string comparisons — and these two questions genuinely are not. It was the browser's (`calendar/month.ts`, which drew the month with it) and came down when the grammar needed the same Monday; the alternative was two answers to which day a week starts on, drawn on a calendar and selected by a query. Never a `Date`: `new Date("2026-08-01")` is midnight UTC, which is the previous day for half the world. The seven weekday NAMES live here too, beside the count that orders them — they came down the same road for the same reason, when the repeat grammar needed them one layer below a client this package may not import, and the browser now takes both its capitalised names and its two-letter column headings off that one list rather than keeping a second Monday.

`Status` is the three `MARKS` — `done`, `doing`, `todo`, declared once in `node.ts` because the per-line rule, the ISO check and the index all read that one list — and it is OPTIONAL wherever it appears: a node nobody marked has no status, and `derive`'s status index is partial over the set rather than total. A node missing from it is a bullet, and `todo` is how a node says the other thing, which someone has to put there (docs/format.md's Status section).

`Site` is the same argument about WHERE. A place in the loaded set is `{file, line}` — `file` relative to the served directory so it reads the same in a browser, a test assertion and a report from another machine, `line` 1-based and the whole address because there is one node per line. Four things in this package are AT a place and carry it: an error's site (`OutlineError`, and the `related` rows beside it), a record in the set (`Located`), the flattened node every read answers with (`Found`) and a mirror's location (`Placement`). They stay four — an error, a record, an answer and a placement are different things, and folding them into each other would be a lie — but the PLACE is one thing, declared once in `node.ts` beside `Located` and spread into the other three.

It was declared four times, once per carrier, which #170's review round noticed and [declined as a drive-by](https://github.com/juspay/olai/pull/170) because it reaches the public surface. Four spellings of one fact is not four names for a type: it is a fact that can be extended in one of four places and compile clean past the other three. Adding a required field to the old `errors.ts` `Site` failed at `OutlineError` producers and nowhere else — not one `Found`, not one `Located`, not one `Placement`. Adding it to this one fails at all four. WHICH carriers a place's new field reaches is the property; how many packages happen to go red is a fact about today's consumers, and this file does not pretend to know it.

A status is STORED, on whatever record carries it, parent or leaf; the index resolves exactly one hop, a mirror standing for its target's mark because that is what it shows. Nothing is computed from a node's children — that was derivation, deleted 2026-08-11 with the rule that existed to defend it, because it read containment as decomposition and made a parent a task nobody had called one. What survives is `progressOf`: how many of a node's child tasks are done, `3/5`, an annotation carried on `Row` and `Situated` for the view to draw beside a title. It feeds nothing — not `withoutDone`, which reads the stored mark, and not blocking.

**Blocked** is the other thing the marks are read for, and it is derived beside them: `after` (with `blocks` normalised into it in the one place that happens, so the acyclicity rule and this see one graph) says `a` comes after `b`, and `b` is in the way while it is a TASK that is not done. A target with no status never blocks — it is not work, so there is nothing under it to finish — and spelling the test `status !== "done"` is the trap docs/format.md writes the rule against. One predicate at both ends of the arrow, racket's own shape: a done node is waiting on nothing, a bullet is neither blocked nor blocking, and archived work is out of it in both directions because it is over. What a blocker IS is `InTheWay`: a node and the mark that makes it unfinished — and "unfinished" is not a sentence this says twice, it is `unfinished`, the one exported predicate that `blockage` here and `unfinishedWithin` over a branch are both built from, about the two different kinds of edge. The ordering graph is built in two passes — every node's own `after` first, then the `blocks` pointing back at it — so the order a reader with room for ONE blocker sees is a promise rather than an accident of where in the directory somebody wrote an unrelated edge; and both halves are filed under the node their target NAMES, mirrors resolved, so the acyclicity rule and this cannot disagree about whether two records mean one edge. It is a SET per source, which is the last thing that normalisation owes its readers: an edge named twice — a field repeating a target, both spellings written down, a placement named beside the node it stands at — is one edge, so a node is never told that one thing is in its way twice. Nothing outside this package asks for the index to DRAW with: what is in a node's way rides on the `Row` and the `Situated` it belongs to, the way its mark does.

**`Derived` is indexes, and five of them read backwards.** Everything above is a lookup rather than a walk, which is why the nodes travel WITH their tables rather than beside them: two parameters would let one revision's nodes be read against another's indexes, and the symptom would be a plausible tree rather than a failure. Six answer forwards — `byId` (first claim wins, the validator's own duplicate rule), `children`, `status`, `after`, `blocked`, and `byFile`, one file's records in DISK order, which is what "what does this outline hold" and "what are its roots" are now instead of a filter over every node in the directory. Five answer backwards, and the first three are the ones that know what an edit REACHED: `mirrorsOf` (the placements standing for a node — `follow` reversed, chains followed, so a mirror of a mirror is filed at the node and not at the hop before), `edgesTo` (`after` reversed, canonicalised by the same act that built it, so the two readings cannot disagree about whether two records mean one edge), and `namedBy` (the format's own `targetsOf` reversed — RAW, what the records SAY, because a refusal has to quote a field and the id somebody wrote rather than what it resolves to, and because `see` is a relation no derivation reads). The last two are not about reaching at all. `taggedBy` files every record under each tag its title or its note writes, keyed by the tag AS WRITTEN — `#herbs` and `@herbs` are two keys, never one, because they are two namespaces in every other reader of this format. Keyed by the tag rather than by a node, because `@alice` and `@order` are the same thing to a title and what makes the second a REFERENCE is that some record claims that id. Asking existence in the index would mean re-reading every note in the directory whenever a node was minted or dropped, so it is asked at the READ instead (`src/backlinks.ts`, `backlinksOf` — which also rules that a placement is not a reference, that an ordering edge is not one either, and that an archived referrer is left out; [docs/format.md](../../docs/format.md)’s References argues each). It has a SECOND reader now, and that is what the written-form key bought: `src/vocabulary.ts` asks it which tags the set uses and how many records carry each (the row editor's completion, answered over the `vocabulary.tags` procedure since `vault-in-browser` took the set out of the browser), where it used to walk every node of the corpus per derivation — **18.5ms walked against 0.47ms read** on the bench vault, and **12.2ms** for the title-only walk that was literally there (a smaller answer: 60 tags against 1,052, since it never looked at a note). All three are arms of one leg, because a ratio quoted against a reconstruction that does more work than the code it stands for is a flattering ratio. Filing the other sigil is not free — the corpus-wide fold goes **6.5ms → 18.6ms per REBUILD**, which `src/patch.bench.ts` prints as its own pair — and the trade is that a rebuild is the fallback path while the completion is asked per keystroke. That same leg prints what the WALK under both costs, because the widening made it the largest single thing a rebuild does: `titleParts` over the corpus's prose is ~12ms stepping its regex with `exec` (which is how it is written, since #249), ~16ms asking `matchAll` for an iterator per call (which is how it was), and ~9ms for the tag-only private loop this package declines to have — three arms checked to find the same tags before any of them is timed, so the decision not to take that last one is a number somebody can re-take rather than a sentence. `byDay` is the fifth, and the newest (`perf-dates-index`): a DAY → the dates that land on it, which is `src/occasion.ts`'s `datesOf` read backwards over the set — the journal, as an index. It is the one index here whose KEYS are promised in an order, ascending by day, because three readings step them and none may sort to get it: the calendar's month walks into the month and stops at its end, and the agenda walks back from today for what has slipped and forward for the next days that have anything. A decade of daily notes is three and a half thousand keys, and sorting them per read was the cost the node was filed over — the patcher pays for the promise the way `byFile` pays for path order, re-sorting only when an edit ADDS or EMPTIES a day. It is also the one index that leaves the trash out AT THE FOLD rather than at each read, and that is a considered difference from `taggedBy` above: that one is about what prose SAYS, so a storage rule inside it would be out of place; this one is about what a journal SHOWS, and a journal does not show what was put away (ruled 2026-08-17). The exclusion therefore stays spelled once for all three readings, which is what the walk it replaced was written to hold, and a month with a thousand archived records on it costs a reader nothing. What the three readings cost now, each against the walk it replaced, is `src/dates.bench.ts`: **the month's dots 0.02ms against 7.30ms (452×), a fourteen-row day page 0.01ms against 7.49ms (730×), the agenda and its count 1.67ms against 8.41ms (5×)** on the bench vault. The agenda's five is the honest one — finding its days is a walk of the index's keys now, but drawing them is still an ancestry walk per row, and 242 days owe something in that corpus. The fold costs **3.82ms per rebuild**, which is the whole of the trade: paid once where a walk was paid once per read, per subscriber, per published revision. The plan the first three are the first slice of is [docs/brainstorming/model-indices.md](../../docs/brainstorming/model-indices.md).

One caller asks the other end of it. `standingBefore` is what a node's `after` targets hold up whether or not the node is work yet, and `@olai/ops` refuses `set_doing` with it. The two readings part at exactly one place — an unmarked source, which `blockersOf` reports as waiting on nothing because a bullet is not being told it cannot start, and which a write that is about to MAKE it work has to hear about. They share `inPlay` and they walk the same graph, so the target side — bullets, done work, the archive — cannot come out two different ways.

`zoom` is the same claim about one node as a page — which record an id resolves to (following a mirror chain to the regular node at its end, so a node has one page and not one per placement), the canonical parent chain above it, and the rows beneath it. Where a node lives and what it is under are facts about the set, so they are answered here rather than carried in a URL that could disagree with the files.

`dates.ts` is the same claim about a DAY. There is no journal file and no stored year→month hierarchy: a day is a question asked of every dated node in every outline, so `datedDays` (which days of a month have something on them, in day order) and `datedOn` (everything on one day, grouped by outline, with each node's ancestry and mark) are one reading of the set that the calendar and the day view both read from — a dot that disagreed with the page it opened would be worse than no dot. Both are LOOKUPS into `Derived.byDay` since `perf-dates-index`, where they were passes over every record of every outline: the month's own keys stepped and stopped at, and one key taken. WHAT puts a node on a day is one module below them (`src/occasion.ts`) — the two fields, the mirror that carries neither, the trash that is on no day, and the fold the index is built with — because a fold cannot live above the reading it feeds. Dates stay TEXT here as everywhere else: a day is a ten-character prefix, a month a seven-character one, and a datetime counts for its own day (`occasion.ts`'s `dayOf`, `monthOf` and `timeOf`, which is where the slicing lives). Two SHAPES sit beside those readings and travel rather than compute — `DatedRequest` / `DatedAnswer`, what the calendar's dots are asked and answered with. They are here for `searching.ts`'s reason: since [vault-in-browser](../../docs/brainstorming/vault-in-browser.md)'s PR 4 the dots are walked on a server and drawn in a browser, so the question crosses a wire and a vocabulary spelled in the wire spec would be a second spelling free to drift from this one. `sameDated` beside them is the schema's own equivalence — what lets a server keep quiet on a revision that moved no dot.

TWO fields are read, not only `date`: a dated `done` (`{"done":"2026-08-11T15:40:03-04:00"}`) places a node too, because a journal without the work that was finished is missing the half of the day that happened. A dated `doing` or `todo` is read by neither question (2026-08-11, human): the format allows it, a journal is narrower than the format, and "picked up on Tuesday" buried the day under everything filed that morning. So a node with two dates is on two days, two dates on one day are one row, and each row says which of the node's dates put it there (`Occasion`), because scheduled-on and finished-on are two different sentences and only the reader can be told which one they are reading. A `done` holding `true` is on no day: it declines to say when, and inventing an answer would file every old `true` under today. The ARCHIVE IS FILTERED OUT, at the one FOLD every date reading here is built from (`src/occasion.ts`'s `dateInto`; ruled 2026-08-17, reversing 2026-08-11): what was put away is drawn on the trash page and nowhere else, so a day, the calendar's dots and the agenda all lose it together and cannot come to disagree about it. It is the exemption blockedness already takes at both ends — nothing waits on what is over — read once more for the question a journal asks. `is:trashed` still reaches the node itself at every door (`filter.ts`), because that clause asks a record for its dates rather than asking a day for its rows.

The same module answers the one question about a day that is not about nodes at all: which DOCUMENT is that day's note. `noteDateOf` is the whole convention — a `.md` whose basename is exactly an ISO date is that day's note, wherever in the tree it sits, and `2026-08-10-recap.md` deliberately is not — with `dailyNotesOn` (the notes of one day, in path order, both of them when two files claim one date) and `dailyNoteDays` (the days of a month that have one) reading it for the day page and the calendar's second mark. It is here rather than beside whatever draws a calendar for the reason the two questions above are one module: a mark and the page it opens must be one reading. Those two take the document PATHS rather than a derived set, which is the shape of the wire — a browser holds every path and only the bodies of what is on screen. Nothing about this is a rule the validator enforces: a daily note is a view convention over filenames, and no record mentions it.

THREE OTHER FILENAMES MEAN SOMETHING here, read the same way and for the same reason — by NAME, with no record saying so, in this package because a rule about what a file IS, spelled in two places, is two answers about one directory. `ARCHIVE` is what was put away; `inboxIn` finds where a captured line lands; `pinsIn` finds the SHELF the sidebar draws — a `Pins.olai` whose top-level nodes are pins, each an ordinary node whose title is an address the app would mint (docs/format.md's Pins). The last two are one walk, `outlineCalled`, because the rule is not "where the inbox is" but "how this format finds the file a directory named". WHERE olai MINTS one when a directory has none is a different question and stays a different function — `mintedInto`, which puts every file olai names for itself under `OLAI_DIR` (`_olai/`: the shelf, the trash, and since 2026-08-20 the inbox, reversing the ruling of the day before). `inOlaiDir` is that mint read backwards, for the one face that draws a LIST of files: the sidebar leaves those rows out of its tree because each of them has a door of its own in that column, which is a drawing rule and never a reading of the set. What a pin's title MEANS is deliberately NOT here: which PAGE an address opens and what a `?q=` on one means is this app's address space, which the format has no business knowing — so that half is the browser's, at view time. What an address IS, on the other hand, is this package's own (`address.ts`): `[document]#[element]`, one grammar for every feature that names something.

`shelf.ts` is that seam spent: the SHELF as a reading of the set — `pinsIn` for the file, its top level in `ord` order, and for each row `pinTargetIn` (the node an address names, asked of the grammar above, so the bare `#id` and the qualified `garden.olai#id` land on one id) resolved through `nodeNamed`. It is here because it is a walk of a whole directory, and the browser stopped doing those ([brainstorming/vault-in-browser.md](../../docs/brainstorming/vault-in-browser.md)): the server recomputes it per published revision and the sidebar is handed the answer, which is what keeps a bare pin's name live with no copy of it stored anywhere. It reads no title as a PAGE and never will — every row of the file travels, the browser's own parser decides which are doors — and `sameShelf` beside it is what keeps a revision that moved no pin from sending a frame.

`inbox.ts` is the same seam, one integer over: `inboxHeldOf` counts the top-level regular nodes of whichever outline `inboxIn` names over the set's paths — the same list capture walks — nested children and placements left out, zero when there is none. `sameInboxHeld` keeps a revision that moved no capture from sending a frame.

`agenda.ts` reads those same dates FORWARD: what is owed rather than what is on. `Owed` — the two numbers a mark outside the page prints — is a SCHEMA here for the reason its sibling next door is, and it carries `OwedRequest` and `sameOwed` with it: the counting happens where the set is and the counts travel, and the one thing the set cannot give the reading is the day it is counted against, so the READER's own today rides the request rather than being read off a server's clock. It adds no field and no rule — `date` says when, the mark says whether it is work, and the two together are the whole reading, so `date` with no mark is an occurrence that can never be late and `date` with `todo` or `doing` is due work. `isOverdue(node, today)` is that predicate spelled ONCE (`todo ∨ doing`, and `day(date) < day(today)` by plain string order, because dates are text here too — both sides through `dayOf`, so it answers about a day whichever shape of ISO value it is handed), and it is read by the days above now on the page's spine and by the tone a date badge takes, the way `blocked` is one predicate read at both ends of its arrow. `agendaOf` assembles the three stretches of one line — what has gone, today, the next days that have anything — out of `Derived.byDay`, read back through the same `groupedOn` and `byOutline` a day page is built from, so the agenda and the day it links to cannot be two readings. It WALKS that index's keys, back from today for what has slipped and forward for the next days that have anything, which is what the promised key order bought: it used to sort every day the set has, twice, per read — and since `vault-in-browser`'s PR 4 that read happens per subscriber per published revision. WHAT SLIPPED ARRIVES AS DAYS, like what is coming (`behind`, ruled with `agenda-spine` 2026-08-18): the page draws one continuous line of time rather than three boxes, so a day is where a node goes and late work has to bring the day it was owed on with it — the outline grouping stays INSIDE each day, for the page that still draws it. `done` is filtered from all three: this question is what is OWED, and what happened is the day view's. The ARCHIVE is out of all three as well, and not by a rule of this module's — it reads the index `occasion.ts`'s fold already left it out of, so a task put away after somebody scheduled it stops being owed on the same revision it stops being on its day. `keepingOwed` is the same answer with rows taken out of it — the filter over the page, applied to each of the three, so a day left with nothing stops being drawn and nothing is re-derived; the silences between the days that remain are not filtered but RECOMPUTED, because how long a wait is, is a fact about the days still on the line rather than data (`web/src/client/agenda/spine.ts`). `owedOf` counts an agenda that has already been read — how many NODES are in Overdue and in Today, never how many outlines they were grouped under — and it takes the ANSWER rather than the set for the reason `nothingDue` does: whatever marks the agenda from outside it (the client's directory entry does) counts the very rows the page draws, instead of walking the directory a second time and being free to disagree. Upcoming is deliberately no part of it — a task due next Tuesday is not news today, and a count that included it could never fall to nothing. TODAY IS AN ARGUMENT, never a clock: a derivation that read one would answer differently on the machine it ran on, and what day it is belongs to the reader (`web/src/client/clock.ts`).

`repeat.ts` is the smallest module here and the one with the most argument per line: the closed grammar a dated node says it COMES BACK in — `every day`, `every week on <weekday>`, `every month`, `every year`, and nothing else — plus the arithmetic that says when the next one is. It is text in and text out: `parseRepeat` reads a record's field, `printRepeat` writes the canonical spelling, and `./repeat.test.ts` holds the two to each other over the whole vocabulary, so what the picker offers and what the validator takes are one list read from either end. FOUR names leave the package — `isRepeat` and `REPEAT_GRAMMAR` for the two rules a write is judged by, `nextOccurrence` for the answer a completion needs, `REPEAT_RULES` for the surface that offers the vocabulary as a list — and the parser, the printer and the `Repeat` union stay inside, reached only by the tests beside them: a grammar with a parser on its surface is an invitation to a second reading of it. `nextAfter` counts with `calendar.ts` above and never leaves integers, which is the one reason this feature could be added to a package whose stance on dates is that they are strings. THE RULE RIDES THE OCCURRENCE THAT IS NEXT — completing one hands it forward (`@olai/ops`' `recurring`), so a finished record is a plain dated node and a recurrence has exactly one live head; that single sentence is what makes un-done/re-done churn unrepresentable rather than policed, and it is argued at length in the module header. The rhythm is the FILE's and never the clock's: one period after the node's own date, so nothing here reads a clock and a late completion spawns the occurrence that was genuinely next (docs/format.md's Repeating).

`stamp.ts` is the other direction, and every date value olai WRITES is minted there: `stampOf` produces a local ISO datetime carrying its offset, which is what the ops layer marks a node with. It lives beside the rule that ACCEPTS one so that what olai writes and what olai reads are two functions in one package rather than a writer above guessing at a shape. (The browser's clock turns an instant into date text too, for the question "which day is `/today`" — nothing it mints is stored, and that the two agree about where a local day ends is a test in `@olai/web` rather than an argument.)

A day's nodes and a zoomed page are built from the same `Situated` — a node, its mark, its rollup, what is standing in its way and its canonical ancestry — because that is one concept with several readers, not a shape two surfaces happened to agree on. A title torn out of its outline says nothing, wherever it is being drawn.

`documents.ts` is the third such claim, about the `.md` files beside the outlines. A document's text is content — verbatim on disk, markdown at view time, nothing about it validated — so what lives here is only what has to be answered the same way twice: where a node's `doc` lands (`docOf`, resolved against the outline that named it, which is the rule the validator checks and the view links with), and what a relative `![](…)` may name (`pictureOf`, `isPicture`). That last one is asked by two packages that cannot import each other — the renderer that rewrites a picture into a URL, and the route that answers it — and two allowlists that drifted apart would mean either a broken image or a served file nobody meant to serve. `isAsset` is the same question asked once more and one step wider: what the media route may ANSWER at all, which is a page and the parts a page draws itself with (a stylesheet, a script, a font) as well as a picture, because a previewed `.html` is fetched by URL and draws itself. The two are deliberately not one list — markdown may still name a picture and nothing else, which is a rule about what markdown MEANS. `bodiedOf` is the third thing markdown can point at, and the third reading of the same arithmetic: where a relative `[…](…)` to another `.md` lands. A vault linking between its own files writes those by the dozen, and resolving one beside the file it was WRITTEN in is what keeps it from being resolved against whatever page it is being drawn on — which is the same reason `doc` is resolved against the outline that named it. Whether the directory actually holds the answer is nobody's business here: this package knows the arithmetic, and the page that opens the address already has a screen for a document that is not there. Two things here are not arithmetic. **`linksIn`** is every ADDRESS a piece of prose points at, spent on a document's body and on a node's note alike, so a `[…](…)` means the same thing wherever it is written. **`firstLine`** is the closest a `.md` has to a title — its first non-blank line with the heading marks off — a DERIVATION because a document has no record for a name to be written on; it was `@olai/web`'s while the browser was the only caller, and moved here whole when `list_documents` wanted the same answer the row beside a `doc` draws. **`bytesOf`** is beside it as the other thing sayable about a document without reading it: its size in UTF-8 bytes rather than in the UTF-16 units JavaScript holds it in, so olai reports the number every other tool a person has reports for the same file.

What is deliberately NOT here is the SENTENCE a path that is not a document is refused with. This package declares what a refusal *is* (`failure.ts`); `@olai/ops` is the only layer that raises one, and it keeps that one too (`noSuchDocument`, beside `notFound`), because a floor that started composing agent-facing prose would be a second voice for the same "no". The facts the sentence is made of — `markdownIn` and `didYouMean` — are here, which is the line: facts down, voice up.

## What a served file IS

`src/document.ts` is the type the [first-class documents](../../docs/brainstorming/first-class-documents.md) arc exists to make, and `src/set.ts` serves it as the directory's ONE collection:

```
data Document = Outline   Face [Node]
              | Markdown  Face Text [Slug]
              | Hypertext Face
```

A sum of products, one arm per kind the registry claims, discriminated on the registry's own word for the file. Every arm carries the same **face** — a `DocumentPath`, a title, the `Address`es its content points at, the `Tag`s its prose writes and the `props` it writes about itself — and all of it is TOTAL. There is no `Maybe` to branch on, which is exactly what made "handle the nodes, skip the rest" the shortest way to write a feature: a document had no addressable identity below the file, so everything keyed on ids excluded it by construction, and graph view drew no `.md`, search walked past every body, backlinks could not name one.

Nodes did not become documents. They became the SUBSTRUCTURE OF ONE ARM — `Node` keeps every field it ever had, and what changed is its standing. The set no longer serves a `nodes` collection beside a `documents` one, so a feature has no node-only list to import; the records are reachable through the outline they are written in, and the one flattening left is the validator's, for the derivation.

The FACE IS DERIVED and it is built at the DECODE (`@olai/ops`' codec), once per file per change, which is where a walk of somebody's prose belongs — `assemble` is a collect. A markdown document's title is its first line, its links are where its `[…](…)` land, its tags are the `#topic` and `@person` in its prose read by the walk a note is read by, and its elements are the slugs of its headings (`src/slug.ts`, whose rule the browser's renderer spends too, because a slug spelled twice is an address this app writes and cannot open). Hypertext is a face and nothing else, and the emptiness is the registry's `kept: false` showing through: its `links` are empty because nothing read it, which is not the same claim as "a saved page points nowhere".

**Frontmatter is a document's own record, and it is `src/frontmatter.ts`.** A `---` block on the very first line, closed by another — micromark's rule, spelled out there because a vault is read by other tools too, and held to it by a test that renders every corner through `remark-frontmatter` and through this function (`@olai/web`'s `markdown/frontmatter.test.ts`) — read into the face's `props`, which is `Custom`: the same open map a node carries, answered by the same `prop:` clause through one `propKeyOf`. It is a stated SUBSET of YAML and not a parser: text, quoted text, flow and block sequences of text, and a refusal for everything else, one key at a time. What the block is NOT is prose — one `proseIn` is the skip `firstLine`, `headingsIn`, `tagsIn`, `linksIn` and the search's body fold all spend, and the BROWSER spends it too (the three faces that draw a whole file strip it before the markdown pipeline sees it), so the page and the face are one function rather than two rules. That is what keeps a `---` off the title, off the page, out of the heading list and out of the tag index — and what keeps it ON the screen in a node's note, which is not a file and has no frontmatter to hide. And it is not a RECORD: a frontmatter `date:` is a property named `date`, so `is:done`, `has:date` and `date:today` still select no document — the honest answer, since a document with a real day would have to be drawn on the day page, the agenda and the calendar.

`src/backlinks.ts`'s `referrersTo` is the reverse reading the face made possible: every document's forward `links`, read backwards, so a document's page can say who points at it. It is a lookup over the faces and then a walk of ONE file, through `recordLinks` — the same function that BUILT the face, because two walks of the same fields would be two answers to "does this record point there".

## Two readings of a set, and what they differ by

`src/changes.ts` takes two sets of records and answers with what CHANGED, node by node — created, archived, marked done, note rewritten. It is here for the same reason the writer is: it is a statement about records, and it has no idea where either side came from. That is what lets it serve two callers whose inputs are nothing alike — what is pending is HEAD against the working tree, a past change is a commit against its parent — with no git anywhere near this package.

It is never a text diff, and that is the format paying for itself in the other direction: a `.olai` diff is one enormous line per node with everything on it changing at once, which is exactly the shape that made line-based merges safe and exactly the shape nobody can read. Matching is by ID ACROSS FILES, so archiving reads as one change to one node rather than as a removal and an unrelated arrival.

`src/committing.ts` is the values that answer travels in — what is waiting, what was last recorded, what git is doing for the directory (`GitState`, with its before-first-frame `GIT_OFF`), whether the repository can take a commit, what asking for one answers with. Git plumbing is `@olai/ops`'s, and so is everything that never crosses the wire: how olai spells a commit message, and the values of the `--commit` flag. What is here is exactly what `@olai/surface` imports, which is why it is here at all — this package is the floor both that layer and the wire spec stand on, as the refusal vocabulary already is. Design: [docs/brainstorming/git-commits.md](../../docs/brainstorming/git-commits.md).

## What a read of the set asks, and what it says back

`src/reading.ts` and `src/searching.ts` are the same argument applied to the other vocabulary that crosses this floor. There are seven reads: four over NODES with one atom between them, one that is a BATCH of ids and shares that atom with nothing, and two over the other kind of file.

| declaration | what answers with it |
|---|---|
| `Site` | not a read at all — the `{file, line}` under all of them, `src/node.ts` |
| `Found` | every read. One node SITUATED — id, title, a `Site`, mark, ancestor titles, the edges it writes, and the `custom` properties it carries |
| `OutlineSummary`, `OutlineAnswer` | `list_outlines` — a count and the top-level titles, per file |
| `Detail`, `NodeAnswer` | `read_node` — the record, its tags, its children, its stamps, and a placement from both ends (`mirrors`, `placed`) |
| `Subtree`, `OutlineRoots`, `SubtreeAnswer` | `read_subtree` — nested, and saying where a walk stopped. THREE arms, because the read takes two kinds of subject: a node walked, a whole OUTLINE walked (`{file, roots}` — every top-level node in it, each walked, each with its own `truncated`, and a placement at the top level is not one of them), and the id the set does not hold |
| `SearchHit`, `SearchAnswer` | `search_nodes` and the ⌘K palette |
| `DocumentSummary`, `DocumentAnswer` | `list_documents` — every served `.md` with the line it opens with and what it weighs |
| `DocumentRequest`, `DocumentBody` | `read_document` — one body, whole and verbatim |
| `Pinned`, `Shelf` | the `pins` cell — the rows of `Pins.olai`, each with the node its address names and what that node is called at this revision (`shelf.ts`). The one shape here that is a READING rather than an answer to a request: nobody asks for it, the server sends it when it changed |
| `InboxHeld` | the `inbox` cell — how many top-level captures the directory's inbox holds (`inbox.ts`). The shelf's twin, one integer over |
| `NamedRequest`, `NamedAnswer` | `nodes.named` — which of these ids the set declares, and the node each one names. The one read that shares no atom with the others, because it says nothing about a node except that it is there: the chat panel asks it once per message about the ids an agent wrote in backticks, and what it needs back is a lookup rather than a record |
| `HomesRequest`, `HomesAnswer` | `nodes.homes` — WHERE these ids are, and which of these files this directory has READ (served, and not among the ones that would not parse — never "declares a record", which would read an emptied outline as unreadable and keep its folds for good). The other read that carries no node: the browser's fold memory asks it about what it has collapsed, so a node that was archived keeps its fold under the file it moved to and a node that is gone stops being remembered. It is not the row above with a `file` on it — that one FOLLOWS a mirror chain, because a backtick means the node a reader would be shown, and this one is the plain record lookup, because a fold is of a record |


`OutlineSummary`'s torn-file row is FLAT and knowingly so: `unreadable` beside a `nodes: 0` and a `roots: []` — a count nobody counted and a claim that the outline is about nothing, on the one file where neither could be known. Every field reads honestly alone; what is untrue is the combination, held apart by a convention a reader has to know. Splitting it into two arms, so the dependent facts exist only on the arm that grounds them the way `NodeAnswer` already does, was written and reviewed on this branch and then reverted: it changes what `list_outlines` answers, and that is the human's ruling to make. A roadmap question, not a defect.

The document pair shares no atom with the four above it, and that used to be the `md-second-class` asymmetry in one line. What can be said about one is its path, its title and its size — the title now READ OFF THE FACE the decode built rather than derived again here, so this listing, a search hit, a palette row and the page's own heading say one name. Its torn-file row is flat for `OutlineSummary`'s reason and written to match it, so one ruling fixes both. And `DocumentBody` has no `{ missing }` arm on purpose: an id is guessed at and worth answering, a path is not — a typo gets the near miss, which only a refusal can carry.

Plus what each one ASKS — `NodeRequest`, `SubtreeRequest`, `SearchRequest`, `DocumentRequest` — and the two numbers an omitted field MEANS, `DEFAULT_SEARCH_LIMIT` and `DEFAULT_SUBTREE_DEPTH`, which are here because the agent-facing prose beside each request quotes them.

The walks are `@olai/ops`' (`Query`) and stay there: which nodes match, how hits are ordered, which mirrors resolve to a node, how far a subtree descends. What is here is only the SHAPE — because the shape travels. Search's travels four ways at once already: an agent reads it off `search_nodes`, the `search.nodes` procedure carries it, the ⌘K palette draws it, and the header's search box draws it again.

It was spelled twice before — three times counting `Query.search`'s own parameter — once in each of the two packages that stand on this floor, and `@olai/surface`'s header claimed the two could not drift. They could: a field added to the ops-side hit and produced type-checked clean across every package, reached the agent, and was dropped by the wire schema's encoder on the way to a browser. One declaration is why that is now unrepresentable rather than merely detected — see [docs/brainstorming/surface-mcp-positions.md](../../docs/brainstorming/surface-mcp-positions.md).

Every field of a hit is a statement about records in this package's own terms: an id, a title, a `file:line`, a mark, the ancestor titles `ancestorsOf` walks, the edge lists a record carries — and, when the query said `withDesc`, the note. That one is the only record field a hit does not carry by default, and the reason is its SIZE rather than its meaning: every other field is bounded like the title beside it, where a note is unbounded prose, and this same request is what the ⌘K palette and two panels ask over the wire on every settled keystroke. It travels whole or not at all; `src/searching.ts` carries the ruling and the argument against a length. The three fields that are not statements about the record — `matched`, which field carried the words; `matchedProps`, which custom keys a `prop:` clause selected the node on; and the `refusals` an unreadable query answers with — are facts about a QUERY, and they sit on the hit and the answer rather than on `Found` for exactly that reason. The first two are two fields because both can be true of one hit and because `matched`'s four values are a closed, weighted list where a property key is an open namespace; `src/searching.ts` carries the ruling. `Refusal` itself is declared next door in `src/filter.ts`, beside the `parseFilter` that produces it, and is a Schema rather than an interface because it does not stay there: the filter over the tree draws its own, and the three doors that ask the server get theirs on the answer.

**The filter grammar is what the single declaration was for, and it proved it one day later.** #168 extended search with `file`, `under`, an optional `matched` and `refusals` — four fields the previous arrangement would have needed spelled twice and kept in step by hand, in two packages that cannot import each other. Seated here instead, they are spelled once: removing `refusals` from this file fails in `@olai/ops` (which produces them), `@olai/web` (which draws them) and `@olai/server` at the same moment, where before it would have failed on one side and compiled on the other. Dropping `path` from `Found` does the same across the same three packages, which is what makes the atom an atom.

**The other three moved BEFORE anything carried them**, which is the cheap end of the same lesson: they were TypeScript interfaces in `@olai/ops`' `query.ts`, so no wire spec could declare them and the second spelling was still ahead rather than behind. What the compiler cannot check on its own is a producer putting a key on an answer the declaration has never heard of — object-literal freshness is lost through a `.map`, so a field DROPPED here still compiles at the one place it is built — and `@olai/ops`' `tools.test.ts` closes that by walking the tool table, calling every read's own reader, and decoding each answer through the declaration that entry carries with `onExcessProperty: "error"`, the same setting `parseOutline` reads records under.


`src/vocabulary.ts` is the seventh read, and the one that is not a query at all: **which tags this set already uses, and how many records carry each.** It is the reading over `taggedBy` that `src/backlinks.ts` is over the pair — the keys of that map, the length of each entry, the trash taken off, most-used first — plus the prefix test one popup applies to it, and it carries its own three shapes (`TagsRequest`, `TagCompletion`, `TagsAnswer`) for `searching.ts`'s reason. ONE export, `completingTags`: the enumeration and the match are two functions inside because they cost differently, and a consumer composing them by hand would be a consumer holding the composition. It ran in the browser until `vault-in-browser`'s PR 2, which took the set out of the browser; it now answers the `vocabulary.tags` procedure, memoised once per revision so a settled keystroke pays the match and nothing else. No grammar and no score: nothing here can disagree with `search_nodes`, because nothing here is asked of the matcher. The cap rides the REQUEST rather than living in the shape, because a row count is a fact about the door that asked.

## What a write ASKS for, and what one that landed says

`src/writing.ts` is the third time this move was made — after `committing.ts` and `reading.ts`/`searching.ts`, and for the identical reason. It holds the twenty-two request schemas, the `WriteRequest` union over them, and `WriteResult`, which is what an op that succeeded answers with.

**Twenty-two schemas, twenty-four write tools**, and the gap is not a typo: the three marks share `MarkRequest`, because the format allows at most one mark and `set_done` / `set_doing` / `set_todo` differ only in the `op` their own NAME fixes. `@olai/ops`' table generates those three off the format's own `MARKS` list — which is the point of keying them, since a mark that was plannable and writable everywhere and had no tool would otherwise be silently missing.

It moved here from `@olai/ops` when the writes went onto the surface: `ops.run` is a procedure now, so the request an agent sends and the answer it gets back are values that CROSS this floor. The ops layer produces them, the surface carries them, and `@olai/ops` re-exports the two under its own names — `Request` and `Applied` — the way `Pending` and `CommitRequest` are already re-exported by their consumers rather than declared twice.

Both are renamed at the move, and the second rename is the load-bearing one:

- `Request` → **`WriteRequest`**, because among `NodeRequest`, `SubtreeRequest`, `SearchRequest` and `CommitRequest` a bare `Request` is the one that does not say which question it is;
- `Applied` → **`WriteResult`**, because `@olai/surface` exports an `Applied` of its own and it is a DIFFERENT type — the keyboard's answer, which adds `undo` and drops `summary`, `sort`, `captured` and `rev`. Two things called `Applied`, both about a write that landed, both carrying `id`/`title`/`nudge`, is the `Outline`/`OutlineSummary` trap again: not a rename away from a compile error, a rename away from a plausible one.

The PLANNER stays in `@olai/ops`, exactly as the matcher and the walks did. What is here is only the shape, plus the two numbers the shapes impose — `NESTING`, the depth to which `add_node`'s `children` is unrolled, and `BATCH_AT_MOST`, how many ops one `apply` may carry. Both live beside the schema that quotes them, and both are facts about what an agent READS (a JSON Schema an MCP host can hold; a refusal a reader can hold) rather than about the format.

**Two of the twenty carry the others** (`olai-batch-verbs`): `UpdateRequest` names several fields of one node, and `ApplyRequest` an ordered list of the write verbs. `ApplyRequest`'s arms are the request schemas THEMSELVES — each already carries the `op` literal that names it, so a batched `set_done` and a called one decode against one declaration and a parallel list of "batch forms" never exists to fall behind. What is taken off on the way in is only the top-level PROSE (`arm`, `TERSE` one level up): every one of those sentences is already in the same `tools/list` frame, on the tool that takes the request, and leaving them doubled cost 8 kB of the first frame of every agent session. Left out of the list are the three writes whose subject is a FILE rather than a node, and `apply` itself.

## Writing is here too, and for the same reason reading is

`src/write.ts` is the only thing in olai that turns records back into bytes, and `src/ord.ts` is the only thing that decides where a node sits among its siblings. Both are statements about the format rather than about whoever is writing, so they live beside the rules that judge them.

The writer takes the records of a WHOLE FILE and gives back the whole file, so every separator has exactly one owner: the newline between two records, the one at the end, the absence of a blank line. That shape is the point. A caller that built its own bytes once produced two records glued onto one line — a file no reader could parse, out of a write every layer above believed had succeeded — and `write.test.ts` asserts the invariant directly, by parsing back what the writer produced for every shape of record the format has.

It also gives "absent" ONE spelling. An optional field holding nothing — `undefined`, `null`, `[]` or `""` — is not written, so `{"after":[]}` cannot reach a file however a writer arrived at it. That is the same bet as the line format itself: two files that mean the same thing must not differ byte for byte, or a line-based git merge conflicts over nothing. A *required* field is written whatever it holds, because dropping one makes a line the reader rejects outright — worse than handing an odd value to the validator that is about to see it anyway.

`ordBetween` is a fractional index over base62 in ASCII order, so the plain string comparison the format promises IS numeric order in this encoding. It answers `null` for the one pair with no answer — nothing sorts between `x` and `x0` — rather than inventing a key in the wrong place; the ops layer renumbers that row instead.

`src/failure.ts` is the other half of the error story: the four KINDS a write refuses with (`usage`, `not-found`, `validation`, `busy`), as schemas, so a refusal travels the wire and an MCP tool result as itself. Four classes rather than one with a `kind` string because they carry different things — only `validation` has a report to show, only `not-found` names what was missed — and a single struct would make every field optional and push "which fields are meaningful" back into prose. There were five: `derived` refused a write that would have stored a computed status, and went with derivation itself.
