# @olai/surface — the typed reactive layer, declared once

The spec both ends speak. The server implements it and the browser subscribes to it, and neither writes a line of wire code: no raw sockets, no hand-rolled routes, no message envelopes. Because the two sides read the same declaration, they are a type error away from disagreeing about the protocol rather than a runtime surprise.

Built on kolu's surface framework (`@kolu/surface`, hydrated from the Nix store rather than installed — which is why it is absent from this manifest and declared once at the workspace root; see `bunfig.toml`).

## The members, and the shapes are the argument

Which kind each member is was a decision. Three are the outline:

- **`outlines` is a collection keyed by root-relative path**, read-only on the wire and served with the batched `deltas` verb. The files belong to the disk, not to the server, so the server reports what it read rather than owning a value it could be asked to change. The unit is one FILE: a probe tick that touched one outline sends that outline's entry and not the corpus, and a `git pull` that rewrote forty of them is still one coalesced `{upserts, removes}` frame. A (re)subscribe opens with the whole keyed set, so a reconnect is a fresh read and nothing has to be resumed.

  **NO BROWSER READS IT** since `vault-in-browser`'s PR 10 (`@olai/server`'s `faces.ts`): a tab held every record of every file and answered every page out of that copy, which is the ruling that arc reversed. It is the AGENT's member now — watching one outline's records, keyed, with deltas, is exactly what a request-shaped reader wants — and what a tab reads instead is `heads` for the directory and `page` for the page it is drawing.

  The key is DECLARED — `keySchema` — rather than inherited from a client   library's default, which is the type-level half of why this member was   re-modelled at all   ([brainstorming/outlines-as-collection.md](https://github.com/juspay/oss.olai/blob/main/projects/olai/brainstorming/outlines-as-collection.md)).
- **`manifest` is a cell**: what is true of the SET rather than of any one file — today, nothing but whether there is one at all, since every other fact about this directory belongs to a file and travels on that file's entry. Its `null` is the state a collection cannot express: an empty snapshot means "this directory holds no outlines", and a first probe that has not finished has to say something else. So a reader tells three states apart from this one member — no frame yet, `null`, a value — exactly as it did from the nullable stream frame this replaced.

  It carries NO set revision, and that is what keeps every document's text off   the wire: a revision belongs to a file, each entry carries the one it was   published at, and a second copy of it here would have made this value differ   on every probe tick. Without it the cell's `equals` holds, and a tick that   touched no `.md` publishes nothing at all.
- **`errors` is a cell**, read-only on the wire, because "what is wrong right now" is one value the server does own. It is deliberately independent of the entries, and that independence is load-bearing: a directory that cannot be READ leaves the last good tree on screen underneath a banner, which is only expressible if the two arrive separately. Since the per-file ruling of 2026-08-29 that is the ONLY thing it carries — a broken outline does not stop the set loading, so what is wrong with it rides on its own entry (`OutlineEntry.broken`, below) and this cell is empty over a directory that was read. What it carries is the validator's **verdict** (`@olai/format`'s `verdict.ts`) rather than a flat list of rows: the rows are in it and travel whole, and the questions a consumer used to re-derive from them are answered off the value (`blamed`, and `summaryOf` over what it files).
- **`git` is a cell**, read-only on the wire, and it is here because of a bug: writes came back not committed on a directory its owner knew was a repository, and the reason went to the server's log where a browser reader never sees it. Whether this directory is a work tree, and whether the last commit worked, is one value the server owns about the DIRECTORY rather than about any file in it — four states (`off` under `--no-commit`, `repo`, `none`, `error` with git's own words). The app header draws them on the ONE control it has for git, the Commit pill, which reads this cell beside `pending`: a quiet `✓ committed`, a dim `commits off` and `no git here`, and a `⚠ git error` carrying what git said. It is read on the MCP face too, as a resource, and that is not a duplicate of the browser's reading — an agent in a terminal asks the same question and gets the same answer, which is HACKING.md's consistency rule rather than a convenience. Its shape is `@olai/format`'s `GitState`, re-exported rather than declared: the ops layer produces the value, this spec carries it, and one declaration on the floor both stand on leaves no second spelling to drift.
  It carries three more facts that are not the repository's own state: the POLICY this directory runs under (which the two preference rows draw, always read-only — flags plus the built-in defaults), what git said when it last refused a PUSH (`pushSaid`, which takes the ✓ off the pill — a growing unpushed count with the reason nowhere is the bug that feature is named after), and whether the quiet-window loop is PAUSED and why (cleared only by `git.resume`). Each of them used to live in one browser tab, so two tabs could disagree about one directory and a reload lost the answer.

`OutlineEntry` carries a file's nodes, its `rev`, and its `broken` — and the last of those is the per-file error scope as DATA: a file the validator found something in KEEPS ITS KEY and carries its errors, so the sidebar still lists it and its own pane is what shows the trouble. Every kind of breakage lands here now, where it used to be only a file that would not PARSE. The two error channels are not a duplication and their split is sharper than it was: an entry's `broken` says which outline is broken and why, because that is a property of the file the pane is drawn from, and the cell says the DIRECTORY could not be read at all, which no file owns and which leaves no listing to hang one off. A file with `broken` is being rendered around; anything in the cell means nothing is being served.

**Entries of one revision arrive together; entries of DIFFERENT revisions coexist.** Only the files a tick touched are upserted, so an unchanged neighbour keeps the `rev` it was last published at — a consumer rendering B's subtree from A's mirror must tolerate A@42 beside B@41 for a frame. That is deliberate and it is the price of the wire being O(changed files); the design doc's cross-file consistency paragraph is the long version.

TWO more collections are keyed by a served file, and the pair is the argument. **`documents`** is one entry per `.md` and per `.html`, served `keys` + `get` and deliberately NO `deltas`: the batched verb is a push of every entry, which for this member is every body, so a reader takes the key set and opens a per-key `get` for the one file it is showing. **`heads`** is EVERY served file with the content left off — one revision each, each file's FACE, and whether it parsed — and it takes the `deltas` the other cannot afford, because that is roughly what the key set already costs. It widened from the bodied files to all of them in PR 10, and that is the design's §3 Sidebar row arriving: the file tree is paths and faces, which is key-set-sized, and it was the last thing a browser read the outlines collection for. So its keys are a SUPERSET of `documents`', and that direction is the one a reader relies on — the file list comes from here, and a bodied file's head is always here to open its body against. The face is the cheap half of a file (`@olai/format`'s `Face`: what it is called, the addresses it points at, the tags it writes) and it is the only way a tab can have it at all — the content is fetched by whoever is showing one, so a browser holding the key set alone knew a file's PATH and nothing else about it, which is the position every feature was in before the [first-class documents](https://github.com/juspay/oss.olai/blob/main/projects/olai/brainstorming/first-class-documents.md) work. It is what lets a palette row carry a name and a document's page say who points at it without fetching a word of prose. **An outline's face is on the same footing now**, and that is what PR 10 changed about this paragraph: it used to be here for cost rather than necessity — a browser COULD build one out of the records it held, at a walk of every title and every note of the corpus per revision, where the server built it once when the bytes changed — and a tab holds no records at all any more, so there is nothing it could be built from. So there are two questions about a served file and each has a member the right shape for it: what does it SAY, one at a time, and what IS it and has it MOVED, all of them at once. (Documents used to be neither: a `documents` array on the `manifest`, every body in the first frame of every subscription, which is what `snapshot-scale` cut out.)

A previewed `.html` is why the second one exists. Its page draws a frame pointed at the file's own address on the media route, so the bytes reach the reader over HTTP and the socket's only job is to say the file changed — and saying that through `documents` meant sending a saved page's megabytes to a tab that drew none of them, ahead of the fetch that did. Both slices are built in one pass over one list on the server (`@olai/server`'s `published.ts`), the bodied one a filter of the whole, which is what makes the containment an edit to break rather than a drift.

`DocumentEntry` carries a third state besides a body and a missing body: `refused`, for a file that is served and will not open. It is not a parse failure (`Head.broken`) and it is not an absence (the key is here). A one-shot `resources/read` is handed that frame rather than held open on a body that will never come.

**`pins` is a cell, and the first member here that carries a READING rather than the files.** The sidebar's shelf: the rows of the directory's `Pins.olai`, and for each row that addresses a node, that node's id and what it is called at this revision (`@olai/format`'s `Shelf`, re-exported rather than declared, the way `Pending` and `GitState` are). A cell rather than a stream or a procedure because it takes no argument — nothing about a shelf depends on who is asking or what they are looking at — and the server knows when the directory moved, so no browser has to hold a token to ask on. Re-answering it per revision IS the feature rather than an optimisation: a bare pin stores an address and never a name, so a node renamed anywhere says its new name on the shelf on the frame the store publishes it. Its `equals` is what makes that cost nothing — the reading mints a fresh array per revision, and almost none of them have anything new to say about a shelf of five doors. It is the browser's face alone: an agent reads the shelf as the ordinary outline it is. It was the first member of the shape `page` below now is: one that carries what a reader DRAWS rather than every record they would have to walk to work that out ([brainstorming/vault-in-browser.md](https://github.com/juspay/oss.olai/blob/main/projects/olai/brainstorming/vault-in-browser.md)).

**`inbox` is that same kind of cell, one integer over.** How many rows of the inbox are marked `todo` or `doing`, at any depth (`@olai/format`'s `InboxHeld`) — an unmarked row is furniture and a placement is not a node. No argument — it is a fact about the directory, not about the reader — which is why it is not a stream the way `owed` is. The door that wears the number already knows which file the inbox is, from the paths. The browser's face alone: an agent asking what the inbox holds asks `list_outlines`.

One more pair is GIT:

- **`pending` is a cell**, read-only on the wire: what is waiting to be committed AND what olai last recorded, which the server DERIVES from git on every published revision, whenever a commit lands by any door, and on a slow sweep of its own — nothing watches `.git`, so committing in a terminal changes this without changing one served byte. The two facts ride together because they are one question asked twice: an empty pending list cannot say whether anything was ever committed here, and `last: null` is what says "never". Its default is the empty value rather than `null`, and there is no third state to tell apart: a page that has not heard yet, a directory that is not a repository and a server with `--commit=off` all draw the same thing, which is nothing. It carries an `equals`, so a sweep that finds nothing new sends nothing.
- **`git.commit` is a procedure**, not a write verb on that cell. Committing is not "set pending to something": it is an act with four answers, three of which are refusals a reader has to be shown — the repository is busy, nothing was waiting, git said no.

FOUR are STREAMS, and this surface had none until `vault-in-browser`'s PR 4 — the sidebar's month of dots and its count of what is late (`src/dates.ts`), and since PR 10 the two the whole design was for (`src/page.ts`):

- **`dated` and `owed` are streams**, which is a CELL WITH AN ARGUMENT: read the answer, listen for "the directory moved", re-read, and send a frame only when the answer changed by value. That is exactly the mechanism the design doc's §2 describes for every page reading to come — `equals`-guarded, recomputed per revision — and the framework owns the plumbing (`{ read, install, isEqual }`, and `@olai/server`'s `runtime.ts` supplies all three).
- **The argument is why neither can be a cell.** One is about the month somebody PAGED TO, which is chrome state living in the sidebar; the other is counted against the READER's own today, which the server cannot know — the dates in the files are what a person wrote down, so what is late is late where they are standing, and two tabs either side of midnight are owed two different answers.
- **And why neither is a procedure**, which is what the two search doors are. A search is asked once and read; these are STANDING views — a date set anywhere has to light its day and move the count with no reload. Asked as procedures they would need a generation to re-ask on, and the only generation a browser has is its own copy of the derivation, which is the very thing this design is taking away.
- **What travels is the READING and not the walk.** `@olai/format`'s `datedDays` and `owedOf(agendaOf(…))` are unmoved; they are called on the other side of the wire now (`@olai/ops`' `Query.dated` / `Query.owed`), and the request/answer shapes are that package's too, re-exported here rather than re-declared for `src/search.ts`'s reason. The owed member carries the two COUNTS and never the agenda: the three stretches the agenda PAGE lists arrive on `page`, below.
- **`page` is the member this whole design was for** (`src/page.ts`): an ADDRESS in, and what that page draws out — its rows with their fold keys, marks, blockers, rollups and child counts, a zoomed node with its crumbs and its backlinks, a day's groups and note paths, the agenda's three stretches, the trash's archives and what emptying would take, and the names of every id the page points at. One subscription per open pane. Its three legs are `dated`'s, which is the point: the mechanism §2 named for "updates to that" turned out to be the one already under the two date readings.
- **`narrowing` is beside it** (`src/narrowing.ts`), and it is the page's FILTER: the same address plus the words in the box, answered with which of that page's nodes the query selects. It was a procedure (`search.matching`), and it was the wrong shape — a filter is a standing view, so a browser had to re-ask it on a generation that moved once per page frame, and every ask walked the whole vault; nine of them for one bulk gesture on a 90,000-node vault ([brainstorming/filter-rides-the-page.md](https://github.com/juspay/oss.olai/blob/main/projects/olai/brainstorming/filter-rides-the-page.md)). Every reader of the answer was a membership test against a row the page already draws, so the walk is the page's now and the re-read is the pulse's. A SECOND stream and not a field on `page`: a subscription re-opens whenever its input notifies, and a query carried on the page's own request would re-send every row of the page for each settled keystroke. The two move on different clocks — the page on the directory, the narrowing on the directory AND on a pair of hands.
- **`moving` is beside them**, and it is the one question in the app that is about the vault and not about any page: whether a row can go where somebody is pointing, for the destinations the move picker's SEARCH just offered. It is a stream rather than a procedure for `page`'s reason — a panel stands open while anybody writes, and what it judges has to be where the row has actually got to.
- **Read-only by construction**: a stream has one verb, `get`, and no write shape to withhold. All five are the BROWSER's alone (`@olai/server`'s `faces.ts`) — an agent asking what is late asks `search_nodes` with a date clause and is answered with the NODES, an agent asking what an outline holds asks `list_outlines` and `read_subtree`, and the `surface://` resource vocabulary has nowhere to put an input anyway.

Four more are the chat, declared next door in `src/chat.ts` because they are a subject of their own:

- **`transcript` is a collection**, served with the batched `deltas` verb. That verb IS snapshot-then-deltas: a subscriber gets every entry that already exists in one frame and then one coalesced frame per tick. So a tab opened halfway through a turn, a tab reloaded after a crash and a tab that has been listening since the first token all see the same conversation, with no replay protocol and no client-side merge. Keying it is what makes a TOOL FRAME updatable: the agent reports a call, then reports it again with a status, and the second report is an upsert on the same key rather than a second row.

  A tool entry carries what its call CHANGED, and structured — never as prose   for a browser to parse back. Two shapes, because there are two kinds of write   and they may not be drawn the same way: a `FileDiff` per file the agent   rewrote directly (path, what it said, what it says now — the client derives   the line diff; the shape is `@olai/acp`'s, re-exported here the way the ask   vocabulary is, because it is ACP's diff report in olai's spelling), and a   `Wrote` for a write that went through the ops layer, which is the node-level   story in the format's own classification because a `.olai` diff is one   enormous line per node.

  `ChatEntry` is a union of those six kinds, discriminated on `kind`. The   encoding of every row the writer produces is unchanged — the same flat   object, optional keys omitted. The decoder now also requires the flags' only   honest value (`streaming` / `stranded` are `true` when present) and the   fields a kind always carries (`status` on a tool, `ask` on an ask, `refusal`   on a refusal), so a non-call row with a `status` is a type error rather than   a fact every consumer re-establishes. A key that does not belong to the   matching arm (`status` on a user row) is dropped at decode rather than   re-emitted — sanitizing, not a second encoding.

  Every entry also carries `since` — WHEN olai first heard of it, minted beside   `seq` by the transcript's one writer, required for the reason `seq` is — the   transcript is the only thing that mints a row and it stamps every one — and   sticky across every later report of the same row. `seq` is where a row sits and `since` is when it arrived, and   the second is on the wire for the same reason the first is: this member is   snapshot-then-deltas, so a duration measured from when a TAB happened to   start looking would have three tabs saying three different numbers about one   call, every one of them short. The chat panel's elapsed readout is the reader   today; it draws the stamp only for a call the wire still calls running whose   turn has not ended. That second half is `stranded`, the sibling of   `streaming` — derived by the same writer, only ever `true`, written onto every   call a turn leaves behind. It is on the ROW rather than being read off the   cell's "is a turn in flight" because a dead agent's rows are deliberately not   cleared: the next thing anybody sends would otherwise make every abandoned   call look like work in progress again, all at once.

  The framework audit asked for "events paired with a collection", because an   event replays nothing to a late joiner. A `deltas` collection is that pair in   one member — the push and the history are the same frames down the same   subscription — so publishing each entry to an event as well would be one fact   delivered twice and a dedup rule in the browser.
- **`saying` is the row still being said**, in pieces, and it is why a streaming answer costs the socket the answer. Every chunk used to be published as the whole row it grew, so what crossed the wire over one turn was the sum of the answer's own prefixes: 1,039,111 bytes for a 3,218-byte answer, in one frame per chunk (`transcript-stream-quadratic`). A `Saying` carries the row it belongs to, the offset in that row's text where it starts, and the new text — nothing else — and the server holds a piece for `SAYING_MS` and merges everything contiguous that arrives inside that window, so a turn is frames on a clock rather than frames per token.

  A SECOND MEMBER rather than a change to how the first is delivered, and the   join is what makes that safe: a piece that ends at or before its row's own   length adds nothing, and one that ends past it contributes exactly the part   past it. So `transcript` goes on answering a new subscriber with WHOLE rows —   the replay and the reload are untouched — and the two members can be   snapshotted a moment apart, in either order, and converge. A row's own   publication is always the last word about it: every upsert carries the text   complete, so the server drops a row's pieces in the same frame that publishes   it, and a cancel mid-stream is that same rule rather than a case of its own.

  `SAYING_MS` is exported beside the shape because BOTH ends spend it: the   server's window and the panel's markdown re-render are one cadence, and a   second number would be either a render per frame with a throttle that never   bites or a throttle a beat out of step with the frames it throttles.
- **`chat` is a cell**: which session this is, what it is called, which model is running, what slash commands the agent offers, whether a turn is in flight, and which MCP servers this conversation has. One value the server owns, read-only on the wire.

  That last one (`servers`, a `ChatServer` per server) is on the cell rather   than in the transcript because it is a standing property of the conversation   and not something that happened at a point in it — a notice row would scroll   away under the first answer, which is exactly where a reader is when they   wonder what the agent can see. Each row carries a `standing`, and which one is   true is decided by WHO said so: `handed` is olai's own knowledge that it put   the server on the wire, `connected` and `unattached` are the AGENT's word   about what it then did with it, and `missing` is olai's probe refusing to hand   one over at all. The two arms that mean "this conversation does not have it" CARRY the reason —   discriminated rather than sitting beside a nullable field, so a failure with   no sentence cannot be constructed — in the server's, the probe's or the   agent's own words, because "it did not attach" is the one thing every way of   failing has in common and the one thing that never helped anybody, and `where`   is the URL or the absolute file the entry named. Empty means there is no   conversation rather than that everything is fine, and a server that is not   installed is on no row at all: nothing failed — unless something already said   it should be there (`PADI_SOCKET`), which is the one absence that is a fault   and the one `where` that is `null`.

  It replaces `mcp-fail-visible`'s failures-only `missing` because the question   people actually ask is the whole of it: an opencode asked which MCP servers it   had listed two and omitted kolu, then called kolu's tools perfectly. What is   NOT on the cell, and cannot be, is the agent's OWN servers — configured where   olai never looks, reported at most once a turn by an agent free to reconnect   one in between, and absent entirely from the leg that forwards nothing. The   panel says "plus the agent's own" rather than letting the list read as   complete.
- **the procedures are the verbs**: send, resend, cancel, new, load, the list the picker draws, and `attach`. Each declares its failure channel, so "a turn is already running" arrives as a `busy` a caller can branch on rather than as an opaque transport error.

**THE DOORBELL is four members and not one**, and where each of the four sits is the whole of its argument. A plugin may put a sentence into a conversation (`@olai/plugin-api`'s `Deliveries`), and this surface carries what both ends need to say so.

- **`UserEntry.rang` is a NAME, on the row**, and absent on nearly every row because nearly every row is a person's. A machine's sentence rides the human's own lane — that is the lane a prompt goes out on and the lane every word about a prompt's fate is already written for — so the mark is what lets the browser draw it with a face of its own instead of in the bubble that means *you said this*, and what takes the *send again* press off it: re-sending a machine's derivation an hour later re-sends a claim that has stopped being true, and whatever derived it rings again by itself. A NAME rather than a flag, because "a machine" is not who rang — a reader of a conversation two plugins can reach needs to know which door it came through, and the browser needs a word to look a face up by. This file spells no plugin: the value is walked out of the registry at the composition root, the way the roster's rows are, and the plugin that rings never supplies it, since a caller-asserted name is a name one plugin could sign another's row with. **It does not survive a replay**, and that is a limit stated rather than a defect to fix here: a conversation resumed from the agent's own store is rebuilt out of message chunks, which carry text and nothing else, so the mark is a LIVE affordance and the durable account is the sentence — which is why `deliver` requires a body to open with its own attribution.
- **`ChatState.wake` is an array on the chat cell** — one `Wake` per plugin whose doorbell a person pointed at a file: whose it is, which file, and how many of its sentences this end is holding and has not let in yet. Empty is the doorbell OFF, which is not a degenerate case to skip past but the state every conversation starts in and the state nearly all of them stay in. It goes WITH the conversation and is cleared when one ends rather than carried across, because drawing the last conversation's file over the next one would be an inheritance nobody asked for. Its key field is `name` and not `plugin`, and that is not style: the cell declares `arrayKey: "name"`, which reaches every array at every depth and merges by POSITION any whose elements do not carry it, so an element field spelled otherwise would make two frames' rows silently swap identity the moment somebody scoped a second plugin.
- **`chat.scope` is the procedure behind it** — this conversation wakes on that file for that plugin's doorbell, or with `file: null` on nothing. It takes the exact `(agent, session)` pair `loadSession` does, because a session id means nothing to the wrong agent and the panel's own session can move under a picker somebody left open. It is **MANUAL and per conversation**: there is no serve-level default and no way to arrive at one. And it is the BROWSER's alone — `@olai/server`'s `faces.ts` names it on `BROWSER` and deliberately nowhere else, so an agent cannot set what wakes it; `faces.test.ts` pins the agent face as an exact set, which makes that physics rather than a promise.
- **`Wake.fault` says that row's doorbell is not watching the file it names, and which of the two ways** — `gone` for a file renamed, moved or deleted out from under a scope somebody set, `unwatchable` for one that is right there and whose KIND that doorbell cannot read. Either way it derives nothing forever, so the conversation goes quiet in a way that reads exactly like a subject with nothing to report; the control has to stop drawing as ON, or the panel is asserting something untrue. It is the ONE piece of this feature's vocabulary that is core's own, and the boundary is exact: core is saying that a file IT STORES is one it cannot find, or one it is holding against a declaration it was handed — facts about core's own record. What the CONVERSATION was told is the plugin's declared sentence for that cause (`@olai/plugin-api`'s `PluginServerHalf.wake.gone` and `.unwatchable`), delivered once and never repeated on the strip. Nullable rather than an optional key, though the record behind it writes the word-or-absent: a face draws one of three things, and an absent key would be a fourth state for it to have an opinion about.
- **`BuiltPlugin.wake` is the STATIC half, on the roster cell** (`src/plugins.ts`): the three strings the strip draws its sentence out of — what the wake is ON, what the file is called as the lead-in to the picker, and what this plugin's held sentences are called in both numbers — plus `kinds`, which is not words at all but WHICH FILES the picker between those words may offer. Three strings and not one, because a sentence with a hole in it would make core the author of everything around the hole: core has the NUMERAL and supplies no word for what is being counted. The kinds are `@olai/format`'s own file-kind words travelling as data, and they are the plugin's for the same reason the words are — a plugin derives its watched set out of a file, so which files it can derive anything at all from is its fact and nobody else's. They ride as plain strings and not literals, so a serve naming a kind this build's registry does not know narrows the picker to nothing rather than failing the roster's decode and taking every plugin's mount with it. It rides the roster rather than `ChatState` because it is compiled in and moves at most once per serve, where the cell moves per frame per conversation. `optionalKey`, and that is load-bearing rather than tidy — a required field fails DECODE for a new tab talking to an older server, and the roster's failed arm is what the browser's subscribe licence is read out of, so one missing key would take every plugin's mount down and not just this one's. Only on a row that is RUNNING, since a picker offered for a plugin this serve did not compose would store a pick nothing will ever read. WHAT THE PICKER IS MADE OF and not the sentences: the plugin declares two more strings, for the two ways its doorbell can stop watching, and both are DELIVERED into a conversation rather than drawn — so `@olai/server`'s `rosterOf` copies the four picker members by name and the wire has no key for either message.

`resend` is the odd one, and what makes it odd says something about the other eight: every one of them acts on the CONVERSATION, and this one acts on a ROW — the `user` entry the agent would not take, named by its key. It is a verb rather than a second `send` because a browser cannot rebuild that message: the row carries its pictures by name and the prompt carries their paths, so what the server kept is the only whole copy of it. Nothing drains it either; a person's click is the only thing that does.

`attach` is the one that carries BYTES, and both halves of that are decisions. It is a PROCEDURE rather than an upload route, because a procedure inherits the origin gate and the session the listener already enforces for the websocket, where a second HTTP route would need its own copy of both. And it is CHUNKED, because a frame that scaled with the file would eventually be an oversized one, and the wire answers that by closing the socket rather than failing the call — taking every other subscription on that tab down with it. HOW it is cut up is not this package's: the arithmetic sits beside the cap it is derived from, in `@kolu/surface/frame-chunking`, and both ends import it from there. `attach.ts` carried a copy of that derivation until the pin that installed it — copied from kolu's own padi, where a 26 MB drop had proved it the hard way — and a margin kept in two places is a margin that eventually disagrees with itself.

What `src/attach.ts` still holds is olai's POLICY: 50 MB per file, which is a separate number from a chunk on purpose (a cap smaller than one frame would mean the chunking never ran), and it lives here for the same reason the media URL does — the browser gates on it before encoding and the server gates on it before writing, and two copies of a threshold are two thresholds.

The same module holds WHAT may be attached, and it is two lists that meet in one place: `/format`'s pictures (what a browser can paint, which is also what a relative `![](…)` may point at) plus `DOCUMENT_EXTENSIONS` — `.pdf`, `.txt`, `.md`, `.csv`, `.json`, the kinds an agent opens from a path rather than looks at. `isPicture` deliberately did NOT grow a `.pdf`: what chat may carry and what a note may draw are different questions, and answering them with one list would put PDFs behind `/media`. `.svg` is in neither — a document that can script is not a picture this app paints nor text it passes on.

It is a SIBLING of `send` rather than a widening of it: the two answer different questions — `attach` says where the bytes landed, `send` says a turn was accepted — and one file is N calls to one send. What `send` grew is a list of PATHS, which are what `attach` answered with; the bytes are already on disk by then, and the agent is handed the path and reads the file itself.

`send` grew a second list on the same argument, and it is the one place this spec says an id rather than a value: the NODES a message is about, as ids. Everything else about them — title, `file:line`, the ancestors that make a bare title mean something — is the SET's answer, and the set is the server's to read; a browser sending its own would be sending a reading of a frame that is already old. So the id crosses the wire, the server resolves it against the same snapshot a keystroke's write is judged against, and the resolved `NodeContext` comes back on the sent message's own row — where it is what the message was about, rather than something a browser remembers about a message it drew.

`attach` answers with the file's NAME as well as its path, and that is not a convenience. The name a caller SENT is a request: the server sanitizes it and suffixes a collision, so `shot.png` pasted twice is `shot.png` and `shot-1.png`, and it is the answer that the transcript row carries. A client keeping the name it sent would be keeping a second answer to "what is this called" — one paste away from drawing one picture on another message's row.

Nothing in the transcript is an optimistic echo — what a person typed appears because the server put it there, exactly like everything else, so two tabs always agree and a send that failed never leaves a message on screen that was never sent. The agent's WRITES are not members at all: they reach the ops layer through the internal MCP server, and what a reader sees of them is the outline entries moving.

The last member is the **keyboard's and the row menu's** (`src/edit.ts`) — one procedure over one tagged union, and the only place a browser may cause a write:

- **the verbs are INTENTS.** `Tab` says "indent this", not "reparent it under the node above and put it last"; `Ctrl+Enter` says "toggle done", not "set" or "clear"; `Ctrl+Shift+Enter` (`walk`) says "walk this row's mark on", not which of the three that lands on — the ring, and the argument for `done` not being a stop on it, are the resolver's. What a row's neighbours are, and what mark it carries, are facts about the SNAPSHOT — so they are read where the snapshot is, against the revision the write is judged against, rather than computed from a tree a tab drew some frames ago and posted back.
- **one union, one procedure** — the shape `@olai/ops` already uses for the same kind of thing (`Request` + `run`). The list of verbs is then spelled once: adding one is an arm here and an arm in the resolver, and every other site is a compile error rather than a silent hole. Five procedures was the first shape, and it was five spellings of one list.
- **it is not the ops request vocabulary re-spelled.** It is smaller (no chosen ids, no `seed` on a created outline, no `blocks`) and, where it differs, it differs because something is resolved behind it — so the verbs that resolve nothing use the ops layer's own words AND its own fields (`title`, `desc`, `date`, `unmirror`, `trash`, `untrash`, `see`, `after`), and a name that differs from an op's is a name with arithmetic behind it. Ops itself learns none of it: an op does not know it is being called over a wire.
- **four of the verbs are the POINTER's**, and they are here to close a DEVIATION rather than to grow the editor: an agent could set or clear a date, retire a placement and trash a subtree, and a person could do none of them (HACKING.md — "MCP and Web ops must be consistent; never deviate"). `date`, `unmirror` and `trash` each resolve to the request the equivalent tool sends. A fence the UI wants stays in the UI: `trash` takes a subtree because `trash_node` does, and the confirm naming how many rows go is the menu's own second step — put here, it would be a rule the agent's op does not have. `date` is the one with two senders and it always carried the op's full `string | null`: the `•••` menu sends the `null` (`Clear date`), and the date picker on a row sends the day somebody chose — the ten characters, verbatim, because a date is TEXT (`docs/format.md`) and nothing on this face parses one. `untrash` is the fourth and the one that closed an equal ABSENCE rather than a deviation: no face could take a node back out of the trash (`parity-unarchive`), so the op was born in `@olai/ops` and both faces got it in the same change — the Trash view's `Put back` sends the id alone and the op follows the recorded chain of ancestor titles; its optional `parent` / `file` are an undo's, carrying the place a trashed row actually sat, read off the snapshot by the server exactly as `place`'s ids are.
- **three more close the same deviation over the two EDGE fields and the outline itself.** `see` and `after` are `set_see` and `set_after` in the ops layer's own shape — two optional lists rather than one target and a direction, because nothing is resolved behind them and a narrower spelling could not express its own inverse (`parity-see`, `parity-after`). Until they landed a person could READ both edges and write neither: the links under a node, the dim and the `blocked by` line of a blocked row. What differs between the two is what the edges MEAN, and that difference is entirely the planner's — an `after` add that would close a loop is refused NAMING the loop, and that sentence reaches the browser verbatim. `outlineNew` is `create_outline` from the sidebar (`parity-create-outline`), `docNew`'s twin down to the shape; it carries no `seed`, which is the one place it says less than the tool — a person types the first row where it will live, so nothing this face can reach is out of an agent's reach, and quick capture already sends a seeded `create` when a directory has no inbox.
- **two of the verbs are an UNDO's**, and they are the one place the list is not shaped like a key: `place` says where a row SAT, `remove` that a row this session created should go. They name absolute things because "put it back" means one, and what keeps that honest is who named the ids — the server derived every one of them from the snapshot the original write was judged against, and rides them back on the answer (`Applied.undo`) for the browser to replay. Nothing restores a snapshot: an undo is one more op at the write gate, judged against the set as it is now.
- **one verb is the SIDEBAR's, and it is the palette's read one convention over.** `pin` carries an ADDRESS — `/#<id>`, `/<path>`, `/agenda?q=…` — because a pin is not a placement of a node (a mirror already means *draw it here too*) and not a field on a record (half the things worth pinning are not nodes). What every one of them IS is a place in this app, and a node's title is text, so a pin is an ordinary node in an ordinary outline. Where the shelf is is read on the server exactly as the inbox is, and it is ONE op for the same reason: an `add` into the `Pins.olai` the directory has, or the `create` that mints it holding exactly this address, so a refused pin leaves no empty file behind. There is no `unpin` — taking one off is `trash` of the pin's own node, which is the removal the set already has, so a verb only this face knew was never spelled. It carries one optional thing beside the address, and the field is a fact about the WRITE rather than about the format: a `name` somebody typed makes the row's title `[name](address)`, the markdown link a named pin has always been, composed where the file is chosen with `@olai/format`'s `pinTitle` — the exact inverse of the reader that draws one. Riding along rather than following as a `title` is what keeps one intention one op, one undo entry and one moment: a pin is never briefly nameless. RENAMING one afterwards is `title` on that row, which is the op an agent sends, so the second half of the feature needed no verb at all.
- **one verb is the PALETTE's.** `capture` carries a title and nothing else — no anchor, no file, no id — because quick capture is the one write whose whole promise is that the page it was made from does not move. Where the inbox is is read on the server, the shape `docDay`'s path already has, and it is still ONE op: an `add` into the inbox the directory has, or the `create` that mints it holding exactly this line, so a refused capture leaves no file behind. An agent makes the same two moves by hand.
- **and one verb is BOTH theirs.** `mark` names the mark a node should carry — what a menu entry means ("this is doing now") and what an undo means ("it carried `todo` before I ticked it off"). Two callers, one arm; a second would have been the same request under two names, free to drift.
- **the two TEXT verbs need no undo twin.** The inverse of setting a title is setting the title it replaced, so an undo sends `title` — same verb, same op, the other text. What it adds is `was`: the text it expects to find. A person typing overwrites whatever is there (which is what `set_title` does for an agent); an undo may only overwrite what IT wrote, so a row somebody else has retyped is refused rather than written over.
- **two of the verbs are COMPOUND, and they are ops rather than sequences.** `split` (`Enter` with text on both sides of the caret) and `merge` (`Backspace` at offset zero) each change an outline in several ways at once, and each is ONE request at the write gate — `split_node` and `merge_node`, the same two ops an agent calls. Assembling them here out of the verbs above would have been the deviation at its plainest: the web doing in one keystroke what MCP needs four calls for. The other half of the argument is atomicity — a sequence can stop in the middle, and a half-landed merge leaves an outline saying something nobody wrote. `split` is the one verb that carries text it did not read off the set (the two halves are the DRAFT's, which is the editor's own and not a reading of the outline) and it carries them as two TITLES rather than a caret index, for the reason no verb on either face names a range into a field. `merge` carries nothing but an id: which sibling is above is a fact about the set. BOTH name the ROW's own record rather than the node the row shows, which is where they part from every plain text edit here: each puts a row on the page a reader has open, or takes one off it, so each is a question about where rows SIT. Asked at a mirror, both are refused in the ops layer's `notANode` words — a placement is not a node, and a split named through one would mint the tail beside the TARGET, in a file the reader is not looking at, leaving the two halves of one sentence unrelated on screen and the caret following the tail off the page.
- **and one is a THIRD compound, born on both faces at once.** `duplicate` (`⌘⇧D`, and `Duplicate` in the row menu and the palette) is `duplicate_node`: one id, no anchor, no title — everything the copy says is already on disk, so the op reads the subtree where the write is judged rather than being handed one. Assembling it here out of `add`s would be `split`'s deviation at its worst (a call per node, from a browser, against a tree some frames old) and would half-land, which for a copy means a branch nobody wrote. Like the two above it names the ROW's own record and is refused at a placement in the ops layer's `notANode` words, for their reason: copying through a mirror would write a branch into the file its target lives in, out of sight of the row that was clicked. What it answers with is the COPY's root, which is what makes its inverse a plain `trash` of that id — `remove`'s answer without `remove`'s narrowing, since a duplicate makes a branch by construction and taking it back means taking the branch it made.
- **one verb is a FIFTH way a row moves, and the only one that names where it is going.** `under` (`⌘⇧M`, and `Move to…` in the row menu) carries a row's record and a parent, and resolves to `move_node` with that parent and no anchor — so the row lands LAST among its new siblings, which is what this app means by putting something under a node and is where `move in` already ends up. A separate arm rather than a fifth `how`, because the other four are questions about the snapshot ("under the sibling above", "up a level") and this one is a node a reader chose out of a search of the whole set; folding it in would have made `id` mean two things and `how` sometimes need a second field. It is not `place` either: that one names a parent AND a neighbour, which is a drag's gesture (a pointer picks a gap between two rows) and not this one's — "which sibling is last" is a fact about the set, read where the write is judged. Every refusal it meets is `planMove`'s own; the picker draws the ones a reader can be told earlier (inside itself, the Trash, the parent it already has) at the AIM, which is the shape a drop over the wrong pane already has and is an aim rather than a fence. The parent may be in ANOTHER OUTLINE and this arm is unchanged by it: `move_node` carries a subtree across files now, and a parent decides its own file, so a search of the whole set reaches every outline without a second field here.
- **neither removal here is a delete.** `remove` is the inverse of an `add`: no key sends it, the only row it can take back is a row that was just made, and what it resolves to is `trash` — narrowed to a node with nothing under it. `trash` is that same op unnarrowed, the human's subtree ruling with a confirm in front of it; the ids come along, so mirrors and `after` edges that name the subtree go on resolving. A key that ERASES one is the one edit a person cannot re-type from memory, nothing on any face does it, and whether this face ever gets a delete KEY is still the deferral #109 recorded.
- **and there is exactly ONE delete, which is not aimed at a row.** `emptyTrash` names no file: everything in the Trash, gone for good. The one field it does carry is `was`, the COUNT the confirm showed — checked in the planner on every attempt, so a record put away between the frame somebody read and the write landing is a refusal naming both numbers rather than something quietly deleted by a retry. Which file is the trash, and whether it holds anything, are facts about the SET, so the server reads them and resolves the verb into ONE `empty_trash` naming `_olai/Trash.olai`. Never a batch of one per leftover `Archive.olai`. It answers with NO inverse, and it is the only arm here that answers so because the world has no inverse rather than because this surface cannot spell one: the records have left the set, and what still holds them is git, to exactly the extent git had already recorded them. The fence is the confirm the Trash page asks first — how many rows go, and that nothing puts them back — and it is not on the wire, for `trash`'s reason: a rule this schema enforced would be a rule an agent's `empty_trash` does not have.

It declares `OpFailure` as its error channel, which is what the editor is built on: a refused write comes back as the validator's own rows, so the draft it came from is kept and the reason shown beside it. What it ANSWERS with is the node the write was about AND WHAT IT SAYS NOW (which only a `merge` cannot know in advance — the joined title is the row above's plus this one's), the ops layer's own `nudge` — advice on a success (the last task under a parent going done), which an agent already receives in its tool result and the person who pressed the key is exactly who it is for — and the inverse above, which is absent only for the one write nothing would take back (an `unmirror` — this face has no verb that places a mirror). A row that has gone to the trash answers with `untrash` now, and a put-back answers with the trash again. Nothing about the collections changed: they are still read-only on the wire, and an edit reaches a reader as the file it produced.

## And one group NO browser may reach

`src/ops.ts` is the AGENT's door — `ops.run` over `@olai/format`'s `WriteRequest` union, and the query answers that had no procedure. It is the other half of the sentence above: a keyboard sends intents and an agent names ops, deliberately different vocabularies over one write gate, and `edit.apply` is untouched by any of it.

One member there answers no tool at all: **`ops.paths`**, the outline PATHS of the served directory. It is the reading a PLAN arm resolves against — a capture is aimed by the inbox convention over the file names, and a face with no store of its own could only get them by asking `ops.outlines` and dropping the counts, which materialises every record in the directory to hand back a list of names, twice when the capture race makes the resolver read again (`perf-capture-paths`). It is a second question rather than a narrowing of the first: `list_outlines` keeps its counts and its roots, because those are what an agent CHOOSES a file by.

Two things about it are worth reading before the file:

- **Why it can exist at all.** Putting the ops vocabulary on the surface used to be inseparable from making it browser-callable, because `serveSurfaceApp` took `handlers` whole: a member existed on every face or on none. That asymmetry is what olai asked upstream about and what [juspay/kolu#2170](https://github.com/juspay/kolu/pull/2170) closed. Every serving face now takes the same `ExposeMap`, so this namespace is open on the HTTP `/mcp` an agent posts at and closed on the websocket a tab opens — and a tab that calls one anyway is refused per request with `SurfaceMemberNotExposed` naming the tag, rather than finding a member missing. Which face gets what is `@olai/server`'s (`src/faces.ts`); this package only declares what exists.
- **Why nothing here names WHO is writing.** The `X-Olai-Writer` trailer is the only thing that can tell one agent's edits from a person's, and it is not a field on any of these: a transport that could name itself could name another. Every caller of this namespace is identified by the FACE it arrived on — HTTP `/mcp` is a terminal agent, an in-process dispatch is whichever agent the composition root built it for — so the writer is bound where the face is composed, by rebinding these handlers for it (`@olai/server`'s `runtime.ts`, `writerAt`). One fact in one place either way; what it removes is the spelling of it a caller could have lied about.

`git.commit`, `git.push` and `search.nodes` are deliberately NOT twinned there, and that is the rule paying off: a member belongs to the agent's door only when the agent's version DIFFERS. Once the writer stops travelling, none of the three does — a commit is the same act with the same request and the same answer, and only the trailer differs, which the face decides.

Two procedures go the other way and are the BROWSER's alone, and neither is a restriction either — each is a fact about what an agent would do with the answer. (The `narrowing` stream above is a third of that kind and is not a procedure at all: it hands back a set of ids and why, useful only to somebody already looking at the rows those ids name, where an agent asking which nodes match asks `search_nodes` and is answered with the nodes.) `nodes.named` hands back the node each of a dozen ids names, for a panel deciding which of an agent's own backticks are pressable; an agent asking whether an id is real reads it. `nodes.homes` hands back a file per id and a list of paths, for a browser reconciling a memory of what it had collapsed against a directory that moved; an agent that wants to know where a node lives reads it, and is told beside everything else about it. The two `nodes` members share a namespace and not a question: `named` FOLLOWS a mirror chain, because a backtick means the node a reader would be shown, and `homes` is the plain record lookup, because a fold is of a record.

PROCESS identity is deliberately NOT a member here. It is a real question — a page bound to a server that has been replaced must know, and both ends of the stale-tab handshake compare that id — but the framework reserves `system/identity` for it and answers it out of every surface, process id included. A member of our own would be a second answer to a question already answered.

**Who is looking is a different question, and is a PROCEDURE rather than a cell.** A trusted login header on this connection (default `Tailscale-User-Login`; the pair is configurable), or nobody when it is absent. A cell is one value for the process; this value is one value for THIS TAB, stamped on the upgrade and unmoving for the life of the socket — nothing to subscribe to. `who.get` is the chip's door; `GET /olai/who` stays for a share sheet and a script. The **path** and the JSON it carries are `src/who.ts` — the same bijection `/media/…` is. The **reading** of the headers is `@olai/identity`'s `identityOf`. The hashed bundle sits at `/_olai/assets/` (`src/bundle.ts`'s `ASSET_PREFIX`), so a vault file under `assets/` is a page.

## One FACT that is not a member — and no longer here

`src/holding.ts` was the other kind of thing here — not a member, not an address, but a fact about a member's subscriptions that the wire had no way to state. A per-key `get` says when a reader OPENS a key; nothing said when the last one LETS GO, because the framework owns that lifetime (a handler answers with a `Stream`, and the stream's scope is the subscription) and did not publish it. So this package wrapped one collection's `get` in a scoped acquire at the composition root, and its own note said WHERE IT WOULD RATHER LIVE is upstream. It lives there now: `holders?: (key) => Effect<unknown, never, Scope>` is a member of `CollectionHandlerDeps` beside `readAll`/`readOne` ([juspay/kolu#2188](https://github.com/juspay/kolu/pull/2188)), so a collection states who is holding what where it is BUILT rather than by being re-written afterwards, and the order that makes it worth anything — hold, then subscribe, then `readOne` — is the framework's own pin (`@kolu/surface`'s `src/collectionHolders.test.ts`). What is left here is what this package always was: one door, the declaration, with no serving-side module in it and no `./holding` subpath beside it. What a hold is WORTH was never ours and did not move — `@olai/server`'s `bodies.ts` owns the count, the read-on-held and everything decided from them.

## One address that is not a member

A picture cannot travel the surface: a document's `![](shot.png)` becomes an `<img src>` and the browser fetches that URL itself. So there is exactly one HTTP route besides the bundle, and it has two ends — the renderer that writes the URL and the route that reads it — in packages that cannot import each other. `src/media.ts` is that bijection: the prefix, `mediaHref`, and `mediaTarget` with the traversal guard and `@olai/format`'s `isAsset` allowlist in it. The guard alone is `mediaPath`, split out for the one reader that asks which file of the vault an address names WITHOUT asking whether the route may answer it — a link clicked inside a preview, which may name a `.md` the route refuses and olai still has a page for. One decoder for both: a second parse of this URL space would be a second traversal guard, and the one nobody thought to attack is the one that would be wrong. Two writers of these URLs, one spelling: the markdown renderer rewrites a picture's `src`, and a `.html` preview's frame is POINTED at one — the file's own address, so that every relative address inside it resolves beside the file with nothing rewritten. Two copies of "what a media URL looks like" would be a contract kept by memory, and its failures are silent in both directions — a URL the client writes and the server does not recognise is a broken image, and a URL the server reads more loosely than the client writes is a file nobody meant to serve.

## What identifies a row, and which members say

A member may DECLARE `arrayKey` — the field that identifies an element of an array inside its value (juspay/kolu#2190). It is read in exactly one place, the seam where a browser MERGES a frame into its store, and it is a fact about the member's SHAPE rather than about any reader, so the spec is the one place both sides can take it from: no `.use()` call site can spell it, override it, or disagree with another about it.

Undeclared, a frame REPLACES every element of every array it merges. Replacement is total — nothing off the wire is `===` what came before it — so a frame that merely repeats what a tab already holds still notifies every reader of every row, and a keyed list's per-row bindings all re-run for a one-character change in one row ([the audit](https://github.com/juspay/oss.olai/blob/main/projects/olai/brainstorming/reactivity-after-the-flip.md)'s §2 Fact B and its 2.11). Declared, an array whose elements carry the field is diffed BY it: an identical frame notifies nothing, and a reorder MOVES the objects a keyed view is following.

ONE field per member, because `reconcile` takes one, and it reaches every array in the value at every depth. Arrays whose elements do not carry it merge BY POSITION — the declared reach of the key, not a fallback around it — which is silent on a repeated frame just the same. So the field to name is the one identifying the arrays whose identity a consumer actually follows.

| Member | Field | Why that one |
| --- | --- | --- |
| `page` | `key` | `@olai/format`'s `Row.key` is the identity a PLACE is drawn under — the chain of ids from the page's roots, which the fold, the editor's `refound` and every `<Key>` in the tree already follow. `id` would name the NODE, and a mirror draws one node in two places. `names`, the crumb trail, `backlinks` and `referrers` carry no `key` and merge by position; their consumers all key by VALUE, so position is the right amount of identity to give them |
| `pins` | `id` | The pin NODE's own id — what an unpin trashes and what a reorder moves, and the key `pins/Shelf.tsx` already draws the shelf by |
| `pending` | `path` | The one name the panel's two row lists share, and they share it deliberately: `Other`'s docstring already promises it is spelled and means the same as `DirtyOutline`'s, because they are "two kinds of ROW and one namespace of keys" |
| `chat` | `name` | Both arrays this cell carries — a `Command` and a `ChatServer` — spell their identity that way, and the cell moves for reasons that are about neither (a turn going `idle → thinking`, a usage report) |

`errors` declares nothing and says so where it is declared: an `OutlineError` is a site, a code and a sentence, and the only required non-nullable field that looks like an identity is `file`, which a broken outline reports several errors against. A key that repeats inside its own array decides identity by collision. (What it would actually want is a third mode `arrayKey` has no spelling for — positional, no identity claimed, silent on a repeat — and the declaration says why that is not worth a spec change for this member. The question is settled a second way since the cell became a verdict: a cell whose value is a struct is replaced.) `manifest`, `git`, `dated`, `owed`, `inbox` and `moving` carry no array of OBJECTS at all. `outlines`, `heads` and `transcript` cannot honour one on the delivery this app reads them through: the batched `deltas` path replaces each named leaf WHOLE rather than merging into it, because a `fold` consumer may be holding that very object. `documents` is served per key and would honour one; an entry is a revision and a body, and holds no array.

Each declaration is pinned against the schema in `src/surface.test.ts` — which reads the declaring SET off the spec rather than off a list beside it, so the table above is checked rather than kept by hand and a fifth member arriving with a key its value does not carry fails there — kolu ships the same per-site guard beside its own, and ships no boot-time check for the reason its PR records: a construction-time schema walk would produce false boot crashes on legitimate recursive or `suspend`ed codecs, which is worse than the mis-declaration it catches.

## The seal, for the same reason

`src/seal.ts` is here on that argument taken once more. A previewed `.html` is answered by `@olai/server` and read by `@olai/web`, and what passes between them is a CONTRACT with three parts: the content policy the response carries (`sealPolicy`, taking the host the request named), the prefix put in front of the file's bytes (`SEAL` — a doctype, a colour scheme, a tape measure and a link handler), and the READER of everything that prefix posts back out — `heard`, which classifies a message into one of `Said`'s three arms (the frame's greeting, the page of this vault a reader clicked a link at, or how tall the page says it is) or into nothing at all — plus `spellsHost`, which answers about the policy what the server has to say out loud when it refuses a host. One reader rather than one per kind, because it is one vocabulary on one channel: three separate parsers made their mutual exclusivity a rule the one consumer kept by trying them in a remembered order, and left no place to say that no one of the prefixes begins another. The producer of those messages is text inside a template literal that no compiler reads, so sender and receiver live in one module: a receiver that spelled the prefix itself would drift from the sender in silence, and the symptom would be a preview stuck on its fallback height forever. Nothing that arrives over that channel is trusted — the frame runs somebody else's JavaScript — so every arm is a claim: a height is clamped by CSS at the other end, and a clicked page is a LOOKUP KEY the client matches against the files it is serving before it navigates. The whole security argument for what the policy does and does not promise — the file's own scripts run, and nothing but this vault may be fetched — is written in that file's header.

## Entry point

`main`, `types` and the `.` export all point at `src/index.ts`, which exports the `surface` definition, the `OutlineEntry` and `Manifest` schemas, the `Edit` vocabulary, the media URL and the seal above. That is the declaration, with no implementation on either side of it, and it is the only door: `./holding` was a second subpath for as long as a serving-side seam lived here, and it went with the module (above).

## Layering

Depends on `@olai/format` and on `@olai/acp`'s `./wire` subpath, and nothing else in the workspace: every olai type on the wire is owned by the package that speaks it and re-exported here — the domain's by `format`, the protocol's ask and diff shapes by `acp` — travelling verbatim. `server` and `web` both depend on this. [docs/architecture.md](../../docs/architecture.md) has the reasoning.

## Running

```sh
just test                    # the whole workspace's unit tests
```

`src/surface.test.ts` earns more than it looks. It asserts that `errors` and `manifest` serve no `set` verb and that `outlines` serves no `upsert`/`delete` — the browser may not write any of the three — that the collection really is served with `deltas` and `keys`, that `documents` is served keys-first with no `deltas`, and that the assembled RPC group contains the framework's own members alongside ours, which only holds if the `@kolu/surface` sources hydrated from the Nix store resolved `effect` out of the root `node_modules`. A second copy of effect, a missing root dependency or a stale kolu pin all land here rather than in the browser. Its second half is the guard on the array-identity declarations (above): a walk of each declaring member's own schema, so a field renamed in `@olai/format` fails here rather than reading as "no identity declared" at the merge, and so a member that declares nothing goes on declaring nothing.
