# @olai/server — the composition root, and the binary

One directory, read and served — and written, by an agent and now by a person at a keyboard. Both go through the ops layer and neither has a path to a file of its own: the browser's edits are surface procedures resolved into ops requests (`@olai/edit-intents`), and the agent's are the ops table projected onto MCP (`olai-plugin-mcp`'s `tools.ts`). Neither of those lives here any more, and that is this package's shape rather than an accident — what is left is the entry point that starts it: `olai web <dir> [--port] [--host] [--commit]`, which puts a browser in front of the ops layer and `/mcp` in front of the same one for any HTTP client — including a TERMINAL, where `olai surface <verb>`, the second subcommand of this same binary, speaks MCP to that same path and is a client rather than a second writer (`dial.ts`, `mcpClient.ts`).

`--commit=off | manual | auto` says how writes reach git, `manual` by default: a write lands on disk and waits, and a Commit button or the agent's `commit` tool asks for one. `auto` is the quiet window — everything waiting records itself once writes stop arriving for fifteen seconds — and `--push=off | auto` says whether a settled commit is then pushed, whichever door made it. `--no-commit` still means `off`, and wins when both are given. The flags are `src/gitPolicy.ts`, and they are one file rather than a declaration per face because that is exactly the divergence the consistency rule forbids: an agent-only face once shipped without the flag at all, so an MCP-driven session could not batch and put four commits into a human's log in fifteen seconds. The one thing that differs between the faces is one clause of the help text: which doors that face actually offers. `src/gitPolicy.test.ts` holds both halves — the truth table, and that nothing BUT that clause differs.

**The flags plus the built-in defaults are the whole policy.** Committing and pushing are facts about the directory, so `--commit` / `--push` are a CLI patch onto the git row's config, drawn under that row on the plugins panel, always read-only. A flag that was GIVEN is named there; omitting it is the built-in default (`manual` / `off`). `src/gitPolicy.ts` is the flags (one mode table, one default, one override, the flag PAIR as one thing); the git row's `fixedPolicy` (`olai-plugin-git`'s `ledger/pending.ts`) is what the loop obeys.

That clause is two halves in two packages, and the split is the point. `commitDoors(face)` is what a SUBCOMMAND offers and is here, in `src/gitPolicy.ts`, beside the flag whose help text interpolates it; `commitDoor(writer)` is what ONE WRITER has, for the sentence its own write carries back, and is the git row's (`olai-plugin-git`'s `ledger/pending.ts`) because a waiting write is the ledger's business. They are different questions and `olai web` is where they come apart — a web serve hands its own panel agent the same `commit` tool, so it genuinely offers both doors, while one writer has one. Keying the help on a writer quietly dropped the tool from `olai web --help`; `gitPolicy.test.ts` now asserts each face names its exact SET, which is what catches a face under-describing itself as well as over-describing. The face is a `CommitFace` — `Writer` minus the two writers that are not subcommands (`chat-agent`, and `auto`, which is the quiet window itself) — so there is still one name for who is asking, not two to keep in step. There is no row for a terminal, and there is nothing missing: `olai surface` is a client of `/mcp` rather than a face, so what it offers and what it is recorded as are that door's.

This package decides one more thing about committing, and it is not the mode — it is WHO each FACE is: the HTTP `/mcp` route says `mcp`; a node session supplies its own writer through its session credential; the browser's websocket says `web`. A third writer is not a face at all: the quiet window's own commits say `auto`, because nobody pressed anything and there may be no browser anywhere. That word is the commit's `X-Olai-Writer` trailer, and a transport that claimed it about itself would be a transport that could claim to be another — which is why it is bound where the face is composed (`src/runtime.ts`'s `writerAt`, which serves one runtime to several faces under several writers) and is a field on no procedure anywhere. Everything else about a commit is the same on both faces, down to the bytes: `olai-plugin-git`'s `ledger/pending.test.ts` commits one identical pending set as each and asserts the trees and the messages match, with the trailer as the only difference. WHO captured is a separate question the trailer cannot answer — git records the repository's own user — so the identity the door HAS (the login a reverse proxy injected on the request; nobody at all on a direct loopback call, where the property is simply omitted) rides the node itself, as a `captured-by` property.

## What this package composes, now that everything is a row

**Olai is a bundle.** The vault, the ledger, search, identity, the journal, the engines, the tenants, the content capabilities, the shell and every transport are rows in `packages/bundle/olai.yml`, mounted as fibers. This package mints the host, provides the two inputs the rows cannot invent for themselves, mounts the bundle, composes whatever surfaces the rows registered into one generation, and opens a port. It knows no plugin's name: `serve.ts` reaches for `BUNDLE_NAMES` and `ROWS`, never for a plugin package (`packages/bundle/src/fence.test.ts` is what keeps that true).

`profiles.ts` names the three profiles and nothing else — `web`, `surface`, `test-minimal` — because a profile is a PATCH over the one catalogue rather than a second list of modules. `web` writes no patch at all, so every row the file does not ship `disabled` runs. `surface` and `test-minimal` disable every row that does not name them in its own `profiles:` field, which today is the MCP-only set (the vault, `mcp`, and the content rows) and a transport-free set (the vault plus the acceptance fixtures). Select one with `olai web DIR --profile NAME`; `olai surface` remains the MCP client and has no rows of its own to run.

Boot has TWO SETTLING BARRIERS and `serve.ts` argues both where they stand. Providers first acquire their independent services; only then can Surface composition publish a coherent transport door; transport rows then register their actual routes and settle again before the listener opens. That is what lets a content-only profile run headless and what breaks the provider/transport dependency cycle. `listener.ts` owns the shared port and composes plugin-contributed routes and upgrades; transport behaviour and credential policy live in the rows, and core supplies composed generations and carries request attribution. Shutdown is four finalizers in a deliberate order, and `serve.ts` names all four where the first of them is registered.

**One brain per vault** is the vault row's now (`packages/plugins/vault/src/lock.ts`): a kernel-held advisory lock on the served directory before the store opens, and a second olai over the same files refuses to boot naming the process that holds it. What this package still does about it is one thing, on its first statement: sweep the state home of records whose directory is gone (`@olai/state`'s `pruneGone`), forked so the walk never stands between the person and the bind.

Talking to the agent is not here, and neither is the ops layer, the projection, the edit vocabulary or the store. Each left as its own row or its own package, and the entries below say where. `@olai/web` is deliberately absent from the dependencies too: the server serves a browser bundle it is handed and never builds or imports one.

The transport implementations live in `packages/plugins/ws`, `packages/plugins/web-app` and `packages/plugins/mcp`. The typed direct client is shared through `@olai/surface/client`; the terminal tool projection is selected by `@olai/bundle/remote`.

## The listener is one call now

`listener.ts` used to spell out the sequence a surface app is served by, copied from kolu's own surface-app example and kept in step with it by hand. It is `serveSurfaceApp` (`@kolu/surface-app`) as of kolu#2137, and what is left in this package is the two decisions that call deliberately leaves to a consumer — whose port this is (`listener.ts`, and the fallback below) and what a listener event sounds like in olai's log (`report.ts`) — plus the two things that left rather than moved, the frame cap and the surface runtime's lifetime. **The argument for all four is `listener.ts`'s own header**, beside the shape it explains; it is not restated here.

The stale-tab gate in that sequence is worth naming even so, because it is what a reader sees: a browser reconnecting after a restart presents the process id it was given by the server that is gone, and it is closed at the handshake rather than served a page it did not build. No id is threaded through this package to make that work — the gate compares against the framework's own `surfaceProcessId()`, the same value `system/identity` answers with and the browser echoes back, so the two ends cannot be pointed at different ids.

One more thing the listener leaves to this package and this package spends exactly once: the trusted UPGRADE HEADER names. They are the identity row's, read live, and the ws row runs kolu's `checkUpgradeHeaders` at every accept — where all it can do about a bad list is narrate the refusal and serve that connection with no named headers, because one row's defect must not take the wire down for every other tenant of it. That is the right answer for a list that went bad mid-serve and the wrong one for a serve that came up with a list nothing can ever serve, so `serve.ts` spends the same check on the list it starts with, one statement before the port opens. An operator's typo stops the boot rather than every socket.

## The manifest is served, the icons are not

`packages/plugins/web-app/src/manifest.ts` is what an installed olai is — the name, the description, the colours and the icon list — served at `/manifest.webmanifest` through `@kolu/surface-app`'s manifest layer, which owns the install-friendly defaults (`start_url`, `display: standalone`) so they are not restated. It is a row's file rather than a block in `listener.ts`: the app's identity has nothing to do with serving it, and it survived that file being reduced to one call and then survived leaving this package altogether — which is what having its own reason to change means. The icon *files* belong to the browser bundle and are served as part of it, which means the two ends of that contract live in two packages that do not import each other. Nothing there can check that a `src` it names is a file that exists — and the static layer answers an unmatched path with the HTML shell, so a stale one would return 200 rather than 404. What checks it is `src/serve.test.ts`, HERE, which stands a real server up, follows every `src` against a dist assembled from the client's public files, and asserts on the content type.

The server does not build the client and does not import it. It serves a bundle it is handed, so `@olai/web` is deliberately absent from its dependencies and the browser build stays a build artifact rather than an import. A fallback that walked from `clientDist.ts` into `packages/web/dist` would be a real `server → web` dependency expressed as a path — invisible to `bun install` and to any layering check. `src/serve.test.ts`'s install-surface tests are the one exception, and they are a test: they copy the client's `public/` and `index.html` into a temp dist so they can fetch the icons the manifest names, which is the contract the two packages cannot type. Production code still does not walk that path.

`/media/*` is the vault row's (`packages/plugins/vault/src/http/media.ts`) and is three decisions and one mechanism. WHETHER to answer is `@olai/surface`'s `mediaTarget` — the traversal guard, with `@olai/format`'s `isAsset` allowlist in it (a page, a picture, a stylesheet, a script, a font), which live there because the client writes those URLs against the same functions. WHAT A PAGE IS ANSWERED WITH is the seal, and that is the mechanism: the content policy on the response and the tape measure in front of the file's own bytes (`@olai/surface`'s `seal.ts` carries the whole argument). HOW to answer everything else is the platform's own file engine (`HttpStaticServer`), the same one already serving the bundle: reading a file under a root is not a thing to hand-roll twice in one process, and the engine brings the stat, the directory case, the MIME type, the byte range and the conditional `304` a browser asks for on its second look at a picture. A page cannot go through it — the seal is a prefix, so the response is not the file's length and cannot honestly claim to be a range of it — so a page is read whole, answered whole, and offers no ranges. The guard is lexical by design: it stops a URL from naming a file outside the directory, and does not chase a symlink someone put inside a tree they are already serving whole. `media.test.ts` is still here, because what it drives is a whole serve.

## Entry point

`main`, `types` and `exports` point at `src/serve.ts`, **not** `src/main.ts`. `main.ts` ends in a top-level run that starts the server and installs signal handlers, so a resolver honouring `main` over `exports` would boot a listener on import. The binary is reached as a script path — by `default.nix` and by the justfile — never as a module.

Everything `serve` opens is a finalizer of the enclosing scope, so shutting down is closing the scope; no caller holds a teardown function it might forget to call. There are four of them and they do not run in reading order — Effect closes a scope's finalizers in reverse registration order, and two of the four are registered twenty and thirty lines after the paragraph that orders them, so that paragraph names all four in the order they actually run and each distant site carries a marker back to it.

## The tools, without a browser

`/mcp` on the running `olai web` is the same ops layer with a different thing in front of it. Its client is a coding agent in a terminal, so it gets what nearly every MCP client expects — a URL, and JSON-RPC over HTTP:

```json
{
  "mcpServers": {
    "olai": {
      "type": "http",
      "url": "http://127.0.0.1:7714/mcp"
    }
  }
}
```

The route is a row now (`packages/plugins/mcp/src/route.ts`), and three things about it are decisions rather than defaults, argued there where each happens:

- **There is one store.** A terminal agent is a client of the running `olai web`, the same way the panel's agent already is. A second process on the same directory is the thing this design retired.
- **Loopback skips the bearer.** A request from `127.0.0.1` reaches the tools with no token; the chat still sends the one it was handed, which is accepted and ignored. Off loopback the token is still required.
- **`--commit` is the serving process's setting.** An HTTP client does not get a flag of its own; how writes reach git was decided when `olai web` started.

And it commits the way the browser does, because it is the same ops layer: ops accumulate, and the agent asks for one commit when a unit of work is finished. The two verbs are the git row's, advertised as MCP tools named `commit` and `push` (the ops table's names). A serve that does not mount that row still advertises them and they refuse in words.

- **the `commit` tool** — message required from the caller in practice (omit it and one is composed from what changed, which can only describe the edits and not why they were made). It sweeps the WHOLE REPOSITORY, not only the outlines: a `.md` or a source file somebody edited by hand is waiting too, and untracked files `.gitignore` does not cover are included. `paths` (optional, repository-root-relative) commits only some of it and leaves the rest waiting; a path nothing is waiting on is refused by name rather than quietly skipped. It answers with what was swept — both counts, node changes and other files — or refuses with the reason on a busy repository — mid-merge, mid-rebase, cherry-pick or a detached HEAD — as structured data rather than prose to parse. It never touches git's index, so anything staged by hand is left exactly as it was.
- **the `push` tool** — the current branch to the upstream it already tracks, and no arguments at all: no remote to pick, no refspec, never a force, and nothing that resolves a divergence. It retires one of the two raw-git verbs an orchestrating agent still needed a shell for. A refusal comes back with git's own words — authentication, a non-fast-forward, a branch with no upstream — because those are a terminal's business to resolve and the words are how that starts.

An agent does not have to read a pending cell to learn a repository is busy: a write's own reply says so. Under `manual` a write mid-rebase or on a detached HEAD comes back naming that state rather than saying it is waiting to be asked about, because "waiting" would point the agent at a tool that is going to refuse.

`src/mcp/route.test.ts` and `src/mcp/tools.test.ts` drive the HTTP face against a real listener from HERE: initialize, tools/list, a resource read, a write refusal as a 200 result, loopback without a token, and off-loopback still refused. Which TOOLS an agent is offered is a function of which rows composed, and since #546 it is nothing else: a verb rides its own row's entry in the rooted bundle `olai-plugin-mcp` hands the adapter, so `reroster` withdraws it with the row and says so with `list_changed`. It was read off `composition.ts`'s published `dispatch` through a hand-written `catalog.ts`, and both are deleted — there is no shared envelope to claim a variant of, and no filter between the roster and the list.

**One shape worth knowing when writing an agent against this:** `commit` re-surveys git itself and never reads a pending cell, so a tool call issued in the same breath as a write's reply is still the repository as it is.

## Starting up, and what you are told when it will not

**A busy port is not a refusal.** If the port asked for is already listening, the listener binds once more on a port the OS picks and says so:

```
timestamp=… level=INFO fiber=#5 message="port in use — serving elsewhere" serve=24ms root=/home/you/outlines asked=7714 url=http://127.0.0.1:40429
timestamp=… level=INFO fiber=#5 message=serving serve=25ms root=/home/you/outlines url=http://127.0.0.1:40429
```

The reader asked to read their outlines, not to own port 7714. Every other listen failure still is a refusal — a host that is not this machine's, a privileged port — which is why exactly one error code recovers rather than "listen failed". The address that gets reported is always the one **actually bound**, and it is its own `url=` field: the browser tests read it out of that line rather than assuming the port they passed, because the printed address is the only thing that knows. The process default is port `0` — the OS picks — so `7714` is a number somebody has to type. Everything about the shape of those lines — one format, the levels, what is a message and what is an annotation, and the `OLAI_LOG_LEVEL` that turns the quiet half on — is [`@olai/log`](../log/README.md).

**A failure is reported as itself.** The surface runtime's `done` settles for two very different reasons — it faulted, or it is being closed — and the discriminator is whether we are still meant to be serving, not fulfill vs reject. Settling while we are still serving is news either way (a reject is the fault; a fulfill is the runtime walking off, which used to be a hang that said nothing). Treating an ordinary close as a fault is how a busy port used to print `surface runtime faulted — unrecoverable: [object Object]` and exit before the real `cannot listen on 127.0.0.1:7714: …` could be reported at all: the teardown that a failed `listen` starts closes the runtime, and closing it settled `done`. So `src/fault.ts` only speaks while we are still meant to be serving, and it renders the rejection with `prettyCause` rather than `String`, which on an Effect `Cause` is `[object Object]`. The two statements that can fail before `runtime.stopped` has a finalizer of its own carry that clause explicitly, in `serve.ts`, for exactly this reason. `src/serve.test.ts` holds it against a real socket; `src/fault.test.ts` holds the four outcomes apart.

**A fault stops the server; it does not exit the process.** `serve` returns an effect that never settles unless the runtime faults, in which case it FAILS — so `olai web` staying up is "waiting on that", and an unrecoverable fault unwinds this scope the way Ctrl+C does, running the finalizers that close the sockets and drain the rows, before `runMain` sets the exit code. It used to call `process.exit(1)` from inside the `catch`, which ran none of them and took any test that came near the path down with it — which is why there was no test.

## Layering

Depends on `acp`, `bundle`, `edit-intents`, `format`, `log`, `ops`, `plugin-api`, `plugin-build`, `sigterm`, `state`, `store` and `surface`, strictly downward. Nothing depends on this. No production source here imports a plugin implementation; the plugin packages in `devDependencies` are test-only contracts and fixtures. [docs/architecture.md](../../docs/architecture.md) has the reasoning — including what `listener.ts` kept when the sequence it used to spell out went upstream to `@kolu/surface-app`.

## Running

```sh
just serve docs              # build the client, serve this repo's own roadmap
just run                     # a worktree's own server, on an OS-assigned port
```

The first is the web edit loop: two `bun --watch` processes (client bundler and server), so a validator rule you change is live on the next reload. `just run` is a worktree's own `olai web` on this repo's docs, on a port the OS picks every boot — a `bun --watch` restart may land on a new one, and neither squat the production `.mcp.json` at `7714` — with the server alone under `bun --watch`. `just nix` is the packaged path: the binary, built from tracked files only, which is what CI and `just e2e` prove.

`/mcp` is JSON-RPC over HTTP, one message per POST, which makes it curl-able — the fastest way to see what an agent is actually offered:

```sh
curl -s http://127.0.0.1:7714/mcp \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

## The agents

Which agents this machine has, how a conversation is bound to one, and what a turn does are `olai-plugin-chat`'s and the engine rows' — one row per ACP agent olai can seat (`claude`, `codex`, `opencode`, `pi` in `packages/bundle/olai.yml`, in the order the picker draws them). A serve that names none of them serves the outlines exactly as it does with one, and the panel says there is no agent rather than hiding.

What is still this package's is the ENVIRONMENT those rows are read against, because a chat agent is a child of THIS process and its environment is this process's — not your login shell's. An agent that resolves a provider key out of the environment finds nothing unless the server was started with it. `docs/running.md` has the `environmentFile` for a user service.

**The shipped defaults are Claude Code and Codex, on every documented launch path.** Each adapter is pinned behind its own executable output — the established Claude/Pi bundle in `nix/acp-agent.nix`, Codex in its row's [`acp/default.nix`](../plugins/codex/acp/default.nix) — and the packaged binary's wrapper bakes both in with `--set-default` (`default.nix`). `just serve` and `just run` resolve the same outputs through their `scripts/acp-*.sh` helpers. Nobody following a documented path has to install either adapter or CLI, and a Codex pin move neither rebuilds nor rewrites the other adapters.

`OLAI_ACP_AGENT` overrides that, and it has two useful shapes:

| value | meaning |
|---|---|
| a command | that is the agent — how the e2e suite points at a scripted one |
| the empty string | deliberately no agent |
| unset | the pinned default, wherever one was baked in |

The empty case works through the packaged binary because `makeWrapper --set-default` emits `${VAR-default}` — one dash, so it substitutes only when the variable is UNSET. The CI lane asserts that spelling too: `:-` would swallow the off switch.

The MCP server a session is handed is this process's own, on this process's listener. Loopback clients may omit the bearer; the chat still sends the one it was handed. `olai-plugin-mcp`'s `route.ts` says why HTTP: the tools are this process's ops over this process's store, and a second olai would be a second store watching the same directory.
