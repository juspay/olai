# @olai/ops — the only writer

Semantic edits over a served directory: create an outline, add a node or a whole subtree, mark done, doing or todo, retitle, note, schedule, move, split one node into two, merge one into the sibling above it, copy one and everything under it, trash, set see references, place and retire mirrors, wire the `after` edges a node waits on. Everything that changes an outline goes through here, and everything an agent may READ of one comes out of here too.

It sits between `@olai/format` (what a record is, and what is legal) and `@olai/store` (how bytes become durable). Neither of those knows what an EDIT is; this package is where "mark `order` done" lives, and it is what the web UI's procedures and the agent's MCP tools both call. Recording a write is a `Ledger` door this layer calls through; the git plugin stands behind it, or `commit` / `push` refuse in words.

## Why the edits are semantic

Every request here names a NODE and a change to it — never a byte range, never a whole file. Five things follow, and each of them is a property nothing else in the system had to arrange:

- **a retry is free.** The store's write gate is optimistic: a `baseRev` the store has moved past comes back as `StaleWrite`, and this package re-derives the same edit against the newer snapshot. "Mark `order` done" means the same thing whatever else changed, so a `git pull`, another tab and the agent can all be writing at once and none of them loses an update. Only two edits that genuinely collide survive the retry, and then the op's own refusal speaks.
- **a broken file is unrepresentable.** A plan is whole RECORDS, re-emitted through the format's own writer, so canonical field order and the one trailing newline are not something a caller can get wrong. The glued-line incident of 2026-08-09 — two records on one line, out of a byte-level edit — is not a thing these ops can express.
- **a refusal can teach.** What a write is refused with travels as DATA — the validator's own rows, pinned to `file:line` — so the agent fixes the line rather than parsing a sentence, and the chat panel draws the same rows.
- **a write that LANDED can carry advice.** Finishing the last open task under a parent comes back with a `nudge` saying so — the moment to consider ticking the parent. Policy, in the answer, never an invariant: the format has nothing to say about a mark and the children under it (docs/format.md's Status), and a set that arrives from a git merge saying two things at once must still load.
- **a state can be made unreachable.** A node storing `done` with unfinished tasks below it is work swept off the page, since done-hiding takes a done row *with its subtree* — so both doors onto that state are gated here, once, and both faces get it. `set_done` over a branch holding open tasks is REFUSED, naming them; open work ARRIVING under a done ancestor — a capture, a `set_todo`, a `set_doing`, a move, a merge that hands its rows to a finished sibling, a return from the trash — takes that ancestor's `done` off and says so in the `nudge`. **Neither door is `set_cancelled`'s**, and the reason is the sweep both of them turn on: nothing hides a cancelled row, so cancelling a branch hides nothing and a stale `cancelled` above an arrival sweeps nothing. What that write does instead is a REMARK — `stillStanding`, which names the unfinished tasks it left standing under the branch, in door one's own two vocabularies — because a contradiction a reader can still see on the page is worth a sentence and is not worth a refusal. The two answers differ because the two gestures do: one is a claim about the branch, made now, by somebody looking at it; the other is somebody writing down work, who is not commenting on a mark three levels up and should not be told no because of it. Trashed subtrees are exempt at both doors, and a mirror is never containment at either — a placement is a second view of a node, not a second obligation. The trash's exemption is also where the state can legally be BORN, so `untrash` asks the arrival question twice: what the subtree lands under, and what it carries — every stale `done` inside it comes off too, since a refusal would strand work in a trash that has no way to edit a mark.

## The files

| `plan.ts` | the whole decision, PURE: a snapshot and a request into the files that write would produce. One planner per verb, dispatched by a TABLE keyed on the op — the shape `tools.ts` has one layer up, and for its reason: a verb the format grows and nothing here plans is a missing key rather than a `switch` that compiles. What it no longer does is ASK (`asked.ts`) or SEQUENCE (`following.ts`), which is the whole of `perf-batch-assemble`'s decomplect |
| `refusals.ts` | the sentences this layer says NO with that more than one caller owes — an unknown id, a mirror named where a node was wanted, a path that is not a document or not an outline, a file the set could not load. Each is said by a WRITE and a READ both, and two spellings of one "no" is how a caller who mistypes a path once comes to learn two different things about it depending on which verb the typo landed at. NOT a drawer of every refusal in the package: one that exactly one op can make stays beside that op, because the reason it is worded as it is is the reason that op refuses |
| `ops.ts` | the loop — read, plan, commit, re-plan on a stale base — and `idle`, which is no `run` in flight. `commit` / `push` / `resume` call through a `Ledger` door; the git plugin stands behind it |
| `sorted.ts` | what a write CHANGED, in one word — the format's own classification, derived from the two readings the write is made of rather than from the op's name |
| `query.ts` | reading the set: search, one node, a subtree **or a whole outline**, the outlines — and the two answers about the other kind of file, the document listing and one document's text. WHAT matches is `@olai/format`'s one matcher (`parseFilter` / `matching` — the words, the operators, the archive rule), because a second implementation of the grammar is how `is:done` comes to mean two things. There are TWO doors onto it here: `search` ranks, caps and situates for a list of hits somebody reads, and `narrowing` answers the page filter with the whole membership — every selected id and the field that carried it, uncapped and unranked, because a page prunes itself by the ids and counts itself against them ("3 of 41" off a capped answer is a sentence with an invented number in it). That second one is the browser's alone: an agent asking which nodes match asks `search_nodes` and is answered with the nodes. It is also asked of ONE PAGE rather than of the set, and that is `filter-ask-carries-revision` ([brainstorming/filter-rides-the-page.md](https://github.com/juspay/oss.olai/blob/main/projects/olai/brainstorming/filter-rides-the-page.md)): a filter is a standing view, so a procedure had to be re-asked once per published revision, and each ask was a whole-vault walk — nine of them for one bulk gesture on a 90,000-node vault. Every reader of the answer was a membership test against a row the page already draws, and a page's reading has already resolved every mirror, so the candidates are the records that page draws (`@olai/format`'s `narrowingOf`) and the member is a STREAM on the revision pulse: the walk costs a page, and a gesture that moves no match sends nothing at all. `named` is a third door and is not onto the matcher at all — which of these ids the set declares, and what each one names, for a chat panel deciding which of an agent's backticks are pressable: a batch of `@olai/format`'s `nodeNamed` (mirrors followed, absence meaning both "nothing declares it" and "the chain is dead"), asked once per message, and the browser's alone for its own reason — an agent asking whether an id is real asks `read_node` and is told everything about it. A FOURTH door is not a query at all — `tags` answers the row editor's completion with the vocabulary the set already writes, ranked and capped for a popup, over `@olai/format`'s one `completingTags` (which is where the counting lives, and where the trash rule is decided); it is the browser's alone too, because what it answers is as many rows as the widget that asked has room for. A FIFTH is not a query either — `homes` answers where these ids ARE, and which of these files this directory has READ — for a browser reconciling what it has collapsed against a directory that moved (`vault-in-browser`'s PR 6). Lookups and no walk at all: `byId` for a file per id, and the SET's own served-and-not-broken pair for the files, so it costs the size of the QUESTION rather than the size of the vault — which is the whole of the change, since the id→file scan the browser used to run did not move here, it stopped existing. Two decisions, both about reading the near-miss index: it asks `byId` rather than `nodeNamed`, because a fold is of a RECORD and a mirror whose chain has died folds by its own id, which followed through the chain would read as a node that is gone while its record sits in the file; and it asks the set rather than `byFile`, because `byFile` answers "holds a record" and an emptied outline would come back unreadable, which a caller reads as "nothing can be concluded" and keeps every fold in it for good. Browser's alone for `named`'s reason. What the answers LOOK like is that package's too (`reading.ts` / `searching.ts` / `vocabulary.ts`), and is NOT re-exported from here — a consumer imports a shape from the floor it is declared on. What is left is the SITUATING and the walks around it — how a hit is built out of a record and its ancestry, the cap this layer asks for and the total that is not capped, which mirrors resolve to a node, and how far a subtree descends — **and where one starts**: `subtree` takes an `id` or a `file`, exactly one, and the second is what makes an outline of N top-level roots one call rather than N. It is the second read here that can REFUSE from the walk itself (`document` is the other, and for the same reason): an id the set does not hold is an answer (`{ missing }`), because an id is minted and carried around in prose, while a path was listed or typed and the useful answer to a typo is the near miss — so a `file` that is not an outline comes back with the closest one that is, or with the outlines themselves when nothing is close (`outlineAt`, the guard and its sentence together, shared with the write that places a node at a file's top level — so one typo is answered one way whichever verb it landed at). The field weights, the done penalty and the order are the floor's too now (`ranked`), for the reason the matcher was: one definition, or a shortlist ranked one way in one door and another way in the next. TWO MORE READINGS joined them with `vault-in-browser`'s PR 4 and neither is a search: `dated` is which days of one month have something on them (the calendar's dots, sorted so the answer changes only when the dots do) and `owed` is `owedNow` at the READER's own today (the count the directory's entry wears). Both are the browser's alone for `narrowing`'s reason — a month of dots and two integers about somebody's Tuesday are things only a screen acts on. Both used to walk the whole set per call, which is what `perf-dates-index` was filed on and what neither of them decided; since that node landed both are readings of `Derived.byDay` and this layer is unchanged by it, which is the point of the seam — an index changes what a reading COSTS and never what it answers. `owed` made the trade a second time with `perf-agenda-history-walk`: it was `owedOf(agendaOf(…))`, which meant assembling the whole agenda — every overdue node in the directory situated with its ancestry, its blockers and its rollup — to count two integers off it, per subscriber per published revision, and it is an addition over an index the patcher keeps now. THIS LAYER IS UNCHANGED BY THAT TOO, and the seam is the same one; what is new is that the count and the agenda page are two spellings of one number where the old shape made them one, so `./src/owed.index.test.ts` is the second differential this package carries — every write of a real gate, then the counts asked twice, through this door and through the corpus walk that reading replaced, at every day the corpus can be read on. **`search` is the third to make that trade and the largest**: it walked every record and every body in the directory per query, and it is handed CANDIDATES now ([`@olai/index`](../index/README.md), opened once per served directory by `make` and spent at this one door). Nothing about the answer moved — the candidates go into the same `matching` / `matchingDocuments` the corpus went into, which resolves the ids, applies the scope, the archive rule and the mirror rule and puts the answer in the set's order, so an index can only ever make this door narrower to read and never different to answer. The argument that it cannot be different is a SUPERSET, and it is pinned by a differential test rather than argued: `./src/search.index.test.ts` asks every query twice, through the door and through the walk, after every write of a real gate |
| `standing.ts` | the five readings a tab HOLDS OPEN — a page, the filter over it, the calendar's dots, what is owed and the move picker's preview — answered once per QUESTION per revision rather than once per subscriber. The framework gives every subscriber its own poll loop (`@olai/server`'s `runtime.ts`), which is the right shape for a subscription's lifetime and the wrong cost for its answer: three tabs on one page were three identical rebuilds of that page per keystroke, and every tab in the directory rebuilt what is owed — the dearest of the five — on every write anybody made (`perf-streams-per-tab`). Three things happen here and they are separate claims. THE SHARE: two subscribers asking the same question of the same revision are asking one question, so the second is handed the first one's answer rather than one equal to it. THE PRE-CHECK: before rebuilding at a new revision, ask whether the revision could have moved the answer — `@olai/format`'s `tape.ts`, which taped what the last run read and re-asks exactly those reads, negative lookups included — and where it could not, the previous answer stands and the rebuild does not happen. That is the half the framework's own equality cannot buy, since `isEqual` runs AFTER the answer is built and so saves the frame and never the work. AND THE COMPARISON, ONCE, where it pays: a rebuilt answer equal to the one before it is handed back as the SAME OBJECT when more than one tab is watching, so every subscriber's own `isEqual` is an identity test instead of a structural walk each — and is not compared at all when one tab is, because that tab would have walked it exactly once either way. Nothing is approximated and no rule about the answers lives here: `query.ts` still says what each of the five IS, and this decides only whether to ask it again. It is held to that by a differential (`./src/standing.testlib.ts`): one op corpus, a room of fake tabs, the same five with none of this in front of them, and every tab held to the same answer AND the same frames revision by revision — with three deliberately broken wirings asserted to be caught, because a harness that cannot fail is not evidence. Two generations of answers and no more, rolled by a NEW READING being asked about — not by a revision going by and not by an ask — so a question nobody holds any more falls out after the next two rolls, and a directory nobody is watching rolls nothing and costs nothing |
| `tools.ts` | the closed list of what an agent may do, and what it may not — plus the three doors it is answered through (`Running`, `Asking`, `Acting`), which is what lets a tool be answered by a surface client with no store behind it. `Asking` carries one member no tool answers: the outline PATHS, which is what a capture's landing is read off — a face with no store could only get them by asking for the whole listing, which counts the records of every file in the directory to hand back names (`perf-capture-paths`) |
| `following.ts` | the set as it reads AFTER a plan — what makes `apply` and `update` a FOLD over `plan.ts` rather than a second planner, and the SEQUENCER of the three things that file used to braid together. A plan's whole files go back through the format's own writer and parser, for two reasons: line numbers are not decoration (sibling ties break on them), and a planner's records are DRAFTS that may spell what a file cannot hold. What a set IS stays the format's — one call to `following`, which splices the files an op wrote into the set the op before it left (`withDocuments`), patches the view onto it and holds the two together at the files that were written. It used to take the directory APART into a map and `assemble` it again per op, a fresh path sort of every served file a hundred times for a hundred ops (`perf-batch-assemble`), and then to walk every record in the directory to check the view it had just patched was about the set it had just built (`perf-reading-patched-check` — the fold was checking a delta it had built itself, so the check is now the op's own footprint); both shapes are in the tree and held to one answer at every op of a scripted run (`following.testlib.ts`, `following.equivalence.test.ts`), which also asserts outright that each arm's view is a view of its own set. It carries the ASKING too, and declines to carry it exactly when an op moved which files there are |
| `asked.ts` | what a planner ASKS of the set, as a value: which outlines the directory serves, which of its files hold nothing, and what sits at a path. Eight call sites used to ask those for themselves, in the middle of deciding what a mark or a move means — the braid `perf-batch-assemble` unwound. The asking is lifted out, a batch asks it ONCE and the fold hands it on, and a planner READS a context instead of reaching for a directory. The answers are held with the set they describe (`@olai/format`'s `outlinePaths`, `outlineNames`, `brokenBy`), so building one costs nothing and asking twice costs once |
| `codec.ts` | the seam where the generic store meets the outline format — and where a validated set is declared to BE `@olai/format`'s `Reading`, the files paired with the one derivation they were judged against, so a snapshot carries the view instead of the raw material for one. It is also where the store's "here is what you last answered and what has moved since" becomes the format's delta: one translation with no rule in it, each moved path with whatever it decoded to, so a validation PATCHES its view instead of building one |

The things a writer may ASK FOR are not in that list any more. They are `@olai/format`'s (`writing.ts`), for the reason the four read shapes are: the surface carries them to an agent's door now, and a vocabulary two packages that may not import each other both need has exactly one home. `index.ts` re-exports the two under the names this layer's own answers use — `Request` and `Applied` — and a module that wants them internally aliases them at its import, which is one door to one package rather than two.

`plan.ts` being pure is the design rather than a preference: everything hard about an op is decided there, over a value, so it is testable without a disk and re-decidable against a newer snapshot. The two impure things an op needs — a fresh id and what time it is — arrive as arguments.

**`done` is stamped with the instant it was made**: `set_done` stores `2026-08-11T15:40:03-04:00`, local and carrying its offset (`@olai/format`'s `stampOf`), never a bare `true` and never a day with no time in it. Finishing happens at a moment, the day view reads the day off the front of the value anyway, so the time costs a reader nothing and orders a day's finished work.

**`doing` and `todo` store `true`** (resolved 2026-08-11, the human's call). The symmetry argument — three answers to one question, written by one op — loses to what a date on a mark now means: it puts the node on that day's journal page (docs/format.md's Days). A stamped `todo` would file every capture onto the day it was written down, and `/today` would stop being a record of what happened. Starting and filing are not events a day is about; `set_date` is how a node is scheduled for one.

Only the record being marked is rewritten; a `true` or a day-only value on any other node comes back exactly as it was read, which is what the format means by validating dates as text.

**`set_doing` is the one mark verb the ORDER is a law for.** A node whose `after` targets include a task nobody has settled cannot start, and the refusal names them — title, id and the mark each one carries. The asymmetry with `set_done` is the design and not an oversight: finishing out of ORDER is sometimes true, so that verb is not gated on the edges at all — what it IS gated on is a different question, the branch under it (above). Starting is an INSTRUCTION about what to pick up next, and a machine told to start what the graph forbids has been told to do the impossible. `set_todo` is not gated at all — filing work is not starting it, and a blocked node must be able to stop claiming to be under way — and neither is `set_cancelled`, since calling work off is a decision rather than an instruction to start, and a blocked node is exactly the sort of thing somebody decides against. The predicate is the format's `standingBefore`, the blocked derivation read from the target end, so a bullet blocks nothing, SETTLED work blocks nothing (`done` or `cancelled`), the archive blocks nothing, and no row is ever drawn ready by one rule and refused by another.

Recording what is waiting is the git plugin's, not this layer's: `olai-plugin-git`'s `ledger/pending.ts` derives it from git and stores nothing.

**The package exports four things, and the rest of that table is inside.** `codec`, `make`, `Query`, `TOOLS` — one socket per concept, not the wires behind it. The planner and the commit hook are what those are made of; a consumer wants the writer, not the plan, and its own tests reach it directly.

**None of the SHAPES belong to this package any more, and none of them is re-exported from it.** `GitState` went first; search's followed (#167); and the last three query answers — the `list_outlines` summary, `Detail` and `Subtree` — are `@olai/format`'s `reading.ts` now, with the requests two of them take. This layer still PRODUCES every one of those values, and that is the division: a shape that crosses a wire is the floor's, because `@olai/surface` may not import this package and a vocabulary spelled here would have to be spelled again there. A consumer imports them from the floor, where they are declared; every consumer of `@olai/ops` already depends on `@olai/format`, so a re-export here would buy nobody an import they could not already write. The summary is `OutlineSummary` there, renamed on the way because that package already exports an `Outline` meaning one file's decoded NODES, which carries `file` and `nodes` too and would have looked compatible at a glance.

The TABLE is exported and used to be private, and the reason it changed is that this package used to own an MCP server too. What a consumer wanted then was the server, and the list was what the server was made of. `@kolu/surface-mcp` is the server now — so the list is what a consumer wants, and the projection onto MCP lives in `@olai/server`, which keeps the MCP SDK out of this layer entirely.

## A subtree in one call

`add` takes an optional `children`, and each child takes the same fields the node itself does — `title`, and optional `desc` / `date` / `mark` / `id` / `props` / `see` / `waitsOn` — with `children` of its own. So capturing an outline is ONE call: one plan, one validation of the whole set, one atomic rename, one commit.

It is a fix for two things that were the same thing. An agent capturing a house outline issued one `add_node` per node — thirteen calls, each paying the full write gate and a round trip — and a failure partway through that sequence left a half-captured subtree behind, with nothing to say which half. A tree that is planned at once cannot half-land: the gate already writes all files or none.

**`create`'s `seed` is that same capture**, `children` and all, so a brand-new outline arrives holding everything it was born with. That is the same argument one level up: `create` then `add` was two plans, and a second one that refused left an EMPTY outline on disk nobody had asked for. Now the file and its contents are one plan — a seed refused anywhere in its tree leaves no file at all, which `src/ops.test.ts` asserts against a real directory. The two tools therefore take one shape (`ROOT` in `@olai/format`'s `writing.ts`): a seed that could say less than a capture would be a reason to make the second call this exists to delete.

- **The mark rides along.** A captured node may be born with any of the four marks, written exactly as `set_done` / `set_cancelled` / `set_doing` / `set_todo` write it — one `marker` function, read by both — so a settling mark records the instant and lands on today's page, and the other two store `true` and place the node on no day. One field rather than three flags, because the format allows at most one mark and a shape that can spell two is a shape a caller can get wrong.
- **Placement is the root's.** `before` / `after` place the node being added among its new siblings; the children are being born, so there is nobody to place them among and they land in the order they were written. File order is the outline's reading order: a parent, then its subtree, then the next sibling.
- **A collision refuses everything.** A chosen `id` that the set already holds, or that another node in the same call also chose, refuses the whole capture — which is also what a cycle attempt looks like when every node is being born at once, since a child naming an ancestor's chosen id is naming a taken one. Nothing lands, because "nothing landed" is the only answer that makes the call atomic.
- **The answer names what it made.** `captured` carries every node's id and title, parent before child. A minted id is unguessable, and an agent that just wrote thirteen nodes should not have to search for them to mark one. It has ONE shape: a plain capture is a list of one, a seeded `create` is too, and it is absent only from the ops that create nothing — which is how the format spells an empty list everywhere else. Only the commit subject asks whether anything came along, since `(+0)` would count nothing.
- **The EDGES and the PROPERTIES ride along too** (`olai-batch-verbs`), and that is the same sentence read forwards. A capture used to say what a node IS and nothing about what it POINTS AT or what it KNOWS, so a subtree arrived and then thirteen more calls wired it — one `set_after` per dependency, one `set_prop` per fact, each its own round trip and its own revision. `props` is `set_prop`'s map several keys at a time, `see` is `set_see`'s list, `waitsOn` is `set_after`'s, and they are written through those verbs' own writers (`withCustom`) and answered with those verbs' own refusals: a shadowed key turned toward the field that owns it, an unknown target answered with the closest id, an edge that would close a loop refused NAMING the loop. **`waitsOn` and not `after`** for one reason and it is worth knowing: at the top of a capture `after` already names the SIBLING the node is placed after, and it is a string where this is a list — two meanings of one word differing by how deep in the tree you stand is exactly what the shared `CAPTURE` shape exists to prevent.
- **`after` on a captured node is REFUSED, naming the bend.** The word costs something and this is the cost paid rather than deferred: below `add_node`'s root, `after` is not a field of a capture at all, and an Effect struct drops a key it does not declare — so an agent that has read `set_after`, or that is looking at the anchor one line up, would lose the whole dependency under a call that reported success. The schema declares the key purely to make it refusable (the `children`-at-the-floor trick, one field over) and the planner turns it away by name, pointing at `waitsOn`. A seed's root gets the same answer, since a file with no other rows has no placement for `after` to mean.
- **A target may point FORWARD.** Every id in the tree is claimed before any edge is read (`plan.ts`'s `wiring`, a deliberate second pass), so a child may wait on a sibling declared later in the same call, or anywhere else in it, or on a node the set already holds. Resolving as the walk arrived would have made "step two waits on step one" legal and "step one is followed by step two" a refusal about an id that is right there in the request. The did-you-mean offers the ids being minted as well as the set's, and the loop check reads the set's ordering graph PLUS the capture's own — so a ring drawn entirely between nodes that do not exist yet is refused here rather than by the validator, against a file nobody has written.
- **A capture may arrive `doing` and blocked, and is not refused.** `set_doing` is gated because starting is an instruction and a node the set ALREADY says cannot start has been told to do the impossible; there is no *already* about a node being born, and `set_after` on a node that is under way is refused nowhere. So the row lands, drawn blocked, saying what it waits for — the discovery, not the instruction.
- **It nests three levels deep, and that cap is the JSON Schema's.** Neither the format nor planning a tree wants a depth limit; what has one is the schema an MCP host reads, and the planner enforces THAT rather than one of its own. A recursive Effect schema compiles to a `$ref` into a `$defs` pool, and the adapter that projects these schemas inlines every local ref and strips the pool, because `$ref` is rejected across the host matrix it is byte-compatible with — so a ref it cannot inline finitely would survive as a pointer into nothing and take the whole tool down. The nesting is therefore unrolled, and three levels is what the capture this was filed for needs while each further level is another whole copy of the child schema in every `tools/list`. The floor of the unrolled schema still declares `children`, on purpose: an Effect struct silently DROPS a key it does not declare, so a schema that simply stopped would swallow the deepest level of a capture and report success. It is refused by name instead, pointing at the id in `captured` a second call should hang the rest off.

## Several writes, one plan

`add`'s `children` is one shape of this argument and `split` / `merge` below are another; `apply` and `update` are the general one (`olai-batch-verbs`). An agent driving this surface paid one round trip per FACT: spawning an orchestration lane cost thirteen calls — one `add_node`, nine `set_after`, three `set_prop` — thirteen revisions, thirteen pending rows, and a seventh that refused leaving six on disk with nothing to say which six.

- **`update` folds the FIELDS of one node**: `{id, title?, desc?, date?, props?, after?, mark?}`.
- **`apply` folds whole OPS over whole outlines**: an ordered list of the write verbs, run as one write.

**Neither is a second planner, and that is the whole implementation.** Both are `plan.ts`'s `folded`, which calls `plan` once per op against the reading the op before it left behind (`following.ts`) and merges what comes out: files by path with last-wins, `captured` concatenated in order, the `nudge`s joined, and `id` / `title` / `file` from the last op — which is the only choice that is right for `update`, where a retitle followed by a mark must report the NEW title. So every refusal is the single verb's own refusal, in the single verb's own words, made at the single verb's own moment; there is nothing here that can drift from what one call does, because it IS what one call does. The tests assert that literally, comparing a batched refusal's message against the same op called alone.

**One plan means one write.** The gate does to it exactly what it does to every other plan: validates the set it would produce ONCE, renames once, publishes one revision. That is also why `apply` is the atomic repair when a file holds several values a declaration refuses: a single `set_prop` of one still leaves the others, the gate refuses the file, and one batch that fixes them all is one validated write that lands. The intermediate sets the fold builds are speculative — nobody draws them, nothing is published at them — which is why the fold does not validate at all, and why it reaches each of them through `@olai/format`'s `following` rather than through `patch` directly: that function builds the set AND patches the view AND holds the two together, and this caller is exactly the shape that guard exists for. `patch` itself is exported — the browser folds delta frames with it (`model-indices` slice 4) — but the browser holds no SET to hold the result against, where this fold assembles a real one per op; a view built from a delta that missed a file makes every record look like a duplicate of itself, so the two consumers differ by what they are holding rather than by what they remembered. **The guard is narrowed to the op rather than run over the vault**, and the reason is that this caller is its own claimant: what a whole-corpus check defends against is a delta that MISSED a file, which is a thing to check when the set and the delta come from different places (the store's set is a directory of decoded files and its delta is a probe's list of which of them ticked). Here one list builds both halves, so what is checked is what the call itself did — the written records are filed under the written paths, in that order — and a disagreement still costs the same rebuild. That is `perf-reading-patched-check`; the whole-corpus door stays exactly as it was for the caller that is making a claim (`reading`), and the batch's reference fold still comes through it so the two are compared at every op. What all this is NOT is free — per op, per file that op touched, one serialise, one parse and one SPLICE of that file into the set the op before it left, and the patcher declines outright on a single-outline directory (nothing of the old view is left to patch onto), so a batch there rebuilds its derivation each op. The splice used to be a whole `assemble` — the directory inverted into a map and re-sorted, per op — which is what `perf-batch-assemble` took out; what remains per op is one pass over an array of references, and the bench prints the end-to-end figure, what the set-building alone is worth and what the whole door is worth, because a fold op is four things and each of those two nodes changed one of them. That is one write's worth of work where the loop it replaces was N writes' worth of disk, and it is bounded by the cap below. A batch refused at op seven leaves the file byte for byte as it was, and the refusal names `` ops[6] `` with that verb's reason under it and that verb's KIND on it (a batch whose op named a missing id is a `not-found`, not a `usage`).

**Each op sees what the ops before it did**, which follows from the same fold: a later op may name a node an earlier one created, mark what an earlier one captured, or find the door-one gate satisfied because two ops above it finished the branch. It cuts the other way too, and deliberately — `[set_after, set_doing]` in one list meets the gate the two calls in that order meet.

**What `apply` will not take is four things.** `create_outline`, `create_document` and `write_document` are the writes whose subject is a FILE rather than a node; each is already atomic over the thing it makes, and a mistyped path has no business inside somebody else's transaction. `apply` itself is the fourth: a batch of batches is one flat batch with an index nobody can name. `update` IS in the list, because a batch of `update`s is the shape "reconcile these five lanes" actually has. The arms are the request schemas THEMSELVES, with only their top-level prose taken off — one declaration, so a batched `set_done` and a called one cannot decode differently, and 8 kB of `tools/list` not spent saying twice what the tool beside it already says.

**`update` carries the CONDITIONAL write too**, and that one had to be carried rather than left out. `was: {title?, desc?}` is `set_title`'s and `set_desc`'s own field, per field, checked inside the plan and therefore on every retry the write gate makes. It covers those two and nothing else, because those are the two verbs that have one — `set_date`, `set_prop` and `set_after` do not. Leaving it out would not have been a smaller surface, it would have been a silent one: an Effect struct DROPS a key it does not declare, so an agent moving from `set_title {id, title, was}` to `update {id, title, desc, was}` would have got everything it asked for minus the guard, with nothing saying so. A `was` naming a field the call does not write is refused rather than ignored, for the same reason.

**Two of `update`'s fields behave differently and both on purpose.** `props` MERGES key by key — a key not named is left alone, `null` (or `""`) removes the one that is — because that is `set_prop` repeated. `after` REPLACES: the array given is the node's whole list and `[]` clears it, because every other field there is that field's whole value. What is actually handed to `set_after` is the whole list as `add` plus whatever it displaces as `remove`, never a pre-computed difference — which is what keeps the incremental verb's no-op refusal ("already comes after exactly …") rather than turning it into a complaint about a call the caller did not make. `set_after` remains the incremental verb for anyone who means to add one edge and keep the rest.

**The MARK is applied last**, whatever order the fields were written in, because a mark is a claim about the node as it now stands. `{mark: "doing", after: ["order"]}` therefore meets `set_doing`'s gate with the edge already in place and is refused; the other order would have landed a `doing` and drawn it blocked a frame later, which is the state that gate exists to make unreachable. `mark: null` takes off whatever mark the node carries — the one spelling here that no single verb has, since each of the three has to be told which mark it is undoing.

A batch runs at most `BATCH_AT_MOST` (100) ops. Nothing about the fold wants a limit; what has one is what a refusal can usefully SAY about an all-or-nothing run.

**Neither verb reaches the web face, and that is not the consistency rule being bent.** The rule is about CAPABILITY — a thing one face can do to an outline that the other cannot — and there is nothing here a browser could not already ask for. What these two remove is round trips, which a browser does not spend: a keystroke is one intent, one write and one undo entry, and folding two keystrokes into one write would take away the second ⌘Z rather than buy anything. The layer under both faces is unchanged, so the day a web gesture genuinely means several ops at once (a multi-row mark, say), the verb is already here.

## Splitting and merging

Two ops that each do several things to an outline at once, and they are ops for exactly that reason. A split is a retitle and a create; a merge is a retitle, a note, N reparentings and an archive. Assembled by a CALLER out of the verbs above they would be two, four or six writes at as many revisions — and a sequence can stop in the middle, which for a merge means an outline saying something nobody wrote (a title already joined with the children still hanging off a row that is about to go). One request is one plan, one validation and one all-or-none rename, which is the property `add_node`'s `children` buys one level up.

It is also what keeps the two faces equal. The web's `Enter` mid-line and `Backspace` at line start are these ops and nothing else; a keyboard that assembled them from `set_title` + `add_node` would be doing in one keystroke what an agent needs four calls for, which is the consistency rule read at its plainest. So both were born here and reached both faces in the same change, the way `untrash` did.

**`split`** takes two TITLES — what the node keeps and what comes off it — never a character offset. An offset is a range into a field, which nothing in this table names, and an offset re-planned against a newer snapshot would cut somebody else's retitle in half; two strings mean the same thing against any revision. The tail lands immediately after the head among its siblings and is born a BULLET: everything that described the node — children, note, mark, date, edges, `doc` — stays with the head, because the new row is one nobody has said anything about yet.

**`merge`** takes one id and reads the sibling above it off the snapshot, for the reason `move_node` does not take "the row above" either. What survives is the decision:

- **the titles run together**, with nothing between them. They were one line before somebody split them, and a separator invented here is text the caller did not type;
- **the notes join a blank line apart**, and a node with none takes the other's. A note that vanished off the page would be a silent loss, and "it is in the archive" is not an answer for a row that is still on screen;
- **the children move**, in order, to the end of the survivor's own. Nothing may be orphaned by a keystroke;
- **the mark, the date, the attached `doc` and the edges go with the RECORD into the archive.** The format allows one of each per node and the survivor already has its own answer, so there is no merge of two — and nothing is destroyed, because the record keeps its id in `_olai/Trash.olai` and `untrash_node` brings it back. What the op owes is that this is never silent, which is what the reply's `nudge` is for: a `done` that has left the live outline is exactly the news a person is owed, and so is the file that was attached to it.

Refused when the node is first among its siblings (nothing above it), when the row above is a MIRROR (a placement has no title to merge into) and, like every text op, on a placement's own id.

## Duplicating, and what a copy is entitled to differ in

`duplicate` copies a node and everything under it as the sibling immediately below. It is the shortest request in the vocabulary — one id — because everything the copy SAYS is already on disk: the op reads the subtree rather than being handed one, so there is nothing to describe, nothing to nest and no depth cap (`add`'s three levels are the JSON Schema's problem, and nothing here is being described to a schema).

The whole semantic is one sentence — **the copy is a second thing, not a second claim on the first** — and every decision falls out of it:

- **every id in it is fresh**, root and descendants alike, decided before any record is built. That is the promise; without it the "copy" would be a set the validator refuses, or a placement wearing a node's clothes;
- **the two STAMPS are the copy's own** — `created` is now, `changed` is absent — exactly as they are on a node a capture brought into being. Those two are the ledger's rather than a writer's (`@olai/format`'s `node.ts`), and a ledger does not make up a past it did not see;
- **everything else is verbatim, THE MARKS INCLUDED.** A `done` keeps the instant it was stamped at, a `todo` stays a `todo`, and the date, the repeat rule, the note, the properties and the attached `doc` all come across. Workflowy preserves completion and so does this, but the argument is stronger than precedent: every alternative INVENTS a claim the caller did not make — dropping the mark says the copy was never a task, re-stamping the `done` says it was finished today, rewriting it to `todo` says it has not started. The one visible consequence is stated rather than hidden: a duplicated `done` lands on the day the original was finished, because that is the only day either record knows about. Sweeping the copy's marks afterwards is an `apply`, which is one call;
- **the title is verbatim too.** No `(copy)`, no `#copy` tag (which is what Workflowy adds): a title is stored exactly as it was typed, and a word nobody typed is a word in somebody's git history;
- **the `ord`s below the root are the originals'**, which falls out of the ids being fresh — each copied child sits among copied siblings only, so the keys that sorted them sort them again. The one key minted is the ROOT's, which lands it immediately after the node it copies.

**What the copy POINTS AT is one rule with two halves**, and it is the half of this op with real design in it. A reference the subtree makes to ITSELF follows the copy — a `see` between two of its nodes, an `after` edge one of them waits on, a mirror placed under it — so the copy is self-contained rather than reaching back into the original. A reference that LEAVES the subtree keeps its target, because that target was not copied and there is nothing else the reference could mean. Which fields those are is `@olai/format`'s `targetsOf`, the same closed list the validator reads forwards and `remove_mirror` reads backwards, so a fourth relation added to the format is re-pointed the day it exists rather than being the one field a copy quietly leaves aimed at the original. And the rule read from the OTHER end is the third case: an edge pointing INTO the subtree from outside it is not followed at all, because the record that made it was not copied and this write may not rewrite it — only the subtree's own records are re-emitted, so copying that edge would invent a second claim and moving it would take one away.

**A mirror is copied as a MIRROR** — the placement, not the identity. Duplicating a Now list gives a second list OF THE SAME WORK, and never a twin of the item: expanding a placement into a node would be this op inventing content nobody wrote. A placement's own id is refused as the subject, in the same `notANode` words every other op refuses one with — `add_mirror` is what places a second one.

It needs no rule of its own beyond that, and deliberately: a subtree that is legal on disk is legal written twice, because the copy is isomorphic to something the validator has already approved. The one thing it inherits is the ARRIVAL gate every other op that lands work somewhere inherits — a stale `done` above the landing, standing over unfinished work the copy brings, comes off and the `nudge` names it.

## Moving, including out of the outline a node is in

`move` is one verb for three gestures — reorder among siblings, reparent, and carry a subtree into ANOTHER OUTLINE — and the third one is the one worth arguing, because for a long while it was refused here in a sentence that read like the format speaking: *every outline is an independent tree, so a parent is always in the same file; archiving is what moves a subtree between them.* The first half is the format's and still holds (`@olai/format`'s `foreign-parent`: a record's `parent` names a record of its own file). The second half was a fact about this planner, which rewrote one file — and what it sent callers to does not do the job. The only cross-file move the vocabulary could express was capture-a-copy-under-fresh-ids plus a `trash` of the original, and an id is unique across the set INCLUDING the trash, so the copy cannot even reuse the ids: every `see`, `after`, `blocks`, mirror placement and typed `ref`/`node` property aimed into what "moved" comes loose, silently. That happened in this repository's own board (the `supervision.olai` extraction, 2026-08-25), which is what filed the gap.

So the promise is `trash`'s own, made about the same journey: **the ids move with the nodes**, and everything pointing at them goes on resolving. Nothing is re-pointed because nothing needs to be — the served directory is one namespace and the node never left it. That covers the four kinds `namedBy` carries (`see`, `after`, `blocks`, a mirror placement) and three it does not: a typed `node` property, a PIN (a title that is an address, which the grammar normalises to the id — so even a qualified `/house.olai#install` survives the file it names going stale), and a DAY PAGE, where the node keeps its date and its place in the day and changes only the group heading, which is the outline.

**One reference a crossing can genuinely break, and it is refused rather than broken.** `node` and `ref` are two promises: `node` is existence, which an id surviving is enough for; `ref` additionally asserts ancestry under a named `under` root (`variantsOf`, direct children). Moving the ROOT carries its variants and every `ref` holds. Moving a VARIANT out of that root makes each `ref` at it `bad-prop` — and the write gate validates the whole set before either file is written, so the move is refused with nothing landing, **naming the third file it would have stranded** (`` would leave `lanes.olai` invalid ``). The law doing its job, said out loud rather than left for somebody to meet. It is NOT a fence at this verb: the gate asks about the files the write puts down PLUS the ones it darkened against the tree that was standing (`@olai/format`'s `darkened`, spent through `Codec.stopping`), so every door that could strand a value pays it — a trash, a merge, a split, and whichever one is written next — while a file that was already broken goes on stopping nothing.

- **the surface is one optional field**, `file`, and it is the pair `add_node` and `untrash_node` already take, judged by the same `landsIn`: a `parent` decides its own outline, `file` alone is that outline's top level, and neither is a new rule to keep in step. A second OP would have had to re-declare the anchor, both loop refusals, the mirror rule, door two and "last among its new siblings" — five rules free to drift apart;
- **the machinery is `trash`'s**, not a second copy: `liftSubtree` for what the source keeps and what travels, `carryingDoc` for the one field that is relative to the outline naming it. The subtree arrives shaped as it left — only the root is re-parented — and one plan carries both files, so the whole set is valid after or nothing moved;
- **nothing is re-stamped beyond what a same-file move already stamps.** The record that moved records a `changed`, because its place changed; marks, dates, `created`, notes and properties travel untouched, exactly as an archive carries a subtree. Moving is not editing;
- **the loop refusal that crosses files is the DRAWING one.** Containment is per-file, so a cross-file parent cannot fold a branch into itself — but a mirror is how one node is drawn in two outlines, so a Now list in one file may not go under work it is showing in another. Same walk, now load-bearing in a case the parent walk could never have covered;
- **the trash is neither end of it.** `trash` records the outline a pile came from and `untrash` tidies that record and re-opens the marks that stop being true once a branch is live again; a move does neither, so crossing into or out of a trash is refused toward whichever of the two the caller meant. Reordering INSIDE the trash is an ordinary move, because nothing crosses.

Both faces get it from the one planner: the move-to picker (`⌘⇧M`) searches the whole directory and sends `move_node` with the parent a reader chose, whatever outline it is in. What a DRAG still cannot do is a limit of that gesture rather than of the set — a drop measures a gap between rows of the file it is carrying — and the pane says so, pointing at the picker.

## Trashing, in racket's terms

`trash` moves a node's whole subtree into `_olai/Trash.olai` — the one trash for the served directory — re-creating the chain of ancestor TITLES it hung off, with the source outline as the outermost title so untrash can put it back. The reference implementation's semantics are kept because they are what the trash is for:

- the scaffold is one record per ancestor carrying its title and nothing else — no dates, no marks, no notes. A chain the trash already has is merged into, matched by exact title at that level, and new arrivals append at the end;
- **nothing is stamped.** Trashing is not finishing: a done node keeps its date, and an unmarked one is put away unmarked rather than being called finished on its way out. What changes is where the node lives;
- **ids move with the nodes**, so a `mirror`, `after`, `blocks` or `see` target goes on resolving — the served directory is one set and the trash is in it. What changes is that those edges stop holding anything up: work put away is over, so it blocks nothing and nothing blocks it (docs/format.md), and the file name that decides which nodes are in the trash is the format's own `TRASH` rather than a second copy of it here. That is exactly why the scaffold nodes get MINTED ids rather than copies of the live ancestors': an id is unique across the set, and a copy would collide with the node it was copied from;
- both files are validated as one set before either is written, and both land in one commit.

`untrash` is the way back out (`parity-unarchive` — for a long while there was none, on any face), and it is the trash read in reverse:

- the subtree returns INTACT, ids and all — the set is one namespace and the node never left it, so nothing can collide and nothing is re-pointed;
- **where it lands is the trash's own record by default**: the outermost scaffold title is the outline it came from, and the rest of the ancestor-title chain is matched inside that outline. Titles, not ids — the scaffold's ids are minted — so the match can fail two ways, and both are refusals that NAME what was found: nowhere (the chain was retitled, or put away itself) and more than one place. `parent` / `file` are the caller's way past them, judged as `add_node` judges the same pair — except that the trash is refused as a destination, because putting something back IN is `trash`'s job;
- it lands LAST among its new siblings: the trash does not record where in a row a node sat, and a guess dressed as a restore would be worse than the honest answer every other arrival gets;
- **the scaffold is tidied on the way out** — an ancestor the removal leaves empty is dropped, provided it is the bare title record `trash` mints and nothing in the set still names it — so trash-then-untrash leaves the trash exactly as it stood;
- **and the scaffold itself may not come back.** Only what was MOVED is restorable. A scaffold record is a copy of a title that never left, so restoring one would stand a second live node beside the original and hang the trash's rows off the copy. Nothing on disk marks a minted record, so the refusal asks the two questions that together are what a signpost IS: the record is BARE — the exact shape `trash` mints, a title standing at a place — and a live node AT THE LANDING already carries that title, which is the copy showing itself (a scaffold exists precisely because its ancestor is still there). Content that happens to be title-only left a hole behind it, so nothing answers to its name and it restores like anything else. Asking only the first would refuse every plain heading anybody put away, which is the ordinary case rather than the rare one.

`empty` is the third verb of that pair and one of the two writes in this layer that DESTROYS — `delete` (below) is the other, at file size, and the pair is one sentence: records are destroyed by emptying the pile that holds them, files by the verb that names one. `empty` names `_olai/Trash.olai` — leftover `Archive.olai` files refused as not the trash — rewrites it holding no records at all, and leaves the file standing:

- **it names THE TRASH and never a node.** There is no way to delete one row out of the trash — that is a shredder aimed at a row, which is #109's still-open deferral. The unit is the pile, the way a bin is emptied rather than picked through;
- **the holder check is over the records this write deletes.** A leftover `Archive.olai` that still names something in the trash holds the emptying, because that leftover is not the trash and is not going;
- **`was` is the count the caller expects**, optional, and checked on every re-plan. A write is re-derived against a newer snapshot when the store moves under it, and this one silently WIDENS: a node put away in between goes too, under a sentence that named a smaller number. With `was` that is a refusal naming both counts — `set_title`'s own guard, one op along;
- **it is refused while anything OUTSIDE the pile still names something in it** — `remove_mirror`'s rule (below) read over a set instead of over one record. Ids move with a node when it is put away, which is exactly why the mirrors and edges naming it go on resolving; deleting those records would leave live outlines naming ids nothing declares, which is a set the validator condemns. The refusal names each such record with its `file:line` and the field it points with, so the way through is re-point, retire, or `untrash` what they name;
- **three more refusals, all about which files these are**: an outline the set does not hold, an outline that is not the trash (nothing here deletes out of a live outline), and a trash that holds nothing — refused rather than written as a diff-less no-op, so "the trash is already empty" is a sentence somebody reads;
- **it destroys exactly as much as it says.** Same gate, same all-or-none rename, same commit door as every other write, so the bytes are recoverable from git to precisely the extent git had already recorded them. A `.md` a trashed node's `doc` named is a FILE and is untouched: nothing in this vocabulary names bytes.

`delete` is the second destructive write, and its unit is a FILE: a document (`.md`) of any content, or an outline holding no records — the file leaves the directory, the listing and every live collection on the write's own revision.

- **the store arm that carries it is a REMOVE, not a rewrite.** `Change.contents: null` says "this path goes", and the gate does with it what it does with any other: probes, checks the base, validates the set the tree would be without the file (decoded and judged, as a rewrite is), lands the unlink after the publishes, and lets the probe report `removed` — which is the load-bearing half, since the commit's own `forget` is what would otherwise hide exactly this diff. No rename is the atomicity model, one unlink after the renames is the trade;
- **an outline goes only EMPTY.** Records are moved by `trash`, not deleted — the refusal names the ones still carried, in id-and-title, capped at the refusal list the rest of this layer carries. This is a rule about what a delete is FOR: the file is the unit, and what "takes an outline's records somewhere else" means is a question the trash answers; a delete that answered it instead would be guessing;
- **a document goes only UNNAMED.** Both doors the format knows resolve a value to a served `.md` — a record's `doc` field and a value of a key DECLARED `doc` — and a document either of them still names is refused, in `remove_mirror`'s `file:line`-per-record shape. The reason is the validator's own: the next load would condemn those records' files on exactly these edges, and refusing here is that finding said early, in the write's own terms. A `path`-declared value is never consulted — it promised a shape only — and neither is a markdown link: going dead is markdown being markdown (docs/format.md's addressing);
- **the `.olai` is the unit it shares with `create`, and the `.md` with `create-doc`; there is no third.** A `.html`, `.csv`, picture or `.pdf` is a file this app SHOWS and never writes, and is refused however empty: it belongs to whatever put it there. The refusal names the kind (`hypertext`, …), never another file — which is the one shape of near-miss a delete must not offer. A `did-you-mean` IS offered where the path itself is the miss — the nearest thing the verb CAN delete, which is the same near-miss `write_document` and `read_document` offer and deliberately not the wider one `report.html` would give for `report.md`;
- **it is not in `apply`, for `create_outline`'s reason:** each file verb is already atomic over the thing it makes, and a mistyped path has no business in somebody else's transaction;
- **an `untrash` retires nothing and an `unempty` creates nothing, and this has no inverse either.** The file is recovered from git exactly as `empty`'s pile is — the same gate and the same commit door, the same caveat, argued where the request is declared (`@olai/format`'s `writing.ts`).

## What comes back: the recurrence

`set_repeat` puts a rule on a dated node — `every day`, `every week on <weekday>`, `every month`, `every year`, and nothing else, the format's whole closed grammar (docs/format.md's Repeating) — and `set_done` on a node carrying one stamps it AND captures the next occurrence. That second half is the design decision worth stating: **it lives in the planner, in one function (`recurring`), and nowhere else.** The browser's `Complete` and an agent's `set_done` are the same request planned by the same function, so "finishing a repeating node makes the next one" is a fact about the OP rather than a behaviour two surfaces agreed to implement — there is no other place both faces could be true at once.

The new node is FRESH rather than the old one re-dated: the completed record keeps its own day and its `done` instant, so eleven finished occurrences are eleven records on eleven days instead of one row whose date kept moving and could prove none of them. It is placed immediately after the node that was finished, born `todo`, and carries the title, the note, the rule and the day the rule names — and nothing else, each omission naming something particular to the occurrence that just ended (edges pointing at work already done, children that recorded that occurrence's work, a `doc` two nodes would then be editing, properties about that one run). The answer names it in `captured` and says which day it landed on in the `nudge`, so neither face has to read it out of prose.

**The rule travels with it**, and that one decision is what makes the churn edge unrepresentable rather than policed: the completed node no longer carries a rule, so un-doing and re-doing spawns nothing, and there is no "have I already spawned this?" flag for anything to remember. Un-doing does not take the occurrence away either — it was a write, and what the set then holds is a recurrence with one live head.

Two consequences fall out of the spawn being a real arrival. The rollup's nudge is SUPPRESSED by one, because "every task under this parent is done now" is a sentence the same write makes untrue and the snapshot cannot see a record that does not exist yet. And door two applies: the occurrence is open work landing under whatever stood over the node that was just finished, so a stale `done` ancestor is re-opened exactly as `set_todo` re-opens one — without it, a finished branch would go on hiding the next occurrence of everything under it.

**No verb here judges the rule, or the pair it makes with a date.** Both are per-line rules of the format's, and what refuses them is the write gate — a write may not produce a file olai cannot read back (`@olai/store`'s `commit`) — so `set_repeat` with a rule the grammar does not have, and `set_date` clearing the day out from under one, are refused in the validator's own words with the code and the `file:line`. That is one wording for one rule however the pair moved, and it is the same gate that now catches a `date` that is not a date and an `id` that is not a slug: they used to LAND, and take their outline off the page with them.

`update` still has one bend in its fixed field order — `repeat` goes before `date` when the call is STOPPING a recurrence — and it is about the FOLD rather than about the pair: each op is planned against the set the ops before it left, and that set is assembled through the parser, so every intermediate record has to be one the format can read. Removal before addition is the only order that works both ways. `apply` needs no such rule because a batch is ops somebody ORDERED; `update` is fields, which have no order at all, so the planner has to choose one.

## The git commit

A commit is something somebody ASKS for. Writes land on disk and wait; the two doors are a Commit button in the browser and the `commit` tool an agent calls when it knows its work is finished, and both are callers of one `Ops.commit`. `--commit=auto` adds a third caller that is nobody: the QUIET WINDOW — the rule is `@olai/format`'s `window.ts`, the timer over it is `src/pending.ts` — which records everything waiting once writes stop arriving for fifteen seconds and is the same `Ops.commit` again. `--commit=off` (`--no-commit`) is for a directory whose history is somebody else's job.

The window is armed by the arrival of a survey rather than by a clock of its own — the composition root hands each reading to `Ops.observe`, and `Ops.loop` is the effect it forks — so a browser keystroke, an agent's op, a quick capture and a `.md` saved in an editor all move the same window and land in the same commit. One per served directory by construction: one olai holds a directory, so there is nothing to elect. `--push=auto` follows every settled commit with a push, whichever of the three doors made it, and a refusal of either verb stops the loop until `Ops.resume`.

`Ops.catchUp` is the fourth thing the root runs, once, at boot: under `--push=auto`, and where the branch has commits its upstream does not, it makes one push so a branch that cannot be sent says so before anybody looks. Nothing about a refusal is remembered across a restart — the state file holds the policy alone — and `olai.service` restarts on its own, so the words are re-earned rather than written down. The "has it anything to send" check is HERE rather than left to `push`, and it is the one place the two verbs want different answers: a branch with no upstream is not a branch that is behind, so the button lets that through to git (a person who pressed it is owed git's words about the remote they have not set) and a boot does not (it would stop the loop of every never-pushed directory at every start). Under `--push=off` a boot attempts nothing at all.

`--commit=auto` used to mean one commit per write, made inside the store's write gate. That is retired, and with it the store's post-publish hook: a train of thought arrived as a dozen commits, which is the thing manual mode was introduced to end.

What is waiting is DERIVED (`pending.ts`), and it is the WHOLE REPOSITORY in two kinds of row. `git status --porcelain` names every dirty file in it — the survey used to be pathspec'd to the served directory, so a person who edited a `README.md` one level up was told nothing was waiting, which is the bug `commit-whole-repo` was filed for. For an outline olai serves, the copy the current commit holds is the committed side (`committed.ts`), the store's own last-good parse is the working side, and `@olai/format`'s `changesOf` compares them into node-level changes. For everything else — a document, a source file, an outline outside the served root — the row is a path and the porcelain's own status letter, because the only richer thing available is a text diff and this is an audit-trail recorder rather than a git client.

A commit names exactly the paths it was asked for (`CommitRequest.paths`, repository-root-relative; omitted is everything) and nothing else, on both `add` and `commit`. It is a SELECTION and never git's index, so work somebody staged by hand is undisturbed and what is left out stays waiting for its own commit and its own message. A path nothing is waiting on is refused by name rather than quietly dropped.

Undisturbed reads both ways, which is what `commit-op-staged-rename` corrected. A rename somebody staged themselves is ONE row naming both halves and one tick; the commit carries the departing half with the arriving one, so it lands as a rename rather than as an add beside a deletion left staged. For an outline, the committed side is HEAD's copy of the file it CAME FROM — read against the name it has now, which HEAD has never had, every node in it reported as created.

**The committed side is read once per commit, not once per keystroke** (`committed.ts`, `perf-git-per-write`). It used to be a `git show HEAD:<file>` subprocess plus a full parse of what came back, for every dirty outline, on every published revision — and under manual commit the dirty list only grows through a session, so typing got slower the longer a commit was deferred. A commit's copy of a file cannot change, so it is asked for as `<sha>:<path>` and remembered under that pair; HEAD moving is not an invalidation but a different key, and there is no invalidation call anywhere for somebody to forget. A keystroke with fifty outlines waiting now costs ONE `rev-parse` and no file read at all — 37ms to 7ms on a quiet laptop, and flat in the dirty list where it used to be linear (`src/pending.bench.ts`, `just bench`). The SUBPROCESS COUNT is the reproducible half of that (50 → 1, asserted exactly in the suite); the milliseconds move with what else the machine is doing, and the ratio at fifty dirty has read between 5× and 6.5× across runs. Two answers are filed and one is not: what a commit HOLDS and what it does not are statements about an immutable object, while a `show` git could not answer is a statement about that attempt — so it is answered for the revision exactly as the per-file read answered it, and asked again on the next. The per-file loop healed itself by re-reading; declining to file is what puts that back.

That the memory answers what re-reading answered is a differential rather than a claim: `src/committed.testlib.ts` keeps the per-file read as the reference arm, and `src/pending.equivalence.test.ts` holds the two to the same panel at every step of a scripted git session — a keystroke, a commit, a checkout back, an amend, a `reset --soft`, a rename, a file that breaks and mends, a file restored out of a commit and one staged then edited again (index moves neither arm reads), a repository with no commits yet.

`Ops.push` is the verb beside it: the current branch to the upstream it already tracks, no arguments, and a refusal carrying git's own words. What is ahead of that upstream comes off the `--branch` header the status call is already printing, so "what is not recorded" and "what is not shared" cost one subprocess between them.

Beside all of it rides the LAST COMMIT olai made — `git log -1` through the audit filter, so a person's own commits are not reported — because what is waiting says nothing about whether anything was ever recorded, and `null` there means "never" rather than "nothing right now".

A clean directory costs three concurrent asks per revision (state, what is dirty, what was last recorded) and no parsing at all. A dirty one adds one `rev-parse` — which commit the remembered copies are filed under — and a `show` only for an outline whose copy at that commit has not been read yet. The `rev-parse` that finds the repository in the first place is a different one and is not per-revision: it is paid when the handle opens, and a positive answer is kept. The repository handle is kept once it is one — a directory does not stop being a work tree — while a negative answer is re-asked, so a `git init` under a running server is picked up on the next sweep.

Committing checks that the repository is FREE first — no merge, rebase or cherry-pick in flight, and not a detached HEAD. Nothing used to, which is how an agent marking a node done mid-conflict could swallow a resolution, and that hole is what decided manual over automatic.

Messages are prefixed `olai`, so `git log --grep '^olai'` is the audit view and `--invert-grep` gives back a person's own history, and every commit carries an `X-Olai-Writer: chat-agent | mcp | web | auto` trailer — git records only the repository's own user, which every commit in it already has. There was a `cli` for a terminal on a socket of its own, and it went when the socket did: `olai surface` is a client of `/mcp` now, so a typed line wears whatever that door is composed as rather than a word of its own. The trailer is also the ONLY thing that differs between the faces' commits: the same pending set committed from the browser and from `/mcp` produces the same tree and the same message, which `src/pending.test.ts` asserts rather than assumes.

A composed message names the biggest change by a fixed order and lists the rest. It names that change by its TITLE — the design's example named the id, and read the same on a roadmap whose ids are slugs somebody chose, but `add_node` mints one when the caller does not supply it, so an agent's captures would put `1vax4izq created` in a log nobody can read and nobody can correct afterwards.

The per-op summary — which is what `auto` commits with, and what a tool result reports — keeps the reference implementation's convention, because a log a person already knows how to read is worth more than a better one they do not:

| op | summary |
|---|---|
| create (with seed) | `capture: TITLE` — the first node is a capture |
| create (seed with children) | `capture: TITLE (+N)` |
| create (empty) | `create: path.olai` |
| delete | `delete: path.md` or `delete: path.olai` — the path IS the title |
| add | `capture: TITLE` |
| add (with children) | `capture: TITLE (+N)` — N is what came with it |
| done / undo | `done: TITLE` / `undone: TITLE` |
| doing / undo | `doing: TITLE` / `not-doing: TITLE` |
| todo / undo | `todo: TITLE` / `not-todo: TITLE` |
| date | `date: TITLE -> 2026-08-10` (or `-> (cleared)`) |
| trash | `trash: TITLE` |
| move | `move: TITLE` |
| split | `split: TITLE` — the title as it read BEFORE the cut |
| merge | `merge: TITLE` — the joined title the survivor now carries |
| title | `rename: TITLE` |
| desc | `note: TITLE` |
| see | `see: TITLE` |
| after | `after: TITLE` |
| mirror | `mirror: TITLE` — the TARGET's title, not the placement's id |
| unmirror | `unmirror: TITLE` |

Beside that summary the reply carries **`Applied.sort`**, which is the same change said in the vocabulary a reader SWITCHES on rather than logs: `done`, `noted`, `moved`, `trashed`. A summary is a commit subject and cannot be branched on, and the chat transcript needs to branch on it — a write through this layer is drawn there as the node-level story (*marked done*, *note rewritten*) and never as a text diff, for the reason the commit panel has never shown one. It is DERIVED rather than tabulated by op name (`sorted.ts`): the two readings a write is made of are both in hand when the reply is assembled, so the same `changesOf` that classifies a pending row classifies this — one classification in this codebase, not two agreeing by hand. Absent when the write changed no record, because there is no honest word for that.

`create` is how a brand-new outline file is born: `add` only writes into a file the set already holds. The path is a relative `.olai` under the served directory, judged segment by segment the way `/media/*` judges a picture name (no absolute path, no `..`), and an existing file is refused rather than overwritten. A seeded create mints its nodes the way a capture does, and that is now one walk rather than a promise: `seed` IS a capture — the same fields, the same `children`, the same depth — through the same `emit` `add` uses, so a new outline holding a dozen nodes is one call and a refused seed leaves no file. An empty one leaves a zero-byte outline for later `add_node`s.

The last field edits (including `see`), the two mirror ops and `after` are this format's own: the reference had no structural move, no separate note edit, and no agent-writable `see`. `date` is the one word that CHANGED — it printed as `move:` there, where a date was what `move` named, and beside this format's real reparenting op that read as a structural change that never happened.

## Placements, and the edges

A mirror is the second half of the format the ops layer could not write, and the gap was not academic: the ledger this repository keeps its own roadmap in has a Now section made of mirror records, and every entry in it was a HAND EDIT of the file — the practice `https://github.com/juspay/oss.olai/blob/main/projects/olai/RCA/2026-08-11-roadmap-stamp-reverts.md` is about. So:

- **`add_mirror` places one.** The record is `{id, parent?, ord, mirror}` and can be nothing else, because it is built here from a request that has no field for a title or a mark — "a mirror carries nothing but its four" is unrepresentable rather than checked. It lands like an `add`: under a `parent`, or at the top level of a `file`, with `before` / `after` among the siblings there and an `ord` minted between them. Two refusals are its own — a target nothing declares, and a placement INSIDE the subtree it shows, which is the one mirror rule that cannot be checked one record at a time (expanding it would never end). That walk is the validator's own graph (`@olai/format`'s `drawnFrom`), downward: a node leads to its children, a mirror to its target, so a loop that closes through another placement is found, and the refusal names it — with the same arrow the validator writes a cycle with, because that is one function too (`chainOf`). All FOUR loop refusals this layer has name the loop rather than merely reporting one, and they are three graphs between them: a move under its own descendant (parent links), an `after` edge closing a cycle (the ordering graph), and TWO over the drawing graph — a placement inside what it shows, and a MOVE that carries one there. That last one is the same walk asked of the record being moved rather than of a target being placed: everything a branch draws moves with it, so a Now list of mirrors may not go under the work it is showing. It arrived late (review of #245), and until it did, `move_node` planned a write the gate then refused as a set-level `mirror-cycle` — a refusal about a file nobody wrote, which is precisely what sharing that graph exists to prevent. The walk itself is `/format`'s `drawingPath` now rather than a local one, so the three rules that ask it cannot answer differently.
- **`remove_mirror` retires one, and that is a PLACEMENT rather than a node.** `id` is the mirror's own — the line goes, and the target keeps its title, its mark, its children and every other placement of it. It is deliberately not `trash_node` (which MOVES a subtree, ids and all, into `_olai/Trash.olai`) and deliberately not a delete of content: the one op in this layer that destroys any empties the TRASH, and this one is about neither the trash nor a file. So it refuses on the id of a regular node, and says which op puts a node away — and it refuses while anything still NAMES the placement (a mirror chained onto it, an edge written at it), listing what to re-point and at which node. That last refusal was the validator's until the 2026-08-11 review: safe, since nothing landed, but what came back was a row about the file the write would have produced, saying an id the caller had just asked to delete is unknown — occasionally with a did-you-mean pointing at its NEIGHBOUR. A refusal that teaches the wrong lesson is worse than one that teaches none. It is still not re-validation: what a record points at is `@olai/format`'s `targetsOf`, the same function the validator's unknown-target rule reads forwards, so a relation added to the format later cannot slip past the scan.
- **`set_after` is `set_see`'s shape over the other kind of edge** — one function plans both — and the difference is the rule. `after` is the ORDERING graph, so an add that closes a loop is refused with the loop named, read over `derive`'s graph with `blocks` normalised in and both ends resolved to nodes: the same graph the validator's acyclicity check walks, so a deadlock closing through a mirror is one loop here and there rather than two answers. `blocks` is not writable, for the reason it is sugar — `a blocks b` IS `b after a`, and a writer that could spell both would put one relation on disk two ways.

Both new fields are READ back too. A hit and a node's own read carry `after` beside `see`, because a target is removed BY ID and a caller that cannot see the list can only guess at it; and `read_node` answers a placement from **both ends**:

- `mirrors` — every placement OF this node, chain followed. The discovery path the surface would otherwise not have: mirrors are left out of search and out of every child list on purpose (a mirror is a second location of a node, and a search returning one would be the same node twice), so the only id `remove_mirror` could ever be handed would be one the same session had just minted. A mirror is not a node, so you ask the node where it is placed. This is the retire path from the finished ITEM's side;
- `placed` — the placements UNDER this node, in sibling order, each carrying the node it shows. The list's side of the same fact, and the one the ledger is actually read with: **"what is on Now?"** was a question this layer could not answer at all (2026-08-11 review), so an orchestrator opening a fresh session — having placed nothing yet, with no item to ask — was back to reading the file by hand, which is the practice these ops exist to end. `children` is not the place for it: that list is what HANGS OFF a node, and it is deliberately free of mirrors, while this is what a node POINTS at. Two questions, two answers.

**And it answers references BACKWARDS**, which is the same argument one relation over: every reference in this format points one way on disk, so `referencedBy` on `read_node` is the only way an agent can ask what TALKS ABOUT a node. Each entry is a situated node (`foundOf`, like every other list here) plus the `ways` it refers — a `see` that lands here, an `@id` written in a title or a note, or both, since one record doing two things is one referrer. The reading is `@olai/format`'s `backlinksOf`, which the browser draws under a zoomed node, so a person and an agent cannot be told different things about one id — and the three exclusions travel with it: a placement is not a reference (that is `mirrors` above), an ordering edge is not one (that is `after` and the derived blockedness), and a referrer in an `_olai/Trash.olai` is left out.

None of that is worth anything if nothing says so where an agent will read it, which is why the read tools' descriptions name these fields and `packages/server/src/mcp/tools.test.ts` fails if they stop.

`custom` is the same argument for a field with no fixed keys: `set_prop` writes a named fact into it, `prop:key` / `prop:key=value` select on it, and **every read that situates a node answers the whole map** — a hit, a child in `read_node`'s list, a row of `read_subtree`, and `read_node` itself. When the caller has named `fields` and asked `custom.<key>` of the rows instead, they answer exactly the keys asked — the map cut to the length of the question, which is a projection and not a second reading. It is produced in `foundOf` beside `see` and `after` — all three through one `carriedOf`, the record's own fields handed back verbatim and each omitted when it holds nothing — which is what makes that one sentence rather than four: a hit and a read of the same node cannot answer different maps, whatever the shape asked, because the shaping reads the one pruning the `heldCustom` rule decides, the same rule `carriedOf` is built from. That helper asks `@olai/format`'s `nothing` and is handed the map `heldCustom` has already pruned — its callers ask the format's function and pass the one answer in, so the pruning happens once per asking wherever the row is read — rather than carrying its own copy of the rule, so a key holding nothing is absent from an answer exactly as it is absent from the line on disk and from what `prop:` finds; when the read had its own copy, a hit reported `custom: {"pr": ""}` for a node `prop:pr` did not return. Selecting by a property used to cost a `read_node` per row to see the fact the query had already matched on, so `prop:agent=claude-opus` answering with each lane's `pr` beside it is the whole point of the field being read at that level. The values go WHOLE — a cut value is one no reader can tell from a short one, and it would cut URLs in the middle; `limit` is where an answer's size is decided, and it is exact. The op writes only inside that field and cannot reach a system one — a node's own facts are fields at the top level, each with a verb of its own — so the only rule it carries is a refusal of keys spelled like those fields, which would otherwise let a node say `done` twice with two meanings. It also refuses a write that would change nothing, which matters here more than the symmetry with `set_done` suggests: every write stamps `changed`, so a set_prop of the value already held would otherwise land, dirty git, and be reported as an edit by a comparison that deliberately cannot see the stamp. The two STAMPS beside it (`created`, `changed`) are the other direction: fields the ops layer writes and no request may, put on in one place (`plan.ts`'s `touched`) so "every write stamps it" is true rather than remembered. They are READABLE from the query grammar since `search-stamp-operators` — `created:last-week`, `changed:today`, `has:created -has:changed` — which is what makes "every write stamps it" a promise a reader can spend rather than one they have to take on trust; a node predating the stamps carries neither and no span reaches it, since nothing invents a past.

**`desc` is the one record field that goes the other way, and the difference is size rather than meaning.** A hit carries every other field of the record by default because each of them is bounded like the title beside it; a NOTE is unbounded prose — this repository's own roadmap keeps whole forensics under a bug — so `search_nodes` takes `withDesc: true` and a selection arrives WITH its notes in that one call rather than in a `read_node` per row. Off by default because the same request is what the ⌘K palette, the edge panel and the composer's `@` list ask over the wire on every settled keystroke, and none of them draws a note: always-on would put every note in the vault on that wire per keystroke, which is the cost `vault-in-browser` spent a whole arc removing. When it is asked for it travels WHOLE, for the reason the property values do and one sharper: `set_desc` and `update`'s `was` both take the note as one text, so a shortened one is a note an edit gets written against. One flag rather than a `fields` list, because what a caller is choosing between is a shortlist and a shortlist with the notes in it — a projection language over an answer whose other fields are all cheap would be a vocabulary invented for one field. `read_subtree` has the same flag, the other way round: a targeted walk usually wants the note, so it is ON by default, and `withDesc: false` is the lean read for a table of contents. Depth bounds levels, not notes, and notes dominate the cost of a walk — the 2026-08-28 incident was a depth-1 outline read that answered ninety thousand characters for one parent id. A `read_node` still carries the note unconditionally: that is one node, asked for by name. **Beyond the note the READS shape rows outright, because a read's caller is choosing more than a note or no note: it names the record — plus the two derived words with standing, `status` and `took`.** `read_node`'s child list and `read_subtree`'s every row take `fields` — title, the marks and their instants, the stamps, the edges, a whole or partial `custom` map, the derived `status`, and `took`, how long the work took in whole seconds (the membership rule's one exception, ruled 2026-08-29: per-step durations are the recurring ask the dial was born for, and fetching the record's instants per row to do the subtraction is ceremony — the arithmetic itself is the format's `tookOf`'s, spelled there) — and answer with id + exactly that, the situating included in what stays behind, which is the request the 51KB lane-walk incident was filed from. The walk's own keys — `children`, `truncated`, and the placements named as `placed` — ride the projection as structure, exactly as the row's id does, so a walk cannot shape the naming away. What each child row carries, and what each `placed` entry's `shows` carries, still obeys `fields`; `truncated` is a flag. A search NEVER shapes: a selection's hit is the situated node, on the argument above that a projection over one selection would be a second answer to "which nodes", dressed as fields.

Git can never fail a write. The bytes are on disk and the browser has already seen them by the time git runs, so a refusal is a `Failed` carrying git's own words and a warning in the log — with those words as a FIELD (`said=…`) rather than inside the sentence, so the message stays greppable and the reason stays readable. Only the files this layer names are ever staged, on both `add` and `commit`: a served directory is a working tree with other work in it. The subprocesses themselves live in the git plugin, which decides nothing and holds that shape in its own tests, along with the repository states that are only testable by putting a repository in them.

**And it says WHY, because "not committed" on its own is six different pieces of news.** That was `git-invisible`: a person writing to a directory they knew was a repository got a bare `committed: false` and nothing else, while the cause went only to a log they were not reading. So this layer answers with two values a caller can render, and neither of them is a boolean — the boolean itself is gone, because nothing commits a write on its own any more and it had one value:

- **`Applied.why`** — one sentence on the reply of every write, and there is always one. The agent reads it in its tool result; the panel draws it beside the call. Under either WAITING mode that sentence says the write is waiting — for the Commit button under `manual`, for the quiet window under `auto` — which is the feature working and must not read as a fault; a reader told otherwise would go looking for a broken repository that is not broken. **Unless the repository is BUSY**, and then it says that instead: a write made mid-rebase, mid-merge, mid-cherry-pick or on a detached HEAD is not waiting for a button or a window, it is waiting for the repository, and the door it would otherwise be pointed at will refuse. Saying "waiting" there is the same mistake `git-invisible` was filed for wearing manual mode's clothes, so this asks the repository its state — one `symbolic-ref` per op, which is the price of a reply that is not confidently wrong.
- **`Ops.git`** — what git is doing for this directory: the state (`off` under `--commit=off`, `repo`, `none`, or `error` with git's own words), plus the POLICY in force, what git said when it last refused a PUSH, and whether the loop is PAUSED and why. A PROJECTION of the same survey `Ops.pending` runs (`gitOf`), never a probe of its own: two probes would be two answers to one question. The server recomputes both together and publishes them onto the `git` and `pending` cells, where the browser reads them into a SINGLE control (`one-git-indicator` retired the second chip that used to draw this one on its own) and an agent in a terminal reads the same cell as a resource.

Two classifications make that honest, and both are git's own answers rather than guesses. A directory git will not answer about is `Unusable` — and so `error` — unless git said its own "not a git repository", because collapsing a broken git into "you have no repository" is precisely what this package used to do; git runs under `LC_ALL=C` so that one sentence is stable. And a REFUSAL is one of the three things `pending.ts` remembers rather than derives, because it is the class of failure a probe cannot see: `rev-parse` answers perfectly happily in a repository with no `user.email`, so a state read from the directory alone looks healthy while every commit fails — and `git status` says how far ahead a branch is, never why it is still ahead. A commit refusal is cleared by the next commit that works; a PUSH refusal is its own field for the same reason it is a second one at all (a repository whose commits land and whose branch will not go is healthy on one question and broken on the other), and is cleared by the next push that works or by there being nothing left unshared.

## The tool surface, and what is missing from it

`TOOLS` is a closed list, and the absences are the design: **no shell, no grep, no directory walk, and no read or write that names a byte.** The agent cannot name a byte, only a node — or, since `md-editing`, a DOCUMENT, which is the one whole-file unit the surface has and is still not a byte range: `create_document` mints a relative `.md` (refused if it exists) and `write_document` replaces one's text whole (refused if it does not — the split is what keeps a typo from minting a file), with an optional `was` that refuses, on every retry, a write over text the caller never read. Both ride the same validate → stage → rename → commit gate and the same audit trailer as every node write. And because the text IS the file, their success is EARNED rather than reported: the landed file is read back before the answer goes out. A refusal there takes back the ANSWER, never the landing — the revision stays published, the set keeps serving what the disk holds — so it says all three of those, names what the disk kept in bytes, and hands `write_document` back as the way forward (2026-09-01: a `create_document` once answered a revision over a body the disk had not kept). **`list_documents` and `read_document` are the read half**, and they arrived late enough to be worth naming as a hole rather than a policy: the `was` guard asked callers for text no tool of theirs could fetch, and a `create_document` could mint a file the same agent could never read back. The listing answers each `.md` with the line it opens with (derived — a document has no record for a name to be written on), what its text weighs, and the properties its frontmatter writes (omitted when it wrote none — the same map a `prop:` hit carries); the read answers one body verbatim, out of the same snapshot every other read answers from. Neither is a directory listing: what is in them is what the served SET holds, so a `.html` — kept as a path with no body — is in neither, and a path the set does not hold is refused with the closest one that is, in `write_document`'s own words through the same `didYouMean`. Reads answer with `file:line`, the node's mark (absent when it carries none, because that is not a task), the ROLLUP of the tasks under it — which is not in the file and is an annotation, never a second answer to what the node is — its ancestor titles, which is what makes a bare title mean something, its parent's id (`parent`, absent at a root — `path` is titles, and a write takes the id), its `see` and `after` targets (when it has any), so a cross-reference and a dependency are both traversable without a second read, and — on a node read — the placements at both ends of it, `mirrors` and `placed`. **The reads do not loop either.** `read_subtree` takes an `id` or a `file`, so a whole outline — every top-level node in it, each walked, each saying for itself where the walk stopped — is one call rather than one per root; `search_nodes` takes `withDesc: true`, so a selection arrives with its notes rather than with a `read_node` per hit; `read_subtree` takes `withDesc: false`, so a table of contents does not haul every root's forensics; and both reads that walk rows take `fields` — `read_subtree`'s every row and `read_node`'s child list — so the rows that come back carry exactly the question rather than the record. And the walk NAMES what it never descends into: every row carries `placed` for the placements under it. The naming rides both dials; `shows` is fully situated unless `fields` named the projection, the way a child row is. A file's top-level placements sit on the answer as the same key, so an outline of only mirrors is not `roots: []` in silence. Those are the read half of the same argument `add_node`'s nested capture and `apply`'s run of verbs make about writes: what a caller cannot build for itself out of a loop is one answer about one revision. `set_see` and `set_after` are the write halves: add and/or remove target ids on an existing node, and an unknown add is refused with the closest id that does exist — the validator's own did-you-mean, one moment earlier, through the very same function (`@olai/format`'s `didYouMean`), so a write and a load cannot disagree about what a typo is or say so in two voices. That refusal used to list every id in the set, which is the right answer for the OUTLINES of a directory and the wrong one for the nodes in it: `search_nodes` is the tool for "I do not know what it is called". A path that is not an outline gets exactly that right answer, and both halves of it — the near miss when one is close enough to be a typo, the list of outlines when none is — from one function, reached through the `outlineAt` gate both the read that takes a `file` and the write that places a node at one's top level go through. It is ONE refusal for an id nothing declares, whatever the id was doing — the node an op is about gets the same help as a target it was asked to point at. Tool descriptions teach the gestures the surface is shaped around — `add_node`'s, that nodes you already know go in ONE call and arrive with their edges and facts on them; `add_mirror`'s, that a curated list is placements rather than copies; `set_after`'s, that a dependency is written from the node that waits; `update`'s and `apply`'s, which is which (several fields of one node, several ops over many) and when neither is the answer, because `add_node` already batches a subtree.

How those tools reach an agent is NOT this package's any more. `@olai/server` projects the table onto `@kolu/surface-mcp` bespoke tools, so an agent reads the same surface a browser does rather than a second declaration of it. What stayed here is what an op MEANS, which is the half that was always ours.

**A node agent's write door is fenced after planning and before the store gate.** `outsideFence` judges the records that actually changed, not the whole file a plan serializes, on both the before and after ancestry; this permits edits at or under the seat while refusing writes above it and moves across the boundary. File/document operations are inside no subtree, `agent-session` is forbidden everywhere on that door, and a released session is closed. Capture remains the deliberate outbox into the vault's inbox. Reads are unchanged.

**There are two writers now, and they are one layer.** The keyboard editor reaches these same procedures by another projection: a browser sends an INTENT over the surface (`indent this`, `toggle done`, `a new sibling after this`) and `packages/server/src/edit.ts` resolves it — against the same snapshot the write will be judged against — into exactly one `Request` for `run`. Nothing about that is visible from here, which is the property worth keeping: an op does not know whether a person or an agent asked for it, and neither of them can name a byte.

A refused write still comes back as an `isError` result carrying its structured detail — a protocol error is for a call the server could not process, and a refusal is an answer that has to reach the model as data it can act on. That contract is why the migration waited on juspay/kolu#2155: it is carried now by that package's `ToolFailure`.

## Layering

Depends on `@olai/format` and `@olai/store`. `@olai/surface` is deliberately absent, and it stayed absent when the browser became a writer: the keystroke → op resolution lives one layer up (`@olai/server`), because putting it here would mean this package importing the wire's vocabulary — and `@olai/web` inheriting `@olai/store` through it. [docs/architecture.md](../../docs/architecture.md) has the reasoning.

## Running

```sh
just test                                        # the whole workspace
bun test packages/ops                            # this package, in the dev shell
```

`src/plan.test.ts` and `src/message.test.ts` are values in and values out — no disk, no store, no protocol. `src/ops.test.ts` and `src/pending.test.ts` are the other half: a real temp directory, a real store, a real git repository and the MCP surface in front of them, asserting the things that are only true end to end — that a write WAITS, that what is waiting comes from git rather than from a tally, and that a busy repository refuses.
